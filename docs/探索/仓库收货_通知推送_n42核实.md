# n42 核实：收货完成后零通知推送

## 核实结论

**PASS —— 说法成立。**

三个收货端点确实零 push_message 调用，采购员不知道货已到，只能等到期未到货提醒那一个途径感知。

## 证据链

### 1. 三个收货端点零 push_message（亲自 grep）

```bash
grep -n 'push_message' purchase_mgmt_router.py
```

输出全部匹配：
- `:17` —— import 声明
- `:1788` —— 预计到货日期批量修改通知（buyer_lead/manager/admin）
- `:1836` —— 预计到货日期单条修改通知（buyer_lead/manager/admin）
- `:2569` —— 请款提交（finance_lead）
- `:2652` —— 请款审批拒绝（requester）
- `:2746` —— 请款审批通过（付款人）
- `:2817` —— 请款付款完成（requester）

**无一处在** `:2013-2127` 三个收货端点范围内。

### 2. `_finish_receive`（:1992-2010）零通知

三个收货端点都调用 `_finish_receive`，其内部链路为：
- `_writeback_sheet_row`（回写清单 → 纯数据操作）
- `_auto_stock_in`（`:1404-1440`——入库流水 → 纯数据操作，零 push_message）
- `_sync_txn_amount`（`:1443+`——改价回写金额 → 纯数据操作）
- `_maybe_auto_reconcile`（自动对账）

**无一调用 push_message。**

### 3. warehouse_router 不推采购员

```bash
grep -n 'push_message.*buyer\|to_role.*buyer\|to_user.*buyer' warehouse_router.py
# 无匹配
```

warehouse_router 的 push_message 调用于：
- `:798/:860` → warehouse_lead（出库审批）
- `:1438/:1462` → logistics（发货清单备货，非收货通知）

### 4. 唯一相关通知是「未到货逾期提醒」

`overdue.py:311-368` 的 `scan_po_arrival_overdue`：扫描 `expected_arrival <= 今天` 且 `arrival_date` 为空的明细，推给采购员本人。这是"还没到货"的提醒，不是"货已到"的通知。

### 5. 前端无主动通知

- `refreshAfterReceive`（WarehouseView.vue:540）仅刷新当前仓库用户，不通知采购员
- `_poOverdue`（PurchaseMgmtView.vue:475）是前端逾期标记，非通知机制

## 反例排除

| 猜想路径 | 结论 | 证据 |
|----------|------|------|
| `_auto_stock_in` 里有通知 | 排除 | `:1404-1440` 纯数据操作，零 push_message |
| warehouse_router 收货后通知采购员 | 排除 | warehouse_router 的 push_message 只给 logistics/warehouse_lead |
| purchase_mgmt_router 其他地方有收货通知 | 排除 | 全文件 9 次 push_message 均为预计到货变更或请款流 |
| overdue.py 有到货通知 | 排除 | `scan_po_arrival_overdue` 是未到货逾期提醒 |

## 影响的量化

收货完成时，采购员**完全收不到任何通知**。采购员感知到货的唯一途径是：
1. 手动刷新采购明细列表，逐条看 `arrival_date` 是否已填
2. 预计到货逾期提醒（`scan_po_arrival_overdue`）——但这只在到期仍未到货时触发，货准时或提前到就永远不会收到
