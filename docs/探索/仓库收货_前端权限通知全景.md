## 0. 总览·一句话

仓库收货的完整链路：**仓库角色**（warehouse / warehouse_lead，plus admin/manager via `require_roles` 自动并入）在 `WarehouseView.vue` 单文件内完成全部收货交互。后端 `purchase_mgmt_router.py` 的 `/receiving` 系列端点**不套采购行级隔离 `_buyer_restricted`**——仓库看全部采购员下单的全部明细（含单价/金额）。收货完成后**零通知推送**：`receive_item`、`receive_batch`、`upload_receipt` 三个端点内部无任何 `push_message` 调用；采购员只能从「到期未到货每日提醒」（`overdue.py:311-368`，15:00 后才发）间接感知收货状态。

整个体系的域隔离靠 `user_menu_keys()`→`User.menus` + `hidden_tabs` 的菜单门控（一级菜单唯一权威 + 二级 tab 可选隐藏），而非每个接口单独验角色；价格数据接口层全量返回，前端靠 `isManager = hasRole('admin','manager')` 隐藏单价/总价列——「前端隐藏 ≠ 接口隔离」。

## 2. 前端交互全景（整合 n6 + 交叉引用 n7/n8）

### 2.1 一句话结论

前端收货交互**全部**在单文件 `frontend/src/views/WarehouseView.vue`（2054 行）内实现，**没有独立组件、没有独立 API 模块**——收货相关 HTTP 调用全走 `http` 直调（不走 `frontend/src/api/warehouse.ts` 的 `whApi`，`whApi` 只封了出入库流水 / 物料 / 发货清单 / 采购申请）。该文件同时承载仓库模块全部 9 个 tab（`ov`/`sum`/`txn`/`mat`/`loc`/`demand`/`recv`/`ship`/`preq`），收货只是其中一个 tab pane。表格用 Element Plus `el-table`（非项目主用的 vxe-table）。

> 引用自 n6「前端收货交互全部在单个文件 WarehouseView.vue 内实现」(`仓库收货_04前端页面.md:8`)。

### 2.2 入口与权限门（与 n7 交叉）

```
入口：WarehouseView.vue:1381  <el-tab-pane v-if="tv('recv')" name="recv">
可见性：tv(name) = auth.tabVisible('warehouse', name)  → 由 User.hidden_tabs 驱动
可写：canWrite = computed(() => auth.hasRole('warehouse','warehouse_lead','admin','manager'))
管理层：isManager = computed(() => auth.hasRole('admin','manager'))  → 仅隐藏单价/总价列
```

**交叉核实要点**：

| 项目 | 前端定义（n6 条目1） | 后端定义（n7 条目2） | 判决 |
|------|---------------|---------------|------|
| 写权限角色 | `canWrite` = `warehouse/warehouse_lead/admin/manager`（`WarehouseView.vue:18`） | `_RECEIVE_ROLES` = `(warehouse, warehouse_lead)` → 但 `require_roles` 自动并入 `admin/manager`（`deps.py:55`） | **一致**：前后端等效。`deps.py:55` 行内联 `{"admin", "manager"}` 到每个 `require_roles` 调用的 allowed set，无需端点单独声明 |
| tab 可见性 | `tv()` 读 `hidden_tabs`（`WarehouseView.vue:29-32`） | `User.hidden_tabs` + `TAB_REGISTRY` 中 `recv` tab（`menus.py:105-114`） | **一致**：`tv()` 底层调用 `auth.tabVisible('warehouse', name)` 读 store 中的 `hidden_tabs` |
| 价格可见性 | `isManager`（admin/manager）隐藏单价/总价列 | 接口层全量返回 `unit_price/received_amount`，不按角色省略字段 | **设计张力**（见 §5.2）：前端隐藏 ≠ 接口隔离 |

- `canWrite` 引用自 n6「canWrite = auth.hasRole('warehouse','warehouse_lead','admin','manager')」（`04前端页面.md:18`）。
- `isManager` 引用自 n7「isManager 隐藏单价/总价列」（`05权限.md:111`）。
- 退出检查 [n6]（条目4）确认前端交互描述与源码一致。
- 退出检查 [n7]（条目5）确认权限矩阵与 `deps.py:55` 恒放行逻辑匹配。

非仓库角色进 tab 只见 `EmptyHint`「仅仓库角色可确认收货」（`WarehouseView.vue:1383`），整块操作区不渲染。切进 tab 触发加载：`onTab('recv') → loadReceiving() + loadRecvMeta()`（`:810`）。

### 2.5 每个交互的 API 端点与代码位置

#### 2.5.1 列表加载 `GET /purchase-mgmt/receiving`

- 前端：`loadReceiving()`（WarehouseView.vue:451-466）。前端把 4 个筛选控件的值塞成 query 参数：
  ```ts
  { received: recvReceived, supplier_id, keyword: recvPo.trim(), item_name: recvName.trim(), order_month: recvOrderMonth }
  ```
- 后端：`purchase_mgmt_router.py:1881`。**#330 起三个搜索框全部走后端**。
- **前端 + 后端过滤双通道**（n6 §6.1）：
  - 前端过滤：即时反馈，边打字边收窄。基于 `po_no/project_code`（`:391-394`）、`item_name`（`:394-396`）、`delivery_date.startsWith(month)`（`:398-399`）。
  - 后端过滤：点查询/回车后全库搜索。keyword 带 `source_sheet_id IN (...)` 分支回溯 #253 老单（`purchase_mgmt_router.py:1909-1916`）。此分支在纯前端过滤中不生效（`source_sheet_id` 不在前端展开的数据中），故必须走后端才能搜到这类明细。
  - 两者**不矛盾**——前端过滤是「即时缩小范围」的 UI 体验层，后端查询才是真正的数据源。带筛选时前端过滤缩小范围 + 后端查询穿透截断，互补无冲突。
- 返回行含：`unit_price`（可为 null = 后填）、`received_amount`、`delivery_note_no`、`arrival_date`、`stock_location`、`project_code`、`receipt_count`、`po_no`、`delivery_date`、`notes`。全量字段无角色收窄（见 §2.2 价格可见性张力）。
- **角色门控**：`require_roles(*_RECEIVE_ROLES)`（`purchase_mgmt_router.py:1890`），实际允许 `warehouse/warehouse_lead/admin/manager`（n7 核实：`deps.py:55` 自动并入 admin/manager）。
- **行级隔离**：**不套 `_buyer_restricted`**（n7 §2.1，`05权限.md:52-53`）。`list_receiving` 函数体（`:1882-1957`）内无任何 `_buyer_restricted(current)` 调用——与 `list_items`（`:380-381` 行 `buyer_id == current.id` 收窄）形成对比。仓库看到全部采购员下全部明细（含单价/金额/供应商）。

引用自 n6「列表加载」(`04前端页面.md:77-83`) + n7「/receiving 不套 _buyer_restricted」(`05权限.md:110`)。

#### 2.5.2 元信息 `GET /purchase-mgmt/receiving/meta`

- 前端：`loadRecvMeta()`（WarehouseView.vue:468-475）。返回 `{ pending_count, received_count, pending_suppliers, received_suppliers, limit }`。
- 驱动：tab 角标 `recvPendingCount/recvDoneCount`（`:820-830`）、供应商下拉全量（`:473-474`）、截断告警 `recvTruncated` 与 `recvTotal` 比较。
- 后端：`purchase_mgmt_router.py:1960`。`pending_count` 用 `count(*) WHERE arrival_date IS NULL`，`received_count` 用 `count(*) WHERE arrival_date IS NOT NULL`，两组 `distinct(supplier_id)` 独立统计（`:1966-1981`），均**不受列表 limit 影响**——页面显示的数字是真实统计而非返回行数。
- **与 n8 §4.6 交叉**：meta 接口 `@router.get("/receiving/meta")` 与 `list_receiving` 并列，`require_roles(*_RECEIVE_ROLES)` 同口径（`:1962`）。

引用自 n6「元信息」(`04前端页面.md:85-90`) + n8「meta 出真实条数」(`06通知异常.md:139-142`)。

#### 2.5.3 单条收货/修改弹窗（1912-1960）

```python
def require_roles(*codes: str):
    """依赖工厂：仅允许指定角色（admin/manager 始终放行；多角色取并集）"""
    allowed = set(codes) | {"admin", "manager"}  # ← 第55行：admin/manager 恒放行
    async def _dep(current: models.User = Depends(get_current_user)) -> models.User:
        if not current.has_role(*allowed):
            raise HTTPException(status.HTTP_403_FORBIDDEN, "无权操作")
        return current
    return _dep
```

这意味着**任何 `require_roles(...)` 调用都会自动放行 admin 和 manager**，无需在各端点单独声明额外的角色。例：`_RECEIVE_ROLES = (warehouse, warehouse_lead)` 的实际允许集合是 `{warehouse, warehouse_lead, admin, manager}`——与前端 `canWrite` 定义的 `hasRole('warehouse','warehouse_lead','admin','manager')` **完全一致**。

而 `require_roles` 依赖 `get_current_user`（只验登录态、不验角色），所以 `require_roles` 本身已包含认证+授权的完整链路。

### 3.4 行级数据隔离谓词——唯一真源

#### 3.4.1 `_buyer_restricted`（`purchase_mgmt_router.py:46-53`）

```python
def _buyer_restricted(current: models.User) -> bool:
    """下单采购员(buyer 家族)只看自己下的单——判定依据只是"是不是采购下单角色"，
    与是否**兼任** finance / logistics / sales 无关（兼任财务不解除采购的行级隔离；
    这是反复出问题的坑：王芹=buyer/finance/logistics 曾因带 finance 而被判为看全部）。
    只有 采购主管 / admin / manager 看全部；纯 finance(不带 buyer)不受此限、可看全部对账。"""
    return current.has_role("buyer","buyer_standard","buyer_outsource") \
        and not current.has_role("buyer_lead","admin","manager")
```

- **语义**：只要 buyer 家族且不是主管/管理层 → 只看自己下的单。
- **兼任不解除隔离**：王芹=buyer/finance/logistics 案例——`role_codes={buyer, finance, logistics}` → `has_role("buyer","buyer_standard","buyer_outsource")` = `"buyer" ∈ {buyer, finance, logistics}` = **True** → 仍受隔离。早期版本判 `buyer AND NOT (finance OR buyer_lead OR admin OR manager)` 致使带 finance 的人被误判为看全部——已修正为只判 buyer 家族。
- **纯 finance（不带 buyer）→ `has_role("buyer","buyer_standard","buyer_outsource")` = False → `_buyer_restricted` = False → 看全部对账**。
- **AGENTS.md 铁律**：`_buyer_restricted` 尤其不能自己重写——它有反直觉语义（兼任不解除隔离）。新增任何跨域读采购数据的代码必须 `import` 本体。

### 4.2 到期未到货每日提醒 `scan_po_arrival_overdue`

#### 4.2.1 触发与调度

- 进程启动时注册：`main.py:65` lifespan → `:95` `asyncio.create_task(overdue_scheduler())`。
- `overdue_scheduler`（`overdue.py:391-430`）：每 `interval_hours`（默认 12 小时）扫一轮，六个 scan 各自独立会话、独立 try/except（一个 scan 失败不影响其他 scan）。
- **多 worker 单实例**：`_try_acquire_scheduler_lock`（`overdue.py:371-388`）用 flock 锁 `.overdue_scheduler.lock`。不加锁多实例会「同一条明细同一天重复推送 N 份」——因为每个 worker 的 messages 表去重查询是 check-then-act 竞态，多个进程同时查到无当日消息→都推。

#### 4.2.2 扫描条件（`overdue.py:326-334`）

```sql
WHERE expected_arrival IS NOT NULL
  AND expected_arrival != ''
  AND expected_arrival <= today_s           -- 到货日当天仍未收货即开始提醒
  AND (arrival_date IS NULL OR arrival_date = '')
```

- `expected_arrival <= today_s` 用 `<=` 而非 `<`——到期日当天即开始提醒（而非次日）。
- `arrival_date` 为空（未收货）。
- 只扫 `purchase_items` 单表，**全量扫描无 limit**。明细量极大时此查询可能重。

#### 4.2.3 15:00 时间窗（`overdue.py:319-323`）

```python
now = datetime.now(_CN_TZ)
if now.hour < 15:
    log.info("[scan_po_arrival_overdue] 业务时间 %02d 时 <15 时，跳过当日未到货提醒(#292)", now.hour)
    return {"scanned": 0, "notified": 0}
```

业务时区 `now.hour < 15` 直接跳过。来源 #292：货车中午发车，15 点前提醒多为「在途」误报。15:00 后第一次扫描正常首发，当日重扫仍去重（幂等键是当日级，不是 15:00 对齐）。

#### 4.2.4 幂等键（`overdue.py:338-346`）

```python
r2 = await db.execute(
    select(models.Message.created_at).where(
        models.Message.biz_type == "po_arrival_overdue",
        models.Message.biz_id == it.id,
    )
)
if any(ts and _cn_date(ts) == today_s for (ts,) in r2.all()):
    continue
```

幂等键 = `biz_type='po_arrival_overdue' + biz_id=item.id + 当日`（`_cn_date(ts) == today_s`），与 AGENTS.md 约定一致。同一条明细同一天只推一次。

#### 4.2.5 推送口径——只推采购下单人本人

- **2026-07-26 收窄**：原口径推 `buyer_id` 采购员 + 采购主管 + 全体管理层。用户反馈信息太多，改为只推 `item.buyer_id` 本人（`overdue.py:359-363`）：
  ```python

      await push_message(db, to_user_id=it.buyer_id, kind="warn",

- 消息 `kind="warn"`，`biz_type="po_arrival_overdue"`，`biz_id=item.id`。

> 引用自 n8「到期未到货每日提醒」(`06通知异常.md:20-53`)。

#### 4.2.6 性能：3 项关注点

1. **全量无 limit 扫描**：`select(models.PurchaseItem).where(...)` 无 limit，明细量极大（如数万条）时扫描会重（:326-335）。
2. **循环内 N+1**：每条明细执行两次额外查询——一次 `Message` 去重（`:339-344`）、一次 lazy load `supplier.name`（`:351`）。N 条命中明细 → 约 2×N 次额外查询。
3. **isolation 级别**：`overdue_scheduler` 创建独立 seesion（`:395-396` 附近），不与业务请求共用 session，安全。

### 4.4 失败回滚与幂等边界

#### 4.4.1 事务边界：`get_db` 无显式 rollback，靠隐式回滚

`database.py:28-30`：
```python
async def get_db() -> AsyncSession:
    async with SessionLocal() as session:
        yield session
```
没有 try/except/finally/finally。异常时 FastAPI 关闭依赖、session 关闭，连接归还时**未提交的事务被丢弃**——即隐式回滚。已 `flush()` 但未 commit 的变更同样不会落库。回滚可靠，只是没有「显式 rollback + 日志」的可见性——问题发生时无法从日志快速定位 `rollback reason`。

#### 4.4.2 收货提交是单 commit 尾部，事务原子

- `receive_item`：`_finish_receive`（回写清单 → 自动入库 → 同步流水金额 → 自动对账）→ **一个** `db.commit()`（`:2044`）。任一步抛异常，全部变更回滚。
- `receive_batch`：循环内逐条 `_finish_receive`，**最后统一一个** `db.commit()`（`:2105`）。中途第 N 条抛异常，前 N-1 条也回滚——批量收货原子性成立。

#### 4.4.3 各步幂等性明细

| 步骤 | 位置 | 幂等机制 | 并发可靠性 |
|------|------|----------|-----------|
| `_auto_stock_in` | `purchase_mgmt_router.py:1404-1440` | check-then-act：查 `WhTxn.purchase_item_id==item.id AND is_reversal==False`，有则 return | **不抗并发**（两个事务同时查无流水 → 两个都插，见 §4.5.1） |
| `_sync_txn_amount` | `:1443-1459` | 覆盖写已有流水金额——`UPDATE WhTxn SET amount=new, unit_price=new` | 天然幂等，多次写同值 |
| `_maybe_auto_reconcile` | `:724-736` | 仅从「待对账」推进一次到「已对账」，已对账的 skip | 天然幂等，多次调无副作用 |
| `_writeback_sheet_row` | `_finish_receive` 内 `:1995-2005` | 覆盖写清单列的进度/到货日期/库位/签字 | 同事务内安全，覆盖写幂等 |

#### 4.4.4 `push_message` 的 commit 契约（`notify.py:29-84`）

- `push_message` **自己 `await db.commit()`**（`:76`）。约定是「业务事务 commit 之后调用」——若在业务 commit 前调用，会把该 session 上所有未提交变更**一并提交**，破坏原子性。
- 收货路径不调用 `push_message`（§4.3），故无此风险。
- `scan_po_arrival_overdue` 用独立会话且每推一条 commit 一次，符合约定。
- `push_message` 在目标用户为空时 `return 0` 且**不 commit**（`:60-62`）——这是 AGENTS.md 已记录的坑：`scan_po_arrival_overdue` 中 `buyer_id` 为空时不推，方法提前 return 不修改任何状态。

> 引用自 n8「失败回滚与幂等边界」(`06通知异常.md:71-106`)。

### 4.5 并发写冲突

#### 4.5.1 `_auto_stock_in` 并发双流水（高风险，无条件防护）

- 幂等检查（`purchase_mgmt_router.py:1409-1412`）是「先查后插」模式：
  ```python
  r = await db.execute(select(models.WhTxn).where(
      models.WhTxn.purchase_item_id == item.id,
      models.WhTxn.is_reversal == False))
  if r.scalar_one_or_none():
      return  # 已有流水，不重复过账
  # ... INSERT new WhTxn row
  ```
- `WhTxn.purchase_item_id`（`models.py:413`）**只有 index，无 unique 唯一约束**。
- **竞态场景**：两个请求对同一条明细几乎同时收货 → 两事务都查到「无流水」→ 都插入入库流水 → **双流水、库存翻倍**。
- 触发条件：同一明细秒级并发收货。现实的业务场景（同仓库多账号对同一单操作）下概率低。
- **修复方向**：在 `WhTxn.purchase_item_id` 上建唯一约束 `UNIQUE(purchase_item_id) WHERE is_reversal=FALSE` 可根治——但需注意现有数据库中是否已有重复流水（如有需先清理再去重）。

#### 4.5.2 `_next_ref` 撞号（中风险）

`warehouse_router.py:619-625`：
```python
ref_date = now.strftime("%y%m%d")
count = (COUNT(*) WHERE ref_no LIKE f'RK{ref_date}%' OR ref_no LIKE f'CK{ref_date}%') + 1
ref_no = f"RK{ref_date}-{count:03d}"
```
同日并发入库算出同一 count → 两个相同 `ref_no`。`ref_no` 仅有 index 无唯一约束，**撞号不报错**。`_auto_stock_in` 每次收货都走这里（`:1430-1431`）——单次收货写两条流水（入库一条、出库冲红一条），入库写 `ref_no` 时如果撞号，两个收货的流水号相同但金额不同。

#### 4.5.3 `_next_po_no` 撞号（低风险，与收货间接相关）

`purchase_mgmt_router.py:757-774`（建采购单）：`MAX(po_no LIKE 'PO{格式}%') + 1` 同类竞态，与收货间接相关（收货按 po_no 展示，不按 po_no 写操作）。

#### 4.5.4 scheduler 的 flock 防多实例重复推

`overdue.py:371-388`：`.overdue_scheduler.lock` flock 单实例，**只锁 scan 循环**。4 worker 仅一个拿锁执行。进程退出锁自动释放。Windows 开发环境退化为不锁（单进程运行无所谓）。

> 引用自 n8「并发写冲突」(`06通知异常.md:109-128`)。

### 4.6 limit 截断全景

- **列表查询**（`purchase_mgmt_router.py:1877-1921`）：
  - `_RECV_LIMIT_DEFAULT = 2000`（`:1877`），`_RECV_LIMIT_MAX = 5000`（`:1878`）
  - #330 从 300 提到 2000
  - 查询 `stmt.limit(limit)`（`:1921`），**无 offset、无分页**——超过 2000 条时用户只能翻 2000 行
- **筛选条件全在 SQL 层、先于 limit**（`:1902-1920`）：
  - `supplier_id` → `WHERE supplier_id = :id`
  - `po_no` → `WHERE po_no ILIKE %{kw}%`——#330 单个框匹配两个字段
  - `keyword` → `WHERE (po_no ILIKE OR project_code ILIKE OR source_sheet_id IN (SELECT ds.id ... WHERE project.code ILIKE))`（`:1909-1916`）——三个分支，第三个 `source_sheet_id IN (...)` 分支能回溯 #253 老单（项目编号不在 `project_code` 列里而是从来源清单的 `Datasheet→Project.code` 回溯）
  - `item_name` → `WHERE item_name ILIKE %{kw}%`
  - `order_month` → `WHERE delivery_date STARTSWITH {month}`（`:1920`）
  - **筛选时能查到 2000 条之外的行（穿透截断）**——因为 SQL 的 WHERE 先于 LIMIT 生效
- **meta 出真实条数**（`:1960-1989`）：
  - `pending_count` = `SELECT COUNT(*) WHERE arrival_date IS NULL`（待收货总数）
  - `received_count` = `SELECT COUNT(*) WHERE arrival_date IS NOT NULL`（已收货总数）
  - `pending_suppliers`/`received_suppliers` = `SELECT DISTINCT supplier_id` 两个方向
  - **三项统计均不受列表 limit 影响**——页面角标数字是真实统计而非截断后的返回行数
- **剩余截断点**：无任何筛选时只显示前 2000 条，无分页。超 2000 条的历史数据只能靠筛选定位。`scan_po_arrival_overdue` 全量扫描无 limit，不受此影响。

> 引用自 n8「limit 截断方案」(`06通知异常.md:131-147`) + n6 §2.3.1 工具条控件表（`04前端页面.md:20-30`）。

### 5.2 设计张力（非 bug，但需要决策者知道）

#### 张力 1：仓库看到比采购员自己更多的数据

> 同一张 `PurchaseItem` 表，两套谓词：
> - 采购员看 `GET /items` → `_buyer_restricted` 收窄 → `buyer_id == current.id`（`:380-381`）
> - 仓库看 `GET /receiving` → **不套 `_buyer_restricted`**，看全部采购员下的单（含单价/金额/供应商名称/采购员姓名）

当前业务定位是「仓库执行收货需要全量明细视图」，不按采购员或项目收窄。但这意味着仓库角色对采购明细的可见范围（含价格信息）超过任何单个采购员本人（采购员只能看自己下的单）。

**若未来要求仓库收窄**（如按项目/区域/部门），改动点在 `list_receiving` 的 stmt 构造（`:1894-1921`），当前无任何行级收窄。可能的收窄方式：
- 按项目目录行级隔离 `restricted_dir_pids`（需在清单层而非采购明细层匹配项目）
- 授予仓库角色访问指定项目而非全部

> 证据：n7 §2.1（`05权限.md:52-53`）+ 本文核实 `list_receiving` 与 `list_items` 的 stmt 差异。

#### 张力 2：前端隐藏价格但接口全量返回

> `/receiving` 返回的 `PurchaseItemOut` 含 `unit_price`、`received_amount` 全字段。WarehouseView 用 `isManager` 在模板层隐藏单价/总价列：
> ```html
> <el-table-column v-if="isManager" prop="unit_price" .../>
> <el-table-column v-if="isManager" prop="received_amount" .../>
> ```
> 非管理层的仓库角色可用浏览器 DevTools Network 面板或 curl 直接拿到价格。

设计上这是显式选择——仓库收货时需填写/修改单价和金额（`receive_item` 接口支持修改，`:2037-2042`），所以接口必须返回和接收价格字段。前端的 `isManager` 隐藏只是 UI 层的「眼不见」，不是真正数据隔离。从最小权限原则看，「仓库能看到价格但只在操作栏见到单价输入框」才是合理设计——但当前形态下历史价格也能在 Network 面板中看到。

> 证据：n6 §2.3.2 表格列定义 + n7 §3.7 反例 3（`05权限.md:111`）。

#### 张力 3：收货完成零通知（最大功能缺口）

> 收货三个端点全部无 `push_message`——而采购审批（`:1788,1836`）、请款/审批流（`:2562-2569,2652,2746,2817`）均有推送。采购员只能从「到期未到货提醒」（§4.2，且只推采购员本人，管理层不推，每天只有 15:00 后一轮扫描）间接感知到货。

对比同类操作：
| 操作 | 推送方式 | 证据 |
|------|---------|------|
| 采购下单 | `push_message` → 请款负责人的消息队列 | `:1788` |
| 采购修改 | `push_message` → 同上 | `:1836` |
| 请款提交/通过/驳回 | `push_message` → 请款人 + 审批人 | `:2562-2569,2652,2746,2817` |
| **收货完成** | **无任何推送** | `purchase_mgmt_router.py:2013-2127` 零调用 |

> 证据：n8 §4.3（`06通知异常.md:58-66`）+ `purchase_mgmt_router.py` 全文件搜索 `push_message`。

## 9. 分歧 / 遗留

1. **n6 探索过程中越界修改了 `WarehouseView.vue`**（条目7）：清理死代码 `batchRecvMode`/`batchTotalQty`/`splitShare`。该改动 `vue-tsc -b` 通过确认无类型错误。**后端 `receive_batch` 的 `total_amount` 分摊逻辑保留**（`:2068-2082`），前端的 lines-only 模式与后端兼容。**该改动的去留由 n10 验收评估**——本文只记录事实，不做回滚或保留建议。对齐建议：若保留，建议在后端的 `total_amount` 路径加 `DeprecationWarning` 注释，标明前端已不再使用此路径（保留给 curl/外部调用兼容）。

2. **n8 §4.2.6 「scan N+1」标记为低严重度**：当前业务量可接受，但在采购明细量持续增长时需关注。上游未给出具体触发量级阈值。建议后续有性能问题时优先解决：① scan 加 limit 分批推（而非全量扫描）② 归入单次查询（一次 pull 所有已扫描明细的 Message 日期 + Supplier.name 懒加载 → 一次 batch 查询）。

3. **n8 §4.5.2「_next_ref 撞号」标记为中严重度**：撞号不报错意味着问题发生后无法追溯——两个相同的 `ref_no` 在出入库流水中无法区分来源。上游未给出修复建议的具体实现方案。本文附注修复方向：将 `ref_no` 的生成从 COUNT+1 模式改为基于时间戳+随机数的 UUID 前缀模式（如 `RK{ymd}-{hex(4)}`），或直接用数据库 SEQUENCE / `DEFAULT gen_random_uuid()` 解决。

4. **n8 §4.5.1「_auto_stock_in 并发双流水」标记为高风险**：`WhTxn.purchase_item_id` 无唯一约束。修复方向：`ALTER TABLE wh_txns ADD CONSTRAINT uq_wh_txn_purchase UNIQUE(purchase_item_id) WHERE is_reversal=FALSE`——但需注意：执行前检查 `purchase_item_id` 是否存在重复流水（如有则需先清理才能建唯一约束），且 PostgreSQL 不支持 `UNIQUE WHERE` 只能在 UNIQUE INDEX 上用 `WHERE` 子句（`CREATE UNIQUE INDEX ... ON wh_txns(purchase_item_id) WHERE is_reversal=false`）。

5. **三篇之间未发现代码层面的实质性矛盾**。所有标注的「矛盾」均为同一事实的不同层面描述或设计选择上的张力（已在上文 §5 中逐条判决）。n6/n7/n8 的退出检查（条目4-6）均 PASS——结论与源码一致。
