## 触发条件（什么条件下真的会发生）

**条件**：仓库操作员（warehouse 角色）调用 `receive_item` 或 `receive_batch`，给一条采购明细填入 `arrival_date`（即标记到货）。

**结果**：
- 采购明细的 `arrival_date` 被更新 ✓
- 库存流水（WhTxn）自动生成 ✓
- 来源清单（项目详单）回写"已到货" ✓
- **采购员（buyer_id）收不到任何 push_message** ✗
- 采购员只能通过手动查看采购明细列表或项目详单来发现货已到

**不发生条件**：
- `arrival_date` 为空时不触发（收货未完成）
- 仓库查看到货明细清单（GET /receiving）不触发通知（合理——查询不产生通知）

## 影响面评估

| 维度 | 影响 |
|------|------|
| 按时到货 | 采购员**零通知**——货到了但不知道，除非手动查 |
| 逾期到货 | 采购员先收到 overdue scanner 的"还没到"警告 → 后来仓库收货 → **收不到"到了"的确认**——信息链断裂 |
| 数据正确性 | 不受影响（收货状态/库存/项目详单回写均正常） |
| 下游流程 | 采购员不知道货已到，可能延迟对账/付款/项目推进（依赖采购员主动检查） |
| 严重度 | 代码层面确实零推送，但属于通知缺口而非数据安全/权限问题；建议严重度由"高"降级为"中" |

## 排除的路径

- **WebSocket**：ws_router 仅 `datasheets/{did}` 和 `overview` 协作文档与看板轮询，不推采购到货事件
- **Message 表直写**：收货流程不写入 Message 表
- **清单元数据变更触发通知**：`_writeback_sheet_row` 仅写 Excel 单元格，不产生通知
- **前端轮询推送**：前端可以轮询 `GET /receiving` 列表，但这是客户端主动行为，不是服务端推送
