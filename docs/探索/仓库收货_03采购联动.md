# 仓库收货 · 采购联动与合并收货

> 主题：采购与收货的联动关系——待收货数据来源与查询（`.limit(2000)` 与 `/receiving/meta` 的 count 与供应商下拉）、PO/采购单与收货单的关联字段、合并收货逻辑、`expected_arrival` 预计到货字段、收货后采购单及明细的状态流转、按采购单号/项目编号搜索。
> 代码主仓：`backend/app/routers/purchase_mgmt_router.py`（收货全部落在此文件）与 `frontend/src/views/WarehouseView.vue`（仓库页「采购收货」tab）。
> 前置阅读：`docs/探索/仓库收货_02数据模型.md`（PurchaseItem 字段定义）。

---

## 0. 一句话总览

**系统没有独立的「采购单表」和「收货单表」**：采购单 = `PurchaseItem.po_no` 字符串列上同号多行的聚合视图；收货单 = 每行 `PurchaseItem` 上写 `delivery_note_no`（送货单号）+ `arrival_date`（到货日期）。**状态流转没有独立 status 字段，全部靠 `arrival_date` 空/非空判定**（待收货=空，已收货=非空）。所有收货接口都在 `purchase_mgmt_router.py`，权限统一 `_RECEIVE_ROLES = ("warehouse", "warehouse_lead")`（:28）。

## 1. 待收货数据来源与查询

### 1.1 主查询 `GET /purchase-mgmt/receiving`

- 定义：`purchase_mgmt_router.py:1881-1957`
- 权限：`require_roles(*_RECEIVE_ROLES)`（:1889）
- 语义（docstring :1893）：「默认列出『待收货』明细（到货日期为空）供仓库确认收货、补送货单号/后填价格」。
- 排序（:1894-1897）：`po_no DESC NULLS LAST, id DESC`（新单在前，无单号排最后）。
- **待收货/已收货切换（:1898-1901）**：仅凭 `arrival_date` 判空——`received=true` 时 `arrival_date IS NOT NULL`，否则 `IS NULL`。无任何独立状态列。

**参数与 SQL 过滤**（:1902-1921）：

| 参数 | 后端过滤 | 行号 |
|---|---|---|
| `supplier_id` | `supplier_id ==` | :1902-1903 |
| `po_no` | `po_no ILIKE %…%` | :1904-1905 |
| `keyword` | `po_no ILIKE OR project_code ILIKE OR source_sheet_id IN (回溯)` | :1909-1916 |
| `item_name` | `item_name ILIKE` | :1917-1918 |
| `order_month` | `delivery_date.startswith(YYYY-MM)`（**下单月份**，不是到货月） | :1919-1920 |
| `limit` | 默认 2000，上限 5000 | :1876-1878, :1921 |

- **`.limit(2000)` 的来历**：`_RECV_LIMIT_DEFAULT = 2000` / `_RECV_LIMIT_MAX = 5000`（:1876-1878）。历史上是 `.limit(300)`，因长周期订单一多，待收货列表被截断、前端只在已加载批里过滤，更早的老单永远搜不到（#330 反馈），才提到 2000 并把筛选下沉 SQL。
- **`keyword` 三分支不能省**（:1906-1916 注释是血泪教训）：第三分支 `source_sheet_id IN (SELECT Datasheet.id JOIN Project WHERE Project.code ILIKE)`——#253 那批明细自己的 `project_code` 是空的，页面显示的项目编号是后面**回溯**出来的，只比对存量字段会在 SQL 阶段就把这些行筛掉（前端过滤时代能搜到），会回归。

### 1.2 `#253` 项目编号回溯补显示（:1924-1946）

- 场景：外协/加工件下单时未带项目号，仓库收货看不到属于哪个项目/加工订单。
- 逻辑：对 `source_sheet_id` 非空且 `project_code` 为空的明细，经 `Datasheet.project_id → Project.code` 回溯出项目编号，回填到输出对象（**只补显示，不落库**）。
- 注意：这条回溯链与 `keyword` 第三分支用的是同一条 `Datasheet→Project` 关联，两处必须同时存在。

### 1.3 收货单图片数量（需求十四，:1947-1956）

- 对返回的明细行，按 `Attachment.biz_type="receipt_doc"` 计数，附到输出 `receipt_count`（前端父行聚合显示"X 张"）。图片本身用 `POST /items/{iid}/receipt` 上传（:2111+）。

### 1.4 真实 count 与全量供应商下拉 `GET /purchase-mgmt/receiving/meta`

- 定义：`purchase_mgmt_router.py:1960-1989`
- **为什么要有它**（docstring :1965-1968 是血泪教训）：此前徽标数直接取被截断列表的 `length`（永远 ≤300，看着像"只有 300 条"），供应商下拉也只从那 300 条去重——长周期供应商根本不出现在选项里，"唯一能穿透截断的筛选维度自己也被截断了"。所以这里两项都**独立查 count，不受列表 limit 影响**。
- 返回（:1983-1989）：
  - `pending_count` / `received_count`：`arrival_date` 空/非空的 `count(*)`（:1969-1973）
  - `pending_suppliers` / `received_suppliers`：`Supplier JOIN PurchaseItem` 后按待/已收货分别 `DISTINCT`（:1975-1981），**全量**供应商下拉
  - `limit`（供前端提示"本页最多显示 N 条"）

### 1.5 前端消费（`WarehouseView.vue`）

- `loadReceiving()`（:451-466）：GET `/purchase-mgmt/receiving`，传 `received`（tab 切换 true/false）、`supplier_id`、`keyword`、`item_name`、`order_month`，不传 `limit`（用后端默认 2000）。
- `loadRecvMeta()`（:468-475）：GET `/receiving/meta`，把 count 刷到徽标 `recvPendingCount`/`recvDoneCount`，供应商列表 `recvMeta.pending_suppliers/received_suppliers`（:377 按 tab 取对应一套）。
- tab 切换：`recvReceived` ref（:360，false=待收货 / true=已收货），模板 :1376 `el-radio-group` 切换即重查。
- 徽标与截断提示：:1401 用 `recvMeta.pending_count / received_count / limit` 渲染"共 X 条，本页最多显示 N 条……用筛选可搜全部"。
- 切换/收货/上传后统一 `loadReceiving(); loadBadgeCounts(); refreshAfterReceive()`（:562, :658）。

## 2. PO/采购单与收货单的关联字段

系统**没有独立 PO 表、没有独立收货单表**，一切挂 `PurchaseItem`（models.py:651-700）行上。字段分工：

| 概念 | 落点字段 | 谁填 | 说明 |
|---|---|---|---|
| 采购单号 | `PurchaseItem.po_no`（字符串） | 下单 | 同号多行=一张单（前端按它聚合父行） |
| 供应商 | `supplier_id`（FK→Supplier） | 下单 | 一张单只该一个供应商（下载 PDF 时兜底拆分，:612-614） |
| 下单日期 | `delivery_date` | 下单 | 也是 `order_month` 筛选依据（下单月份） |
| 合同号 | `contract_no` | 下单 | — |
| 订单/项目编号 | `project_code`（字符串） | 下单，可收货时补/改 | #253 仓库收货可补（`PurchaseReceiveIn.project_code`，schemas.py:1391） |
| 来源清单 | `source_sheet_id` + `source_record_id` | 从清单下单 | 收货时回写清单"进度=已到货"；也供 keyword 第三分支回溯 |
| **送货单号** | `delivery_note_no` | **仓库收货** | models.py:664 |
| **到货日期** | `arrival_date` | **仓库收货** | models.py:665，填了即"已收货" |
| **预计到货** | `expected_arrival` | 采购下单 | models.py:666，见 §4 |
| 库位 | `stock_location` | **仓库收货** | #204 从采购下单挪到收货时填（models.py 注释） |
| 收货金额 | `received_amount` | 收货/后填价 | — |
| 收货单图片 | `Attachment`（biz_type=`receipt_doc`, biz_id=明细 id） | 仓库上传 | :2111+，前端父行聚合张数 |

**同一明细行同时承载"采购属性"与"收货属性"**，这是本系统收货设计的核心事实：没有"收货流水头"，收货就是更新明细行字段 + 触发尾部动作（§3.3）。

## 3. 合并收货逻辑

### 3.1 单条收货 `PUT /items/{iid}/receive`

- 定义：`purchase_mgmt_router.py:2013-2046`；schema `PurchaseReceiveIn`（schemas.py:1384-1391）。
- 必填：`arrival_date`（:2026-2027 校验），填了即已收货。
- 可带：`delivery_note_no`、`unit_price`、`received_amount`（后填价格流程，见 §3.4）、`stock_location`（#204，填了才写不覆盖为空）、`project_code`（#253，放入库前改，让入库流水能挂上项目）。
- `received_amount` 缺省时按 `qty × unit_price` 反算（:2041-2042）。
- 尾部统一走 `_finish_receive`（:2043）。

### 3.2 合并收货 `POST /items/receive-batch`

- 定义：`purchase_mgmt_router.py:2049-2107`；schema `BatchReceiveIn`（schemas.py:1400-1408），一行 `BatchReceiveLine = {item_id, unit_price, received_amount}`。
- 两种填价方式（docstring :2055-2058）：
  1. **合并总价** `total_amount`：按各行数量权重把总价分摊到 `received_amount`，**末行兜余数保证合计精确**，单价=金额÷数量（:2068-2082）。
  2. **逐行** `lines`：每行分别填单价/收货金额，金额缺省按 `qty × unit_price` 反算（:2083-2094）。
- 公共：同一 `delivery_note_no` + `arrival_date` + `stock_location`（整批一个库位）+ `project_code`（整批一个订单编号）写所有行（:2095-2103）。
- **前端提交走 lines 逐行**（`submitBatchReceive` :639-660，body.lines 逐行填价），`total_amount` 后端能力保留但前端当前未用（需求四早期形态）。

### 3.3 公共尾部 `_finish_receive`（:1992-2010）

每收货一行就执行，四步联动：
1. **回写清单**（:1995-2005）：有 `source_sheet_id+source_record_id` 时，`_writeback_sheet_row` 写「进度=已到货」+ 到货日期列（`_ALL_ARRIVAL_COLS`）+ 仓库签字/仓库列（`_ALL_WH_SIGN_COLS`，值=当前用户姓名）+ 库位列（`_ALL_WH_LOC_COLS`，#250）。
2. **自动入库** `_auto_stock_in`（:2006，实现 :1404-1441）：幂等（:1409-1412 按 `purchase_item_id` 且非冲红查已有流水，有了就 return），生成 `WhTxn`（direction=in、source="采购入库"、金额=数量×单价、挂 `purchase_item_id`、ref_no 按当天入库序列）；物料不存在自动建 `WhMaterial`，库位随最近收货更新；**收货不再自动出库**（:1439-1440 已删 is_stock=False 自动"采购领用"出库，出库统一走仓库领料）。
3. **流水金额同步** `_sync_txn_amount`（:2009，实现 :1443-1459）：#329 修 bug——`_auto_stock_in` 幂等导致"已收货改价"不会重新过账，金额停在旧价；这里统一回写：整条入库金额跟 `received_amount` 走，否则退回 `qty × unit_price`。
4. **自动对账** `_maybe_auto_reconcile`（:2010，实现 :724-736）：`invoice_status=待对账` 且付款方式∈{现金全款,对公全款} 且已收货且 `paid_amount ≥ received_amount-0.005` → 自动置「已对账」（只从待对账推进一次，不覆盖已人工确认的）。

### 3.4 收货后改价（"已收货"页签点修改）

- 前端：已收货 tab 的父行按钮是「合并修改」（:1475-1476），单行是「修改」（:1478），打开同一个 `openBatchReceive`/`openReceive` 弹窗，`submitBatchReceive`/`submitReceive` 提交。
- 后端：改价走**同一个** `PUT /items/{iid}/receive`（receive_item，:2013）或 `receive-batch`，因为字段就是明细行本身；改价后 `_finish_receive` 里的 `_sync_txn_amount` 保证库存/项目材料成本同步（:2007-2009 注释）。
- #329 采购改收货价：后端本就允许改 `received_amount`（合并单父行无独立改价入口是历史缺口，已并入逐条改价表格 + 按数量分摊总价助手）。

## 4. `expected_arrival` 预计到货字段

- 落点：`PurchaseItem.expected_arrival`，`String(10)`（models.py:666），ISO 日期，采购下单时填，选填。
- **下单时回写清单**：清单（Datasheet）有「预计到货」列（`_ALL_EXPECTED_ARRIVAL_COLS = ("预计到货",)`，:839）就写该列（:881, :1221, :1300, :1394 多个下单入口共用）。缺列的表在 `_ensure_expected_arrival_field` 里自动补列（:847-861）。
- **批量修改** `PUT /items/batch-expected-arrival`（#297，:1752-1790，schema `PurchaseBatchExpectedArrivalIn` = `{ids, expected_arrival}`，schemas.py:1378-1381）：传 null/空串=清空；改了回写清单对应列 + 给相关人发通知（修改通知）。
- **单条修改**：`PUT /items/{iid}` 编辑（`PurchaseItemUpdate`，schemas.py:1348）也能改 `expected_arrival`，同样回写清单（:1826）。
- **消费方（到期未到货提醒）**：`overdue.py` 的 `scan_po_arrival_overdue`——`expected_arrival ≤ 当日` 且 `arrival_date` 为空 → 给采购员/相关角色推送"预计到货已到期未到货"提醒；`expected_arrival` 被改过则按新日期重算。这是该字段唯一的主动消费，收货后 `arrival_date` 填上自然不再触发。
- 前端：`PurchaseItemOut.expected_arrival`（schemas.py:1421）→ 收货/采购列表展示；待收货列表里不因它分组。

## 5. 收货后采购单及明细的状态流转

**结论：没有显式状态机，状态是派生值。**

1. 下单时：`arrival_date = NULL` → 前端归类「待收货」tab。
2. 收货（单条或合并）：`arrival_date` 填非空 → 前端归类「已收货」tab（`recvReceived=true` 查询 `arrival_date IS NOT NULL`，:1898-1901）。
3. 同一张 PO 内的行**各自独立**到货：合并收货只是"一次收多行"，行级状态互不影响；前端父行 `arrival_date` 聚合为"单一日期/多个"（groupedRecv :444-445）。
4. 收货的级联（§3.3 四步）：清单进度→已到货、自动入库（`_auto_stock_in`）、流水金额同步（`_sync_txn_amount`）、自动对账（`_maybe_auto_reconcile`）。
5. 采购单**没有**"已收完/完成"的总状态——只要行还空着 `arrival_date` 就还在「待收货」里（多个供应商/分批到货全靠行级字段表达）。`receiving/meta` 的 `pending_count`/`received_count` 是给用户看的总览，不是状态。

**状态流转相关的其他旁路**（非收货写，但依赖 `arrival_date`）：
- 采购请款/付款：`_attach_pay_status`（:623-629）按已付金额+请款单状态算付款状态；`_maybe_auto_reconcile` 依赖 `arrival_date`（:732）。
- 收货单图片上传：`POST /items/{iid}/receipt`（:2111+，需求十四），与状态无关但挂在明细行上。

## 6. 按采购单号/项目编号搜索

### 6.1 前端入口（`WarehouseView.vue`）

- 搜索框：`recvPo`（采购单号/项目编号，一个框，#315/#330）、`recvName`（物料名称）、`recvOrderMonth`（下单月份）、`recvSupplier`（供应商，来自 meta 全量下拉）。对应模板 :1376 一带。
- 提交后 `loadReceiving()`（:451-466）把 `recvPo→keyword`、`recvName→item_name`、`recvOrderMonth→order_month`、`recvSupplier→supplier_id` 传后端。
- #330 起三个搜索框全部**下沉后端 SQL**（注释 :458），不再前端过滤——否则超 2000 上限的老单永远搜不到（回归教训：`keyword` 必须带 `source_sheet_id IN (...)` 第三分支，见 §1.1）。

### 6.2 后端口径

- `po_no` 参数：单查采购单号 `ILIKE`（:1904-1905）。
- `keyword` 参数：一个框同时匹配「采购单号 / 项目编号（含回溯）」三分支（:1909-1916），见 §1.1。
- 项目编号两种来源都能搜到：直接 `project_code ILIKE` + `source_sheet_id` 回溯分支（#253 补显示的编号也在 `PurchaseItem.project_code` 落库前就能被回溯分支命中）。

## 7. 权限与角色

| 接口 | 角色 | 行号 |
|---|---|---|
| `GET /receiving`、`GET /receiving/meta`、`PUT /items/{iid}/receive`、`POST /items/receive-batch`、`POST /items/{iid}/receipt` | `_RECEIVE_ROLES = ("warehouse", "warehouse_lead")` | :28, :1889, :1962, :2017, :2052 |
| `GET /orders/{po_no}/pdf` | `_PURCHASE_ROLES`（采购系）+ warehouse 两个 | :598（#234/#235 放开仓库） |
| 采购下单/编辑 | `_WRITE_ROLES = ("buyer","buyer_lead","buyer_standard","buyer_outsource")` | :25 |
| 采购查询全量 | `_PURCHASE_ROLES`，受限采购员用 `_buyer_restricted` 行级收窄 | :23, :608-609 |

- **收货不区分采购员行级权限**：仓库角色的 `_RECEIVE_ROLES` 能看到所有待收货明细（收货是仓库职能，不套 `_buyer_restricted`）。
- `_buyer_restricted`（受限采购员只能动自己的单）只作用在采购读写与 PDF 下载，不作用在收货。

## 8. 反例与排除（试过不成立 / 已停用的路径）

- **`.limit(300)` 时代的前端过滤**：筛不掉 limit 之外的老单（#330），已改成 SQL 下沉 + limit 2000 + `/receiving/meta` 兜底真实 count——不要再改回前端过滤。
- **收货自动出库**：`is_stock=False` 时自动生成「采购领用」出库已**删除**（:1439-1440），收货一律只入库到所选库位；出库走仓库领料。排查"收货后库存变负/不见了"时先看这条。
- **前端合并总价（total_amount）模式**：后端 `receive-batch` 仍支持 `total_amount` 按数量分摊，但前端当前 `submitBatchReceive` 只传 `lines` 逐行，不再传 `total_amount`——两条路径并存，改前端时别以为 total_amount 已废弃。
- **父行只"整单维护"改不了价**：#329 历史缺口（合并单父行没有独立改价入口），已并入逐条改价表格+分摊助手，不要重建"单改父行金额"的接口。
- **独立状态列/状态机**：本设计靠 `arrival_date` 派生状态，若为"待收货→已收货"加 status 列会和现有 `arrival_date IS NULL` 双写失步——不要引入第二状态源。
