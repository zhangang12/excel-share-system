# 仓库收货：数据模型与库存记账

> 探索主题：仓库收货。本文档覆盖「数据模型与库存记账」——receiving 相关表、PurchaseItem / WhTxn 结构、收货时库存增减、`_auto_stock_in` 幂等、`_sync_txn_amount` 金额回写、改价同步、分摊分位差。
> 证据一律标 `文件:行号`。代码以 `backend/app/` 下为准。

## 0. 一句话结论

**系统里没有独立的「收货单/收货头表」**。收货不是一个事务对象，而是三件事的叠加：①在 `purchase_items` 行上把 `arrival_date` 填上（一填即视为已收货）；②向 `wh_txns` 写一条 `direction='in'` 的库存流水（`_auto_stock_in`，幂等，同一明细只过一次账）；③回写来源清单「到货日期/进度/仓库签字/库位」。库存金额与成本的真源是这条 `wh_txns` 流水的 `amount`，由 `_sync_txn_amount` 在改价后回写保持一致。

## 1. 核心表结构与字段语义

### 1.1 `purchase_items`（采购明细，收货状态的载体）

定义 `backend/app/models.py:651-700`。收货相关字段：

| 字段 | 语义 | 谁填 / 何时 |
|---|---|---|
| `arrival_date` String(10) | **到货日期，非空=已收货** | 仓库收货接口必填（`receive_item` :2026 校验）；`PurchaseItemUpdate` **刻意不开放此字段**（schemas.py:1370-1371 注释：防止采购员绕过收货流程直填/清，让「到期未到货提醒」失真） |

## 2. 收货时库存增减：`_auto_stock_in`

`backend/app/routers/purchase_mgmt_router.py:1404-1440`。

### 2.1 幂等（关键）

```python
ex = await db.execute(select(WhTxn).where(
    WhTxn.purchase_item_id == item.id, WhTxn.is_reversal == False))
if ex.scalars().first():
    return
```

同一 `purchase_item_id` 且非冲红已有流水 → 直接 return，**只过账一次**。因此第二次收货/改价不会重新生成流水（这是 `_sync_txn_amount` 存在的根因，见 §3）。

### 2.2 入库细节

1. **物料定位**：按 `name` + `spec`（spec 空时匹配 `spec IS NULL`）精确查 `wh_materials`（:1413-1416）。
2. **找不到则自动建物料**：`WhMaterial(name=item_name, spec=spec, unit="个", category="采购入库", location=loc)`（:1418-1422）；找得到且收货带库位则更新 `m.location = loc`（单库位模型，"最近一次收货放哪，物料当前库位就是哪"）。
3. **挂项目**：`project_code` → 查 `Project.id`，没有则 `pid=None`（:1425-1428）。
4. **业务日期**：`arrival_date or 今天`（:1429）。
5. **单据号**：`_next_ref(db, "in", bd)` → `"RK{yyyymmdd}-{NNN}"`，NNN 是当日已有 RK 流水数+1（`warehouse_router.py:619-625`）。
6. **金额**：`amt = round(qty × unit_price, 4)`；`unit_price is None` 时 `amount=None`（:1432-1433）。
7. **写流水**：`direction="in"`, `source="采购入库"`, `party=供应商名`, `location=(loc or m.location)`, `purchase_item_id=item.id`（:1434-1438）。

### 2.3 只有入库、没有自动出库

`is_stock=False` 时的「采购领用」自动出库**已删除**（:1439-1440 注释）：收货一律只入库到所选库位；出库统一走仓库领料（出入库登记 / 物料需求一键领用）。注意 `_auto_stock_in` 的 docstring（:1405-1406）**仍写着旧语义**（"非备货再自动出库"），是过期注释，以代码为准。

## 3. 改价回写：`_sync_txn_amount`

`backend/app/routers/purchase_mgmt_router.py:1443-1459`。

### 3.1 为什么需要它

因 `_auto_stock_in` 幂等，改价不会重新生成流水——**不回写的话，采购明细金额改对了，库存金额与项目材料成本还停在旧价上**（#329 修复）。入口注释写得很清楚（:1446-1448）。

### 3.2 口径（核心：整条 vs 部分）

```python
for t in tr.scalars().all():                      # 该明细所有非冲红流水
    t.unit_price = item.unit_price
    if item.received_amount is not None and item.qty and t.qty == item.qty:
        t.amount = round(item.received_amount, 4)      # 整条一次性入库：跟收货金额走
    elif item.unit_price is not None:
        t.amount = round((t.qty or 0) * item.unit_price, 4)  # 其余：退回 qty×单价
```

- **整条明细一次性入库**（`t.qty == item.qty`，当前唯一实际路径）→ `amount` 直接等于 `received_amount`。因为合并收货的单价是「金额÷数量」反算的，`qty × unit_price` 会有分位差，跟 received_amount 才能保证**采购明细收货金额与库存/项目成本是同一个数**。
- **部分入库等其他情况**（防御分支，当前代码无部分收货路径）→ 退回 `qty × unit_price`。

### 3.3 调用点（两个）

- `update_item`（PUT `/items/{iid}`，:1795，`_sync_txn_amount` 在 :1823）——**仓库在「已收货」页签点「修改」改价**的入口；`PurchaseItemUpdate` 放开 `unit_price` / `received_amount`（schemas.py:1358-1359）。
- `_finish_receive`（:2009）——收货尾部的统一回写（覆盖"收货时后补价格"场景）。

## 4. 收货主流程

### 4.1 单条收货 `receive_item`（PUT `/items/{iid}/receive`）

`:2014-2046`，角色 `_RECEIVE_ROLES = ("warehouse", "warehouse_lead")`（:28）。顺序：

1. 校验 `arrival_date` 必填（:2026-2027，"一填即视为已收货"）。
2. 写 `delivery_note_no` / `arrival_date`。
3. **库位**：填了才写，不覆盖已有非空值（:2030-2033，#204）。
4. **订单编号**：`body.project_code is not None` 才改（:2035-2036），且放在入库前——入库流水能挂上项目（:2034 注释）。
5. **价格**：`unit_price` / `received_amount` 可选补填；`received_amount` 没填时若 qty & unit_price 有值则自动 `received_amount = round(qty × unit_price, 4)`（:2037-2042，后填价格流程）。
6. `_finish_receive(...)` → commit。

### 4.2 合并收货 `receive_batch`（POST `/items/receive-batch`）

`:2050-…`，同样 `_RECEIVE_ROLES`。两种填价方式（schemas.py:1400-1408）：

- **合并总价 `total_amount`**：按各行数量权重分摊到 `received_amount`，单价 = `round(share/qty, 4)`；
- **逐行 `lines`**：各行分别填单价/收货金额，没填金额时用 `qty × unit_price`。

### 4.3 共同尾部 `_finish_receive`

`:1992-2010`，四步：

1. **回写清单**：若 `source_sheet_id & source_record_id` 非空，写「进度=已到货」+ `_ALL_ARRIVAL_COLS`（到货日期/到料日期，:836）+ `_ALL_WH_SIGN_COLS`（仓库签字/仓库，:837）= 当前操作人姓名 + `_ALL_WH_LOC_COLS`（库位，:838，有该列的清单才写，#250）。
2. `_auto_stock_in`（§2）。
3. `_sync_txn_amount`（§3）——统一保证金额同步。
4. `_maybe_auto_reconcile`。

### 4.4 自动对账 `_maybe_auto_reconcile`

`:724-737`：`现金全款/对公全款` + 已收货(`arrival_date` 非空) + 已付清(`paid_amount >= received_amount - 0.005`) → `invoice_status` 从「待对账」置「已对账」；只从「待对账」推进一次，不覆盖已人工确认过的状态。

## 5. 实时库存聚合：`_stock_map`

`backend/app/routers/warehouse_router.py:34-55`：

```python
实时库存(material) = init_stock + Σ(in) − Σ(out)
```

- 按 `material_id` + `direction` 分组聚合，in 加、out 减；可选 `upto=biz_date`（含当日，用于期初/期末）。
- **没有独立的库存余额表**，库存永远是实时聚合结果——收货入库就是多了一条 in 流水，`_stock_map` 自然反映。
- 全仓没有盘点/调拨/退料/报废实现；采购退货靠「仓库冲红（reverse :868）+ 删明细」两原语拼出。

## 6. 数量分摊的分位差（重点）

### 6.1 源头：合并收货分摊

`receive_batch` :2068-2082：

```python
share = round(body.total_amount * (weights[idx] / wsum), 2)   # 每行按数量权重，round 2 位
# 末行：
share = round(body.total_amount - allocated, 2)               # 兜余数，保证合计精确
it.unit_price = round(share / it.qty, 4)                      # 单价=金额÷数量反算
```

- 每行金额 round 到 **2 位**（分），末行用 `total − Σ已分摊` 兜住舍入差，**合计精确等于填入的总价**。
- 但单价是反算的（`share ÷ qty`，round 到 4 位）→ 必然存在 `qty × unit_price ≠ share` 的**分位差**（float 除法舍入）。

### 6.2 消化：`_sync_txn_amount` 整条跟 received_amount

`_sync_txn_amount` 对整条明细的流水**不**用 `qty × unit_price` 重算，而是直接 `amount = round(received_amount, 4)`（:1456-1457），正好把 6.1 的分位差消掉——保证 WhTxn 流水金额、采购明细收货金额、项目材料成本三处同一数。部分入库分支才退回 `qty × unit_price`（当前无此路径，防御用）。

### 6.3 同类分摊模式

合计开票也是同一套"按收货金额比例分摊、末条兜余数"做法（:2161-2162，#100）；「合并父行整单维护」则刻意**不分摊**，总额记首行（:2188）。

## 7. 反例与过期点（下一棒别再踩）

- ❌ **不存在 Receiving / 收货单 / 收货头表**——全仓无 `Receiving`/`ReceiveOrder` 类。收货状态就是 `purchase_items.arrival_date`。找"收货单"没有意义。
- ❌ **`is_stock` 已废弃**：:811/:1213/:1380 收货一律只入库，`is_stock` 恒 True，别再按它写逻辑。
- ⚠️ **`_auto_stock_in` 的 docstring（:1405-1406）是过期注释**，仍写着"非备货再自动出库"，实际 :1439 已删；看代码别信注释。
- ⚠️ **`_sync_txn_amount` 的"部分入库"分支目前是死代码**（收货都整条过账），是防未来部分收货的防御分支，不是已实现功能。
- ⚠️ **两个价格口径别混**：`wh_materials.unit_price` 是参考单价（库存总览总价用），`wh_txns.unit_price/amount` 才是采购入库的实际成本；改价只回写后者。
- ⚠️ **`_auto_stock_in` 修改 `m.location`**（单库位模型）：同一个物料被多次收货到不同库位，物料当前库位会被最后收货覆盖——若未来要多库位共存需先改这个模型。
