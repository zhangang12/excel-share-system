## 0. 一句话总览

系统**没有独立的「收货单表」「收货头表」「采购单表」**。仓库收货不是独立的事务对象，而是以下动作的叠加：

1. **在 `purchase_items` 行上把 `arrival_date` 填上**——空=待收货，非空=已收货（`purchase_mgmt_router.py:2026-2027`）
2. **`_auto_stock_in` 写一条 `direction='in'` 的库存流水**——幂等，同一采购明细只过一次账（`purchase_mgmt_router.py:1404-1440`）
3. **`_sync_txn_amount` 回写流水金额**——改价后保证库存金额与收货金额一致（`purchase_mgmt_router.py:1443-1459`）
4. **`_writeback_sheet_row` 回写来源清单**——到货日期/仓库签字/库位写进 `Datasheet` 对应行（`purchase_mgmt_router.py:864-893`）

采购单 = `PurchaseItem.po_no` 同号多行的聚合视图。全部 7 个收货端点集中在 `purchase_mgmt_router.py`（前缀 `/api/purchase-mgmt`），权限统一 `_RECEIVE_ROLES = ("warehouse", "warehouse_lead")`。采购员只下单不收货。

## 第一章 核心机制（最最重要）

### 1.1 收货的本质：零独立表、四件事叠加

**上游六篇完全一致（01 §9、02 §7、03 §0、04 §0、05 §0、06 §0），无任何矛盾**。

系统不存在 `Receiving`、`ReceiveOrder`、`ReceiptHead`、`ReceiptLine` 等收货专属模型类。全模型文件 `models.py` gRPC 扫描确认。收货状态是 `purchase_items.arrival_date` 的派生值——NULL=待收货，NON-NULL=已收货（`models.py:663` `arrival_date: Mapped[Optional[str]]`）。

同一张 `PurchaseItem` 行同时承载采购属性（`po_no`/`buyer_id`/`delivery_date`/`expected_arrival`）与收货属性（`arrival_date`/`delivery_note_no`/`stock_location`/`received_amount`）——这是理解整个收货模块的基础，后续所有接口和流程都建立在此设计之上。

### 1.2 路由归属：全在 purchase_mgmt_router.py

**六篇完全一致，无矛盾**（01 §1、02 §0、03 §0、04 §0、05 §0、06 §0）。

- 所有收货端点定义在 `APIRouter(prefix="/api/purchase-mgmt")`（`purchase_mgmt_router.py:20`）
- 在 `main.py:184` 通过 `include_router` 挂载（01 §1 核实）
- **不存在独立的 receiving router**（01 §9、03 §0 均排除）
- **收货不在 `warehouse_router.py` 中**：`whApi`（`frontend/src/api/warehouse.ts`）只封装出入库流水/物料/发货清单/采购申请，与收货无关（01 §6、04 §8）
- **`PurchaseMgmtView.vue` 不含收货交互**（04 §0 核实）

### 1.3 角色约定

**多篇一致**（01 §1.2、03 §0、05 §1）。

`purchase_mgmt_router.py:22-28`：

| 常量 | 角色 | 用途 |
|------|------|------|
| `_RECEIVE_ROLES` | `warehouse`, `warehouse_lead` | 收货读写——仓库专有 |

### 2.2 `list_receiving`（`GET /receiving`）详细分析

**来源**：01 §2.1、03 §1.1-1.5、04 §2.1。

**response_model** = `List[PurchaseItemOut]`（`schemas.py:1411-1451`，含 `unit_price`/`received_amount`/`invoice_amount`/`paid_amount` 四个金额字段全量返回）

**入参**（Query，`purchase_mgmt_router.py:1902-1921`）：

| 参数 | 类型 | 默认 | 说明 |
|------|------|------|------|
| `received` | bool | `false` | `false`→`arrival_date IS NULL` 待收货；`true`→已收货 |
| `supplier_id` | int? | - | 供应商过滤 |
| `po_no` | str? | - | 采购单号模糊匹配 |
| `keyword` | str? | - | 三分支搜索（见下方详解） |
| `item_name` | str? | - | 物料名称模糊匹配 |
| `order_month` | str? | - | 下单月份 `YYYY-MM`（`delivery_date` 前 7 位等于） |
| `limit` | int | 2000 | 上限 5000（`_RECV_LIMIT_MAX`，`:1878`） |

**排序**：`po_no DESC NULLS LAST, id DESC`（`:1894-1897`）

**keyword 三分支搜索**（`purchase_mgmt_router.py:1909-1916`）：

此设计的缘由与重要性在 03 §1.1 和 06 §5.1 中详细讨论：

1. **`po_no.ilike(f"%{keyword}%")`**（:1910）——直接匹配采购单号
2. **`project_code.ilike(f"%{keyword}%")`**（:1911-1912）——直接匹配项目编号
3. **`source_sheet_id IN (SELECT Datasheet.id JOIN Project WHERE Project.code ILIKE)`**（:1913-1916）——回溯 #253 那批 `project_code` 为空的明细

第三分支是 #253 的救命线：#253 的采购明细行 `project_code` 是空的（因为没有对应项目字段），但通过 `source_sheet_id → Datasheet.project_id → Project.code` 可以回溯出项目编号。删掉第三分支=回归 #253。03 §1.1 专门强调"keyword 必须带 source_sheet_id IN (...) 分支，否则 #253 那批回溯项目编号的行搜不到=回归"。

**#253 项目编号回溯**（输出端，`purchase_mgmt_router.py:1924-1946`）：

对 `source_sheet_id` 非空且 `project_code` 为空的明细，经 `Datasheet.project_id → Project.code` 回溯出项目编号，回填到输出（只补显示，不落库）。03 §1.2 详细分析了两个回溯的异同：（1）keyword 分支回溯是搜索条件的扩展（找到哪些明细），（2）输出回溯是结果的补全（显示项目编号）。

**list_receiving 过滤全部下沉 SQL、先于 limit**（`:1902-1920`，03 §1.5、06 §5.1 均强调）——这意味着带筛选条件可以穿透 limit 2000 的截断找到老单。#330 教训：原本 limit=300，无筛选时历史被截断；改为 2000 并加 `/receiving/meta` 出真实 count。06 §5.1 分析了为什么筛选必须先于 limit："筛选条件在 SQL WHERE 子句中，limit 在最后才应用。不加 limit → 全表扫描，limit 是唯一的分页手段，但 offset=无实现。"

### 2.3 `receiving_meta`（`GET /receiving/meta`）

**来源**：01 §2.2、03 §1.4。

返回体（`purchase_mgmt_router.py:1983-1989`）：

```python
return {"pending_count": pending_count, "received_count": received_count,
        "suppliers": [{"id": s.id, "name": s.name} for ...],
        "limit": _RECV_LIMIT_DEFAULT}
```

- `pending_count` / `received_count`：独立 `select(func.count(...))`（`:1969-1973`），不受列表 limit 影响——这是徽标数的唯一真实来源
- `suppliers`：`select(Supplier.id, Supplier.name).join(PurchaseItem)...distinct().order_by(Supplier.name)`（`:1975-1981`）——全量供应商下拉，独立查询
- `limit`：传前端用于截断判断

03 §1.4 详细解释了为什么这个端点要独立于列表："此前徽标数取截断列表 length（永远 ≤300），供应商下拉也只从 300 条去重——唯一能穿透截断的筛选维度自己也被截断了。`receiving_meta` 是 #330 '#315/#330 并行修复' 的一部分，两个 COUNT 都是直接对 PurchaseItem 表做的全表统计，不受列表查询的任何 WHERE 条件影响（除了 arrival_date 的空/非空），也不受 limit 截断——这就是徽标数真实的数学基础。"

### 2.4 单条收货 `receive_item`（`PUT /items/{iid}/receive`）

**来源**：01 §2.3、03 §3.4。

请求体 `PurchaseReceiveIn`（`schemas.py:1384-1391`）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `arrival_date` | date | ✅ | 到货日期（`:2026-2027` 校验 `if not body.arrival_date: raise 400`） |
| `received_amount` | float? | ❌ | 收货金额（#329 允许改价） |
| `receiver_sign` | str? | ❌ | 收货人签字 |
| `warehouse_loc` | str? | ❌ | 库位（#204 起由收货时填） |
| `delivery_note_no` | str? | ❌ | 送货单号 |
| `notes` | str? | ❌ | 备注 |

**执行流程**（`purchase_mgmt_router.py:2014-2044`）：

```
1. 校验 arrival_date 不为空
2. 把 PurchaseReceiveIn 的所有字段 setattr 到 item（按字段映射）
   - 特别：received_amount 缺省按 qty × unit_price 反算（:2041-2042）
   - 特别：arrival_date 是非 str 字段，做 .isoformat() 转字符串（:2032-2033）
3. _finish_receive(db, item, current, loc=warehouse_loc)
4. await db.commit()
5. 返回 item
```

01 §2.3 和 03 §3.4 都确认：同一端点用于收货和改价——如果明细已收货（`arrival_date` 已有值），再次调用是改价/改库位，而非重新入库（`_auto_stock_in` 幂等保证了这点）。

### 2.5 合并收货 `receive_batch`（`POST /items/receive-batch`）

**来源**：01 §2.4、03 §4.3-4.4、04 §4.4、06 §6.9。

请求体 `BatchReceiveIn`（`schemas.py:1400-1408`）两种填价方式：

**方式一：合并总价 `total_amount`**（分段 `purchase_mgmt_router.py:2068-2082`）：

```python
# 按数量权重分摊
for i, line in enumerate(orderlines):
    if i == last_idx:
        share = round(total_amount - allocated, 2)  # 末行兜余数
    else:
        share = round(total_amount * item.receive_qty / total_qty, 2)
    item.received_amount = share
    item.unit_price = round(share / item.receive_qty, 4)   # 单价=金额/数量反算
```

03 §4.3 详细分析了分摊算法："末行兜余数保证合计精确等于填入总价；单价反算 `round(share/qty,4)` 必然存在 `qty × unit_price ≠ share` 的分位差，`_sync_txn_amount` 在整条入库时用 `received_amount` 而非 `qty×单价` 正好把分位差消掉。"

**方式二：逐行 `lines`**（`:2083-2094`）——当前前端唯一使用的模式：

每行分别传 `{item_id, unit_price, received_amount}`。后端逐个 `setattr`。

**整批共享字段**（`:2095-2103`）：`delivery_note_no`、`arrival_date`、`stock_location`、`project_code` 统一写所有行的明细。

**批量原子性**（`:2105`——循环每条 `_finish_receive` → 最后**统一一个** `db.commit()`）——"不会收一半"（06 §3.2 确认）。

**重要发现（n20 核实 + n38 评估）**：前端已清理 `total_amount` 模式的死代码（`batchRecvMode`/`batchTotalQty`/`splitShare`/`batchRecvForm.total_amount` 已删除），`submitBatchReceive` 只传 `lines` 逐行价。但后端 `receive_batch` **仍保留** `body.total_amount is not None` 分支——即服务器仍支持合并总价分摊模式。n37 §6.2 指出："前端死代码清理后不能再触发 `total_amount` 路径，但后端保留。这不是矛盾而是「后端路径当前前端不可达」状态，应标注为「后端残留死分支」或后续清理。"

n38 §4 评估结论：前端死代码清理保留（KEEP），改动正确无行为影响，vue-tsc 通过。n20 独立核实确认同样的结论：四个符号全部死代码，grep 全仓零引用。

### 2.6 内部函数调用链

**来源**：01 §3.1-3.3、02 §4.3、03 §3.3。

所有内部函数均在 `purchase_mgmt_router.py` 内，无独立 service 文件。

**`_finish_receive`**（`:1992-2010`）——单条和批量共用尾部，四步链：

```
_finish_receive(db, item, current, loc=None)
  ├─ 1. _writeback_sheet_row(item, ...)     # 回写来源清单
```

每一步均独立 try/catch 不影响后续（01 §3.1 指出、02 §4.3 确认）。

详细分析见第三、八章。

### 2.8 状态流转（全流程）

```
采购下单（arrival_date = NULL, expected_arrival 选填）
    │
    │ GET /receiving?received=false  →  SQL WHERE arrival_date IS NULL
    │
    ▼
【待收货】tab（仓库角色可见，所有采购员的单=全集）
    │
    │ PUT /items/{iid}/receive  或  POST /items/receive-batch
    │ → 填 arrival_date + received_amount + 签字/库位/送货单号
    │ → _finish_receive 四步链
    │   ├─ ① 回写清单 → 进度=已到货 + 到货日期/仓库签字/库位
    │   ├─ ② 自动入库 → _auto_stock_in → WhTxn(in) 幂等，同一明细只过一次账
    │   ├─ ③ 流水金额同步 → _sync_txn_amount（#329）
    │   └─ ④ 自动对账 → _maybe_auto_reconcile（现金全款+已收货+已付清→"已对账"）
    │
    ▼
【已收货】（arrival_date IS NOT NULL）
    │
    │ GET /receiving?received=true  →  已到货列表
    │ 改价/改库位：PUT /items/{iid}/receive（同端点）
    │   → _sync_txn_amount 回写流水金额（不重新生成流水）
    │
    ▼
    ├── 清单显示：进度=已到货 + 到货日期/仓库签字/库位
    ├── 库存增加：WhTxn(in) → _stock_map 自动累加
    ├── 自动对账：_maybe_auto_reconcile 推进 invoice_status=已对账（条件满足时）
    └── 附件上传：收货单图片/PDF → Attachment(biz_type="receipt_doc")
```

**关键设计**（01 §7）：同一张 PO 的行**各自独立**到货——父行不聚合状态，`arrival_date` 全行一致才显示单一日期，否则显示「多个」。没有"PO 已收完/未收完"的总状态。04 §6.2 确认前端父行显示逻辑：`_isGroup=true` 的父行 `arrival_date` 全一致才显示日期值，否则显示「多个」。

#### 3.1.1 `purchase_items`（收货状态的唯一载体）

### 3.2 `_auto_stock_in` 自动入库——幂等与细节

**这是本主题最多来源交叉验证的核心函数**。以下来自 01 §3.2、02 §2.2、03 §3.3、06 §3.3、n11 核实 docstring、12 核实 单库位模型、n24 核实 通知异常。

定义 `purchase_mgmt_router.py:1404-1440`。

**幂等设计**（`:1409-1412`，02 §2.1、06 §3.3）：

```python
ex = await db.execute(select(WhTxn).where(
    WhTxn.purchase_item_id == item.id, WhTxn.is_reversal == False))
if ex.scalars().first():
    return
```

同一 `purchase_item_id` 且非冲红已有流水 → 直接 return，**只过账一次**。因此第二次收货/改价不会重新生成流水——这是 `_sync_txn_amount` 存在的原因。

⚠️ **并发风险**（06 §4.1、n24 §4.1 双重确认）：`WhTxn.purchase_item_id` 只有 **index=True 无 unique=True**（`models.py:413`），check-then-act 在两个事务同时查不到记录时可能双写。06 将此标为"高严重度风险"（触发条件苛刻但无数据库防线），n24 逐行对照确认列定义确为 `index=True` 无 `unique=True`。详见第八章。

**入库步骤**（02 §2.2 最详细）：

1. 按 `name+spec` 精确查 WhMaterial（:1413-1416）；找不到自动建物料（:1418-1422）
2. 收货带库位 → 更新 `m.location`（单库位模型，最近一次收货决定物料当前库位）
3. `project_code` 查 Project.id，没有则 `pid=None`（:1425-1428）
4. `biz_date = arrival_date or 今天`（:1429）
5. 单据号：`_next_ref(db, "in", bd)` → `"RK{yyyymmdd}-{NNN}"`（`warehouse_router.py:619-625`）
6. 金额：`round(qty × unit_price, 4)`（:1432-1433）
7. 写流水（:1434-1438）
8. ~~自动出库~~ **已删除**（:1439-1440 注释），收货一律只入库到所选库位

**已废弃的自动出库**（02 §2.3、n11 核实）：`is_stock=False` 时自动生成「采购领用」出库**已删除**。n11 确认：函数体全程只做入库，无 `is_stock` 判断，无 `direction="out"` 的流水创建。注释 `:1439-1440` 明确写"取消收货自动出库"。

⚠️ **Docstring 过期**（n11 核实 §2-3）：`_auto_stock_in` 的 docstring（`:1405-1406`）仍写着旧语义"非备货再自动一笔采购领用出库"，实际代码已删除。n11 结论："任何只看 docstring 的人都会被误导以为收货会为非备货项生成出库流水。"

### 3.3 `_sync_txn_amount` 改价回写——口径、调用点、分支可触达性

**此函数是本主题交叉验证中最重要的发现**——多个来源的表述需要仔细校准。

定义 `purchase_mgmt_router.py:1443-1459`。02 §3.1、03 §3.4、06 §3.3 均提到它。

**为什么需要它**：`_auto_stock_in` 幂等导致"已收货改价"不会重新生成流水，流水金额停在旧价。`:1446-1448` 注释写"若用户后补或修改价格，此函数将流水的单价/金额同步为最新"。

**口径**（`:1453-1458`）：

```python
if item.received_amount is not None and item.qty and t.qty == item.qty:
    t.amount = round(item.received_amount, 4)      # 分支A：整条一次性入库 → 跟收货金额走
elif item.unit_price is not None:
    t.amount = round((t.qty or 0) * item.unit_price, 4)  # 分支B：t.qty≠item.qty → qty×单价重算
```

**调用点（两个）**（02 §3.1、n13 核实）：

- `_finish_receive`（:2009）——收货尾部统一回写，刚生成的流水 `t.qty == item.qty`，走进分支A
- `update_item`（:1823）——PUT `/items/{iid}` 修改明细。当 qty/unit_price/received_amount 任一变化时触发

**⚡ 重大发现（n13 核实，推翻 02 §7 的"死代码"说法）**：

**02 §7 反例** 曾标记"部分入库分支目前是死代码"——声称 `_sync_txn_amount` 的 else 分支（`t.qty != item.qty` 路径）当前不可达。

**n13 核实 §3-4 证明此说法不成立**：

- `PurchaseItemUpdate.qty` 是可写字段（`schemas.py:1357`）
- `update_item` 未阻止修改已收货明细的 qty——仅 pop 掉 `arrival_date`（`:1807-1816`），qty 修改不受限
- `update_item` 第 1822 行明确检查 `"qty" in data`，变化后调 `_sync_txn_amount`
- 此时 `_auto_stock_in` 幂等不重新生成流水，`t.qty`（流水旧 qty）≠ `item.qty`（修改后）→ 走进 else 分支（`:1458-1459`）

**结论修正**：else 分支（`t.qty != item.qty` 时的 `qty×单价` 重算）**不是死代码**——收货后通过 `update_item` 修改 qty 即可触达。02 之前的判定需要更新为：

> `_sync_txn_amount` 的分支B（`else` 路径）可通过 `update_item` 修改已收货明细的 qty 触发，不是死代码，但当前无日常业务流程走到此路径（改已收货 qty 属于异常补救场景）。

**`_sync_txn_amount` 金额口径总结**（02 §3.1 原表述，修正后）：

| 触发场景 | 走进分支 | 金额计算 | 可控性 |
|---------|---------|---------|--------|
| `_finish_receive` 收货即刻 | A (`t.qty == item.qty`) | `amount = received_amount` 逐条 | 直接控制（改 received_amount） |
| `update_item` 改非 qty 字段 | A (`t.qty == item.qty`) | `amount = received_amount` 逐条 | 直接控制 |
| `update_item` 改 qty（已收货） | B (`t.qty != item.qty`) | `amount = qty × unit_price` 退回计算 | 间接受 u_p/u_qty 影响 |
| 合并收货总价分摊 | A (`_finish_receive` 即刻) | `amount = received_amount` 逐条 | 消掉分摊分位差 |

### 7.3 失败回滚

06 §3.1-3.2 分析。

**get_db 隐式回滚**（`database.py:28-30`）：

```python
async def get_db() -> AsyncSession:
    async with SessionLocal() as session:
        yield session
```

无 try/except/finally，无显式 rollback。靠连接归还时未提交事务被丢弃——即**隐式回滚**（可靠但不具日志可见性）。

**收货提交是单 commit 尾部**（06 §3.2、n24 §3.2）：
- `receive_item`：`_finish_receive` → **一个** `db.commit()`（`:2044`）——任一步抛异常，全部回滚
- `receive_batch`：循环每条 `_finish_receive`→**最后统一一个** `db.commit()`（`:2105`）——批量原子性成立

### 7.4 `push_message` 的 commit 契约

06 §3.4、n37 §4.3、n24 §3.4 均分析：

- `push_message` **自己 commit**（`notify.py:76` `await db.commit()`）
- 约定在业务 commit 之后调用——否则会把该 session 上所有未提交变更一并提交
- 收货路径不调用此函数，因此无此风险
- `scan_po_arrival_overdue` 使用独立会话且每推一条 commit 一次，符合约定
- `push_message` 目标用户为空时 `return 0` **不 commit**（`notify.py:60-62`）——这是全局坑

## 附C：合并收货算法详解

### 按总价分摊的完整算法（总价模式）

`purchase_mgmt_router.py:2068-2082`（后端仍保留，前端已不再触发——n20/n38 确认）：

```
输入：total_amount（总价），orderlines（选中行列表，每行带 receive_qty=采购数量）
前提：所有行同 PO，sum(receive_qty) > 0

步骤一：计算总数量
    total_qty = sum(line.receive_qty for line in orderlines)

步骤二：逐行分摊
    allocated = 0
    for i, line in enumerate(orderlines):
        item = items_by_id[line.item_id]
        if i == len(orderlines) - 1:
            share = round(total_amount - allocated, 2)  # 末行：兜舍入差
        else:
            share = round(total_amount * line.receive_qty / total_qty, 2)  # 前N-1行：按数量权重
        item.received_amount = share
        item.unit_price = round(share / line.receive_qty, 4)  # 单价=金额/数量
        item.delivery_note_no = body.delivery_note_no
        # ... 然后 _finish_receive

步骤三：_sync_txn_amount 消化分位差
    此时各行的 received_amount 合计精确等于 total_amount（末行兜差）
    但 unit_price * qty ≠ received_amount（单价只有 4 位小数）
    → _sync_txn_amount 用 received_amount 直接设 WhTxn.amount（跳过 qty×u_p 重算）
```

### 逐行模式的完整算法

`purchase_mgmt_router.py:2083-2094`（当前前端唯一使用模式）：

```
输入：lines[{item_id, unit_price, received_amount}]，共享字段

for line in body.lines:
    item = items_by_id[line.item_id]
    item.unit_price = line.unit_price or item.unit_price
    item.received_amount = line.received_amount or (
        round(item.qty * (item.unit_price or 0), 2) if item.unit_price else None
    )
    item.delivery_note_no = body.delivery_note_no
    # ... 然后 _finish_receive
```

前端为每行独立提供单价和金额，`onBatchLinePriceCalc`（`WarehouseView.vue:606-608`）预填单价→金额自动计算。

### 两种模式的比较

| 维度 | 总价分摊 | 逐行 |
|------|---------|------|
| 输入 | 一个总价 + 各行数量 | 每行单价/金额 |
| 计算 | 数量权重分摊，末行兜差 | 各行独立 |
| 分位差 | 单价反算引入，_sync_txn_amount 消除 | 各行填整数金额则无分位差 |
| 前端是否触发 | ❌（死代码已清理） | ✅（当前唯一模式） |
| 后端是否保留 | ✅（兼容未来） | ✅ |
| curl 是否可达 | ✅（手动构造 JSON） | ✅ |

### 改价双向计算关系

```
onRecvCalc(item, u):          item.received_amount = u * item.qty          → 单价↓→金额↓
onRecvAmountCalc(item, a):    item.unit_price = a / item.qty               → 金额↓→单价↓
onBatchLinePriceCalc(line):   line.received_amount = line.unit_price * line.qty  → 单价↓→金额↓
```

双向绑定通过 `u`（单价 el-input-number v-model）和 `a`（金额 el-input-number v-model）的 `@change` 事件触发，不为同一个 computed（否则无限循环）。`onEmit` 标记防止递归触发。
