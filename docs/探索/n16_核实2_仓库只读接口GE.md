# n16 · 核实#2 证伪 · 仓库域只读接口 GE

> 核实员，证伪视角。规则：默认立场是这条是错的，先努力证伪。

## 要核的说法

> 仓库域只读接口 GET /materials、/txns、/summary、/locations、/po-items 在接口层只挂 get_current_user（任何登录用户可读），域隔离完全依赖前端 User.menus+hidden_tabs，管理员误配菜单或直接 curl 即可读到库存/流水/采购已到货行

## 核实路径

逐层查问——接口层、依赖函数、全局中间件、nginx——看有没有说法遗漏的后端门控。

### 第二层：`get_current_user` 做了什么

`backend/app/deps.py:11-28`：

```python
async def get_current_user(authorization, db) -> models.User:
    # 1. 从 Header 取 Bearer token
    # 2. decode_token(token) → payload
    # 3. payload.sub → user_id
    # 4. select User WHERE id=user_id
    # 5. 检查 is_active
    # → 返回 user
```

只做三件事：**验 token → 查用户 → 验活性**。不做任何角色判断、菜单比对、域隔离。

### 第五层：前端域隔离（唯一真实隔离层）

- **菜单一级门控**：`user_menu_keys()`（menus.py:142-154）—— admin/manager 全量 bypass；其余按 `User.menus`，NULL 兜底 `DEFAULT_ACCOUNT_MENUS`。
- **二级 tab 门控**：`User.hidden_tabs`（menus.py:105-135 `TAB_REGISTRY`），前端 `WarehouseView.vue:29-32` 据此显隐。
- **路由守卫**：`MainLayout.vue:185-189` 按 `auth.hasMenu(key)` 渲染一级菜单。

这些全部是前端层面的控制，接口层零角色校验。

### 第六层：n7 已有结论对照

n7「权限与可见性」文档（仓库收货_05权限.md）已独立得出相同结论：
- :72-73 — "读接口大量只挂 `Depends(get_current_user)`，接口层只验登录，域隔离靠前端菜单。"
- :112 — "仓库域只读接口接口层零角色校验：域隔离完全依赖 `User.menus` + `hidden_tabs`。若某账号被管理员误配 `warehouse` 菜单或 hidden_tabs 未收敛，可直接读到库存/流水/采购已到货行。"

两份独立核实结论一致。

## 反例试过但不成立

1. **以为有全局中间件做菜单门控**：`main.py` 里只有 CORS + 桌面统计，无权限中间件。全项目 grep `dependency_overrides` 无命中。
2. **以为 nginx 有路径级拦挡**：nginx 对所有 `/api/` 一路 proxy_pass，无路径区分。
3. **以为 `get_current_user` 隐含角色过滤**：读完 deps.py:11-28，只验 token + is_active，无角色判定。

## 判决

**PASS** —— 说法成立，无法证伪。

七个独立窗口的证据互相印证，结论统一：

- 接口层：五个端点只挂 `get_current_user`，零角色门控
- 依赖层：`get_current_user` 是无差别的登录验证，不做域隔离
- 中间件层：无全局菜单/权限拦截
- nginx：无路径级门控
- 后果：任何登录用户（不论角色）持有效 token 即可 curl 读到库存/流水/采购已到货行
- 域隔离唯一实控层：前端 `User.menus` + `hidden_tabs`（可被管理员误配绕过）
- 已与 n7 独立核实结论对照，一致
