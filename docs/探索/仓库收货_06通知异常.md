## 1. 到期未到货每日提醒 `scan_po_arrival_overdue`

### 1.1 触发与调度

- 进程启动时注册：`main.py:65` lifespan → `main.py:95` `asyncio.create_task(overdue_scheduler())`。
- `overdue_scheduler`（`overdue.py:391-430`）：每 `interval_hours`（默认 12 小时）扫一轮，六个 scan（任务/尾款到期/尾款周催办/人事/管理层待办/采购到货）各自独立会话、独立 try/except，一个挂了不影响其余（`overdue.py:425-429` 是 `scan_po_arrival_overdue` 的调用）。
- **多 worker 单实例**：`_try_acquire_scheduler_lock`（`overdue.py:371-388`）用 `settings.files_dir` 下的 `.overdue_scheduler.lock` 做 flock；拿不到锁的 worker 直接跳过整个 scheduler（`overdue.py:395-398`）。注释明确写死原因：不加锁多实例会「同一条明细同一天重复推送 N 份」（因为幂等检查本身是 check-then-act 竞态）。Windows 下 flock 不支持，`except ImportError` 返回无锁对象（不锁，单机开发可接受）。

### 1.2 扫描条件（`overdue.py:326-334`）

- `expected_arrival` 非空且 `< now`（`<` 而非 `<=`，即**到期日当天即开始提醒**，不等到过了一天）。
- `arrival_date` 为空或 `''`（未收货）。
- 只扫 `purchase_items` 单表，无 supplier 等过滤；全量扫描**无 limit**。

### 1.3 15:00 时间窗（`overdue.py:319-323`）

业务时区（`_CN_TZ`，UTC+8）`now.hour < 15` 直接跳过本次扫描。来源 #292：货车中午发车，15 点前提醒多为「在途」误报。测试 `test_po_arrival_reminder_window.py` 专门验证这个窗。

### 1.4 幂等键（`overdue.py:338-346`）

查 `messages` 表 `biz_type='po_arrival_overdue' AND biz_id=item.id`，若已有**当日** `created_at` 的消息则跳过（`_cn_date(ts) == today_s`）。幂等键 = `biz_type + biz_id + 当日`，与 `overdue.py` 其它 scan 及 AGENTS.md 约定一致。

### 1.5 推送口径（`overdue.py:349-364`）—— 只推采购下单人本人

- **2026-07-26 收窄**：只 `await push_message(db, to_user_id=it.buyer_id, ...)`。
  - 旧实现推「采购员 + 采购主管 + 全体管理层」（`overdue.py:357` 附近注释记录已删）。
  - `buyer_id` 为空（历史手工数据未指定采购员）的明细**不推任何人**——静默，需人工捞。
- 消息 `kind="warn"`，`biz_type="po_arrival_overdue"`，`biz_id=item.id`，内容含采购单号、物料名、供应商名、预计日期、超期天数。
- 返回 `{"scanned": n, "notified": n}`（`overdue.py:368`）。

### 1.6 性能：N+1

`overdue.py:339-346` 循环内每条明细执行一次 `Message` 当日去重查询，且 `it.supplier.name`（`overdue.py:351`）是 lazy load —— 明细量大时每轮扫描产生约 2×N 次额外查询。当前业务量可接受，未做批量预取。

## 2. 收货完成后的站内 / 企微推送 —— 【没有】

这是本主题最突出的结论：**收货完成后系统不向任何人推送通知**。

- `receive_item`（`purchase_mgmt_router.py:2013-2046`）：填送货单号/到货日期/库位/订单编号/单价/收货金额 → `_finish_receive` → `db.commit()`，无 `push_message`。
- `receive_batch`（`:2049-2107`）：合并收货，同样无 `push_message`。
- `upload_receipt`（`:2111-2127`）：上传收货单图片，`save_upload` + commit，无推送。
- 全文件 `push_message` 仅出现于采购审批（`:1788/:1836`）与请款/审批流（`:2562-2569/:2652/:2746/:2817`），**收货路径零调用**。

对采购/管理侧的感知：采购员只会收到「到期未到货」提醒（§1，且只推本人）；货到了没有任何人被告知「已到货」。若需要「收货完成 → 通知采购员/管理层」的通知链路，需新增（例如在 `_finish_receive` 尾部按 `item.buyer_id` 推送）。

> 排除的猜想：曾以为 `warehouse_router.py` 里某处「备货完成/上传」推 logistics 的 `push_message` 属于收货——已核实那是**发货清单**流程，不是采购收货（`warehouse_router.py:1438/1462`）。

## 3. 失败回滚与幂等边界

### 3.1 事务边界：`get_db` 无显式 rollback，靠隐式回滚

`database.py:28-30`：

```python
async def get_db() -> AsyncSession:
    async with SessionLocal() as session:
        yield session
```

没有 try/except/finally，没有显式 `rollback`。异常时 FastAPI 关闭依赖、session 关闭，连接归还连接池时**未提交的事务被丢弃**——即隐式回滚。SQLAlchemy 语义下已 `flush()` 但未 commit 的变更（如 `_auto_stock_in` 里 `db.flush()` 创建的 `WhMaterial`，`purchase_mgmt_router.py:1422`）同样不会落库。

结论：回滚是可靠的，只是没有「显式 rollback + 日志」的可见性。若某 handler 中途出错且 session 里已有脏数据，错误响应返回后不会有任何残留。

### 3.2 收货提交是单 commit 尾部，事务原子

- `receive_item`：`_finish_receive`（回写清单 → 自动入库 → 同步流水金额 → 自动对账）→ **一个** `db.commit()`（`:2044`）。任一步抛异常，整条明细的全部变更（清单回写、入库流水、金额、对账状态）一起回滚。
- `receive_batch`：循环内逐条 `_finish_receive`，**最后统一一个** `db.commit()`（`:2105`）。中途第 N 条抛异常，前 N-1 条的变更也全部回滚——批量收货原子性成立，不会出现「收了一半」。

### 3.3 各步幂等性

| 步骤 | 位置 | 幂等机制 | 并发可靠性 |
|---|---|---|---|
| `_auto_stock_in` | `purchase_mgmt_router.py:1404-1440` | check-then-act：查 `WhTxn.purchase_item_id==item.id 且 is_reversal==False`，有则 return（`:1409-1412`） | **不抗并发**（见 §4） |
| `_sync_txn_amount` | `:1443-1459` | 覆盖写已有流水金额 | 天然幂等 |
| `_maybe_auto_reconcile` | `:724-736` | 仅从「待对账」推进一次，不回退不覆盖 | 天然幂等 |
| `_writeback_sheet_row` | `_finish_receive` 内 `:1995-2005` | 覆盖写清单列 | 同事务内安全 |

### 3.4 `push_message` 的 commit 契约（`notify.py:29-84`）

- `push_message` **自己 `await db.commit()`**（`notify.py:76`）。约定是「业务事务 commit 之后调用」——若在业务 commit 前调用，会把该 session 上所有未提交变更**一并提交**。
- 收货路径不调用 `push_message`（§2），故无此风险；`scan_po_arrival_overdue` 用独立会话且每推一条 commit 一次，符合约定。
- `push_message` 在目标用户为空时 `return 0` 且**不 commit**（`notify.py:60-62`）——这是 AGENTS.md 已记录的坑（verify-gate 的码行落库依赖调用方 commit 副作用，本主题无关但同源）。

## 4. 并发写冲突

### 4.1 `_auto_stock_in` 并发双流水（check-then-act 无唯一约束）

- 幂等检查 `purchase_mgmt_router.py:1409-1412` 是「先查后插」，而 `WhTxn.purchase_item_id` 在 `models.py:413` **只有 index，无唯一约束**。
- 两个请求对**同一条明细**几乎同时收货：两事务都查到无流水 → 都插入入库流水 → 双流水、库存翻倍。SQLite 写锁会串行化但不会阻止两个事务先后通过检查；Postgres 在默认读已提交下同理。
- 触发条件苛刻（同一明细秒级并发收货），但**无任何数据库防线**。修法：给 `wh_txns.purchase_item_id` 加唯一索引（注意 `is_reversal` 冲红流水也引用 `purchase_item_id` 吗——`models.py:420` `is_reversal`，冲红时 `purchase_item_id` 是否复用需确认，加唯一索引前先查冲红路径）。

### 4.2 `_next_ref` 撞号

`warehouse_router.py:619-625`：`ref_no = "RK/CK{ymd}-{COUNT(当日同前缀)+1:03d}"`。同日两个并发入库都算出同一序号；`ref_no` 仅 index（`models.py:418`）非唯一，**撞号不报错**，出现两条同号流水。`_auto_stock_in` 每次收货都走这里（`purchase_mgmt_router.py:1430-1431`）。

### 4.3 `_next_po_no` 撞号

`purchase_mgmt_router.py:757-774`（建采购单）：`MAX(po_no 当日)+1` 同类竞态，并发建单撞号。与收货间接相关（收货按 po_no 展示）。

### 4.4 scheduler 的 flock（防多实例重复推）

`overdue.py:371-388` `_try_acquire_scheduler_lock`：`.overdue_scheduler.lock` flock 单实例，已在 §1.1 说明。注意它**只锁 scan 循环**——若 4 worker 各起一个 scheduler，仅一个拿锁执行；锁文件随进程退出释放。

## 5. limit 截断

### 5.1 列表查询

- `purchase_mgmt_router.py:1877-1878`：`_RECV_LIMIT_DEFAULT = 2000`，`_RECV_LIMIT_MAX = 5000`。#330 从原来的 300 提到 2000。
- 查询 `:1894-1921`：待收货（`arrival_date is None`）/已收货（`isnot(None)`）分页无 offset，直接 `stmt.limit(limit)`（`:1921`）。
- **筛选条件全在 SQL 层、先于 limit**（`:1902-1920`）：`supplier_id` / `po_no` / `keyword`（**含 `source_sheet_id IN (从来源清单回溯项目编号)` 分支，`:1909-1916`，#253 那批行自身 `project_code` 为空，只比存量字段会搜不到）` / `item_name` / `order_month` —— 带筛选时能查到 2000 条之外的行（穿透截断）。

### 5.2 `receiving/meta` 出真实条数

`purchase_mgmt_router.py:1960-1989`：`pending_count` / `received_count` 用 `count(*)` 独立统计（不受列表 limit 影响），外加两个视图各自的**全量**供应商下拉（`distinct().order_by(name)`）。背景（注释 `:1966-1968`）：此前徽标数取截断列表 length、供应商下拉只从前 300 条去重——现在两项都独立查。返回还带 `limit` 字段供前端提示。

### 5.3 剩余截断点

- **无任何筛选时**，待收货/已收货列表只显示前 2000 条（按 `po_no desc, id desc`），无分页。超过 2000 条的历史只能靠筛选（供应商/关键词/月份）定位；`meta` 给了真实 count，但前端是否提示「仅显示前 2000 条」需前端侧确认（`frontend/src/views/purchase/*` 收货页）。
- `scan_po_arrival_overdue` 全量扫描无 limit（§1.2），不受此影响。

## 6. 历史遗留问题点

1. **收货完成零通知**（§2）：最大功能缺口，收货对采购/管理层无感知。
2. **scan 只推采购员本人**（`overdue.py:359-360`）：`buyer_id` 为空的明细（历史数据）静默不提醒，无兜底（如按供应商汇总告警）。
3. **scan 全量无 limit + N+1**（§1.6）：明细量涨后每轮扫描开销线性涨，且逐条查 `Message` + lazy `supplier`。
4. **check-then-act 幂等不抗并发**（§4.1）：`WhTxn.purchase_item_id` 无唯一约束，双流水风险无防线。
5. **`_next_ref` / `_next_po_no` 撞号**（§4.2/4.3）：同日并发撞号不报错。
6. **`push_message` 无用户不 commit + 企微失败仅 warning**（`notify.py:60-62,82-83`）：manager 无 active 用户时调用方事务语义受影响；企微推送失败静默（站内已落）。
7. **前端右下角提醒弹窗无轮询**（项目知识：`MainLayout.vue:137` `checkFeedbackReplies` 只 onMounted 调一次）：到货提醒若未来走弹窗链路，需注意实时性。
8. **`_maybe_auto_reconcile` 的浮点容差**（`purchase_mgmt_router.py:735` `paid_amount >= recv - 0.005`）：±0.005 容差做「全款已付」判定，属历史选择，非 bug。
9. **合并收货分摊的分位差**（`receive_batch` `:2074-2080`）：按数量权重分摊总价、末行兜余数（`:2075-2076`），单价反算（`:2082` `round(share/qty,4)`）在 `qty` 较大时有分位差，`_sync_txn_amount` 已按「整条一次性入库跟收货金额走」兜底（`:1456-1457`）。
