# 智能体 v2 架构设计

> 状态：**待评审**。评审通过再动代码。
> 背景：v1（当前生产）被指出「不是智能体」。本文先讲清楚**为什么不是**，再给分层设计。

---

## 一、现状诊断：v1 到底是什么

不是「差一点」，是**结构上就不是智能体**。三条事实：

### 1. 13 个工具里 12 个是同一个形状

| 工具 | 形状 |
|---|---|
| `po_arrival_overdue` / `po_arriving` / `balance_due` / `overdue_orders` / `receivable_blind` / `shipment_receiver` / `ledger_incomplete` / `leads_followup` / `order_pending` / `invoice_pending` | **列一类**（category → rows） |
| `po_overdue_by_supplier` / `morning_report` | 上面几类的聚合 |
| `project_status` | **唯一**按实体钻取的 |

后果：代码里写着 `for _ in range(4)` 的多轮工具循环，**实际永远只跑 1 轮**——
第一轮把那一类列完就没有下一步可走了。多轮预算是白给的。

**没有 `find → get → agg` 的递进，ReAct 就无事可做。** 这是 v1 最根本的问题，
不是提示词写得不够好。

### 2. 没有任何状态

每条消息从零开始。表现：

- 说不了「南京那个项目」——必须报编号
- 说不了「这笔先放着」——下次照推
- 说不了「刚才那个客户还有什么单」——它不知道「刚才」是谁

### 3. 没有模型路由

`model = body.model or cfg["model"]`，一个默认值走到底。
意图分类、实体解析、长清单格式化、深度分析——**全用同一个大模型**。

### 4. 性能：35.9 秒

实测「采购未到货，全部列举，按超期排序」：**35.9s / 1743 个流式片段**。
慢的原因不是查库（工具 2~14ms），是**让大模型一个字一个字把 46 行数据打出来**。

## 二、目标架构

```
                    ┌──────────────────────────────────────┐
   用户提问 ──────► │  ① 路由层（小模型/规则，~200ms）        │
                    │     意图分类 · 实体解析 · 技能匹配      │
                    └───────┬──────────────────────┬───────┘
                            │ 命中技能              │ 未命中
                            ▼                      ▼
                    ┌───────────────┐      ┌──────────────────┐
                    │ ② Skill 执行  │      │ ③ ReAct 循环      │
                    │  固定编排      │      │  plan→act→observe │
                    │  可预测、可测  │      │  →reflect（≤6 轮）│
                    └───────┬───────┘      └────────┬─────────┘
                            └──────────┬────────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │ ④ 工具层  find_* / get_* / list_* /   │
                    │           agg_* / act_*（卡片）       │
                    └──────────────────┬───────────────────┘
                                       ▼
                    ┌──────────────────────────────────────┐
                    │ ⑤ 渲染层（**代码渲染，不是模型打字**）  │
                    │    模型只产：结论 + 排序依据 + 选哪些   │
                    └──────────────────────────────────────┘
        ⑥ 记忆（会话内焦点 / 跨会话偏好与已阅）贯穿 ①③⑥
        ⑦ 知识库 RAG（口径、SOP、历史结论）供 ①③ 检索
```

---

## 三、逐项设计

### ① 工具层重构（**优先级最高，其它都依赖它**）

把 13 个平铺工具改成四类，让多轮推理有东西可链：

| 类 | 作用 | 例子 | 现状 |
|---|---|---|---|
| `find_*` | 模糊词 → 实体 id | `find_project("南京那个")`、`find_customer("迈克斯")`、`find_supplier("诺朋")` | **完全没有** |
| `get_*` | 单实体全景/纵深 | `get_project(id)`：任务/采购/台账/发货/回款一次给全<br>`get_customer(id)`：历史回款节奏、平均账期、拖欠记录<br>`get_supplier(id)`：准时率、平均超期、涉及项目 | 只有 `project_status` |
| `list_*` | 按类列（现有的） | `po_arrival_overdue` 等 12 个 | ✅ 已有 |
| `agg_*` | 算数：环比/占比/趋势/分布 | `agg_trend("po_overdue", months=6)` | **完全没有** |
| `act_*` | 带人审门的动作（卡片） | 现有 3 张卡 | ✅ 已有 |

**为什么这是第一优先**：有了 find/get/agg，「为什么这个月采购拖期变多」才可能被拆成
`agg_trend → list_overdue → find_supplier → get_supplier`。现在它只能回一句「共 46 条」。

### ② ReAct 循环

现有：`for _ in range(4)`，无计划、无反思、无预算控制。

改：

```
plan    复杂问题先出一步计划（简单问题跳过，别为「共几条」也规划一遍）
act     并发执行（已有 asyncio.gather）
observe 工具结果进上下文
reflect 「够回答了吗？还缺什么？」——只在 plan 存在时执行
```

**停止条件要明确**：轮次上限 6、token 预算上限、以及**「同一工具同参数不得重复调用」**
（现在靠提示词第 5 条口头约束，应该在代码里硬拦）。

**数值校验**：模型给出的合计/占比，用工具原始数据在代码里复算一遍，对不上就打标。
这是把「幻觉数字」从概率问题变成确定性问题。

### ③ Skills（可预测性来自这里，不是来自模型即兴发挥）

一个 Skill = **固定的工具编排 + 固定的输出模板**。适合反复问、答法有定式的问题：

| Skill | 编排 | 输出 |
|---|---|---|
| `每日简报` | 已实现（briefing.py） | 3 条 + 理由 + 动作 |
| `项目体检` | `find_project → get_project → agg_*` | 进度/成本/回款/风险 四段 |
| `客户回款画像` | `find_customer → get_customer → agg_trend` | 平均账期、要催几次、建议节奏 |
| `供应商拖期复盘` | `list_overdue → group → get_supplier` | 集中度 + Top N + 建议动作 |
| `月度经营复盘` | 多个 agg_* | 固定六段 |

Skill 命中就**不进 ReAct**——省一次规划、答案稳定、可以写测试。
ReAct 只负责没被 Skill 覆盖的长尾。

### ④ 记忆

分三层，**不要一上来就上向量库**：

| 层 | 存哪 | 内容 | 失效 |
|---|---|---|---|
| 会话焦点 | 内存/请求上下文 | 当前在聊哪个项目/客户/供应商 | 会话结束 |
| 用户状态 | `app_settings`（已有模式） | 已阅/暂缓的条目、关注的指标、常用问题 | 手动或 cooldown |
| 术语别名 | 表 | 「南京那个」→ 项目号；口头简称 → 供应商全名 | 长期，可编辑 |

简报的 `agent_briefing_sent`（5 天冷却）已经是第二层的雏形，扩展它即可。

### ⑤ RAG —— 索引什么

**不索引业务数据**（那是工具的活，RAG 查数据只会带来幻觉）。索引的是**规则与经验**：

- **字段口径**：「发货款应收」到底算什么、和「发货前付」的关系
- **已知数据坑**：发货单大量停在待发货、尾款没到期日催办扫不到、合同额为 0 算假亏损
  —— 这些现在**硬编码在提示词里**，加一条改一次代码，不可持续
- **SOP**：请款审批看什么、什么情况该驳回
- **历史结论**：以前问过的分析结论与当时的口径

规模很小（几十~几百段），**用 Postgres 全文检索起步就够，不必上向量库**。

### ⑥ 模型路由与降级

| 任务 | 用什么 | 理由 |
|---|---|---|
| 意图分类、Skill 匹配 | **规则优先，小模型兜底** | 就那么几十种问法，规则命中率高且 0 延迟 |
| 实体解析（「南京那个」） | 小模型 + 数据库模糊匹配 | 候选集有限，不需要大模型 |
| 计划 / 分析 / 结论 | **大模型** | 这是唯一真正需要推理的地方 |
| 长清单格式化 | **不用模型**（见⑦） | — |
| 大模型失败 | 小模型重试 → 规则降级 | 现有降级会返回功能菜单，**必须改成返回数据**，不是自我介绍 |

⚠️ **降级必须让人看得出来**。这次事故的教训：`_llm_stream` 一个 NameError 被 except 吞掉，
静默降级成功能菜单，表现为「12ms 秒回」，差点被当成性能优化生效。
**降级要在响应里显式标记，并在监控里报警。**

### ⑦ 性能：最大的一笔不在缓存，在「别让模型打字」

现状 35.9s / 1743 片段，就是模型在逐字输出 46 行数据。

**改法**：模型只产出结构化的少量内容 —

```json
{ "结论": "46 条未到货，18 条已逾期；2026-053 一个采购单占 16 条，风险集中",
  "排序依据": "over_days desc",
  "分组": "已逾期 / 今日到期",
  "点名": ["TH20260727-029"] }
```

**明细行由代码渲染**（数据本来就在工具结果里）。

| | 现在 | 改后（估） |
|---|---|---|
| 模型输出 | ~1700 字 | ~150 字 |
| 总时长 | 35.9s | **3~5s** |
| 数字幻觉风险 | 有（模型手打每一个数） | **0**（代码渲染） |
| 截断误报 | 有 | **0**（代码知道总数） |

其它性能项（按收益排）：会话内工具结果缓存 → 首字优化 → 提示词瘦身。

## 四、落地顺序

| 阶段 | 内容 | 为什么这个顺序 | 粗估 |
|---|---|---|---|
| **1** | 工具层 `find_*` / `get_*` / `agg_*` | 其它全依赖它；不做这个，ReAct/Skill 都是空转 | 大 |
| **2** | 渲染层：模型只出结论，明细代码渲染 | 立刻拿到 10x 性能 + 消灭数字幻觉 | 中 |
| **3** | Skills 框架 + 3 个内置技能 | 把高频问题从「即兴」变成「可测」 | 中 |
| **4** | 记忆三层 | 让多轮对话成立 | 中 |
| **5** | ReAct 强化（plan/reflect/数值校验） | 前四步做完才有意义 | 中 |
| **6** | 模型路由 + 降级可见 | 成本与稳定性 | 小 |
| **7** | RAG（口径/SOP/历史结论） | 把硬编码在提示词里的口径搬出来 | 中 |

**阶段 1+2 是分水岭**：做完这两步，它才第一次配叫智能体；
只做 3~7 而不做 1，等于在空转的循环上加装饰。

## 五、明确不做

- **不做通用 Agent 框架**（LangChain/AutoGPT 那套）。这是单一业务域，编排写死比通用编排更可靠、更好测。
- **不做写操作的自动执行**。所有改数据仍然走 L3 卡片人审门（手册第三章原则），
  智能体永远只读 + 出卡片。
- **不上向量库**（暂时）。知识条目量级是几百，Postgres 全文检索够用，
  上向量库徒增运维面。
- **不做多智能体互相调用**。当前问题不是并行不够，是纵深不够。

## 六、待确认

1. **阶段 1 的 `get_*` 先做哪个实体**？项目 / 客户 / 供应商，建议**客户**
   （回款是当前最痛的，且 `receivable_blind` 已经把问题暴露出来了）。
2. **35.9s vs 3~5s**：阶段 2 会改变输出的「质感」——明细变成代码渲染的固定格式，
   模型不再自由发挥排版。需要确认这个取舍可接受。
3. **RAG 的口径条目谁来写**？技术能写字段口径，业务口径（什么情况该驳回）需要业务给。
