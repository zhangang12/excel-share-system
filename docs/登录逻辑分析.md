# 登录逻辑分析（全链路汇总）

> 汇总自 n23–n28 六片探索：`docs/login-explore/01-backend-auth.md`（n23 后端认证主链路）、`02-login-gate.md`（n24 外网闸门）、`03-frontend-login.md`（n25 前端接入）、`04-desktop-login.md`（n26 桌面客户端）、`05-mobile-login.md`（n27 mobile 勘察）、`06-account-menus.md`（n28 账号/菜单/角色）。
> 本文按登录全链路组织：客户端/网络识别与免闸判定 → 密码认证 → 外网闸门 → token 签发与校验 → 前端接入与凭证存取 → 菜单加载 → 登出。每条结论标真源（`文件:行号`）与来源分片；跨片矛盾或口径不一致在 §8 摊开。

## 0. 一句话全景

全系统**只有一种登录协议**：`POST /api/auth/login` 验密码 →（命中外网闸门时插一步 6 位码）→ 发 **无状态 JWT**（HS256，8h / 记住我 30 天）→ 前端存 localStorage、axios 带头、按 401 决定是否登出。浏览器 / 桌面客户端（Electron 壳）/ mobile（Capacitor 壳 + H5 包）三者**复用同一套后端端点**，差异只在「如何把客户端身份带给后端」与「免闸判定」上。

```
POST /auth/login (username+password+remember)
   │ ① bcrypt 验密（01:auth_router.py:75-80）
   │ ② is_active 校验
   │ ③ 更新 last_login
   │ ④ 免闸判定（admin→桌面头→内网IP→开关）—— auth_router.py:86-109
   ├─ 命中闸门 → 发 6 位码给 manager 角色 → 返回 pre_token（不发 token）
   │        → 前端切第二步 → POST /auth/login/verify-gate (username+pre_token+code+remember)
   └─ 免闸 / 验码通过 → _issue_token → JWT(sub+exp) + UserOut  →  前端存 pms_token/pms_user
        → fetchMenus 拉菜单 → MainLayout 按菜单渲染 → 登出 = 前端清 localStorage（无状态）
```

## 1. 客户端形态与网络识别（免闸判定前置）

### 1.1 三端入口形态

| 端 | 加载方式 | 路由模式 | API 根 | 来源 |
|---|---|---|---|---|
| 网页端 | nginx `/` 反代 | history（`createWebHistory`） | 相对 `/api` | n25 `router/index.ts:8`, `api/index.ts:4-9` |
| 桌面客户端 | Electron `loadFile(desktop/app/index.html)`（file:// 内置页） | **hash**（`createWebHashHistory`） | `http://8.141.123.141/api`（VITE_API_BASE） | n26 `main.js:590-605`, `vite.config.ts base='./'`, n25 `api/index.ts:4-9` |
| mobile H5 | Capacitor WebView 加载 `www/` 包 | hash（`#/login`） | `http://8.141.123.141/api`（**硬编码**，非环境变量） | n27 helper.js @42489, `h5/main.ts:10-12` |

关键分歧点（三端取数方式不同）：
- 路由模式判据 = `!!import.meta.env.VITE_API_BASE`：设了（桌面构建）→ hash，否则 history（n25 `api/index.ts:91` `HASH_ROUTER`）。file:// 下绝对路径路由会解析成不存在的文件 → 黑屏（#343，见 §5.4）。
- mobile H5 的 baseURL 是**构建产物里写死**的 `http://8.141.123.141/api`，不是环境变量注入（n27：helper.js 偏移 @42489）。与浏览器走相对路径、桌面走 VITE_API_BASE 都不同。

### 1.2 客户端身份如何到后端

| 通道 | 头部 / 参数 | 用途 | 来源 |
|---|---|---|---|
| HTTP 请求头 | `X-PMS-Client: desktop/<version>` | 免闸判定 + 在线统计 | n26 `api/index.ts:18`，n24 `auth_router.py:90` |
| HTTP 请求头 | `X-PMS-Device: <deviceId>` | 设备闸名单 + 统计台账 | n26 `api/index.ts:19`，n24 `gate.py:67-85` |
| HTTP 请求头 | `X-PMS-User: <username>` | 统计台账展示（仅统计） | n26 `api/index.ts:20-23` |
| HTTP 请求头 | `Authorization: Bearer <token>` | 认证 | n25 `api/index.ts:97` |
| WebSocket | `?token=`（query 参数） | ws 鉴权（ws 不带头） | n23 `ws_router.py:45-49`，n26 `useRealtime.ts:39-49` |

- 三头只在**桌面客户端**注入（`window.pmsDesktop?.isDesktop` 判真，n26 `api/index.ts:11-30`）；**mobile H5 不注入任何 X-PMS 头**（n27：www 产物 grep `X-PMS`/`deviceId` 零命中）→ 手机端不走桌面免闸，与浏览器同属「外网需验证码」档。
- ws 身份只靠 `?token=`（n26）：ws 连不上会缺该设备最近在线统计，但不影响登录。
- 后端统计中间件按 device_id 60s 节流 upsert `desktop_clients` 表，与闸门判定无关（n26 `main.py:132-157`；n23 `main.py:139-157`）。

### 1.3 客户端真实 IP 判定（`auth_router.py:48-56 _client_ip`）

```
1. X-Real-IP 非空 → 直接取（nginx proxy_set_header X-Real-IP $remote_addr 用 TCP 真实地址覆写，不可伪造）—— n24 nginx/conf.d/default.conf:37
2. 否则 X-Forwarded-For 取【末段】（nginx $proxy_add_x_forwarded_for 把真实地址追加到链尾；取首段可被客户端伪造成 X-Forwarded-For: 假IP）—— n24 auth_router.py:49-51
3. 兜底 request.client.host（uvicorn 直连）
```

排除的猜想：**"XFF 应取首段"不成立**——首段可伪造，实现刻意取末段（n24 §11）。

### 1.4 免闸四路径与判定顺序（login 验密、验 active 之后）

判定代码：`auth_router.py:86-109`（n23 §2.1 / n24 §2 双片一致）：

| 次序 | 路径 | 条件 | 代码位置 |
|---|---|---|---|
| 1 | admin 角色 | `has_role("admin")` —— 连闸门配置都不读，完全跳过 | auth_router.py:92 |
| 2 | 桌面客户端 | `X-PMS-Client: desktop/...` 头；`device_gate` 关（默认）即免；开则还需 `X-PMS-Device` 在 `device_ids` 名单 | auth_router.py:90, gate.py:67-85 |
| 3 | 内网 IP | 回环/私网（`ipaddress.is_loopback/is_private`）恒判内网，或命中 `intranet_cidrs` 名单 | gate.py:54-64 |
| 4 | 开关关闭 | `gate_enabled=0` | auth_router.py:98 |

- 非 admin 才进闸门分支；admin 判定在一切之前（n24 `auth_router.py:92`）。`has_role` 是角色并集判断（n23 `models.py:99-101`）。
- 回环+私网恒判内网 → 本地开发/内网部署不受闸门影响（n24 gate.py:54-64）。
- **开关开而名单空 = 所有桌面端都要验证码**，是刻意字面语义；admin 恒免闸兜底不会锁死（n24 gate.py:77-79）。
- ⚠️ 免闸的 `X-PMS-Client` 头**可被 curl 伪造**（加个头就绕过整道闸门）；真正防线是 `device_gate`（设备名单，默认关）。见 §8.3。

## 2. 密码认证（`POST /api/auth/login` 第一段）

请求契约（n23）：`POST /api/auth/login`，body `{username, password, remember}`（`LoginIn`，schemas.py:700-704）。`remember=true` 只把 token 有效期延到 30 天，**密码不落客户端**（auth_router.py:59-62）。

流程（n23 §2.1，auth_router.py:74-109）：
1. 按 username 查 users 表。
2. `verify_password` 校验；**用户不存在或密码错误统一返回 401 "用户名或密码错误"**（auth_router.py:77-78，不泄露账号是否存在）。
3. `is_active=False` → **403 "账号已停用"**（auth_router.py:79-80）。
4. 更新 `u.last_login` 并 commit。
5. 进入免闸判定（§1.4）→ 命中闸门返回 `GateRequiredOut{gate_required, pre_token, message}`（不发 token，切 §3）；免闸走 `_issue_token`。

密码存储（n23 §5 / n28 §2 一致）：
- **bcrypt**，`hash_password = bcrypt.hashpw(plain, bcrypt.gensalt()).decode()`，存 `users.password_hash`（String(255)），每用户随机 salt，明文不落库（auth.py:9-14）。
- `verify_password` 用 `bcrypt.checkpw`，**异常一律返回 False**（防时序泄露，auth.py:22-23）。
- 新密码最小 6 位（`ChangePasswordIn`，schemas.py:743-745）。
- 改密点：本人 `auth_router.py:160` / 管理端重置 `admin_router.py:239`（n28 §2）。改密后旧 token 仍有效（无黑名单，见 §4.6）。

### 2.1 停用账号状态码口径不一致（401 vs 403）

**这是全链路一处跨文件口径矛盾**：
- `login` 对停用账号返回 **403 "账号已停用"**（auth_router.py:79-80）。
- `get_current_user` 对禁用账号返回 **401 "账号已禁用"**（deps.py:24-27）。

同是「账号停用」，登录时 403、已登录请求时 401。n23 已标注「历史如此，未见 issue」（01 §12）。若统一语义需改 deps.py:26。

## 3. 外网闸门（两步验证码）

命中条件见 §1.4：非 admin + 桌面/内网/开关均不豁免。机制主体在 `backend/app/gate.py`。

### 3.1 `issue_code` 发码流程（gate.py:129-158，n24 §5）

1. **限频**：同账号最近 1 分钟已发过 → 429 "验证码发送过于频繁，请 1 分钟后再试"（`_RATE_PER_MIN=1`，gate.py:21）。已去掉每日 10 条上限与错 5 次锁定（2026-07-28，gate.py:21 注释）。
2. **作废旧码**：同账号所有 `used=False` 行置 `used=True`——同一账号同时只有 1 个有效码，重发即作废（gate.py:139-143）。
3. **生成**：`code = f"{secrets.randbelow(1000000):06d}"`（6 位数字含前导零）；`pre_token = secrets.token_urlsafe(24)`（第一步下发、第二步换 token 的会话凭证）。
4. **存储** `LoginGateCode` 行：**只存 `code_hash = sha256(code)`**，不存明文（gate.py:149, models.py:1199）；`expires_at = now + 10 分钟`。
5. **通知**：`push_message(db, to_role="manager", kind="warn", text=...)`，文本含用户全名(username) + 明文验证码 + 10 分钟有效（gate.py:153-157）。push_message 自带 commit，码行同事务落库（gate.py:157）。
6. 返回 pre_token 给客户端 + 写审计 `login_gate_issue`（auth_router.py:105-108）。

### 3.2 manager 角色扇出与企微外发（notify.py:29-84，n24 §5.1）

- `to_role="manager"` 按角色 code 取 role_id，扇出给锚点 role_id 命中**或** user_roles 关联命中的所有 active 用户，每人一行 Message（notify.py:44-59）。站内消息与码行同一事务 commit。
- 企微外发：绑了 `wxid` 且 wecom 配置齐 → `_send_wecom`；**失败仅 `log.warning` 绝不阻塞**（"站内消息已落"）。
- **角色池无人 → 丢弃并返回 0**：若无 manager 角色用户，外网用户会卡死在第二步；seed 默认建 `manager` 账号故正常运行不受影响（n24 §5.1）。

### 3.3 `verify-gate` 验码换 token（auth_router.py:112-130 + gate.py:161-177，n24 §6）

- 输入：`{username, pre_token, code, remember}`（`GateVerifyIn`，schemas.py:721-726）。
- **只查 username + is_active，不验密码**——第一步已验过密码，`pre_token` 就是会话凭证（auth_router.py:116-119）。
- `verify_code`：按 `user_id + pre_token + used=False` 找行，不存在/已用/过期 → 400 "验证码无效或已过期，请重新获取"；`sha256(code.strip())` 与 code_hash 不符 → `fail_count += 1` 并 commit（**只计数不锁定**）→ 400 "验证码错误"；命中 → `used=True` + commit。
- 成功后更新 last_login → `_issue_token` 发 token + 写审计 `login`。

排除的猜想：**"verify-gate 不重查免闸条件=漏洞"不成立**——pre_token 只在 login 命中闸门时下发一次、单账号单有效码、码仅经 push_message 发 manager，是设计使然（n24 §11）。

### 3.4 nginx 登录限频（外围防线，nginx/conf.d/default.conf:1-3,42-50）

- 每 IP 登录接口 **10 次/分钟**，burst=5 nodelay，超限 429（`limit_req_zone $binary_remote_addr zone=login_limit:10m rate=10r/m`）。
- 只作用于 `location = /api/auth/login`，**不含 verify-gate**（验码接口由应用层 1 条/分钟限频兜底，§3.1）。
- 与闸门关系：闸门防「越权登录」，nginx 限频防「密码爆破」，互补（n24 §9）。

### 3.5 闸门审计事件

| action | 触发点 |
|---|---|
| `login_gate_issue` | 发码成功（auth_router.py:105） |
| `login_gate_fail` | 发码限频 429 / 验码失败（auth_router.py:102,124） |
| `login` | 免闸直接登录 / 验码成功后登录（`_issue_token` 内，auth_router.py:69） |

## 4. Token 签发与校验

### 4.1 签发 `_issue_token`（auth_router.py:65-70）

```python
token = create_access_token(u.id, minutes=REMEMBER_MINUTES if remember else None)
await write_audit(db, user=u, action="login", ip=ip or None)
return schemas.TokenOut(access_token=token, user=_user_to_out(u))
```
登录成功必写审计 `audit_logs.action='login'`（带 ip）。

### 4.2 JWT 结构与有效期（auth.py:26-45）

- 算法 **HS256**，密钥 `settings.secret_key`，payload = `{"sub": str(user_id), "exp": utc过期时间}`，可选 extra 扩展。
- 默认 8 小时（`access_token_expire_minutes=480`，config.py:29）；「记住我」30 天（`REMEMBER_MINUTES=30*24*60`，auth_router.py:62）。
- **无 refresh_token、无滑动续期**：过期即需重新登录；`decode_token` 对任何 PyJWTError 返回 None（auth.py:39-45）。
- token 不携带密码，仅 sub+exp（n23 §3）。

### 4.3 `get_current_user` 校验（deps.py:11-28）

1. `Authorization` 头取 `Bearer <token>`（大小写不敏感前缀，deps.py:15-17）。
2. 解码失败/过期 → 401 "登录已过期"；缺头 → 401 "未登录"；payload 无 sub → 401 "无效凭证"。
3. 按 sub 查库，用户不存在或 `is_active=False` → 401 "账号已禁用"。
4. 返回完整 `models.User` ORM，路由直接用 `current.role_codes` / `has_role()`。

### 4.4 401/403 语义汇总（deps.py + auth_router.py）

| 场景 | 状态码 | 消息 | 出处 |
|---|---|---|---|
| 缺 Authorization 头 | 401 | 未登录 | deps.py:15-16 |
| token 解码失败/过期 | 401 | 登录已过期 | deps.py:19-20 |
| payload 无 sub | 401 | 无效凭证 | deps.py:22-23 |
| 用户不存在 / 禁用（已登录态） | 401 | 账号已禁用 | deps.py:24-27 |
| login 用户名或密码错 | 401 | 用户名或密码错误 | auth_router.py:77-78 |
| login 账号停用 | 403 | 账号已停用 | auth_router.py:79-80 |
| 角色不足 | 403 | 无权操作 等 | deps.py:31-41,52-62 |

### 4.5 WebSocket 复用同一 token（ws_router.py:45-49）

从 query `?token=` 取同一 JWT 解码，仅验 sub，失败 close(1008)。**不查库验 is_active**——与 HTTP 的 get_current_user 不同，WebSocket 通道不校验账号禁用态（n23 §10）。

### 4.6 无状态边界：无吊销 / 无 refresh / 无 session

- **token 吊销/黑名单：不存在**。改密、禁用账号都不会使已签发 token 失效——禁用只在下次请求经 get_current_user 查库时生效（deps.py:26）。
- **refresh token / 自动续期：不存在**。唯一延命手段是登录时带 `remember=true` 换 30 天 token。
- **session / cookie：不存在**，纯 Bearer token 无状态认证（n23 §9）。
- 后果：token 8h 到期 → 下一次请求 401 → 前端拦截器登出（#343 黑屏教训，见 §5.4）。

## 5. 前端接入与凭证存取

### 5.1 三端接入对比（详见 §1.1）

桌面：VITE_API_BASE 直连 + hash 路由 + 三统计头；mobile：硬编码绝对地址 + hash 路由 + 无统计头；浏览器：相对 /api + history 路由 + 无统计头。后端全部复用，**API 只增不改**（AGENTS.md 红线）。

### 5.2 localStorage 凭证 key 清单（三端基本共用）

| key | 内容 | 网页端 | 桌面端 | mobile H5 |
|---|---|---|---|---|
| `pms_token` | JWT | ✓ `auth.ts:7-17` | ✓ 同 | ✓ `h5/session.ts`（n27：token key 与桌面端一致） |
| `pms_user` | 用户对象 JSON | ✓ | ✓ | ✓ |
| `pms_menus` | 一级菜单 key | ✓ | ✓ | —（H5 无菜单体系） |
| `pms_can_view_detail` | 详单可点性 | ✓ | ✓ | — |
| `pms_remember_name` | 记住用户名 | ✓ `LoginView.vue:46-49` | ✓ | — |
| `pms_h5_remember` | H5 记住账号 | — | — | ✓ `H5LoginView` 常量 `w` |
| `pms_disable_ws` | 关 ws（'1'） | ✓ `useRealtime.ts` | ✓ | — |

关键约定（n25 §2.1）：`isLoggedIn = computed(() => !!token)`——**只要 localStorage 有 token 就算已登录，无过期判断**；过期由接口 401 触发拦截器登出（§5.4）。

### 5.3 axios 拦截器（frontend/src/api/index.ts）

- **请求拦截器**（:11-30）：从 localStorage 读 `pms_token` 加 `Authorization: Bearer`；桌面端加 X-PMS 三头（§1.2）；`responseType==='blob'` 时 `timeout=0`（#188 文件下载不被 30s 掐断）。
- **响应拦截器**（:122-140）：401 且非 `/auth/login` → 清 `pms_token`/`pms_user` → `goLogin()`；登录接口本身 401 不跳页（`isLoginRequest` 判断，:127），让 LoginView 自己展示错误。其它错误 → `extractErrorMessage(err)` 弹 `ElMessage.error`。
- **H5 独立 http 封装**（h5/http.ts）：刻意不复用 `@/api/index.ts`（那个文件 import 了 element-plus 的 ElMessage，会把 element-plus/vxe-table 拖进 H5 包，n25 §4.5）。401 → 清 token/user → 非 login 页则 `location.hash='#/login'`。

### 5.4 401 跳转 `goLogin()` —— #343 黑屏教训（api/index.ts:90-120）

- **绝不能写 `location.href='/login'`**：桌面端 file:// 加载下绝对路径解析成 `file:///login` 不存在文件 → Chromium 换错误空页 → 整窗深蓝无响应。这是反馈 #343「到 4 点多就黑屏」的真身（token 8h 到期，早上 8:15 登录的人下午 16:15 踩中；近 14 天 8 人踩 23 次，注释 :94-105）。
- 正确做法（:107-120）：`HASH_ROUTER=!!VITE_API_BASE`；hash 模式 `location.hash='#/login'` + `location.reload()`（清残留 store）；history 模式 `location.href='/login'`。`redirecting` 防一次 401 风暴重复跳。
- 桌面端另有主进程兜底：`did-fail-load`（非 ERR_ABORTED）→ 重载内置首页（n26 main.js:497-507）。

### 5.5 桌面端三头注入与 deviceId 持久化

- 头注入：n26 `api/index.ts:11-30`（见 §1.2）。`deviceId` 由 preload 注入 `window.pmsDesktop.deviceId`（n26 preload.js / main.js:196-198）。
- deviceId 持久化（main.js:176-193）：存 `userData/device.json`，首用 `crypto.randomUUID()`；写失败（杀软拦 %APPDATA%）→ 每次启动换 ID → 服务端设备名单永远认不出这台机器，启动会上报 `desktop_reports`（n26 §3 / AGENTS.md 已知坑）。

## 6. 菜单加载（登录后的可见性层）

### 6.1 运行时唯一权威：`user_menu_keys()`（menus.py:142-154）

```python
codes = user.role_codes
if codes & {"admin","manager"}:  return _ALL_KEYS + _ADMIN_KEYS   # 全量，不读 User.menus
configured = user.menus if user.menus is not None else DEFAULT_ACCOUNT_MENUS
return canonical_menu_order(set(configured) | {"agent"})
```

菜单三态（n28 §7）：
1. **admin/manager**：业务 19 key + 管理组 9 key 全量，不读 User.menus。
2. **普通账号**：`User.menus` 即完整清单（建号时快照；改角色不联动菜单，n28 §4.4）。
3. **NULL 兜底**：`DEFAULT_ACCOUNT_MENUS = ["catalog","list","messages","oa"]`（menus.py:58）。
4. **`agent`（AI 助手）全员无条件追加**。

`ROLE_DEFAULT_MENUS`（原 ROLE_MENUS 矩阵）**运行时不读**，仅建号预填/存量迁移模板（menus.py:132-139；n28 §4.3）。

### 6.2 前端加载时序

1. **登录成功 `finishLogin`**（LoginView.vue:51-66）：写 `auth.token/user` + localStorage → `auth.menus=null` 清缓存 → `await auth.fetchMenus()` → `router.push('/overview')`。
2. **`auth.fetchMenus()`**（auth.ts:59-68）：`GET /auth/menus`（auth_router.py:138-147，返回一级菜单 key + can_view_detail）→ 写 `menus` + `canViewDetail` + localStorage；接口失败保持现状不阻塞。
3. **MainLayout onMounted**（MainLayout.vue:125-137）：`if (isLoggedIn && !user) fetchMe()` → `fetchMenus()`（侧边栏渲染权威）→ `refreshUnread()` 60s 轮询角标 → `checkFeedbackReplies()` 弹未读反馈回复提醒（只调一次无轮询）。
4. **路由守卫**（router/index.ts:185-205）：public 放行 → 未登录跳 login → requireAdmin 且非 isAdmin 跳 overview → 有 menuKey 且无权限 → fallbackRoute → project-detail/projects 无 canViewDetail → fallback → overview 无 catalog 菜单 → fallback。
5. **fallbackRoute**（:208-214）：跳第一个可见菜单（catalog→overview、list→projects、其它→对应 name）。

### 6.3 前端 hasMenu 过渡态（与后端三态的差异）

前端 `hasMenu(key)`：`menus === null` 时只放行老默认 `catalog`/`list`（避免闪烁，auth.ts:47-50）——**这是未加载完的过渡态**，最终权威仍是后端的 `user_menu_keys()`/`GET /auth/menus`。两者不矛盾，但排查"菜单闪烁/短暂多出两项"时知道根因在此。

### 6.4 角色与菜单的关系（2026-07-21 起）

- 角色**不再管菜单**，只管业务归属（部门工作台/推送/行级过滤/负责人）；菜单按账号 JSON 配置（n28 §5）。
- `User.role_id` 仅是存量兼容锚点，权限判定一律 `role_codes`/`has_role()` 并集（models.py:28-29,79-89,99-101）。
- `finance_lead` ⊇ `finance` 硬编码隐含（models.py:85-88）。
- 前端 `isAdmin = hasRole('admin','manager')`（auth.ts:35）——admin 或 manager 都算管理员，与后端 `user_menu_keys()` 全量 bypass 一致（n25/n28 双片印证）。
- 登录响应里的 `_user_to_out`（auth_router.py:17-45）：`role_codes` 用 property（含 finance_lead⊇finance）、`menus` 用账号配置、`grant_menus` = menus ∩ 管理组 key（派生值，不再独立存储）。

## 7. 登出（无状态）

- `POST /api/auth/logout`：**仅返回 "已登出"，无服务端状态可清**（JWT 无状态），靠客户端删 token（auth_router.py:167-170）。
- 前端 `auth.logout()`（auth.ts:102-111）：调 logout（失败静默）→ 清 token/user/menus + 4 个 localStorage key。
- H5：`clearSession()` + `router.replace('/login')`（n25 H5HomeView.vue:128 / n27 H5ChatView @103464）。
- 生效边界：改密/禁用账号不会使已签发 token 失效（§4.6）——"登出"只是本端清 token，别的端/旧 token 仍有效直到过期。

## 8. 交叉印证与口径不一致清单

六片结论交叉比对，绝大多数一致（免闸四路径、token 时长、401 语义、菜单三态均由 ≥2 片独立得出）。以下为需要摊开的**不一致 / 值得注意**之处：

1. **停用账号 401 vs 403（跨文件语义矛盾）**
   `get_current_user` 对禁用账号返回 401 "账号已禁用"（deps.py:24-27），`login` 对停用账号返回 403 "账号已停用"（auth_router.py:79-80）。n23 单片指出，历史如此未见 issue；若要统一需改 deps.py:26。
2. **`LoginGateCode.fail_count` 注释过时**
   models.py:1204 注释仍写 ">=5 锁定"，实际 2026-07-28 起代码**只计数不锁定**（gate.py:162 注释明确，n24 §7.1 标注）。表结构注释残留过时，功能以 gate.py 为准。
3. **桌面免闸头可伪造（设计取舍 vs 安全边界）**
   `X-PMS-Client: desktop/...` 头可被 curl 伪造绕过闸门（gate.py:67-85）。n24/n26 均承认此点，真正防线是默认关闭的 `device_gate`。属刻意取舍（省事 vs 安全），非 bug；但评估外网安全时须知情。
4. **菜单加载的过渡态差异**
   后端权威是 `user_menu_keys()` 三态；前端 `hasMenu` 在 `menus===null` 时临时放行 catalog/list（auth.ts:47-50）。不是矛盾，但"菜单闪烁"类现象由此而来。
5. **mobile H5 与桌面端差异**（不是矛盾，是刻意）
   mobile 无 X-PMS 头 → 外网必走验证码闸；桌面有头 → 默认免闸。同一个人手机与电脑登录体验不同，属架构使然（n27 §4）。
6. **`User.grant_menus` 已停用**（n28 §6）：存量列保留，读取侧已并入 menus。grep 到 grant_menus 引用时注意它不再是生效配置。
