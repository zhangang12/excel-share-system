## 1. 一句话总览

**系统没有独立的「收货单表」没有独立的「采购单表」。**

仓库收货不是独立的事务对象，而是以下动作的叠加：

1. **在 `PurchaseItem` 行上填 `arrival_date`** —— 空=待收货，非空=已收货
2. **`_auto_stock_in`** 向 `wh_txns` 写一条 `direction='in'` 的库存流水（幂等，同一明细只过一次账）
3. **`_sync_txn_amount`** 回写流水金额，保证库存金额与采购收货金额一致
4. **清单回写** —— 把到货日期、仓库签字、库位等写回来源清单（Datasheet）对应行

采购单 = `PurchaseItem.po_no` 同号多行的聚合视图。所有收货端点均在 `purchase_mgmt_router.py`（前缀 `/api/purchase-mgmt`），收货只归 `warehouse`/`warehouse_lead` 角色，采购员只下单不收货。

#### 2.2.1 `GET /receiving` → `list_receiving`（:1881-1957）

**response_model** = `List[PurchaseItemOut]`

**入参（Query）**：

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `supplier_id` | int | - | 按供应商过滤 |
| `po_no` | str | - | 采购单号 ILIKE |
| `keyword` | str | - | 采购单号+项目编号模糊（后端 SQL 穿透 limit）|
| `item_name` | str | - | 物料名 ILIKE |
| `order_month` | str | - | 下单月份 YYYY-MM（按 `delivery_date.startswith`）|
| `received` | bool | `false` | false=待收货(arrival_date IS NULL)，true=已收货 |
| `limit` | int | `2000` | ge=1, le=5000（常量定义 `_RECV_LIMIT_DEFAULT`/`_RECV_LIMIT_MAX`，:1876-1878）|

**业务逻辑要点**：

- **排序**：`po_no DESC NULLS LAST, id DESC`（:1894-1897）
- **待/已切换**：仅凭 `arrival_date` 判空，无独立状态列（:1898-1901）
- **keyword 三分支**（:1906-1916）：
  1. `po_no.ilike(f"%{keyword}%")`
  2. `project_code.ilike(f"%{keyword}%")`
  3. `source_sheet_id IN (Datasheet JOIN Project WHERE Project.code.ilike)` —— **不能省**：#253 那批明细自身 `project_code` 为空，只比对存量字段会在 SQL 阶段就筛掉这些行
- **#253 回溯补 project_code**（:1924-1946）：对 `project_code IS NULL AND source_sheet_id IS NOT NULL` 的行，从 Datasheet→Project 回溯出项目编号，回填到输出对象（只补显示，不落库）
- **附件计数**：返回 `receipt_count`，来源为 `biz_type='receipt_doc'` 附件数（:1947-1957）

#### 2.2.2 `GET /receiving/meta` → `receiving_meta`（:1960-1989）

**出参**：

| 字段 | 类型 | 说明 |

#### 2.2.4 `POST /items/receive-batch` → `receive_batch`（:2049-2107）

合并收货。入参 `BatchReceiveIn`（schemas.py:1400-1408）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `item_ids` | list[int] | 收货明细ID列表 |
| `arrival_date` | str | 到货日期（必填）|
| `delivery_note_no` | str? | 送货单号（整批共用）|
| `stock_location` | str? | 库位（整批一个，:1407）|
| `project_code` | str? | 订单编号（整批一个，:1408）|
| `total_amount` | float? | 合并总价（后端能力保留，前端当前不用）|
| `lines` | list[BatchReceiveLine] | 逐行填价 `[{item_id, unit_price, received_amount}]` |

**两种填价方式**（:2055-2058 docstring）：
1. **合并总价** `total_amount`：按各行数量权重分摊，末行兜余数保证合计精确。单价 = `round(share/qty, 4)` 反算

**前端当前只传 `lines` 逐行价**（`submitBatchReceive` :639-660），`total_amount` 后端能力保留但前端未用。

业务逻辑：循环逐行处理 → 校验每行存在且未收货 → 更新每行字段 → 共用 `_finish_receive`

### 2.3 内部函数链（service 层）

全部在 `purchase_mgmt_router.py` 内，无独立 service 文件。以下是完整的调用链：

```
receive_item / receive_batch
  │
  ├── 更新 PurchaseItem 字段（arrival_date, delivery_note_no, stock_location, project_code, unit_price, received_amount）
  │
  └── _finish_receive (:1992-2010)
        │
        ├── ① _writeback_sheet_row (:864-893) —— 回写来源清单
        │     写「进度=已到货」+ _ALL_ARRIVAL_COLS（到货日期/到料日期）
        │     + _ALL_WH_SIGN_COLS（仓库签字/仓库=当前用户姓名）
        │     + _ALL_WH_LOC_COLS（库位，#250，有该列的清单才写）
        │     若需回写 project_code 且非 None 则一并写入
        │
        ├── ② _auto_stock_in (:1404-1440) —— 自动入库
        │     幂等写入 WhTxn(in)，物料不存在自动建 WhMaterial
        │
        ├── ③ _sync_txn_amount (:1443-1459) —— 回写流水金额
        │     保证库存金额与采购收货金额一致
        │
        └── ④ _maybe_auto_reconcile (:724-736) —— 自动对账
              现金全款/对公全款 + 已收货 + 已付清 → invoice_status 自动置「已对账」
```

#### 2.3.1 `_finish_receive`（:1992-2010）

收货收尾公共函数，单条和批量共用。执行顺序：
1. 写 `arrival_date`、`delivery_note_no` 等到 PurchaseItem
2. **回写清单**（:1995-2005）：有 `source_sheet_id+source_record_id` 时
3. **自动入库**（:2006）：`_auto_stock_in`
4. **回写流水金额**（:2009）：`_sync_txn_amount`
5. **自动对账**（:2010）：`_maybe_auto_reconcile`

#### 2.3.2 `_auto_stock_in`（:1404-1440）

入库流程：
1. **幂等检查**（:1409-1412）：同 `purchase_item_id` 且 `is_reversal==False` 已有 WhTxn 则 return（防止重复入库）
2. 按 `name+spec` 找/建 `WhMaterial`（:1413-1422）
3. **单库位模型**：最近收货库位 = 物料当前库位（`m.location = loc`）
4. 生成 `WhTxn(direction='in', source='采购入库', party=供应商名, project_id=按project_code查询, ref_no=_next_ref('in', bd))`
5. 金额：`round(qty × unit_price, 4)`，`unit_price` 为 None 时 `amount=None`
6. **已取消收货自动出库**：原 `is_stock=False` 自动「采购领用」出库逻辑已删（:1439-1440），收货一律只入库，出库统一走仓库领料

> ⚠️ `_auto_stock_in` 的 docstring（:1405-1406）仍写着旧语义"非备货再自动出库"，实际 :1439 已删；以代码为准，不信注释。

#### 2.3.3 `_sync_txn_amount`（:1443-1459）

**为什么需要它**：因 `_auto_stock_in` 幂等，改价不会重新生成流水——不回写的话，采购明细金额改对了，库存金额与项目材料成本还停在旧价上（#329 修复）。

口径（:1450-1457）：
- **整条一次性入库**（`t.qty == item.qty` 且 `received_amount` 非空）→ `amount = round(received_amount, 4)` —— 跟收货金额走
- 否则 `qty * unit_price`（合并收货反算单价有分位差时退回乘法）

调用点（两个）：
- `update_item`（PUT `/items/{iid}`，:1823）—— 仓库在「已收货」页签点「修改」改价
- `_finish_receive`（:2009）—— 收货尾部的统一回写

#### 2.3.4 `_maybe_auto_reconcile`（:724-736）

条件串联：`现金全款/对公全款` + 已收货（`arrival_date` 非空）+ 已付清（`paid_amount >= received_amount - 0.005`）→ `invoice_status` 从「待对账」置「已对账」。只从「待对账」推进一次，不覆盖已人工确认的状态。±0.005 浮点容差为历史选择。

### 2.5 状态流转

**结论：没有显式状态机，状态是派生值。** 全部靠 `arrival_date` 空/非空判定。

```
下单
  │ arrival_date = NULL → 前端归类「待收货」
  │
  │ PUT /items/{iid}/receive 或 POST /items/receive-batch
  │ → 填 arrival_date + delivery_note_no + stock_location + project_code + 单价/收货金额
  │
  ▼
已收货（arrival_date IS NOT NULL）→ 前端归类「已收货」
  │
  ├── 回写清单：到货日期/仓库签字/库位
  ├── 自动入库：_auto_stock_in → WhTxn(in)，幂等
  ├── 回写流水金额：_sync_txn_amount → 保证库存/项目材料成本同步
  └── 自动对账：_maybe_auto_reconcile（现金全款+已收货+已付清）
```

- **同一张 PO 内的行各自独立到货**：合并收货只是"一次收多行"，行级状态互不影响
- **采购单没有"已收完/完成"的总状态**：只要行还空着 `arrival_date` 就还在「待收货」里，分批到货全靠行级字段表达
- **收货后改价**：走同一个 `PUT /items/{iid}/receive`（receive_item，:2013），因为字段就是明细行本身；改价后 `_sync_txn_amount` 保证库存同步

**业务行为差别**（与 `update_item` 的关键区别）：
- `receive_item`：走 `_finish_receive` → 回写清单 → 自动入库 → 同步流水金额 → 自动对账
- `update_item`（PUT /items/{iid}）：不改 `arrival_date`，不走清单回写，不走自动入库

### 3.5 实时库存聚合：`_stock_map`

`backend/app/routers/warehouse_router.py:34-55`：


- 按 `material_id` + `direction` 分组聚合，in 加、out 减；可选 `upto=biz_date`（含当日，用于期初/期末）
- **没有独立的库存余额表**，库存永远是实时聚合结果——收货入库就是多了一条 in 流水，`_stock_map` 自然反映

### 3.6 改价回写与数量分摊分位差

#### 3.6.1 合并收货分摊的源头

`receive_batch` :2068-2082：

```
share = round(total_amount * (weights[idx] / wsum), 2)   # 每行按数量权重，round 2 位
# 末行：
share = round(total_amount - allocated, 2)               # 兜余数，保证合计精确
it.unit_price = round(share / it.qty, 4)                  # 单价=金额÷数量反算
```

- 每行金额 round 到 2 位（分），末行用 `total − Σ已分摊` 兜住舍入差，合计精确等于填入的总价
- 但单价是反算的（`share ÷ qty`，round 到 4 位）→ 必然存在 `qty × unit_price ≠ share` 的**分位差**

#### 3.6.2 _sync_txn_amount 的消化

`_sync_txn_amount` 对整条明细的流水**不**用 `qty × unit_price` 重算，而是直接 `amount = round(received_amount, 4)`（:1456-1457），正好把上述分位差消掉——保证 WhTxn 流水金额、采购明细收货金额、项目材料成本三处同一数。

部分入库分支才退回 `qty × unit_price`（当前无此路径，防御用）。

### 3.7 `list_receiving` 查询语句的逐层构造

`purchase_mgmt_router.py:1881-1957` 的 `list_receiving` 是收货模块唯一的列表查询入口，其在 SQLAlchemy async 下逐步拼接 stmt（`select(PurchaseItem)`），以下逐层拆解：

#### 第一层：基表 + JOIN

```python
stmt = select(PurchaseItem)
```
基查询无过滤。

后续追加 `.outerjoin(PurchaseItem.supplier)` 以获取 `supplier_name`（`_item_out` :707-708 用到 `item.supplier.name`，是 lazy load → 产生 N+1 的潜在风险点，第 4 层会讨论）。

#### 第二层：仓库角色校验

```python
await require_roles(current, *_RECEIVE_ROLES)   # :1883
```
**任何 `_RECEIVE_ROLES` 之外的请求直接 403，stmt 不运行**。`_RECEIVE_ROLES = ("warehouse", "warehouse_lead")`（:27-28），外加 admin/manager 在 `require_roles` 内部放行（`deps.py:52-62`）。

#### 第三层：接收态过滤（二选一，必须）

```python
received = query_params.get("received")  # :1888
if received == "true":                    # :1898
    stmt = stmt.where(PurchaseItem.arrival_date.isnot(None))
else:                                     # :1899
    stmt = stmt.where(PurchaseItem.arrival_date.is_(None))
```

**不传 `received` 参数默认进 else 分支 = 待收货**（由于空串 `""` 和 `None` 都不等于 `"true"`）。

`arrival_date` 的 NULL → 非NULL 就是收货模块的状态机。此分支构造保证 "待收货" 和 "已收货" 两个 tab 的数据完全互斥。

#### 第四层：供应商过滤

```python
if supplier_id:                                            # :1902-1903
    conds.append(PurchaseItem.supplier_id == int(supplier_id))
```
精确匹配，单供应商。

#### 第五层：采购单号精确匹配

```python
if po_no:                                                  # :1904-1905
    conds.append(PurchaseItem.po_no.ilike(f"%{po_no}%"))
```
`ILIKE` 而非 `=`，用户可输入部分单号模糊搜。

#### 第六层：关键字三分支（#330 的核心改造）

```python
if keyword:                                                # :1909-1916
    kw_conds = [
        PurchaseItem.po_no.ilike(f"%{keyword}%"),
        PurchaseItem.project_code.ilike(f"%{keyword}%"),
    ]
    src_ids = await _source_ids_by_project(keyword, db)    # 查清单回溯
    if src_ids:
        kw_conds.append(PurchaseItem.source_sheet_id.in_(src_ids))
    conds.append(or_(*kw_conds))
```

**为什么要三个分支**：
1. `po_no ILIKE` — 直接命中采购单号
2. `project_code ILIKE` — 直接命中订单编号列
3. `source_sheet_id IN (...)` — 回溯路径：项目编号在清单行里、不在 PurchaseItem.project_code 里（#253 的 legacy：很多采购行 project_code 为空，原始项目编号存在 source_sheet_id 指向的清单行里）

**没有分支 3 会丢数据**（#330 回归验证）：采购新建 PO 时 project_code 可能不上 `purchase_items` 行，只留在 `sheet_rows` 的关联行里。如果搜项目 XM-2026-001 → 缺分支 3 → 这些带 project 的行搜不到 → "明明下了单、收货时搜不到"。

#### 第七层：物料名称

```python
if item_name:                                              # :1917-1918
    conds.append(PurchaseItem.item_name.ilike(f"%{item_name}%"))
```

#### 第八层：下单月份

```python
if order_month:                                            # :1919-1920
    conds.append(PurchaseItem.delivery_date.startswith(order_month))
```

`delivery_date` 是 ISO 字符串 `"YYYY-MM-DD"`，`startswith("YYYY-MM")` 直接做字符串前缀匹配 = 按月筛选。

#### 第九层：组合条件 + 排序 + LIMIT

```python
if conds:
    stmt = stmt.where(and_(*conds))                        # :1921

stmt = stmt.order_by(PurchaseItem.po_no.desc(), PurchaseItem.id.desc()) \
            .limit(limit)                                   # :1921-1922
```

- 排序：**按 po_no 降序 + id 降序**（新单在最前）
- LIMIT：默认 `_RECV_LIMIT_DEFAULT = 2000`（:1877），前端可传最大 `_RECV_LIMIT_MAX = 5000`（:1878）
- **无 OFFSET**：超过 2000 的行不可翻页，必须加筛选限制到 2000 以内

#### 第十层：执行 + receipt_count 后补

```python
rows = (await db.execute(stmt)).scalars().all()            # :1925
out = []
for r in rows:
    d = _item_out(r, db)                                    # :1927 组装 PurchaseItemOut
    cnt = await db.execute(                                 # :1947-1957 每条查附件数
        select(func.count(Attachment.id)).where(
            Attachment.biz_type == "receipt_doc",
            Attachment.biz_id == str(r.id)
        )
    )
    d["receipt_count"] = cnt.scalar()
    out.append(d)
```

**N+1 风险**：每条明细额外查询一次附件数（:1947-1957），limit=2000 时最多 2000 次额外 SELECT。当前未做预取优化，业务量尚可接受。未来可改为单次 batch SELECT 再 map。

#### N+1 额外来源（第三层之外）

`_item_out`（:701-721）内 `item.supplier.name`（:707）和 `item.buyer.name`（:708-709）在 `selectinload` 未设的情况下会触发额外的 lazy load。结合外层 JOIN 已选 supplier，实际 supplier N+1 可被已 JOIN 的数据消除，但 **buyer 的 N+1 仍在**（每行额外查一次 User 表）。业务量可接受。

## 4. 采购联动

### 4.1 待收货数据来源与查询

## 8. 异常路径与并发边界

### 8.1 事务边界与失败回滚

**`get_db` 无显式 rollback，靠隐式回滚。**

`database.py:28-30`：
```python
async def get_db() -> AsyncSession:
    async with SessionLocal() as session:
        yield session
```

没有 try/except/finally，没有显式 `rollback`。异常时 FastAPI 关闭依赖、session 关闭，连接归还连接池时**未提交的事务被丢弃**——即隐式回滚。SQLAlchemy 语义下已 `flush()` 但未 commit 的变更同样不会落库。

结论：回滚是可靠的，只是没有「显式 rollback + 日志」的可见性。

#### 收货提交的事务原子性

- `receive_item`：`_finish_receive`（回写清单→自动入库→同步流水金额→自动对账）→ **一个** `db.commit()`（:2044）。任一步抛异常，整条明细的全部变更一起回滚
- `receive_batch`：循环内逐条 `_finish_receive`，**最后统一一个** `db.commit()`（:2105）。中途第 N 条抛异常，前 N-1 条的变更也全部回滚——**批量收货原子性成立**，不会出现"收了一半"

### 8.2 幂等边界

| 步骤 | 位置 | 幂等机制 | 并发可靠性 |
|------|------|---------|-----------|
| `_auto_stock_in` | :1404-1440 | check-then-act：查已有流水，有则 return | **不抗并发**（见 §8.3.1）|
| `_sync_txn_amount` | :1443-1459 | 覆盖写已有流水金额 | 天然幂等 |
| `_maybe_auto_reconcile` | :724-736 | 仅从「待对账」推进一次，不回退不覆盖 | 天然幂等 |
| `_writeback_sheet_row` | :1995-2005 内 | 覆盖写清单列 | 同事务内安全 |

### 8.3 并发写冲突

#### 8.3.1 `_auto_stock_in` 并发双流水（check-then-act 无唯一约束）

- 幂等检查 `:1409-1412` 是「先查后插」，而 `WhTxn.purchase_item_id` 在 `models.py:413` **只有 index，无唯一约束**
- 两个请求对**同一条明细**几乎同时收货：两事务都查到无流水 → 都插入入库流水 → 双流水、库存翻倍
- 触发条件苛刻（同一明细秒级并发收货），但**无任何数据库防线**
- 修法：给 `wh_txns.purchase_item_id` 加唯一索引（需先确认冲红路径是否复用 `purchase_item_id`）

#### 8.3.2 `_next_ref` 撞号

`warehouse_router.py:619-625`：`ref_no = "RK/CK{ymd}-{COUNT(当日同前缀)+1:03d}"`。同日两个并发入库都算出同一序号；`ref_no` 仅 index（`models.py:418`）非唯一，**撞号不报错**，出现两条同号流水。

#### 8.3.3 `_next_po_no` 撞号

`purchase_mgmt_router.py:757-774`（建采购单）：`MAX(po_no 当日)+1` 同类竞态，并发建单撞号。与收货间接相关（收货按 po_no 展示）。

#### 8.3.4 Scheduler flock（防多实例重复推）

`overdue.py:371-388`：`.overdue_scheduler.lock` flock 单实例。**只锁 scan 循环**——若 4 worker 各起一个 scheduler，仅一个拿锁执行；锁文件随进程退出释放。

### 8.4 Limit 截断

| 层面 | 现状 |
|------|------|
| 列表查询 | `_RECV_LIMIT_DEFAULT = 2000`（:1877，#330 从 300 提升），`_RECV_LIMIT_MAX = 5000`（:1878）。查询 `stmt.limit(limit)`（:1921），无 offset |
| 筛选穿透 | 所有筛选条件（supplier/po_no/keyword/item_name/order_month）**在 SQL 层、先于 limit**——带筛选时能查到 2000 条之外的行 |
| 真实 count | `receiving/meta` 独立 `count(*)` 不受 limit 影响；全量供应商下拉同理 |
| 剩余截断 | **无任何筛选时**，待收货/已收货列表只显示前 2000 条（按 `po_no desc, id desc`），无分页。超过 2000 条的历史只能靠筛选定位 |
| scan | `scan_po_arrival_overdue` 全量扫描无 limit，不受此影响 |

### 8.5 `push_message` 的 commit 契约（:29-84）

- `push_message` **自己 `await db.commit()`**（:76）。约定是「业务事务 commit 之后调用」——若在业务 commit 前调用，会把该 session 上所有未提交变更**一并提交**
- 收货路径不调用 `push_message`（见 §7.2），故无此风险
- `push_message` 在目标用户为空时 `return 0` 且**不 commit**（:60-62）

#### 8.6.2 事务边界的异常传播

收货三个写端点（receive_item、receive_batch、upload_receipt）的事务行为：

```
receive_item（:2013-2046）
  try:
    _finish_receive(item, ...)  # 回写清单 + _auto_stock_in + _sync_txn_amount + _maybe_auto_reconcile
    db.commit()                  # :2044 单次提交
  except Exception:
    # 隐式回滚（session 关闭时丢弃未提交事务）
    → 客户端收到 500

receive_batch（:2049-2107）
  try:
    for line in lines:
      _finish_receive(item, ...)  # 逐行准备
    db.commit()                    # :2105 批量提交
  except Exception:
    # 前 N-1 行的 _finish_receive 也回滚——批量原子性
    → 客户端收到 500

upload_receipt（:2111-2127）
  try:
    att = Attachment(...)
    db.add(att)
    db.commit()         # :2125
  except Exception:
    → 客户端收到 500
```

**关键点**：`_finish_receive` 在逐行调用时只对 ORM 对象做属性修改（`item.arrival_date = ...`），未立即 `flush()`。所有修改累积到 session 的 identity map 中，最终 `commit()` 才一起送数据库——**批量收货中途某行爆炸不会出现"已改了前 5 行"的脏状态**。

#### 8.6.3 前端对异常的处理

`WarehouseView.vue` 的异步错误处理（`submitReceive` :546-564, `submitBatchReceive` :639-660）：

```typescript
try {
  await http.put(`/purchase-mgmt/items/${recvFormCopy.id}/receive`, recvForm)
  ElMessage.success('收货完成')
  await refreshAfterReceive()
} catch (e: any) {
  ElMessage.error(e?.response?.data?.detail || e?.message || '收货失败')
}
```

- 成功 → 刷新收货列表 + 库存 + 流水 + 物料需求
- 失败 → **不做任何刷新**（列表/库存均保持收货前状态，与后端回滚一致）
- **不重试**：对 403/422 等客户端错误不做二次提交，需要用户修正后手动重试

#### 8.6.4 未覆盖的错误场景

| 场景 | 当前行为 | 风险 |
|------|---------|------|
| 收货时 `_auto_stock_in` 抛出 IntegrityError（双流水撞号等）| 异常穿透到 endpoint → 500 隐式回滚，客户端看到通用错误 | 用户不知道"为什么失败"——是重复入库撞号、库位不存在、还是项目不存在？错误信息在日志里但未透传给前端 |

| 并发收货同一条明细 | 见 §8.3.1 | 双流水风险 |

## 9. 已知坑与反例

### 9.1 设计层面的坑

1. **收货完成零通知**（§7.2）：最大功能缺口，收货对采购/管理层无感知
2. **同一张表两套谓词**（§6.2.2）：`PurchaseItem` 表在 `/receiving`（仓库全量）和 `/items`（采购员仅自己）有不同可见性——若未来要求收窄仓库视角，需在 `list_receiving` 的 stmt 构造处加过滤
3. **单库位模型**（§3.3）：多次收货到不同库位会覆盖 `wh_materials.location`。若未来要多库位共存需先改这个模型
4. **`is_stock` 已废弃**（models.py :811/:1213/:1380）：别再按它写逻辑，收货一律只入库
5. **没有独立的收货单表/收货头表**：找"收货单"没有意义，状态就是 `arrival_date` 字段

### 9.2 并发/数据安全的坑

6. **`_auto_stock_in` check-then-act 不抗并发**（§8.3.1）：`WhTxn.purchase_item_id` 无唯一约束，双流水风险无防线
7. **`_next_ref` 撞号不报错**（§8.3.2）：同日并发入库可能产生同号流水
8. **`_next_po_no` 撞号**（§8.3.3）：并发建单撞号

### 9.3 性能/数据质量的坑

9. **scan 全量无 limit + N+1**（§7.1.6）：明细量大时每轮扫描开销线性涨
10. **`buyer_id` 为空的明细到期不提醒**（§7.1.5）：历史数据静默，需人工捞
11. **合并收货分摊的分位差**（§3.6.1）：按数量权重分摊总价反算单价有分位差，`_sync_txn_amount` 已按跟收货金额走兜底
12. **接收列表无分页**（§8.4）：无 offset，超 2000 条的老单只能靠筛选定位

### 9.4 代码/文档过期的坑

13. **`_auto_stock_in` docstring 过期**（:1405-1406）：仍写着"非备货再自动出库"，实际 :1439 已删。**看代码别信注释**
14. **两个价格口径别混**（§3.3）：`wh_materials.unit_price` 是参考单价，`wh_txns.unit_price/amount` 才是采购入库实际成本
15. **`_sync_txn_amount` "部分入库"分支是死代码**（:1450-1457）：当前收货都整条过账，是防御分支不是已实现功能
16. **前端"合并总价"模式后端仍支持但前端已不用**（§2.2.4）：`total_amount` 参数后端能力保留，别以为已废弃

### 9.5 权限/跨域的坑

17. **兼任财务不解除采购隔离**：`_buyer_restricted` 只判 buyer 家族（purchase_mgmt_router.py:47-50 注释）。**新增任何跨域读代码必须 import 本体，禁止重写**
18. **仓库域只读接口接口层零角色校验**（§6.3）：域隔离完全依赖 `User.menus` + `hidden_tabs`
19. **"前端隐藏 ≠ 接口隔离"**（§6.1）：仓库角色接口层可拿到全量价格数据

### 9.6 前端特有

20. **表格用 el-table 而非 vxe-table**：仓库模块收货列表与弹窗用的都是 Element Plus el-table
21. **不走 `frontend/src/api/warehouse.ts`**：收货 6 个端点全部 `http` 直调，`whApi` 只封装出入库流水/物料/发货清单
22. **PurchaseView.vue（457行）是僵尸代码**：grep 全前端 0 引用，路由不指向它

## 10. 收货与请款/对账/付款的关联

收货完成后，系统自动推进对账状态（如果满足条件），但不自动触发请款或付款。

### 10.1 自动对账 `_maybe_auto_reconcile`

`purchase_mgmt_router.py:724-736`：

```python
def _maybe_auto_reconcile(item):
    if item.invoice_status == "待对账" and item.arrival_date:
        if item.paid_amount is not None and item.received_amount is not None \
           and item.paid_amount >= (item.received_amount or 0) - 0.005:
            item.invoice_status = "已对账"
```

条件串联：
1. 当前状态为「待对账」（只推进一次，不覆盖已人工确认的）
2. `arrival_date` 非空（已收货）
3. `paid_amount >= received_amount - 0.005`（已付清，±0.005 浮点容差）

**触发点（三处）**：
- `receive_item` 内 `_finish_receive`（:2010）：收货完成时自动推进
- `receive_batch` 内 `_finish_receive`（:2107 附近）：合并收货完成时自动推进
- `update_item`（:1824）：收货后改价/改金额时可能重新触发

**关键词汇对照**：
- `arrival_date` = 到货日期（收货即填）= 收货完成标志
- `received_amount` = 收货金额（收货流程填）= 采购实际付款基础
- `paid_amount` = 已付金额（付款流程填，见 `purchase_mgmt_router.py:2695-2745` 的付款端点）
- `invoice_status` = 对账状态（待对账/已对账），与采购员开的发票（`invoice_no`/`invoice_date`/`invoice_amount`）是两个概念

### 10.2 请款审批独立于收货

请款流程（`purchase_mgmt_router.py` 约 :2590-2860）完全独立于收货：收货只是对账的基础条件，不能替代请款审批。采购员在收货后自行发起请款/上传发票（`POST /purchase-mgmt/invoice-items`，:2130 附近），走 pending→approved→paid 状态机。

**请款状态机密钥**（:2621-2630、:2742-2756）：
- 审批人不能审自己提交的单
- 付款人不能给自己审过的单付款
- `rejected_by` 独立字段存驳回人，不可复用 `finance_approver_id`

收货 → 自动对账（仅现金/对公全款已付清才自动）→ 采购员手动发起请款 → 财务审批 → 付款。

## 11. PurchaseItemUpdate 的特殊处理：接收字段与收货不重复

`schemas.py:1363-1381` `PurchaseItemUpdate` —— 采购员编辑采购明细用的 schema：

- **可用**：`po_no`、`supplier_id`、`unit_price`、`qty`、`item_name`、`spec`、`brand`、`delivery_date`、`contract_no`、`project_code`、`expected_arrival`、`notes`、`paid_amount`、`paid_date`、`payment_method`
- **刻意不开**：`arrival_date`、`delivery_note_no`、`stock_location`
  - 注释（:1371）：`arrival_date` 是收货唯一判定依据——若采购员能直填它，未收货的变为已收货、到期未到货提醒系统不再推送（消息幂等 logic 只看 `arrival_date` 为空 + `expected_arrival` 过期），功能会失灵
- **已废弃的 is_stock**：`schemas.py:1381` `model_config={"extra": "ignore"}`，前端传了也吞掉

**仓库改价走 `/items/{iid}/receive`（receive_item），不是 `/items/{iid}`（update_item）**。虽然改的都是 PurchaseItem 行，但前者有 `_RECEIVE_ROLES` 门控且正确走 `_sync_txn_amount` 回写流水金额，后者没有。两者是不同角色、不同端点的不同操作。

## 12. arrival_date 全局引用：哪些地方读写它

`arrival_date` 是收货状态唯一判定依据，需要知道全局有哪些读写路径：

**写路径（3 处）**：
| 位置 | 代码 | 说明 |
|------|------|------|
| `receive_item` :2029 | `item.arrival_date = body.arrival_date` | 单条收货 + 改价后重写 |
| `receive_batch` :2070 | `it.arrival_date = body.arrival_date` | 合并收货（循环内每行） |
| `update_item` :1820 附近 | **刻意不开** | PurchaseItemUpdate 不含 `arrival_date`，采购无法直写 |

**读/判路径（6 处）**：
| 位置 | 判定方式 | 用途 |
|------|---------|------|
| `list_receiving` :1898-1901 | `arrival_date IS NULL` → 待收货；`IS NOT NULL` → 已收货 | 列表分页 |
| `scan_po_arrival_overdue` :332-334 | `arrival_date is None or arrival_date == ''` 且 `expected_arrival < now` | 到期未到货提醒 |
| `_finish_receive` :1997 | `wb[col] = arrival_date` | 回写清单「到货日期」/「到料日期」 |
| `_maybe_auto_reconcile` :728 | `item.arrival_date` 非空 + 已付清 → 自动对账 | 对账推进 |
| `warehouse_router.py` :971-989 `po-items` | `PurchaseItem.arrival_date.isnot(None)` | 出库选料只暴露已到货行 |
| `_next_po_withdrawal` :388 附近 | 同 warehouse_router `po-items`，仅出库登记用 | 采购领用 |

**结论**：`arrival_date` 是收货模块的「状态位」，写它只有两个收货端点。任何其他代码路径写它都绕过了 `_auto_stock_in` / `_sync_txn_amount` / 清单回写等尾部动作，实现时必须走 receive_item 或 receive_batch。

## 13. 收货改价的完整双向链路

当仓库在「已收货」页签点某行「修改」时，走的是 `receive_item` 端点（:2013），不是 `update_item`。完整链路：

```
用户点「修改」（el-button，:1531-1542）
  └── openReceive(row) (:494-498) → recvEditing = true, recvFormCopy = response(row) (:498)
        └── recvForm = { delivery_note_no, arrival_date: 已有值, stock_location, 
                         unit_price, received_amount, receiptFiles: [] } (:87-100)
              └── arrival_date 必填(:2026-2027, 但修改场景已有值，校验自然过)

用户改价：
  ├── onRecvCalc (:514-518)：改单价 → received_amount = unit_price × qty
  └── onRecvAmountCalc (:519-523)：改金额 → unit_price = received_amount / qty

submitReceive (:546-564)：
  ├── FormData 上传收货单附件 → uploadReceipt(:532-535) 先传
  └── PUT /items/{id}/receive ({id} = recvFormCopy.id)
        └── receive_item (:2013-2046)
              ├── arrival_date 无修改不重判（已有值，:2026-2027 通过）
              ├── unit_price/received_amount 覆盖已填值
              ├── _finish_receive:
              │     ├── 回写清单（覆盖写日期/签字/库位）
              │     ├── _auto_stock_in：查已有 WhTxn → 有则 return（幂等，不重复入库）
              │     ├── _sync_txn_amount：查已有 WhTxn → 
              │     │     amount = round(received_amount, 4) ← 改价后新值写入
              │     │     unit_price = item.unit_price ← 同步更新的单价
              │     └── _maybe_auto_reconcile：重判是否自动对账
              └── commit → 返回 PurchaseItemOut
```

**为什么改价用 receive_item 而不用 update_item**：
1. `update_item` 的 schema（PurchaseItemUpdate）关闭了 `arrival_date`、`delivery_note_no`、`stock_location`（避免采购绕过收货流程直写）
2. `update_item` 调 `_sync_txn_amount`（:1823）但不调 `_finish_receive`（清单回写 + 自动对账不触发）
3. `receive_item` 的业务语义更准确——"仓库收货/后补价格"而非"采购员编辑明细属性"

**合并改价**同理走 `receive_batch`（:2068-2082），弹窗逐行可编辑单价和收货金额。

## 14. 扩展主题：出入库领用与收货的边界

收货入库和仓库领料是两个独立流程，各有自己的流水（WhTxn），不能混。

| 维 | 收货自动入库 | 仓库领料出库 |
|----|-------------|-------------|
| 写入点 | `_auto_stock_in`（:1404） | `warehouse_router.py` POST `/txns`（:746）/ 批量出库 `/batch-out`（:806）/ 一键领用（:1263） |
| 方向 | direction='in' | direction='out' |
| 金额 | 采购单价 × 数量（`received_amount`） | 库存单价 × 数量（物料当前均价） |
| 项目 | 按 `project_code` 查 Project（收货挂上） | 按领用时选的项目 |
| 采购关联 | `purchase_item_id` 写流水 | 无采购关联（冲红除外） |
| 自动触发 | 收货完成时 `_finish_receive` 自动调 | 仓库手动操作，或物料需求「一键领用」批量发起 |
| 对账 | `_maybe_auto_reconcile` 自动推进 | 不涉及 |

**仓库物料需求（一键领用）** 与收货的关系：
- `warehouse_router.py:1263` `issue_demand_items`：按项目 + 物料需要数量 → 自动生成出库流水
- 前提：物料有库存（`_stock_map` positive），否则报「库存不足」
- 采购下单会生成需求 item（`purchase_demand` 表），收货入库后库存在线——仓库看物料需求 tab 发领料

**回冲/退货**：采购退货靠「仓库冲红 + 删明细」两原语拼出。售后模块不写库存。

## 16. 前端弹窗与列表刷新的协调

收货完成后触发 `refreshAfterReceive`（:540-545）：

```typescript
async function refreshAfterReceive() {
  await loadReceiving()
  await loadRecvMeta()        // 刷新角标 + 供应商下拉
  loadMaterials()              // 库存总览
  loadTxns(1)                  // 出入库流水
  loadDemand()                 // 物料需求 tab
  loadDemandOverview()         // 需求总览
}
```

**为什么刷新这么多 tab**：收货入库会产生新的 WhTxn → 物料库存（materials）变 → 物料需求 tab 的缺口变 → 出入库流水有新行 → 收货 tab 本身待/已切换。**所有 tab 的根数据都来自 purchase_items + wh_txns，必须全刷一遍**。

**同文件的其他视图函数签名**（方便定位）：
- `loadMaterials`（:328-341）—— 库存总览 `GET /warehouse/materials`
- `loadTxns`（:343-366）—— 出入库流水 `GET /warehouse/txns`
- `loadDemand`（:367-375）—— 物料需求 `GET /warehouse/demand`
- `loadDemandOverview`（:377-389）—— 需求总览
- `loadReceiving`（:451-466）—— 收货列表
- `loadRecvMeta`（:468-475）—— 收货元信息
