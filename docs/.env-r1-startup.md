## 一、启动全链路（main.py lifespan，第 65-103 行）

FastAPI 以 `lifespan` async context manager 接管启动/关闭。起点：`create_app()` 第 111 行将 lifespan 注入 `FastAPI(...)`。

### 启动步骤（严格顺序）

| 步骤 | 职责 | 函数/位置 | 幂等性保证 |
|------|------|-----------|-----------|
| **0. 多 worker 串行锁** | `--workers N` 部署时防止竞态 | `main.py:77-79` — `pg_advisory_lock(872193641)` | Postgres 会话级排他锁：同一时刻只有一个 worker 跑步骤 1-4，其余排队 |
| **1. 建表** | 创建新表（不改存量表） | `main.py:81-82` — `Base.metadata.create_all`，在 `engine.begin()` 事务内 | SQLAlchemy `create_all` 本身幂等（表已存在则跳过） |
| **2. 补列/拉宽类型/去 NOT NULL** | 给存量表加新增列、放宽列类型（仅 Postgres） | `main.py:83` — `ensure_schema_columns(engine)` @ `data_migration.py:168-205` | **每列逐个检查**：`inspect.get_columns()` 查列是否存在 → 不存在才 `ALTER TABLE ADD COLUMN`；`_WIDEN_COLUMNS` 和 `_DROP_NOTNULL` 同理 |
| **3. 种子数据** | 初始化 22 个角色 + admin/manager 两个账号 | `main.py:84-85` — `seed(db)` @ `seed.py:45-104` | 角色：逐个查 `WHERE code=xxx` → 不存在才 INSERT，存在则同步 name/desc（can_push 只在 NULL 时初始化）；用户：查 `WHERE username=xxx` → 不存在才创建 |
| **4. 数据迁移** | 存量数据修正（36 项） | `main.py:86` — `run_data_migrations(db)` @ `data_migration.py:2274-2458` | 每项独立 try/except，失败只 warn 不阻塞启动；各项内部均按"先查后改"设计幂等（如 `backfill_user_menus` 只回填 menus 为 NULL 的账号） |
| **5. 释放锁** | 让下一个 worker 入场 | `main.py:88-90` — `pg_advisory_unlock` + 关闭锁连接 | — |
| **6. 启动日志** | 打印 DB 地址、文件目录可写性 | `main.py:91-94` | — |
| **7. 启动逾期扫描调度器** | 后台周期任务 | `main.py:95` — `asyncio.create_task(overdue_scheduler())` | flock 单实例（见下） |
| **8. 启动智能体每日简报调度器** | 后台周期任务 | `main.py:98-99` — `asyncio.create_task(briefing_scheduler())` | flock 单实例（见下） |

### 关闭步骤（第 100-103 行）

1. `task2.cancel()` + `task.cancel()` 取消两个后台循环任务
2. `await engine.dispose()` 释放数据库连接池

## 二、步骤 2 详解：ensure_schema_columns

**文件**：`backend/app/data_migration.py:168-205`

### 处理的三个维度

| 维度 | 数据源 | 操作 | 适用范围 |
|------|--------|------|---------|
| 补新列 | `_NEW_COLUMNS` 字典（第 19-149 行） | `ALTER TABLE ADD COLUMN` | SQLite + Postgres |
| 拉宽列类型 | `_WIDEN_COLUMNS` 字典（第 158-160 行） | `ALTER TABLE ALTER COLUMN TYPE` | 仅 Postgres |
| 去 NOT NULL | `_DROP_NOTNULL` 字典（第 163-165 行） | `ALTER TABLE ALTER COLUMN DROP NOT NULL` | 仅 Postgres |

### 幂等设计（第 169-183 行）

```
for 每张表:
    existing_cols = inspect.get_columns(table)  # 查现有哪些列
    if 表不存在: skip（全新库，create_all 已含新列）
    for 每个待补列:
        if 列已存在: skip
        ALTER TABLE ADD COLUMN ...
```

### 需要关注的特殊点

1. **`_NEW_COLUMNS` 中不允许重复键**：同一表名出现两次会后者覆盖前者，导致前一批列永远不被补。`tests/test_schema_columns_no_dup.py` 盯防。
2. **`fix_oa_activated_at_tz`（第 209-239 行）**单独处理，不走 `_WIDEN_COLUMNS`：因为 `ALTER TYPE USING AT TIME ZONE 'UTC'` 对已是 `timestamptz` 的列再跑一次会挪时区差，必须先查 `information_schema.columns.data_type` 确认是 `timestamp without time zone` 才动。

## 四、后台任务一：逾期扫描调度器 (overdue_scheduler)

**文件**：`backend/app/overdue.py:394-433`

### 调度参数

- **触发**：lifespan 启动行 `main.py:95`
- **周期**：每 `interval_hours=12` 小时（默认 12h）
- **多 worker 保护**：`_try_acquire_scheduler_lock()` @ `overdue.py:374-391` — 文件锁 `.overdue_scheduler.lock`（fcntl flock，非阻塞排他锁），拿不到锁的 worker 直接 return

### 每轮扫描 6 项（第 400-433 行）

每项使用独立 `SessionLocal()` 会话，异常只 warn 不崩调度器：

| 扫描函数 | 行号 | 幂等键 | 推送目标 | 备注 |
|---------|------|--------|---------|------|
| `scan_overdue` | 402 | `biz_type="order_overdue"` + `biz_id=order_id` + 当日 | 部门主管 (lead_role) + manager | 逾期任务：`status=in_progress` 且 `due_date < 今天` |
| `scan_balance_due` | 407 | `biz_type="balance_due"` + `biz_id=ledger_id`（终身一次性） | 销售本人 + sales_lead + manager | 尾款到期前 14 天起提醒 |
| `scan_balance_overdue` | 412 | `biz_type="balance_overdue"` + `biz_id=ledger_id` + 7 天窗口 | 第 1 周→销售 / 第 2 周→+主管 / 第 3 周→+管理层 | 逾期尾款周催办升级 |
| `scan_hr_reminders` | 417 | `biz_type="hr_contract"/"hr_regular"` + `biz_id=emp_id` + 7 天窗口 | hr + manager | 合同到期前 30 天 / 试用转正前 7 天 |
| `scan_management_todos` | 422 | `biz_type="mgmt_todo_remind"` + `biz_id=target.id` + 当日 | 收件人 + 下达人（仅逾期抄送） | 逾期/未回复承诺时间 |
| `scan_po_arrival_overdue` | 427 | `biz_type="po_arrival_overdue"` + `biz_id=item.id` + 当日 | 采购员本人 | 仅 15:00 后触发（#292），到期未到货 |

### 时区处理

所有扫描统一使用中国业务时区 `_CN_TZ = UTC+8`（`overdue.py:20`），幂等判定和逾期判定均按业务自然日，避免 UTC/本地日界错位导致重复推送。

## 五、后台任务二：智能体每日简报调度器 (briefing_scheduler)

**文件**：`backend/app/agent/daily.py:164-178`

### 调度参数

- **触发**：lifespan 启动行 `main.py:98-99`
- **周期**：每天中国时间早 8:00（`agent/daily.py:39` — `_PUSH_HOUR_CN = 8`）
- **多 worker 保护**：`_try_lock()` @ `agent/daily.py:144-161` — 文件锁 `.agent_briefing.lock`，同 overdue_scheduler 套路

### 执行逻辑 (run_once, `daily.py:65-129`)

1. **读收件人**：从 `app_settings.agent_briefing_users`（JSON 数组存 username）取值；默认空数组 → 跳过不发
2. **读已推记录**：从 `app_settings.agent_briefing_sent` 取 JSON，按 5 天冷却期（`briefing._REPEAT_COOLDOWN_DAYS = 5`）过滤已推条目
3. **并发生成**：N 个收件人并发调用 `briefing.build(u, top=3, skip_refs=...)` 各自取数
4. **顺序推送**：拿到结果后逐个 `push_message` 推站内+企微双通道，带 H5 深链
5. **记录已推**：写回 `app_settings.agent_briefing_sent`
6. **空简报不发**：没有待办项时不打扰

### 收件人配置

- 配置位置：`app_settings` 表，key = `agent_briefing_users`
- 值格式：`["username1", "username2"]` JSON 数组
- 留空（默认）= 关闭，不推任何人
