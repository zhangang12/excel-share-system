## 一、开发 vs 生产 Docker 差异对比

| 维度 | 开发（docker-compose.yml） | 生产（docker-compose.prod.yml） |
|------|--------------------------|-------------------------------|
| **编排文件** | `docker-compose.yml`（50 行） | `docker-compose.prod.yml`（86 行），需配合 `.env.prod` |
| **容器组成** | 3 个：postgres + backend + frontend | 4 个：postgres + backend + frontend + **nginx** |
| **postgres 镜像** | `postgres:16-alpine` | `postgres:16-alpine`，相同 |
| **postgres 端口** | `127.0.0.1:5432:5432`（只绑本地） | 不暴露外部端口，仅容器间通信 |
| **restart 策略** | 无 | 所有服务 `restart: always` |
| **backend Dockerfile** | `Dockerfile.dev`：`uvicorn --reload`，单 worker | `Dockerfile.prod`：`uvicorn --workers 4`，无热重载 |
| **frontend Dockerfile** | `Dockerfile.dev`：`npm run dev --host 0.0.0.0`（Vite HMR） | `Dockerfile.prod`：多阶段构建，先 `npm run build && build:h5`，产出静态文件由内嵌 nginx 托管 |
| **frontend 端口** | 直接暴露 `5173` | 不暴露端口，由外层 nginx 反向代理到 `frontend:80` |
| **nginx** | 无 | `nginx:1.27-alpine`，暴露 80/443，挂载 conf.d、证书、wecom 验证、桌面客户端更新包、H5 OTA 等 |
| **volume 挂载** | `./backend:/app`（源码热挂载）、`frontend_node_modules`（匿名卷） | `uploads_data:/app/uploads`（持久化上传文件）、`nginx_logs`（日志持久化） |
| **主机卷挂载** | 无 | `./nginx/conf.d`、`./nginx/certs`、`./nginx/certbot-www`、`./nginx/wecom-verify`、`./desktop-releases`、`./h5-ota`（6 个 bind mount，均为只读） |
| **数据库密码** | 默认值 `pms_dev_pwd`（env 缺省） | 无默认值，必须由 `.env.prod` 提供 |
| **环境变量** | `DATABASE_URL`、`SECRET_KEY`（2 个） | 加 `ACCESS_TOKEN_EXPIRE_MINUTES`、`DEFAULT_ADMIN_*`、`FILES_DIR`、`SALES_ORDER_APPROVAL`、`WECOM_*`（~10 个） |
| **基础镜像** | backend: `python:3.12-slim`，frontend: `node:20-alpine` | backend 同左；frontend 构建阶段 `node:20-alpine`，运行阶段 `nginx:1.27-alpine` |
| **启动命令** | `docker compose up -d` | `docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build` |

### Backend Dockerfile 关键差异

```diff
# Dockerfile.dev
- CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]

# Dockerfile.prod
+ CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "4"]
```

生产使用 4 个 worker 进程（AGENTS.md 提及 `--workers 4` 下周期任务需 flock 单实例）。

### Frontend Dockerfile 关键差异

- **开发**：单阶段，`node:20-alpine` 跑 `npm run dev`（Vite 开发服务器，HMR 热更新）
- **生产**：双阶段构建
  - 阶段 1（builder）：`npm run build` → `/app/dist`（网页端）+ `npm run build:h5` → `/app/dist-h5`（H5 助手端）
  - 阶段 2（runtime）：`nginx:1.27-alpine`，COPY `nginx.conf`（SPA 路由兜底）+ `dist` + `dist-h5`，暴露 80
  - H5 挂在 `/h5/` 子路径，与网页端各自独立

## 二、Nginx 路由规则

项目有两层 nginx：

### 2.1 外层 nginx（`nginx/conf.d/default.conf`，生产网关）

对外入口，监听 80（HTTP）和 443（HTTPS 模板，注释状态）。

| 路由 | 目标 | 说明 |
|------|------|------|
| `/.well-known/acme-challenge/` | `/var/www/certbot` | ACME http-01 验证（Let's Encrypt） |
| `~ ^/WW_verify_.*\.txt$` | `/var/www/wecom` | 企业微信可信域名验证文件 |
| `= /api/auth/login` | `backend:8000` | **登录限频**：10r/m，burst 5（`limit_req_zone login_limit`） |
| `/api/agent/chat/stream` | `backend:8000` | **SSE 流式**：`proxy_buffering off`、`proxy_cache off`、`chunked_transfer_encoding on`、read timeout 300s |
| `/api/` | `backend:8000` | 通用 API，read timeout 300s |
| `/ws/` | `backend:8000` | WebSocket 升级，read timeout 86400s（24h） |
| `/desktop/` | `/opt/pms/desktop/` | 桌面客户端更新包（`autoindex off`，`Cache-Control: no-cache`） |
| `/h5-ota/` | `/opt/pms/h5-ota/` | 手机 APP 热更新包（同上） |
| `/` | `frontend:80` | 前端 SPA（由 frontend 容器内 nginx 提供） |

安全头：`X-Frame-Options: SAMEORIGIN`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`server_tokens off`。

### 2.2 内层 nginx（`frontend/nginx.conf`，前端容器内）

前端容器内嵌的静态文件服务器，监听 80。

| 路由 | 行为 | 说明 |
|------|------|------|
| `/assets/` | `try_files $uri =404` | 带 hash 的构建产物，`Cache-Control: public, max-age=2592000, immutable`（30 天） |
| `/h5/assets/` | 同上 | H5 助手端独立 assets，30 天强缓存 |
| `/h5` | `try_files $uri $uri/ /h5/h5.html` | H5 独立 SPA 路由兜底，`index h5.html` |
| `= /h5/h5.html` | 直接返回 | `Cache-Control: no-cache, no-store, must-revalidate` |
| `/` | `try_files $uri $uri/ /index.html` | 网页端 SPA 路由兜底（Vue Router history 模式） |
| `= /index.html` | 直接返回 | 不缓存，保证拿最新入口 |

关键设计：两层 nginx 不冲突——外层负责路由分发（API/WS/静态资源），内层只负责前端 SPA 的静态文件与路由兜底。

## 三、发版全链路

### 3.1 链路概览

```
本地 ops/release.sh  ──SSH──▶  服务器 ops/upgrade.sh  ──▶  备份 → git pull → docker rebuild → 健康检查 → 成功/回滚
```

### 3.2 本地端：`ops/release.sh`

| 参数 | 作用 |
|------|------|
| `--push` | 先 `git push` 到 `origin/main`，再触发服务器部署 |
| `--logs` | 部署成功后跟随后端日志（`docker logs -f --tail=60 backend`） |
| `--no-rebuild` | 只重启不 rebuild（仅改 `.env` 时用） |
| `--health` | 仅在服务器跑 `health-check.sh`，不部署 |
| `--dry-run` | 只打印 SSH 命令，不执行 |

**依赖**：`.deploy.local`（gitignored）提供服务器连接信息：
- `DEPLOY_SSH_ALIAS`（优先）或 `DEPLOY_HOST` + `DEPLOY_USER` + `DEPLOY_PORT` + `DEPLOY_KEY`
- `DEPLOY_PATH`（服务器项目目录，如 `/opt/pms/excel-share-system-main`）
- `DEPLOY_BRANCH`（默认 `main`）

**逻辑**：
1. 读 `.deploy.local` 组装 SSH 连接
2. 若 `--push`，先 `git push origin HEAD:$DEPLOY_BRANCH`
3. 若本地领先 origin 且未 `--push`，打印警告（服务器只部署已推送的代码）
4. SSH 执行 `cd $DEPLOY_PATH && bash ops/upgrade.sh $UPGRADE_ARGS`
5. 退出码 0 = 成功；1 = 失败但已回滚；2 = 失败且回滚也失败（需人工介入）

### 3.3 服务器端：`ops/upgrade.sh`

**步骤**（5 步）：

1. **记录当前 git commit**（用于回滚锚点）
2. **备份**：`SKIP_UPLOADS=1 bash ops/backup.sh`（仅备份数据库，上传文件由每日 cron 负责）
3. **git pull**：`git fetch && git pull --ff-only`（仅快进合并，拒绝冲突）
4. **重建并启动**：`docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build`
5. **健康检查**：
   - 先轮询 `curl http://localhost/api/health` 最多 60 秒
   - 通过后跑 `bash ops/health-check.sh --quiet` 完整检查
   - **任何一步失败 → 自动回滚**（`bash ops/rollback.sh --to $OLD_COMMIT`）

**退出码**：0 = 升级成功；1 = 失败但已回滚（线上仍是旧版）；2 = 失败且回滚也失败（严重，需人工登录处理）。

### 3.4 健康检查：`ops/health-check.sh`

检查项目（共 9 项）：

| 检查项 | 判定 | 失败严重度 |
|--------|------|-----------|
| 4 个容器状态（`docker inspect`） | 必须 `running` | **FAIL**（阻断升级） |
| postgres 可连（`pg_isready`） | 接受连接 | **FAIL** |
| backend `/api/health` | HTTP 200 + `"status":"ok"` | **FAIL** |
| 磁盘 `/` 使用率 | ≥90% FAIL，≥80% WARN | ≥90% FAIL |
| 内存使用率 | ≥90% WARN，否则 OK | 仅 WARN |
| 数据库大小（`pg_database_size`） | 始终 OK（仅记录） | 从不 FAIL |
| 备份新鲜度（最近 SQL 备份文件） | >36h WARN | 仅 WARN |
| backend 1h 异常日志（ERROR/Traceback/Exception） | >50 FAIL，>5 WARN | >50 FAIL |

所有检查均带 `timeout` 保护（8~20 秒），防止被检服务卡死拖死脚本本身。

退出码 = FAIL 计数。WARN 不改变退出码，不阻断升级。

### 3.5 回滚：`ops/rollback.sh`

| 用法 | 说明 |
|------|------|
| `bash rollback.sh` | 回退到 `HEAD~1` |
| `bash rollback.sh --to abc123` | 回退到指定 commit |
| `bash rollback.sh --list` | 列出最近 10 次 commit |

步骤：`git checkout $TARGET` → `docker compose up -d --build` → 等 60 秒确认 health check 通过。

## 四、服务器运维 Cron 配置

### 4.1 安装：`ops/setup-cron.sh`

需要 root 权限，安装三项：

#### (1) 每日备份 — `/etc/cron.daily/pms-backup`
- 由系统 `cron.daily` 触发（默认 6:25）
- 执行 `bash ops/backup.sh`，日志写入 `/var/log/pms-backup.log`

#### (2) 健康检查 + 自愈 — `/etc/cron.d/pms-health`
- 每 5 分钟：`bash ops/health-check.sh --quiet`
- 失败时自动 `docker compose restart backend`
- 日志写入 `/var/log/pms-health.log`

#### (3) 日志轮转 — `/etc/logrotate.d/pms`
- `weekly`，保留 4 周
- 压缩、不转空文件

### 4.2 备份脚本：`ops/backup.sh`

**内容**：
1. **数据库**：`docker exec postgres pg_dump | gzip > /backup/pms-db-YYYYMMDD_HHMMSS.sql.gz`
2. **上传文件**（可选，默认启用）：tar `uploads_data` 卷 → `/backup/pms-uploads-*.tar.gz`
3. **滚动清理**：DB 备份保留 30 天（`KEEP_DAYS`），uploads 额外限制最多 7 个（`KEEP_UPLOADS`）
4. **远程上传**（可选）：`--upload-cos` 上传腾讯云 COS，`--upload-oss` 上传阿里云 OSS

**关键变量**：`BACKUP_DIR`（默认 `/backup`）、`SKIP_UPLOADS=1`（仅备数据库，发版前置备份用）、`KEEP_UPLOADS`（防频繁发版撑爆磁盘）。
