第七章　上线与运营：评估集、灰度、可观测、失败模式

前六章讲的是把东西做出来。这一章讲的是怎么证明它是对的、怎么让它慢慢铺开、怎么在它出事的时候比用户先知道。这三件事恰好是普通开发最容易跳过、而 FDE 唯一不能跳过的部分——因为普通开发交付的是代码，FDE 交付的是"这套东西在你们公司能长期用下去"这个承诺。

本章的核心结论（先说结果）

Agent 系统的失败大多数不是崩溃，是安静地答错。接口 200、日志无异常、用户看到一张排版漂亮的 Markdown 表格——数字是错的、行是多的、结论是编的。传统运维那一整套（健康检查、错误率、P95）对这类失败完全失明。所以 Agent 上线必须额外带三件在传统项目里不存在的东西：评估集（发现答错）、问答级审计（事后能查是怎么答错的）、纠错回路（让用户告诉你它答错了，而不是默默不用了）。缺任何一件，这个 Agent 都会在上线后三个月内变成没人用的摆设——不是因为它不好用，是因为没人再信它。

7.1　为什么"我试了几个问题感觉还行"不算验收

这是本项目 AI 助手第一版的真实验收方式，也是绝大多数 Agent POC 的验收方式：开发者自己登录，问三五个问题，回答通顺、数字看着像那么回事，上线。

它有四个结构性缺陷，每一个都能单独让验收失效：

  1. 验收者永远是权限最大的那个人。开发者用 admin 登录。而 menus.py:151-152 对 admin/manager 直接返回全量菜单，deps.py:125 的 user_can_view_project 对管理层无条件放行。也就是说，用 admin 测出来的"看得见"永远是对的——所有行级越权在 admin 视角下天然不可见。那个 P0 越权（案例见 3.1）能上线到生产，根因之一就是它在开发者的账号下表现完美。
  2. 手测天然只测"有数据"的路径。没人会专门去构造"今天恰好 0 条未到货"的情况，也没人会去测 balance_date 正好等于今天 +14 天的边界（agent_router.py:141 的 threshold）。而这些边界恰恰是业务方最先发现、且最伤信任的地方——他数了一遍是 13 条，助手说 12 条，从此他不再问助手。
  3. 模型不是确定性的，一次通过不代表下次通过。agent_router.py:492 把 temperature 压到 0.2，这能降低漂移但消不掉。同一句"下周有什么到货"，这次调 po_arriving(days=7)，下次可能调 po_arrival_overdue——两个工具的语义完全相反（一个是未来要来的，一个是该来没来的），用户看不出差别，只会觉得"这系统时准时不准"。
  4. 没有基线就没有回归。下一次你改 system prompt（agent_router.py:477-484）、加一个工具、把默认模型从 A 换成 B（agent_router.py:826 的 PUT /config 一改就是全局生效），你无法回答"有没有改坏别的"。手测的结论保存在你的记忆里，而记忆不能 diff。
一句话标准

验收不是"我觉得它答得不错"，是"给定这份用例集，在这个模型这个版本下，通过 N/M 条，未通过的这几条是已知且可接受的"。前半句是集合，后半句是签字。没有集合，没有签字，就没有验收——只有一次演示。

7.2　评估集怎么建

7.2.1 五个层次，缺一层就有一类问题永远发现不了

层回答什么问题失败长什么样断言方式能不能自动化
L-事实　事实准确性数字对不对说 12 条，实际 13 条与权威口径（业务端点 / overdue.py 扫描器）比对，精确相等完全可以
L-权限　权限正确性该看见的看见、不该看见的看不见普通销售拿到全公司尾款同一问题两个身份问，断言 A 的结果集 ⊄ B 的结果集；断言明细里不出现他人标识完全可以，且必须
L-工具　工具选择正确性问 X 有没有去查 X问"下周到货"却查了"逾期未到货"断言 sources / tools_used 等于期望工具集（agent_router.py:955 已经把它回给前端了）可以
L-拒答　拒答正确性查不到时是否老实说查不到项目不存在，编一个进度出来断言回答包含"查不到/无权/做不到"语义，且不包含任何数字半自动（关键词 + 人工抽查）
L-卡片　卡片正确性（L3）卡上写的与系统里的一致吗卡显示 8 万，实际单据 12 万断言 facts 每个字段 == 确认时端点读到的权威值；不等则拒绝提交可以，且是 L3 的准入条件

这五层的顺序不是随便排的，它是按"错了以后多难挽回"降序排的：卡片写错会导致真实的钱付错；越权会导致数据泄露且无法收回；数字错会毁掉信任；工具选错和不肯拒答只是体验差。资源不够时从下往上砍，永远不要砍上面两层。

7.2.2 用例从哪来：四个来源，没有一个来自"我想一想"

来源一：真实用户反馈。本项目最大的现成资产就是这条闭环——user_feedback_router.py 里已经跑着"提反馈 → 管理层回复 → 站内消息 + 企微双通道推送提出人"（:155-186，推送在 :179-183 调 notify.push_message）。历史反馈里凡是带"我看到的数和系统里不一样""为什么别人的单我也能看到"这类字眼的，逐条转成评估用例。真实反馈的价值在于它自带正确答案：用户已经告诉你他期望看到什么了。

来源二：真实业务问题。不要问业务方"你希望 AI 能回答什么"，问他"你上周为了搞清楚一件事，打开了几个页面"。本项目最典型的是采购员每天早上要看的三件事——今天该到什么货、哪些已经拖了、哪家供应商拖得最狠——这恰好就是 po_arriving / po_arrival_overdue / po_overdue_by_supplier 三个工具的由来（agent_router.py:96/66/121）。这类问题的期望结果必须由业务方自己写，写完签字。

来源三：历史工单/缺陷。本项目近期的三件真实事件全都能直接变成用例：#331 职责分离拦住出纳付款（需求.docx 第十六项内控要求，admin 也不留后门）→ 变成 L-卡片 的用例 E29；#333 杨坛因 _is_sales() 不排除主管而被误拦 → 变成 L-权限 的用例（"主管身份下该看到全部"也是一种正确性）；tool_po_overdue_by_supplier 的口径 bug（agent_router.py:123-135：聚合跑在 :93 已截断的 20 条上，item_total 却取全量 count）→ 变成 L-事实 的用例 E02。凡是修过一次的 bug，都必须有一条评估用例钉住它，否则换个模型它就会以另一种形式回来。

来源四：故意构造的越权探测题。这一类不是从业务里来的，是你自己想出来攻击自己的。构造方法很机械：把权限测绘表（第二章 2.6 的产出）的每一行，翻译成一句自然语言提问。本项目的 7 类行级规则就对应 7 组探测题——采购按 buyer_id（purchase_mgmt_router.py:46/349-350）、销售按 sales_uid（sales_router.py:53/239-240）、线索按 owner_uid、项目目录按派单（deps.py:95）、项目详情按成员（deps.py:125）、任务按 worker_id、OA 多路可见。每组至少两条：一条"我应该看到的"，一条"我不该看到别人的"。

7.2.4 评估怎么跑：人工基线 + 回归自动化

这两件事是不同的东西，很多团队混为一谈然后两边都没做好。

人工基线（一次性，上线前，2-3 人 · 半天）。目的是确定期望结果，不是发现 bug。做法：把 30 条用例的"期望结果"栏空着，让业务方（采购员、销售、财务各一位）当场填。他们填的东西会推翻你的一部分假设——本项目就发生过这种事：#333 里杨坛以为销售主管应该能看全部，代码里 _is_sales() 不排除主管把他拦了。期望结果由业务方定义、开发者只负责实现，这个分工必须在评估集上确立，否则上线后每一次分歧都会变成"到底谁说了算"的扯皮。填完打印签字，这份签字件是后面所有争议的裁判。

回归自动化（每次改动，CI 里跑）。本项目已经有现成的骨架可以照抄：backend/tests/test_agent_perms.py（160 行）用临时 SQLite + ASGITransport 直接打 app，:24 显式设 AGENT_LLM_API_KEY="" 强制走规则降级路径，全程不依赖任何外部服务。这个模式对 L-权限、L-事实、L-拒答 三层完全够用且必须常驻 CI——因为这三层的正确性由代码保证，与模型无关。

# 分两个文件，两种跑法，不要混在一起

# ① test_agent_eval_offline.py —— CI 每次跑，零成本、确定性、必须全绿
#    AGENT_LLM_API_KEY="" → 走 _rule_chat（agent_router.py:708）
#    覆盖 E01-E15、E22、E24、E26、E27-E30，共 22 条
#    这些用例断言的是「工具返回了什么」和「谁能看到什么」，与模型无关

# ② test_agent_eval_llm.py —— 手动/发版前跑，有成本、非确定性、看通过率
#    需要真 API Key，覆盖 E16-E21、E23、E25，共 8 条
#    每条跑 3 次取多数（模型有抖动，单次结果没有统计意义）
#    输出不是 PASS/FAIL 而是一张表：模型 × 用例 × 3 次通过数

第二类的产出形态很重要：它不该是一个红绿灯，该是一张记分卡。因为"3 次里对 2 次"这种结果在传统测试里没有意义，在 Agent 评估里却是最常见也最有信息量的状态——它告诉你这条用例处在模型能力边界上，要么改 prompt 要么换模型要么接受它。把它硬做成 PASS/FAIL，团队会开始为了绿灯而重试，评估就废了。

本项目还有一个便宜的加分项：规则降级路径本身就是一份天然的 oracle。_rule_chat（:708-740）是纯关键词匹配 + 模板格式化，零幻觉、完全确定。对同一个问题，可以断言 LLM 路径的 tools_used 与规则路径的 tools_used 一致——不比对文字，只比对"查了什么"。这就把 L-工具 层的自动化成本降到了几乎为零。

7.3　灰度与回滚

7.3.1 先给谁用

标准答案是"先给一小部分人"，但挑谁比"挑几个"重要得多。本项目的选人标准，按优先级：

  1. 提反馈最积极的那几个人。本项目有现成名单——user_feedback 表按 user_id 分组计数，提得最多的前 5 位就是天然的灰度用户。这批人的价值不是"他们宽容"，恰恰相反，是他们会说。一个沉默的用户遇到错误答案只会不再用，你什么都学不到；一个爱提反馈的用户会给你一条带截图的工单。
  2. 业务上"错了能兜住"的岗位优先。采购员看错到货日期 → 打个电话核实，成本几分钟；出纳看错付款金额 → 可能真付错。所以第一批放采购/设计/生产的查询场景，财务金额类和所有 L3 卡片场景放最后。
  3. 覆盖权限的极端形态。灰度名单里必须包含至少一个多角色兼任账号（如王芹 = buyer+finance+logistics）和至少一个权限最窄的账号（如仓库王利利）。这两类是越权和过度拒绝的高发人群，只放"典型用户"等于没测。
  4. 不要先给管理层。反直觉但很重要：管理层是 menus.py:151-152 全量放行的，他们用得再顺也证明不了权限正确；而且他们一旦形成"这东西挺准"的印象，后面普通员工报错时你会失去话语权。

注意 G3 的"卡片确认率"是个双向指标：太低说明 Agent 在推没用的东西（用户懒得点），太高反而危险（说明用户在无脑点，即第五章 T7 的确认疲劳）。健康区间大概是 60%-85%，超过 90% 要去看看是不是卡片都太简单、或者用户根本没在看 facts。

7.3.3 灰度怎么实现：本项目的三个现成抓手

抓手一：菜单开关。menus.py:154 目前是 set(configured) | {"agent"}——AI 助手菜单对所有登录用户无条件追加，这在灰度期是错的。灰度期应改为读 User.menus 里是否显式含 agent，灰度名单 = 给这几个账号的 menus 加一项。改一行，零风险，且和系统既有的账号级菜单配置口径一致（menus.py:145-147：一级菜单按账号配置，角色矩阵已废除）。注意不能用前端 hidden_tabs 那套做灰度——它只在前端隐藏、后端零处强制，不是可信边界。

抓手二：桌面客户端版本机制。本项目有几十人在用 Electron 客户端，且有完整的版本台账：main.py:127 的统计中间件按 X-PMS-Client/X-PMS-Device/X-PMS-User 请求头 upsert 到 desktop_clients（models.py:1079-1089，60 秒节流），desktop_router.py:24 的 GET /api/admin/desktop-clients 直接给出在线版本分布。这意味着灰度期你能随时回答"现在线上跑着几个版本、谁还在旧版"——这个能力在多数客户现场是没有的，要格外珍惜。

抓手三：强制最低版本。desktop/version.json 的 min_version 字段 + desktop/main.js:141 的 checkForceUpdate()：客户端启动时拉 version.json，低于 min_version 只给"立即更新"一条路。当前仓库里 package.json:3 是 1.0.22，version.json 的 min_version 是 0.0.1（即不强制）。如果 Agent 出了必须立刻停用的问题，抬 min_version 是最快的"全员下线旧行为"手段，比等所有人自愿更新快一个数量级。desktop/main.js:135-147 还做了 5s 超时 + 拉取失败视为不强制，服务器挂了不会把所有人锁在启动页——这个降级方向是对的。

7.3.4 回滚：什么条件下退，怎么退

本项目的发版链路已经把"失败自动回滚"做进去了，这是巨大的现成资产。ops/upgrade.sh 的流程是：备份数据库（:30-31，跳过 uploads 卷避免每次发版 tar 几百 MB）→ 拉代码 → 重建 → 等 60s 起来（:59，不起来就 rollback.sh --to $OLD_COMMIT，:64-65）→ 跑完整 health-check.sh --quiet（:72）→ 不过就回滚（:76-77）。退出码分三档：0=成功、1=失败但已回滚、2=失败且回滚也失败（:9）。本地一条 bash ops/release.sh 通过 SSH 触发（ops/release.sh），失败线上仍是旧版。

但这套东西对 Agent 的失败模式是失明的。health-check.sh 检查的是容器状态、pg_isready、/api/health、磁盘、内存、DB 大小、备份新鲜度、近 1h 错误日志数（:112-116，>50 条判 fail）。Agent 答错、Agent 越权、Agent 成本翻十倍，这些全部不触发任何一项——接口是 200，日志是干净的。所以 Agent 需要一套独立于发版健康检查的回退判据：

级别触发条件动作耗时
立即回退任何一条权限类报错（用户说"我看到了不该看的"）①立刻把 agent 菜单从所有非 admin 账号摘掉（一条 UPDATE）②ops/rollback.sh --to <上一版> ③查 agent_chat_logs 圈定受影响的问答范围并书面告知菜单摘除 < 1 分钟
立即回退发现 Agent 绕过了内控（如职责分离）同上 + 立刻停用所有卡片类型< 1 分钟
当天处理降级比例 > 30%（LLM 供应商不稳）不回退代码——降级路径本来就是可用的（:957-967）；改配置切备用 base_url/模型改配置即时生效（:764 每请求实时读库）
当天处理单日成本 > 预算 3 倍切小模型 或 临时收窄灰度名单同上
观察事实类报错（数字对不上）先复现（用 trace_id 查 tool_calls），确认是口径 bug 还是幻觉，再决定改代码还是改 prompt不阻塞
回退的第一手段不是回滚代码，是关菜单

rollback.sh 要 git checkout + docker compose up -d --build，几分钟起步，且会顺带回退这一版里所有与 Agent 无关的业务修复。而"把 agent 菜单摘掉"是一条 SQL，秒级，只影响 Agent。灰度设计的核心价值就是让"停掉这个功能"和"回滚这次发版"解耦。这条经验在任何客户现场都成立：上线一个新 Agent 之前，先确保你有一个不需要发版就能关掉它的开关。

7.4.2 agent_chat_logs 现在缺什么

现状（models.py:1108-1122）记了：user_id / username（快照，改名删号后仍可查）/ question / answer（各截断 5000，:892）/ tools_used / via / model / duration_ms / created_at。写入在 _log_chat（:909-926），全 try/except 包裹、失败只 warning——"审计是旁路"这个设计是对的，保持不动。

照着 7.4.1 的表逐条对，缺的是四类：①成本类（token、金额）——所以今天无法回答"这个月花了多少钱"；②工具入参——只知道调了 balance_due，不知道查的是谁、返回了几行，出了越权事故无法圈定影响范围；③轮次——4 轮被压成一行，无法诊断"模型在打转"；④卡片动作——L3 之后最关键的一项，现在完全没有。

第五章 5.5 已经给出了扩列方案（trace_id / prompt_tokens / completion_tokens / cost_cents / rounds / tool_calls / cards_emitted + 新表 agent_card_actions）。这里补三条运营侧的实现要点：

  • cost_cents 必须按"当时的单价"落库，不能只存 token 数事后乘。单价会变、会换供应商、会有阶梯折扣。存 token 数事后算，等于把历史成本变成一个永远算不准的东西。
  • tool_calls 里的 args 落库前要过脱敏白名单。project_status 的 code 参数可以存，但工具一旦扩展到带客户名、身份证号的场景，入参本身就是敏感数据——而 agent_chat_logs 是 admin/manager 可分页查询的（:970-996）。别在补审计的时候造出一个新的泄露面。
  • 所有新列可空，老行不迁移。AgentChatLog 的注释里写了"表由 Base.metadata.create_all 自动创建，无需迁移脚本"（models.py:1111），这套模式对加可空列同样成立。历史数据算不出成本，这是可以接受的；为了历史数据去写迁移脚本回填一个猜出来的价格，才是真的错。

扩列之外还有一条路：新旧循环并存期该建新表 agent_sessions 而不是继续往这张表上堆列，理由与两张表的分工见第十二章 12.2；这张表本身既是审计资产也是一份泄密面（全公司问答全文的汇聚点），单独的处置见 9.7。

7.4.3 把它变成一个能回答的问题

指标躺在表里不算可观测。可观测的标准是：老板问"AI 助手这个月花了多少钱、谁在用、问得最多的是什么"，你能在 30 秒内给出答案，而不是"我查一下"。

#失败模式症状（用户/监控看到什么）根因处置

7.6　用户培训与预期管理

7.6.1 用他们的语言解释能力边界

不要说"它是一个基于工具调用的只读数据 Agent，支持 7 个数据域，做了行级权限继承"。业务同事对这句话的每一个词都没有感觉。

本项目实际有效的说法是这样的：

给业务同事的三句话

①「它只是帮你把几个页面的东西一次说完，它看到的和你自己点进去看到的完全一样。」——这句话同时解释了价值（省点击）和边界（不越权），而且它必须是真的，所以第五章那个 P0 越权不修完，这句话就不能说。
②「它只会看，不会动。要改数据，还是你自己点。」——L1/L2 阶段的完整边界。等 L3 上线后改成"它会把该你批的事整理成一张卡递给你，但按钮还是你自己按，按下去走的还是原来那套流程和审批"。
③「它算错了不丢人，你告诉我，我一晚上就能改。你不说，它就一直错。」——这句是最重要的，它建立的是纠错回路而不是权威感。

反过来，有几种说法绝对不能用：不能说"它很智能"（下次它蠢的时候你就没法解释了）；不能说"它是 AI，偶尔会出错很正常"（这是在给自己的 bug 找借口，且会让用户对所有回答都不信任）；不能说"你问的方式不对"（问的方式永远是对的，是系统没理解）。

7.6.2 首次使用的引导

本项目的现有设计已经踩在正确的方向上，只是还没被当成"引导"来经营：

  • 首屏欢迎语（AgentView.vue:33-41）直接列出四类能问的问题，并给了"TH-2501 进度"这样的可照抄格式——给格式比给描述有用十倍。
  • 快捷问题 chips（AgentView.vue:18 的 QUICK_QUESTIONS = ['今日晨报','采购未到货','尾款到期','逾期任务']，:207-212 渲染）。这是最好的引导载体：用户不需要想"我能问什么"，点一下就有结果。
  • 追问建议 chips（:231-236），内容来自后端 _suggestions_for（:347-359），按实际调用的工具映射（_TOOL_SUGGESTIONS，:322-330），且按用户权限过滤——无权的工具对应的建议不显示（:351）。这个"不给你看你点不了的东西"的细节很对，避免了"点了才发现没权限"的挫败。
  • 数据来源标签（sources，:955）。告诉用户这个数字是从哪个查询来的，这是建立信任最便宜的手段。

要补的两件事：

① 快捷问题应该按角色不同。现在 QUICK_QUESTIONS 是前端写死的四条，一个仓库管理员点进来，四条里有三条他一点就被拒（E12 已经证明会命中 _deny）。第一次使用就连吃三个"你无权"，这个用户基本就流失了。改法：把首屏 chips 也走 _allowed_tools 过滤，和追问建议用同一套逻辑——后端已经有 _SUGGESTION_TOOL 映射（:334-344），前端只需要在初始化时请求一次。

② 第一次进入弹一个 30 秒的引导。三张卡：能做什么（照抄欢迎语）/ 不能做什么（不能改数据、看不到别人的、有些模块还没接）/ 答错了怎么办（指向反馈入口）。第三张最重要，而且是最常被忘掉的。

7.6.3 「它答错了」怎么处理：把纠错做成回路，而不是投诉

这是整章里最软但最决定成败的一节。用户第一次发现 Agent 答错时，只有两条路：要么他告诉你，要么他默默把这个功能划掉。而默认路径是后者——因为"跟系统较真"在他的工作里没有任何收益。你要做的就是把前者的成本降到几乎为零，并让反馈这个动作有明确的正反馈。

本项目的现成资产可以直接复用，几乎不需要新建东西：

  1. 反馈入口已有：user_feedback 全流程已跑通——提交（user_feedback_router.py:49）、管理层列表与统计（:86）、回复（:155）。
  2. 自动通知已有：回复时 fb.reply_read = False（:174）触发提出人下次登录右下角弹窗（my_unread_replies，:191），同时 push_message 双通道推送——站内消息 + 企微，绑了企微即微信可达（:179-183）。
  3. 只需新增一件事：在每条 AI 回答下面加一个「答得不对」按钮，点了以后预填一条反馈，内容 = 用户原问题 + AI 回答 + trace_id，用户只需要补一句"应该是 13 条不是 12 条"就能提交。把纠错成本从"打开反馈页面重新描述一遍"降到"点一下再打十个字"，这一个改动带来的纠错量差距是数量级的。

回复要短。这是用户 2026-08-01 明确提的要求，也确实是对的：两三句说完改了什么、在哪看、客户端版本，不写小作文。举个具体例子：

反例（没人会读完）：
  感谢您的反馈！经排查，该问题是由于 tool_po_overdue_by_supplier 函数在
  聚合时使用了已截断的 Top20 明细数据，而 item_total 字段取自全量 count，
  导致两个数字口径不一致。我们已在 agent_router.py 中修复该逻辑，将聚合
  改为在全量数据上进行……

正例：
  供应商汇总的总条数算错了，已修好，现在和明细能对上。
  重新问一次「哪个供应商拖期」即可。客户端 1.0.23。

三句话分别回答了用户真正关心的三个问题：是不是我看错了（不是，确实错了）/ 现在能用了吗（能）/ 我要不要做什么（重问一次，顺便看看版本对不对）。技术细节一个字都不需要——它对用户没有信息量，只会让人觉得在被敷衍。

纠错回路的健康标志

不是"纠错次数少"，是"纠错次数在下降，且提纠错的人数在上升"。前者说明质量在提高，后者说明信任在建立。如果纠错次数是 0，最可能的解释不是它全对了，是没人在用——这时候去看 7.4.1 的 DAU，通常能验证。

本项目还有一个特别的优势：几十人的规模、真实在用、有活跃的反馈闭环，意味着纠错回路的延迟可以做到"当天"。这在大客户现场是奢侈品（那里一个 bug 从发现到修复要过三道流程）。要珍惜这个速度——它是小团队交付 Agent 最大的结构性优势，用户体感上"我说了它就改"带来的信任，比任何准确率数字都强。

最后一句：上线不是终点，是可观测性开始产生价值的时点

Agent 项目和传统项目最大的运营差别在于：传统系统上线后趋于稳定，Agent 系统上线后才开始暴露真实分布。用户会用你完全没想到的方式提问，会问你没建工具的域，会在你以为很清楚的地方误解。这些信息在上线前一天都不存在，在上线后第一周会成吨涌来。
所以第七章真正想说的是：不要把上线当成交付的结束，把它当成评估集开始持续生长的起点。第一版评估集 30 条是你猜的，三个月后它会有 100 条，其中 70 条来自真实用户——那 70 条才是这个系统真正的验收标准。而 FDE 与普通开发最大的分野，就是他知道要去把那 70 条捡回来。
