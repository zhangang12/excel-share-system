第二章　测绘：把 ERP 的业务域、数据枢纽和权限模型摸清楚

这一章讲的是写第一行 Agent 代码之前必须做完的事。FDE 进客户现场最容易犯的错，是拿着 demo 里的 「连上库就能问数」直接开工——结果要么工具查不到数，要么查到了不该查的。这两种失败都不是模型能力问题， 是测绘没做。

2.1　为什么必须先测绘：Agent 的能力边界 = 数据边界 ∩ 权限边界

一句话原则：Agent 能回答的问题集合，等于「系统里真的存了这个事实」和「问的人本来就有权看这个事实」的交集。 这两个集合都不在你脑子里，只在客户的代码和数据里。测绘就是把这两个集合画出来。

交集的两边各自失守，症状完全不同，代价也完全不同：

数据边界失守 = 没用（可修复） 用户问「这批货到仓库了吗」，而系统里根本没有单一的「到仓」状态位，只有采购明细上的 arrival_date 和仓库流水两处半重叠的记录。这类失败尴尬但不致命，改工具就行。
权限边界失守 = 事故（不可撤回） 本项目就发生了：backend/app/routers/agent_router.py 的 7 个数据工具里，6 个的函数签名里根本没有用户对象， 因而不可能做行级过滤——这是签名层面的必然，不是「忘了写 if」。 一个普通销售员问一句「尾款」，拿到的是全公司客户名 + 尾款金额 + 归属销售； 而他打开销售部页面时，sales_router.py:239-240 会把查询收窄成 sales_uid == 本人。 逐工具对照与根因分析见 3.1，这里只需要它证明一件事：数据泄露没有回滚按钮，所以边界必须在动手前就摸清楚。

这条教训可以直接迁移：任何「绕过现有页面直接读库」的 AI 通道，默认就是一条越权通道， 除非你能逐条证明它复现了页面的过滤。而要证明，你得先知道页面到底过滤了什么——这就是测绘。

2.2　业务域地图：55 张表怎么分

backend/app/models.py 共 55 个 ORM 模型（grep -c __tablename__ = 55）， 按业务归属可以切成 13 个域。分域不是为了好看，是为了后面每个域单独回答三个问题： 谁能看 / 敏感到什么程度 / Agent 该不该碰。

records.values 是 Agent 的天然边界 models.py:171-183：Record.values 是一个 JSON 列，形状为 { str(field_id): value }， 字段定义在 fields 表里、按 datasheet_id 归属（models.py:160）， 而 datasheets 又按 project_id 归属（models.py:140）。 这意味着：同一个业务语义的列（比如「数量」），在 100 个项目里是 100 个不同的 field_id。 虽然 sheet_templates.py:18 的 SHEET_TEMPLATES 固定了五张模板表 （钣金装配 / 标准件清单 / 外协加工 / 不锈钢原料下料单 / 激光件清单）让列名可预期，但列名到 id 的映射是逐项目的， 且存量项目还留着旧版形态（sheet_templates.py:109 LEGACY_SHEET_TEMPLATES）。 结论：EAV 层不适合做跨项目聚合问数。Agent 可以回答「TH-2501 的标准件清单有多少行」， 不该去回答「今年所有项目一共采购了多少个 M8 螺栓」——后者的正确来源是 purchase_items，不是 records。 这条边界是测绘出来的，不是拍脑袋定的。

一级枢纽 projects.id：全库有 11 处硬外键指向它 （models.py 第 127、140、232、265、284、329、364、410、426、447、570 行）， 分别是 project_members、datasheets、dept_orders、produce_group_tasks、sales_ledger、shipments、 attachments、wh_txns、aftersales、feedbacks、revision_requests。只要 join 走 project_id，就是可靠的。

二级枢纽是全系统最脆的一根绳：projects.code ↔ purchase_items.project_code models.py:618：project_code: Mapped[Optional[str]] = mapped_column(String(64), index=True) ——只是一个带索引的字符串列，没有外键约束、没有大小写规范化、允许为 NULL。 它的写入口至少三处：手工新建采购单（purchase_mgmt_router.py:1317）、 按项目清单生成（purchase_mgmt_router.py:1151）、 Excel 批量导入（purchase_mgmt_router.py:1548，值直接来自表格里的「订单编号」单元格）。 三个入口都不校验这个值是不是真实存在的 projects.code。
后果一：项目成本汇总会静默漏数。reports_router.py:449-461 的成本第二腿是按 project_code 分组求和的，配到项目时只做了 .strip()（reports_router.py:489）， 没有大小写归一。而 agent_router.py:249-251 查项目时反倒做了 code.upper() 兜底重试—— 同一个仓库里两处对大小写的假设不一致，这本身就是测绘该抓出来的信号。
后果二：确实有一批明细 project_code 是空的。purchase_mgmt_router.py:1866-1888 写得很直白：这些行来自项目清单（有 source_sheet_id）但下单时没带项目号， 页面上显示的项目编号是临时回溯出来的、只改了返回对象、没有落库。 于是它们在页面上看着有项目，在成本汇总的 GROUP BY project_code 里却不存在。
系统自己知道这件事：reports_router.py:588-598 的「孤儿采购」清单专门捞 project_code 为空、或既不是项目编号也不是字典里非项目订单号的明细； reports_router.py:611-643 还做了采购口径 vs 仓库口径的双口径对账。 Agent 回答任何涉及项目成本的问题，必须带口径声明：说清楚「未归集的孤儿采购 N 笔、金额 X」， 否则给出的毛利数就是一个系统性偏高、且无人知道偏多少的数。

三级枢纽三个：purchase_items.po_no（models.py:611，同一供应商多零件行共享的分组键， 同样无唯一约束）；wh_txns.purchase_item_id（models.py:406，采购↔仓库之间唯一的硬连接， 后面的防双算逻辑全靠它）；以及 users.id——七类行级规则毫无例外全挂在它上面， 所以「当前用户是谁」是整个测绘工作里唯一不能出错的输入。

2.4　成本归集主干：为什么口径必须复用，不能让 Agent 自己拼

reports_router.py:409-412 把口径写在注释里，一字不差：毛利 = 合同额 − 材料领料成本(加权均价) − 直发/外协采购 − 安装/售后费用 − 物料运输费(我方)，不含人工，是「材料边际贡献」口径。四条腿的取数分别是：

腿来源取数条件（reports_router.py）归集键
收入sales_ledger.amount一项目一行（:481-487）project_id
1 材料wh_txns 出库 × 加权均价direction=out 且 is_reversal=False 且 reversed=False（:434-447）project_id（硬）
2 直发/外协purchase_items.received_amountreceived_amount>0 且 id NOT IN (有 wh_txn 的)（:450-456）project_code（软）
3 售后aftersales.coststatus='approved'（:464-467）project_id（硬）
4 运费shipments.freight_costfreight_payer='我方' 或 NULL（:471-475）project_id（硬）

防双算的机制是「两腿互斥」：收货时生成了 wh_txn 的采购明细，成本走仓库腿（领料 × 加权均价）； 没经仓库过账的（直发到工地、外协加工费）才按 project_code 走采购腿。互斥靠的就是那句 PurchaseItem.id.not_in(linked)（reports_router.py:450、455）。 同样的防双算思路在资金面板里再出现一次：reports_router.py:829「已进『已批未付』请款单的明细， 13 周排程从应付里剔除」，否则同一笔钱会在 W0 流出和到期排程里各算一遍。

这就是「语义层必须复用」的全部理由 上面这些不是数学，是业务裁决：为什么排除冲红对？因为冲红是撤销不是负成本。为什么售后只算已审批？ 因为登记态还可能被驳。为什么运费只算「我方」？因为客户承担的运费不进我们成本。 这些裁决是业务方一条条拍板过的，写在代码里，不写在任何模型能读到的地方。 让 Agent 自己拼 SQL 算毛利，它会拼出一个语法正确、数字漂亮、业务上错的答案——而且错得很难发现， 因为它和财务手算的差额永远只有几个点。所以本项目 L3 设计里，凡涉及资金面板 / 13 周现金流 / 项目毛利榜， Agent 工具一律转调 reports_router 现成函数，一行 SQL 都不新写。 迁移提示：换个客户，这个「语义层」可能长成 dbt 模型、BI 里的度量值、或者一堆 Excel 公式。 形态不重要，找到它、复用它，而不是重新实现它。 还要记住第二件事：口径不是常量，它会漂。本项目 #332（balance 一列两义）就是活证据—— 测绘只是拿到了「今天的口径」，它变了之后 AI 侧感知不到， 漂移源清点、「口径变更 → 评估用例」对照表、以及怎么让变更自动通知到 Agent 维护者，见 11.5。

2.5　权限模型测绘（本章重点）

本项目的权限不是一层，是五层，层与层之间不是包含关系而是交叉关系。 测绘时必须逐层记录，混成一句「按角色控制」就等于没测。

第一层：菜单（一级菜单，按账号配置）

权威函数是 menus.py:142 user_menu_keys()。口径是 2026-07-21 起改的： 不按角色推，按账号配置——admin/manager 全量可见，其余账号读 User.menus 这个 JSON 列（models.py:61），NULL 时兜底 DEFAULT_ACCOUNT_MENUS（menus.py:58）。 原来的角色菜单矩阵已废除，ROLE_DEFAULT_MENUS（menus.py:64）只在建号和存量迁移时取一次默认值。 业务菜单 18 个 key（menus.py:19 MENU_DEFS），管理组菜单 9 个 key （menus.py:42 ADMIN_MENU_DEFS）。注意 agent 这个 key 是 user_menu_keys 里无条件追加的（menus.py:154）——AI 助手菜单对所有登录用户开放。

陷阱一：hidden_tabs（二级 tab 权限）只在前端隐藏，后端零处强制 menus.py:99 的 TAB_REGISTRY 注册了 4 个菜单下的二级 tab（采购管理 6 个、财务部 11 个、 人事部 2 个、仓库 9 个），管理端可以按账号勾选隐藏，值存进 User.hidden_tabs（models.py:54）。 但全仓库 grep 下来，这个字段的唯一消费点是前端：frontend/src/stores/auth.ts:39-43 的 tabHidden()；后端只在 auth_router.py:39 原样吐给前端、在 admin_router.py:213 存回去，没有任何一个 API 端点校验它。 换句话说：把出纳的「付款」tab 藏起来，只是让按钮不渲染；他手里那张 token 直接 curl 付款端点，照样过。
对 Agent 的直接含义：hidden_tabs 不能作为工具授权的依据。 如果按它来门控，等于把一个前端渲染开关当成了安全边界——本身不安全，还会给人「已经管住了」的错觉。
陷阱二（测绘才发现的）：菜单和 API 授权是两套坐标系，而 Agent 挂错了那一套 user_menu_keys 在后端只有三个调用点：auth_router.py:128（吐菜单给前端）、 admin_router.py:278（管理端配置）、以及 agent_router.py:412 / 429。 没有任何一个业务端点用菜单做授权——业务端点一律用 require_roles(...)， 比如 purchase_mgmt_router.py:23 的 _PURCHASE_ROLES、 hr_router.py:29 的 _HR。 于是 Agent 的 _allowed_tools（agent_router.py:409-424）建立在一根与真实 API 授权不同源的轴上， 两个方向都会跑偏：给某账号配了 purchase_mgmt 菜单但他的角色不在 _PURCHASE_ROLES 里， Agent 放行、页面 403；反过来，一个 finance 角色的账号如果没配 purchase_mgmt 菜单， 页面能进采购对账、Agent 却拒答。
这正是第三章原则一「Agent 工具只调现有 router 函数并传真实 current」的实证依据： 只要工具复用业务端点，授权轴自动同源，这类偏差在结构上就不会出现。

第二层：角色

seed.py:14 定义 25 个角色。测绘要点四条： ① 多角色取并集——models.py:76 role_codes 把锚点 role 和 roles 关联表合并成一个 set， has_role（models.py:95）是「任一命中即真」； ② finance_lead ⊇ finance 是全系统唯一的角色包含关系， 实现就一行：models.py:83 发现 finance_lead 就自动把 finance 塞进集合， 一处生效、菜单/端点/前端 hasRole 全跟着变； ③ require_roles（deps.py:52）隐式把 admin/manager 加进白名单—— 所以看到 Depends(require_roles("finance")) 要读成「finance ∪ admin ∪ manager」， 甚至 require_roles() 不带参数（oa_router.py:304、535）意思是「仅 admin/manager」； ④ 有一个 viewer 角色被 deps.py:45 require_not_viewer 引用，但不在 seed 的 25 个里—— 这种「代码里有、种子里没有」的悬空引用，是测绘时该记下来问客户的典型条目。

要记住的不是「王芹」这个人，是它的形状：一个角色的加入解除了另一个角色的限制。 只要有人在第二个地方「自己再写一遍角色判断」，几乎必然重现它——因为「财务当然能看全部账」在直觉上太顺了。 本项目的防线是把判定收敛成一个函数全域复用；Agent 层的防线是根本不写第二遍，直接调业务函数。
迁移提示：进任何客户系统都要专门找一遍这种「角色叠加改变可见范围」的规则，并当面向业务确认方向 （放宽还是维持收紧）。这类规则永远不在权限文档里，只在事故复盘里。

第四层：字段级

field_permissions 表按 (field_id, role_id) 记 can_view/can_edit （models.py:206-214）。两条语义必须记准： 多角色取并集（field_perm_router.py:124-127，任一角色允许即允许）、 缺配置 = 默认放行（field_perm_router.py:120-122：只要有一个角色没配这个字段， 该角色默认全放行，并集自然就是全放行；写侧同理，datasheets_router.py:363-364 「仅当所有角色都配了且都不允许编辑才拦」）。 更要命的是只有 can_edit 在服务端强制——读侧的 list_fields（datasheets_router.py:170-184）原样返回全部字段， can_view 只通过 GET /me/datasheet/{did}（field_perm_router.py:132） 下发给前端做渲染遮蔽。字段级「可见性」和 hidden_tabs 一样，是 UI 约定不是安全边界。

第五层（容易漏测）：记录级/关系级约束

还有一类规则既不是角色也不是行级，而是「当前用户相对于这条记录的历史角色」——内控职责分离。 purchase_mgmt_router.py:2561「不能审批自己提交的请款单」、 :2711-2712「审批人不能给自己审过的单付款」， 而且注释明写对管理层同样生效、不留后门（:2559）。 数据模型为此专门拆了 rejected_by / reject_stage 两个字段 （models.py:754-760），就是为了不让出纳驳回覆盖掉真正的审批人、把职责分离判错人。 对 L3 卡片的直接含义：Agent 生成「去付这笔款」的卡片时，收件人可能恰好是那笔单的审批人—— 卡片必须由服务端判定后再决定发不发，不能只看「他是 finance 角色」。

2.6　测绘产出物：域 × 可见性 × 敏感度矩阵

FDE 交付给客户签字确认的，不该是一份架构图，而是下面这张表。它的作用是把「Agent 能碰什么」 变成一个业务方看得懂、能逐行说 yes/no 的清单。本项目的填法（节选）：

四条填表规则，是从本项目踩出来的：

  1. 敏感级按「泄露后果」定，不按字段名定。供应商银行账号看着像配置数据，实际是付款诈骗的直接素材。
  2. JSON 自由列一律降级处理。records.values / projects.extra / purchase_items.custom_values / oa_requests.detail 都是自由列， 字段级权限对它们完全无效（权限挂在 field_id 上，自由列里的键不是 field）。
  3. 返回上限必须写进矩阵，而且要说清它是红线不是偷懒。系统有独立的导出审批闸门 （deps.py:75 ensure_can_export + export_requests 表）， 开启后非管理层导出要走审批。Agent 一次吐 200 行明细，等于给所有人开了一条绕过导出审批的后门。 所以工具里那些 rows[:20]（agent_router.py:93、118、165、196）是合规边界。
  4. 把「已知口径缺陷」也写进矩阵。比如 tool_po_overdue_by_supplier（agent_router.py:121-135）在已截断成 Top-20 的明细上做供应商聚合， 返回的 item_total 却取的是全量 count——用户会看到「共 137 条」下面挂着一份只覆盖 20 条的供应商榜。 客户签字前就该知道这件事，而不是上线三个月后自己发现。

2.7　可迁移方法论：在陌生系统里怎么快速测绘权限

换个客户，表名、框架、语言全变，但测绘的动作是固定的四步。核心信条只有一句： 文档说的不算，代码说的算，实测说的最算。

  1. 先找列表接口，只读它的 where 子句。行级规则的真相 100% 在列表查询里。 本项目找 _all_view / _buyer_restricted / restricted_dir_pids 这类判定函数， 再顺着调用点走一遍——一个函数被调 30 次，说明它是硬规则；只被调 1 次，说明其余 29 个端点大概率漏了。 换成 Django 就是找 get_queryset() 覆写，Rails 找 scope / Pundit policy， Spring 找 @PreAuthorize 和 MyBatis XML 里的动态 where，多租户 SaaS 找 tenant_id 注入点， Postgres 重度用户还要查 pg_policies 有没有 RLS。
  2. 找依赖注入/装饰器，做一张「端点 × 守卫」清单。本项目是 Depends(require_roles(...))、require_admin_or_manager、require_can_view_detail。 重点抓没有守卫的端点：logistics_router.py:95 的发货看板用的是裸 get_current_user，docstring 写着「其它角色只读不限制——数据无敏感金额」（:98）。 这是有意为之，但你必须把它作为一条已知决策记下来，因为它意味着 Agent 拿物流数据时没有域门控可继承。
  3. 反向索引所有 has_role 调用点。用一个角色名 grep 全仓库，得到的定义比角色表里的中文名准得多。 本项目 grep finance 会同时命中 models.py:83 的自动注入、 oa_router.py:357 的 OA 全通、purchase_mgmt_router.py:23 的采购对账放行—— 三处含义各不相同，汇总起来才是它的真实权力半径。
  4. 实测对拍。拿两个真实账号（一个受限岗位、一个主管），同一个端点、同样的参数、不同的 token， diff 返回的 id 集合。这一步能抓出前三步全部漏掉的东西：前端隐藏但后端敞开（hidden_tabs）、 读侧不过滤但写侧过滤（字段级 can_view）、以及最常见的——文档写了但代码没实现。 本项目根目录有一份《权限矩阵.md》，menus.py 的注释直接标注它记录的是历史口径， 运行时早已换成按账号配置。这就是「文档不算数」的现场证据
交付形态：测绘文档该长什么样 给客户的测绘产出物建议只有三件：① 2.2 的业务域表（含每表真实 count(*)）； ② 2.3 的枢纽图，并把所有软关联用红色标出、附上「这条 join 会漏多少数」的实测数字； ③ 2.6 的域 × 可见性 × 敏感度矩阵，逐行留签字位。 前两张是你的工作底稿，第三张是责任边界，唯一需要业务方逐行签字。 签完之后 Agent 的工具清单就能从它机械推导：标「禁」的域不出现工具；标了上限的，工具里硬编码上限； 带口径缺陷的，返回值里必须携带口径声明字段。
做完测绘你会发现，真正难的从来不是让模型学会调工具，而是在动手之前就说清楚它到底被允许知道什么。 这件事没有捷径，也正是 FDE 的价值所在。
