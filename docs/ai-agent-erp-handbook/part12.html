第十二章　演进与终止：灰度共存、数据迁移，以及什么时候该承认它不值得做

前十一章都在回答「怎么把它做出来、做对、做稳」。这一章回答两个几乎没人写进手册的问题：怎么把新一代和上一代同时挂在生产上而不出事，以及什么时候该主动停。第二个问题是本手册的收口，也是 FDE 这个职业里最能分出资深与不资深的一条线。

本章的核心结论（先说结果）

第一，L1 → L3 没有「切换日」。生产上会有一段时间两条代码路径同时活着，而这段时间里最贵的事故不是崩溃，是分批越权——两批用户走不同的循环，新路径的行级过滤和老路径差一行，你就同时拥有「一部分人看得见不该看的」和「日志里看不出来」这两件事。

第二，Agent 项目正确的结局有两个：扩大，或者体面地停。「不温不火地留着」是最差的第三种——它持续消耗维护预算、持续占着一个菜单位、持续给业务方一个「公司在搞 AI」的错觉，却没有任何一个岗位真的因为它少干活。本章给出把第三种结局挤掉的判据。

12.1　为什么必须共存，而不是「上线新版、下线旧版」

本项目有三个结构性事实，决定了灰度共存不是可选项：

  1. 老桌面客户端会一直在。AGENTS.md:66 写死了一条铁律：「API 只增不改（老客户端长期并存），破坏性变更只能走 --min-version 强制升级流程」。强制升级的开关在 desktop/version.json:2 的 min_version，客户端启动时拉取比对（desktop/main.js:141-142）。也就是说，只要你不想让几十号人在同一个上午被强制更新客户端，POST /api/agent/chat 的请求体和响应体形状就不能变——现有响应是 {reply, fallback, sources, suggestions}（agent_router.py:954-956），L3 的卡片只能新增字段挂上去，老客户端读不到就当没有。
  2. 4 个 worker 各跑各的。生产是 uvicorn --workers 4，进程之间不共享内存。任何「灰度开关」如果做成进程内变量或环境变量，你就得重启才能改；而 Agent 的故障是「答错」不是「崩溃」，你需要的是秒级拉闸，不是十分钟的发版窗口。
  3. Agent 的对错没有健康检查。ops/upgrade.sh 的自动回滚（ops/upgrade.sh:64-65 与 :76-77）依赖 ops/health-check.sh，而健康检查只知道进程活没活、接口 200 没 200。一个把采购逾期数字算多了 3 条的 Agent，在这套体系里永远是健康的。所以回滚必须有一条不依赖健康检查的人工通道。

迁移提示：这三条在别的客户身上会换形态——老客户端可能是 App Store 审核周期、可能是嵌在钉钉里的 H5 缓存、可能是集团统一门户的 iframe；多进程可能变成多 Pod；健康检查可能是 Prometheus。但「有一批用不上新版的旧客户端」「开关必须跨进程即时生效」「正确性没有自动探针」这三件事，在企业内网系统里几乎必然同时成立。

12.2　存量审计表怎么办：保留 agent_chat_logs，新增 agent_sessions

12.2.1 现有表的能力边界

agent_chat_logs（backend/app/models.py:1108-1122）一次问答一行，字段是 user_id / username / question / answer（各截断 5000，agent_router.py:892 的 _LOG_TEXT_MAX） / tools_used / via / model / duration_ms / created_at。写入在 _log_chat（agent_router.py:909-927），整段包在 try/except 里——审计是旁路，写失败只记 log 不炸聊天。这个设计本身是对的，不要动它。

但它有四个说不出口的东西，而这四个恰好是第 12.5 节要用来做扩大判据的原料：

问不出来的问题缺什么为什么这次必须补
这次问答花了多少钱prompt/completion token、单价没有成本就无法算 ROI，无法回答「扩大投入值不值」
模型调工具时传了什么参数工具入参（现在只有工具名，models.py:1118）越权复盘时「他问了什么」不够，要知道「工具被喂了哪个 project_code」
绕了几轮才收敛轮次（循环上限 4，agent_router.py:522）轮次分布是「工具划分是否合理」的最灵敏指标
这是一次对话的第几句会话 ID没有会话就算不出「重复提问率」和「追问深度」——第 12.5 节两个核心信号全废

12.2.2 两张表的关系：新表承载会话，老表一行不改

正确做法不是把老表加宽到十几列，而是加一张会话表，老表只加一列外键。理由很实在：GET /api/agent/chat-logs（agent_router.py:970-995）的响应字段是逐个手写出来的，老桌面客户端的审计页按这个形状渲染；加列不动老字段 = 老客户端零感知，符合 AGENTS.md:66。

agent_sessions（新表，一次会话一行）
  id / user_id / username（快照，同老表口径）
  loop_path      "legacy" | "agentscope"   ← 灰度期唯一的真相来源
  model / rounds / prompt_tokens / completion_tokens / cost_cents
  tool_calls     JSON: [{name, args, ms, rows}]  ← 带入参，越权复盘用
  card_type / card_state  （L3：proposed/confirmed/expired/rejected）
  started_at / ended_at

agent_chat_logs（老表，只加一列）
  session_id  INTEGER NULL   ← 存量行永远是 NULL，不回填、不需要回填

「不回填」是有意的。存量行没有会话概念，硬造一个会返回假数据；而所有以会话为单位的统计天然应该只在「有 session_id 的那部分」上算——这等于自动给你划出了「新旧两个时代」的分界线，比任何版本标记都可靠。

12.2.3 建表方式：本项目的具体路径

本项目没有 Alembic。schema 由两段代码负责，分工写在 data_migration.py:17 的注释里：「create_all 只建新表、不给已有表加列」。

要做的事走哪条路证据
新增 agent_sessions 表在 models.py 里写一个 class 就完了，启动自动建backend/app/main.py:82 Base.metadata.create_all；models.py:1111 对 AgentChatLog 原话「表由 Base.metadata.create_all 自动创建，无需迁移脚本」
给 agent_chat_logs 加 session_id必须进 _NEW_COLUMNS 字典，走 ALTER TABLE ADD COLUMNbackend/app/data_migration.py:19 起的 _NEW_COLUMNS；执行体 ensure_schema_columns（data_migration.py:137-157），已存在则跳过，幂等
存量数据口径修正（如给老行打标）run_data_migrations，函数必须幂等data_migration.py:1-5 文件头「所有函数必须幂等」「不做 schema 改动」

还有一个容易踩的坑，本项目已经踩过并修好了：4 个 worker 同时启动会一起判定「列不存在」然后一起 ALTER，后启动的撞 DuplicateColumn 直接退出，外部表现是 nginx 间歇性 502（main.py:68-75 的注释把这个现象描述得很完整）。修法是 Postgres 会话级 advisory lock pg_advisory_lock(872193641)（main.py:76-90）把整段启动串行化。你加新表新列的时候什么都不用做——这把锁已经替你挡住了，但你要知道它在，否则哪天有人「优化启动速度」把它删了，你会在下一次加列时看到 502。

迁移提示：换个客户大概率有 Alembic 或 Flyway，那么上面这套「create_all + 补列字典」直接换成一个 migration 文件。不变的是三条判断：新表 vs 加列走的是不同风险等级；存量行宁可留 NULL 也不要假回填；多实例启动时的 DDL 竞态必须有锁或有单独的迁移 Job。

12.3　两套循环并行：怎么切，以及那个真正危险的点

12.3.1 开关放哪：本仓库已有现成范式

不需要发明。本项目已经有两处「配置存库、每次请求实时读、保存即全局生效」的实现，抄第二个就行：

  • 外网登录闸门：backend/app/gate.py:55-56 的 get_gate_config，读 app_settings 的 gate_enabled / intranet_cidrs，默认开。
  • Agent 的 LLM 配置：agent_router.py:762-773 的 _effective_llm_config，优先级 DB > .env，注释原话「每次请求实时读库（量极小），admin 页面保存后全局立即生效」。

灰度开关就是 app_settings 里再加几个 key，写入口沿用 PUT /api/agent/config 的守卫 _require_admin_only（agent_router.py:788-792，比 require_admin 更严，manager 也 403）。请求级读库让 4 个 worker 天然一致，改完不用重启——这正是 12.1 第 2 条要的秒级拉闸。

agent_loop.mode      = "legacy" | "canary" | "agentscope"   全局挡板
agent_loop.users     = "12,27,31"        白名单 user_id（canary 时生效）
agent_loop.domains   = "purchase_mgmt"   只有这些域的工具走新循环
agent_loop.shadow    = "1"               影子比对开关（见 12.3.3）

12.3.2 三种切流维度，本项目只有一种可用

维度怎么切适用本项目
按用户白名单user_id in agent_loop.usersL3 卡片确认——卡片错了要有人负责，必须是知情的人首选。先放 3 个人：一个采购、一个财务、一个管理层，覆盖三类不同的行级规则
按比例哈希hash(user_id) % 100 < N互联网千万级流量不用。几十人规模里 10% = 3 个人，统计上毫无意义；且必须按 user_id 而非按请求哈希，否则同一个人今天走新路明天走老路，同一句话得到两种答案，信任当场崩塌
按数据域工具名所属域在 agent_loop.domains 内工具本来就按域分组的系统次选、可与白名单叠加。本项目的工具门控本来就是按菜单域写的（agent_router.py:414-423），域是天然的切分边界；采购域问题密度最高（对应扫描器 overdue.py:311）

12.3.3 最危险的点：灰度期的分批越权

一句话风险

灰度期两批用户走两条代码路径。如果新路径的行级过滤与老路径有任何一行差异，你得到的不是「A/B 实验」，是「一部分人被越权、另一部分人没有」——而且因为对照组表现正常，你会更慢地发现它。

这个风险在本项目不是理论。第五章那个 P0 的形状就是：7 个注册工具里只有 tool_project_status（agent_router.py:241）接收 current，其余 6 个签名里根本没有用户对象——agent_router.py:66 的采购工具没有 buyer 过滤（而页面侧 purchase_mgmt_router.py:349 有 _buyer_restricted），agent_router.py:138 的尾款工具没有 sales 过滤（页面侧 sales_router.py:239 有 _all_view），agent_router.py:168 的部门逾期只做到部门级（orders_router 还有 worker_id == me）。你在做 L3 改造时会顺手修这个洞——于是新路径有行级过滤、老路径没有，两条路径对同一个用户返回不同的结果集。这在灰度期是「预期内的差异」，也正因为「预期内」，真正的意外差异会藏在里面看不见。

三条必须同时做的防线：

防线一：门控只有一份，新循环不许自带。现在的门控写在两个地方，且注释明说是双保险：_allowed_tools 决定下发哪些 schema 给模型（agent_router.py:409-424），_run_tool 在执行前再门控一次（agent_router.py:427-472，:517 注释「_run_tool 内仍二次门控，双保险」）。换 AgentScope 时的正确姿势是把这两段原封不动抽成 app/agent/guard.py，新循环只负责「怎么循环」，不负责「能不能看」。守卫必须放在工具包装器的最内层——第六章那五个坑之一——这样无论哪条循环调它，过的都是同一段代码。只要门控出现第二份实现，灰度就已经失败了，剩下的只是什么时候被发现。

防线二：同一份权限断言，跑两遍。本项目已经有这份断言：backend/tests/test_agent_perms.py（160 行）。它构造 warehouse / finance / admin 三个身份，断言 warehouse 用户问「采购未到货」被拒、问「尾款到期」被拒、问非成员项目返回「无权查看该项目」、且 suggestions 被过滤为空。注意它开头设了 AGENT_LLM_API_KEY="" 强制走规则降级路径——也就是说它今天测的是工具层门控，不是 LLM 循环。这反而是好消息：把它参数化成 loop_path in ("legacy", "agentscope") 跑两遍，成本极低，而它断言的东西恰好是灰度期唯一不能有差异的东西。把「两遍全绿」设成灰度开关能不能打开的硬前置。

防线三：影子比对，而且它在本项目是安全的。AGENTS.md:56 的铁律「AI 助手的所有数据工具永远只读 SELECT」有一个很少被提到的红利：同一个请求可以把工具层跑两遍而没有任何副作用。所以灰度期可以开 agent_loop.shadow：用户请求走老路返回，同时用同一个 current 走一遍新路径的工具层（不调 LLM，只调工具），逐行比对结果集，不等就写告警。这一步不需要模型、不花 token、不影响响应（异步旁路），却能在零用户暴露的前提下把「新旧路径行级过滤是否一致」验证到生产真实数据上——而这件事是任何测试库都造不出来的，因为测试库里没有王芹那 200 条真实采购单。

12.3.4 回滚路径：三层，越靠上越该常用

层动作生效时间影响面什么时候用
① 配置级app_settings 里 agent_loop.mode = "legacy"秒级，无需重启，4 worker 同时生效只回退循环实现，功能仍在默认拉闸方式。发现新路径答错、越权、慢，先拉这个再排查
② 菜单级menus.py:154 去掉无条件追加的 | {"agent"}发一次版；用户下次拉 /api/auth/menus 即消失入口消失，后端 /api/agent/chat 仍在线（老客户端不会 404）决定整体停用、或事故期间彻底断人流
③ 版本级ops/release.sh → ops/upgrade.sh：备份 → 拉码 → 重建 → 健康检查 → 失败自动回滚十分钟量级整站只有当 Agent 改动同时破坏了别的模块时才用。不要用整站回滚来解决 Agent 答错

注意 ops/upgrade.sh:9 的退出码约定：0=升级成功 / 1=失败但已回滚 / 2=失败且回滚也失败。只有 2 需要你半夜起床，1 意味着线上还是旧版、是安全的。这条约定值得在任何客户现场复制——它把「发版失败」从一个恐慌事件降级成一条日志。

12.4　兼容约束：API 只增不改，令牌短寿命

12.4.1 契约怎么演进

L3 卡片挂进现有响应的方式只能是加字段：

// 现在（agent_router.py:954-956 / :965-967）
{ reply, fallback, sources, suggestions }

// L3（老客户端读不到 cards，行为完全不变）
{ reply, fallback, sources, suggestions, cards: [...], session_id }

三条不能破的线：不改字段名、不改字段类型、不把可选变必填。ChatIn（agent_router.py:884-887）同理——新增的 loop 之类参数必须可选且有默认。真要做破坏性变更，只有 --min-version 一条路（AGENTS.md:66），代价是全员被迫更新客户端，这是一个需要跟业务负责人商量的动作，不是一次技术决定。

12.4.2 卡片令牌的生命周期：抄 login_gate_codes

L3 的形态是「Agent 出卡片 → 人点确认 → 用人自己的 token 打现有业务端点」，所以卡片令牌不承担鉴权，它承担的是「你确认的还是当初给你看的那张卡吗」。本仓库已经有一个同类物件可以照抄：LoginGateCode（models.py:1093-1104）——code_hash（只存 sha256 不存明文）、pre_token 关联会话、expires_at 10 分钟、used 一次性、重发即作废旧码。卡片令牌把它的字段换个语义即可：

字段作用为什么必须有
facts_hash生成卡片时那批权威事实的哈希确认时后端重新读一遍权威值再算哈希，不等就拒绝——这是第三章「事实源在服务端」在时间维度上的落地
expires_at短寿命（建议 ≤ 15 分钟）卡片描述的是「此刻的」业务状态。放一天再点，卡上金额早就不是账上金额
used一次性防重复提交。业务端点自身的幂等不能替代它，因为两次提交可能是两个不同的合法动作
user_id + card_type绑定人与类型白名单类型白名单在可信前端代码里决定端点（第三章原则③），令牌里再存一份用于服务端交叉校验

迁移提示：如果客户系统里已经有「一次性凭证」的实现（支付确认码、审批链接、二次验证码），一定要复用它而不是新写——不是为了省代码，是为了让安全评审只需要评审一次。本项目 gate.py 那套已经过了一轮真实的安全打磨（限频、只存哈希、重发作废），凭空再写一套只会把水搅浑。

扩大投入的判据必须是「从库里能查出来的数」，不是「大家反映挺好用」。下表左边是信号，右边是本项目今天能不能算——算不出来的那三个，正是 12.2 那张新表存在的理由。

12.6　什么时候该承认它不值得继续做

12.6.1 终止信号清单

信号怎么观测为什么它是终止信号而不是优化信号
用户绕过它　宁可自己翻页面周活长期低位；或高频用户只剩 1-2 个（而且其中一个是你自己）企业内网系统没有增长黑客可做。用户已经知道有这个东西、已经试过、然后选择了不用——这是最终判决，不是冷启动问题
纠错成本高于收益每周花在「为什么它答错了」的排查工时 > 它替所有用户省下的工时Agent 的排查是最贵的一类排查：非确定性、跨模型版本、复现要凑数据。这个比值一旦倒挂，很难靠调优翻回来
每次业务变更都要改一堆工具一个季度内因业务口径变更被迫同步改 Agent 工具 ≥ 3 次说明 Agent 层变成了业务口径的第二副本。参见 #332：balance 一列同时是「合同尾款条款额」和「未收余额」，改口径时不得不加 balance_contract 保可逆（data_migration.py:56）。这类变更在制造业 ERP 里是常态，不是意外
评估集通过率长期上不去L-事实层 < 95%，且连续三轮迭代无改善三轮无改善意味着你已经把 prompt、工具划分、模型都试过了。继续投入是在赌下一代模型，而赌下一代模型不是交付
真正的痛点是数据质量或流程评估集失败案例根因归类，「数据缺失/数据错」占 > 50%本项目现成的例子：projects.code ↔ purchase_items.project_code 是字符串软关联无外键，成本汇总会静默漏数（第一章）。这种情况下 Agent 越准，错得越有说服力

12.6.2 决策树：区分「该停」和「该改方向」

把上面的信号丢进这棵树。大多数看起来像「该停」的情况，其实是「该改方向」——但也确实有几条通向真正的停。

Q1 用户不用它，是因为「答得不对」还是「不需要问」？
   ├─ 答得不对 ────────────────► 改方向：收窄场景 / 接语义层 / 换模型
   └─ 不需要问 ──► Q2

Q2 他不需要问，是因为「页面已经够好」还是「他要的是推送不是问答」？
   ├─ 页面够好 ────────────────► 【停】这块痛点本来就不该给 Agent（第一章）
   └─ 要的是推送 ──────────────► 改方向：做 L2 主动推送
                                  （扫描器与双通道推送已在：overdue.py:35/80/138/197/238/311，
                                   overdue_scheduler 每 12 小时，notify.push_message 站内+企微）

Q3 场景对、路径对，但准确率上不去，根因在哪？
   ├─ prompt / 工具划分 ───────► 改方向
   ├─ 数据质量 ────────────────► 【停 Agent】预算转做数据治理（更贵，但更值）
   └─ 权限口径太碎 ────────────► 改方向：先做权限继承改造，改完再评估

Q4 只有一个岗位在用，且他只反复问一类问题？
   └────────────────────────────► 【停 Agent】把那个工具做成报表页（见 12.6.3）

Q4 那条是最容易被忽略、也最能省钱的一条：很多 Agent 工具其实就是一个还没做的报表。tool_po_arrival_overdue（agent_router.py:66-92）本质上就是「到期未到货清单」这张表；本仓库 reports_router.py 里已经有四个同形态的报表端点（月度 :189、项目毛利 :425、成本审计 :530、资金面板 :732）。如果一个用户每天问同一句话，他要的不是对话，是一个书签。

12.6.3 怎么体面地停

「停」不等于 git revert。四步，每一步都保留了复活的可能：

  1. 先关菜单，不删代码。改 menus.py:154 一行，去掉 canonical_menu_order(set(configured) | {"agent"}) 里那个无条件并入的 {"agent"}。前端路由守卫（frontend/src/router/index.ts:191-193）会把访问 /agent 的人跳到第一个可见菜单，后端 /api/agent/chat 继续在线，老桌面客户端不会 404。
    本仓库已经这么干过一次：钣金组菜单 2026-06-19 并入生产部、不再单列 key=sheet（menus.py:27），但 frontend/src/router/index.ts:98-103 的 /sheet 路由至今原样躺着，只是没人能进。零风险的下线方式，本项目验证过。
  2. 审计一行不删。agent_chat_logs 全部保留。它是「我们试过、试到什么程度、为什么停」的唯一物证。半年后有人问「AI 这事儿咱们搞过吗」，你能调出真实问答记录和降级率曲线，而不是一段回忆。这比任何复盘文档都可信，因为它不是写出来的，是长出来的。
  3. 把有价值的工具沉淀成报表页。工具函数是纯只读 SELECT（AGENTS.md:56），搬进 reports_router.py 只需要换掉签名、套上现有的权限依赖、前端加一个 tab。注意这一步同时是在还债——搬过去时你必须把行级过滤补齐（那 6 个没有 current 的工具），而这是本来就该做的事。
  4. 写一段两百字的结论，发给业务负责人。内容只有三句：我们试了什么、数据说明了什么、我们把什么留下来了。不要含糊其辞地让它自然消失——静默下线会让业务方觉得「IT 又搞了个半截工程」，而一次明确的结论会让他们下次更愿意配合你做新东西。

12.6.4 这一条对 FDE 的意义

敢于建议客户停止一个项目，是资深与不资深的分水岭

不资深的 FDE 会一直加工具、一直调 prompt、一直换模型，因为停下来意味着承认前面的判断有误，也意味着这个项目不再需要他。资深的 FDE 知道：客户买的不是 Agent，是那个业务动作被解决。用一张报表页解决 = 交付成功；用 Agent 解决不了还硬撑 = 交付失败，还额外留下一个要长期维护的、非确定性的、会在模型升级时无声改变行为的东西。

这一节和第一章形成闭环：第一章问「哪些痛点不该给 Agent」，第十二章处理「上线后才发现它确实不该给 Agent」。两者是同一个判断在不同时间点的两次执行，第二次比第一次更难，因为第一次只需要克制，第二次需要认错。

12.7　沉没成本的诚实处理：哪些是纯赚的

如果停了，前面的投入并不都打水漂。把资产分成三档，诚实标注——标高了是自欺，标低了是浪费。

投入停了还留下什么估值
权限继承改造　给工具传 current、抽出统一守卫它修的是一个与 Agent 无关的洞：agent_router.py:66/138/168 那三处过滤缺失，本质是「有一段代码绕过了页面侧的行级规则」。改造过程还会反向暴露业务端点之间的口径不一致纯赚
权限测绘文档　七类行级规则、语义层地图它是交接文档的一部分，下一个开发者、下一次安全审计、下一次业务口径争论都要用纯赚
评估集　tests/test_agent_perms.py 等它断言的是「warehouse 用户不该看到尾款」——这句话不管有没有 Agent 都成立。直接留在 backend/tests/ 那 71 个测试文件里当权限回归纯赚
工具函数的 SELECT 逻辑搬进 reports_router.py 变报表端点半赚
LLM 配置范式　白名单 :749、打码回显 :776、DB>env :762、admin 独占 :788以后接任何 LLM 功能（自动写周报、附件摘要）都能整段复用这套 kv 配置半赚
TOOL_SCHEMAS / SYSTEM_PROMPT / 追问建议　:361 / :477 / :322纯 Agent 资产，停了就废废
L3 卡片令牌与确认链路没做到 L3 就停 = 全废；做到了才有复用价值高风险

最后一行值得单独说：L3 是本项目投入最大、可回收率最低的一段，所以它应该最后做、最晚承诺。先把 L1 的越权补完、把审计补厚、把评估集立起来——这三件事无论结局如何都是赚的；等这三件事的数据说话之后，再决定要不要押 L3。把「纯赚的」排在前面做，是对沉没成本最好的防御。

12.8　本项目的退出条件

下面五条是可观测的，写在这里的目的是提前把判断固定下来——事到临头再定标准，标准一定会向「再试试」倾斜。

#条件触发动作
1权限硬门槛：扩写后的 tests/test_agent_perms.py（含行级断言）连续两次发版不能全绿立即关菜单（menus.py:154），不是「下个迭代修」。越权是不可撤回的损失
2使用门槛：上线 8 周后，agent_chat_logs 周独立提问人 < 全体账号 20%，且趋势不上升进 12.6.2 决策树，重新评估场景
3可用门槛：via='rule' 降级率连续两周 > 20%，或 rule-fallback:timeout 占降级过半说明 30 秒每请求超时（agent_router.py:499）+ 无 stream + 4 轮无全局 deadline（:522）这套架构撑不住当前问题复杂度。要么改架构，要么停
4口径漂移门槛：一个季度内因业务口径变更被迫同步改 Agent 工具 ≥ 3 次转向「工具只调 reports_router.py 语义层、不自己写口径」；改不动则停
5根因门槛：评估集失败案例中根因为「数据缺失/数据错」的 > 50%停 Agent，预算转数据治理（软关联补外键、EAV 收敛）

这五条里，只有第 1 条是「立即执行」，其余四条触发的都是「重新评估」而不是「自动停」。把「立即执行」的条件控制在一条以内很重要——条件太多，你会开始跟自己讨价还价；只有一条，且是安全条款，就没得讨价还价。

整本手册的一句话

Agent 不是目的，「这件事以后不用再问了」才是。能用一个报表页做到，就别上 Agent；上了 Agent 做不到，就换回报表页。中间这十章讲的所有技术——工具边界、权限继承、语义层复用、评估集、灰度、卡片确认——存在的唯一理由，是让你在做这个判断时有真数据可依据，而不是靠感觉和面子。

迁移提示：这张表换到任何客户都成立，会变的只有阈值和证据来源。周活 40% 在几十人的制造业内网是合理线，在几千人的集团系统里 15% 可能就够；证据来源在有数仓的客户那里是 BI 看板，在本项目是三张表加一次 grep。但「每个阶段都必须有一条不合格时的退出动作」这一条不能变——一个只有进入条件、没有退出条件的项目，最后一定会靠惯性活着，而靠惯性活着的项目，是 FDE 履历上最不值钱的那一行。
