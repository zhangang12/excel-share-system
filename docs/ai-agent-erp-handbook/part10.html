第十章　模型选型、工具调用可靠性与系统压力

前九章讨论的都是"这套 Agent 该长成什么样"。这一章讨论两件更硬的事：拿哪个模型来驱动它，以及它跑起来会把这套系统压成什么样。这两件事在 POC 阶段完全不存在——单人测试、串行提问、一个模型、没人算钱。它们会在上线后第三周同时出现，而且往往是同一天出现：财务问了一句"这个月尾款情况"，助手在四轮里扫了七次全表，同时另外八个人在用页面，数据库连接池见底，整个系统一起卡住。

本章的核心结论（先说结果）

第一，选模型不看榜单看工具调用。ERP Agent 的模型只干两件事：决定调哪个工具、把结果组织成人话。前者错了后面全错，而这项能力和 MMLU 分数几乎不相关。必须用你自己客户的真实问题做一个 20-30 条的小基准，跑出命中率再决定。

第二，Agent 的成本有两种，token 那种反而是便宜的那种。本项目 tool_morning_report（agent_router.py:219）一次调用内部串了 4 个子工具、4 次全表扫；模型一轮最多并发 4 个工具（agent_router.py:532）、最多 4 轮（agent_router.py:522）。原本一次页面查询（purchase_mgmt_router.py:368 带 SQL 分页）在 Agent 路径上会放大成十几次无分页全表扫。数据库、连接池、慢查询才是真正的账单。

第三，降级到规则比降级到另一个模型更诚实。本项目 agent_router.py:957-959 把"LLM 任何异常"一律降到关键词规则路径。这个设计被很多人当成"临时凑合"，其实它是本项目 Agent 层唯一一个可用性 100% 的部件——不依赖任何外部服务。它的问题不是不该存在，是没告诉用户"你现在拿到的是降级答案"。

10.1　选模型的标准不是榜单分数，是工具调用可靠性

本项目给模型的活很窄。系统提示词要求"需要数据时先调用工具，可连续调用多个；拿到工具结果后直接总结，不要重复调用同一工具"（agent_router.py 系统提示词第 5 条），下发的工具只有 7 个（agent_router.py:361 的 TOOL_SCHEMAS，且按用户菜单裁剪，见 agent_router.py:409 的 _allowed_tools）。参数也简单到极点：po_arriving 只有一个 days，overdue_orders 只有一个带 enum 的 dept，project_status 只有一个必填 code。

就这么窄的活，模型依然有六种稳定可复现的失败形态。这不是"模型不够聪明"，是 function calling 这条链路本身的固有失效模式：

失败形态在本项目里长什么样用户看到什么能否被现有代码接住
① 不调工具直接编问"这周有几条到期未到货"，模型不调 po_arrival_overdue，直接根据历史消息里的旧数字回答"12 条"一句非常自信、格式漂亮的错误答案接不住。agent_router.py:526-530 对"无 tool_calls 且有 content"的分支直接 return，不区分它是不是该调工具
② 调不存在的工具名模型编出 get_purchase_list / query_orders依赖 _run_tool 兜底部分接住。_run_tool（agent_router.py:427）走的是一串 if name == ...，未匹配的名字落到末尾分支；但工具名不会进 tool_names（agent_router.py:540 要求 name in TOOL_LABELS），审计日志里看不出发生过这件事
③ 参数 schema 不合法arguments 不是合法 JSON，或 days 传成 "三天"静默按默认值执行接住但静默。agent_router.py:535-538 JSON 解析失败直接 args = {}；int(args.get("days") or 3) 遇到 "三天" 会抛 ValueError 冒到 _chat_with_llm 外层，最终被 :957 吞掉降级成规则路径——用户拿到的是一个完全不同的答案，且不知道
④ 参数值幻觉用户说"看下上次那个项目"，模型自己编一个 code="TH-2501"（这个编号就写在工具描述里当示例）"未找到该项目"，或者更糟——真的查到了别人的项目接不住，也最危险。工具描述里写示例值是标准做法，但示例值就是最强的幻觉诱饵
⑤ 该调多个只调一个问"下周要盯什么"，只调了 po_arrival_overdue，漏了 balance_due 和 overdue_orders答案不完整，但看起来完整接不住。这是最隐蔽的一种——没有任何错误信号，只是少了一半事实
⑥ 重复调用同一工具连续 4 轮都调 po_arrival_overdue，参数一模一样等 4 次 LLM 往返后抛错，降级接住但代价高。agent_router.py:546 抛"LLM 工具调用轮次超限"，此时已经烧掉 4 次 LLM 调用 + 最多 16 次工具执行的时间和数据库开销
注意 ①③⑤ 这三种的共同点

它们都不产生任何异常、不打任何 warning、HTTP 200，审计表 agent_chat_logs（models.py:1108-1122）里也看不出异样——via 是 "llm"、duration_ms 正常、tools_used 是一个合法的工具名列表。第七章说"Agent 的失败大多数不是崩溃，是安静地答错"，这里给出的就是那句话在 function calling 这一层的具体机制：模型的失败方式恰好是你的监控看不见的那一种。所以选模型这件事不能靠观感，必须靠一个能把 ①③⑤ 判出来的基准。

10.2　用真实问题做一个小型工具调用基准

做法很朴素：把客户真实会问的话收集 20-30 条，每条人工标注期望调用哪个工具、带什么参数，然后对每个候选模型跑一遍，只看工具调用层，不看最终文字。为什么只有 20-30 条？因为这些题必须是人工标注、人工复核的，200 条你标不动也维护不动；而且工具只有 7 个，20-30 条已经能覆盖每个工具 + 每类陷阱。

下面是本项目可以直接用的一份（题面全部来自真实使用场景与 _rule_chat（agent_router.py:708）里那些关键词所对应的真实问法）：

指标定义要比"准确率"细，因为不同失败的代价差好几个数量级：

  • 工具命中率：调对工具集合（多工具题要求集合相等）的比例。低于 90% 不能当默认模型。
  • 参数正确率：在工具调对的前提下参数完全匹配的比例。目标 ≥85%。#4/#5/#7 是这项的主战场。
  • 幻觉参数率：#16、#18 这类"没给的值自己编出来"。这项的容忍度是 0——它直接对应"给用户看了别人项目的数据"这种事故。
  • 越界率：#20、#22 这类该拒绝却动手的比例。容忍度同样是 0。
  • 轮次中位数：中位数应该是 2（一轮调工具 + 一轮总结）。中位数到 3 说明有系统性重复调用，直接对应 10.1 的 ⑥ 和 10.7 的数据库压力。
  • 零调用率：本该调工具却直接作答（形态 ①）。这是最难测也最必须测的一项——判定方法是看返回里有没有 tool_calls，不是看文字对不对。
这份基准怎么跑（复用本项目已有的测试约定）

本项目测试是独立 asyncio 脚本 + 临时 SQLite（backend/.venv/bin/python tests/xxx.py），不是 pytest。工具调用基准可以完全套这个模子：建一个固定的小数据集（比如 12 条采购明细、5 条台账、8 条部门任务），跑 _llm_request（agent_router.py:487）拿到第一轮返回，只断言 tool_calls 的名字和参数，不执行工具、不看文字。这样一轮基准 = 24 次 LLM 调用，单模型几分钟、几毛钱，可以每次换模型都跑。

关键设计：不要在基准里执行真实工具。执行工具会把 LLM 的错误和数据的偶然性混在一起——你会分不清"答案不对"是模型选错工具还是测试数据本来就那样。只断言意图，这条基准才是可复现的。

10.3　为什么 temperature=0.2，以及它的代价

agent_router.py:492 把 temperature 固定成 0.2，payload 里只有 model / messages / temperature，加上有工具时的 tools 和 tool_choice: "auto"——没有 stream，没有 max_tokens，没有 seed，没有 top_p。

0.2 对这套系统是合理的，理由有三条，都跟"工具调用"这个具体任务绑死：

  1. 工具选择是分类任务，不是生成任务。7 个工具里选 1-2 个，正确答案唯一。采样温度在这里唯一的作用就是让本来 top-1 的正确选项偶尔输给 top-2 的错误选项。
  2. 参数抽取是抄写任务。"超过 7 天"里的 7 是抄的，不是想的。温度越高越容易抄成 5 或 10。
  3. 第七章那条评估集要求可复现。温度 1.0 下同一题跑三次三个结果，你根本没法判断某次改动是变好了还是运气好。0.2 让"跑一遍就能大致相信结果"成立——这是评估成本，不是模型质量。

代价也要说清楚，而且代价落在了这套系统实际会遇到的地方：

代价具体表现在本项目严不严重
错误答案会被稳定复现#6"下周有什么到货"如果这个模型倾向误判成 po_arrival_overdue，那它每次都错，不会偶尔蒙对这其实是好事。稳定的错误可以被基准抓到、被提示词修掉；随机的错误只能靠用户投诉发现
总结文字会重复、单调同一类问题的结论句几乎一字不差不严重。ERP 场景要的就是"每天早上那句话长得一样"
模糊问题上不敢发散用户问得很含糊时，低温模型更容易硬选一个工具而不是反问有点严重。#18 那类题在低温下反而更容易踩幻觉。这不该靠调温度救，该靠提示词里明确写"编号缺失就反问"
温度对失败形态 ①⑤ 基本无效"不调工具直接编"和"该调多个只调一个"是模型的倾向性问题，调温度改不动这两项只能靠换模型或改提示词，别指望参数调优

现状缺口 没有 max_tokens 意味着单次响应长度不设上限——一个话痨模型可以在总结轮吐几千 token，既拖长响应也直接变成账单。没有 stream 意味着用户在 30 秒里看到的是一个纯粹的转圈。这两项都是 L2 之前应该补上的，见 10.6。

10.4　多模型并存：评估矩阵爆炸与"默认/可选"分层

本项目允许用户在请求里指定模型：ChatIn.model（agent_router.py:887），后端校验它在白名单内（agent_router.py:942-943），白名单由 _model_whitelist()（agent_router.py:749）从生效配置解析，默认值是 "deepseek-chat,deepseek-reasoner"（config.py:64），默认模型 deepseek-chat（config.py:62）。而生效配置来自 app_settings 表 > .env，admin 在页面上改一下就全局生效。

这个设计本身没问题，但它带来一个容易被忽略的账：每往白名单里加一个模型，你的验证义务就 ×2。24 条基准 × 3 个模型 = 72 次标注复核；再叠加第七章那套业务评估集（比如 40 条），就是每次改提示词都要跑 192 次。而提示词是会经常改的——每加一个工具、每修一次口径都要改。

最坏的情形不是工作量，是"没人知道哪个组合被验证过"

agent_chat_logs 记了 model 字段，所以事后能查某次问答用的哪个模型。但没有任何地方记录"这个模型在哪一版提示词下通过了什么基准"。三个月后有人问"deepseek-reasoner 靠谱吗"，唯一诚实的答案是"不知道，当初加进去是因为想试试"。这就是评估矩阵爆炸的真实后果：不是跑不完，是没人承认自己没跑。

对策：把模型分成两个等级，写在配置和 UI 上

默认模型（Default）可选模型（Optional）
数量永远只有 1 个0-2 个，超过 2 个就是没在维护
评估义务全量：24 条工具基准 + 全部业务评估集，每次提示词/工具变更后重跑关键子集：工具基准里标 0 容忍 的那几条（#16 #18 #20 #22）+ 每个工具至少 1 条基线，共 11 条
准入门槛工具命中率 ≥90%、参数正确率 ≥85%、幻觉参数率 =0、越界率 =0幻觉参数率 =0、越界率 =0，命中率不设硬线
UI 呈现默认选中，不标注必须显式标注「未完全验证，回答可能不如默认模型准确」
谁能改admin（agent_router.py:788-792 的 _require_admin_only，比 require_admin 更严，manager 也 403）同左

这个分层用现有代码就能落地，改动量很小：_model_whitelist() 的返回本来就是"名单 + 默认模型自动并入"的结构，GET /models（agent_router.py:803 附近）已经同时返回 models 和 default。前端拿到这两个字段，把 models 里非 default 的那些统统打上"未完全验证"的角标即可——不需要新表、不需要迁移。

白名单该按什么标准维护，什么时候踢掉一个模型

加进来的标准：它得能回答一个"为什么需要它"的问题，而且答案不能是"多一个选择"。真实合理的理由只有三类——成本档位不同（便宜档用于晨报这种高频固定问法）、能力档位不同（推理模型用于跨域归因）、供应商不同（避免单一供应商故障）。

踢出去的触发条件，任何一条命中就该踢，而不是"再观察观察"：

  • 幻觉参数率 > 0。一次都不能有。这条对应的是数据泄漏风险，不是体验问题。
  • 连续两次提示词变更后没人跑关键子集。没验证的模型 = 未知的模型，未知的模型不该在下拉框里。
  • 近 90 天审计日志里选用次数为 0。查一句 agent_chat_logs 按 model 分组就知道。没人用的选项只增加维护面积。
  • 供应商侧废弃或改名。模型名是字符串直传给 /chat/completions，供应商下线了它，用户选中后拿到的是 HTTP 400 → 被 :957 吞掉 → 静默降级到规则路径。用户只会觉得"助手今天变笨了"。
  • 同档位有更好的替代。白名单不是历史博物馆。

10.5　供应商故障的降级链：为什么"降到规则"比"降到另一个模型"更诚实

现状是一行 except Exception：agent_router.py:957-959，LLM 抛任何异常都记一条 warning，然后走 _rule_chat（agent_router.py:962）。失败原因被 _fallback_reason() 归成 timeout / http-500 / ConnectError 之类，拼成 "rule-fallback:timeout" 写进审计表的 model 字段。另外，如果压根没配 api_key，agent_router.py:961 直接是 "rule-fallback"——也就是说这套 Agent 从来就能在完全没有 LLM 的情况下工作。

这个设计好在哪：降级路径的可用性是 100%，且这个 100% 不依赖任何外部服务。规则路径调的是同一批 _run_tool，走同一套菜单门控，格式化用的是本地模板函数（_po_overdue_text 等）。DeepSeek 挂了、机房断网了、api_key 过期了、账户欠费了——用户问"有哪些采购超期没到"依然能拿到一张正确的表。对一个几十人天天在用的内部系统，这个性质的价值高于任何模型能力。

但必须讲清它的能力边界

能力LLM 路径规则降级路径（agent_router.py:708）
多轮上下文有，最近 10 轮回灌（agent_router.py:945-946 截取 history[-20:]）无。_rule_chat 签名里根本没有 history 参数，每句话都是第一句话
参数抽取有，模型抽 days / dept / code几乎没有。只有两处：days 靠"下周/一周/7天"关键词硬编成 7 否则 3；code 靠正则 [A-Za-z]{2,}-?\d+。min_overdue_days、dept 完全抽不出来
多工具组合有，一轮最多 4 个无。每个分支 return 一个工具的结果就结束
意图判定模型语义理解顺序固定的关键词 if 链，先匹配先赢

最后那条"顺序固定"会产生真实的歧义事故，可以直接从代码读出来：_rule_chat 里 "供应商" in m 这个分支排在采购分支之前。所以用户问"下周有哪些供应商的货要到"，规则路径会命中 po_overdue_by_supplier（到期未到货按供应商汇总），而用户想要的是 po_arriving（未来到货）。语义完全相反，而用户不会知道自己拿到的是反的。同理，"逾期" 分支排在尾款分支之后，问"尾款逾期"会走 balance_due（对的），但问"逾期的尾款和任务"只会给尾款。

现状最该补的不是能力，是标签

接口返回里其实已经有 "fallback": true（agent_router.py:965）。只要前端在降级答案上打一条"⚠ 大模型暂不可用，以下为规则匹配结果，仅支持单一意图"，10.5 讲的所有边界问题就从"沉默的错误"变成"用户知情的降级"。这是本章性价比最高的一项改动——零后端改动，纯前端一行。

要不要做多供应商 failover

直觉上"DeepSeek 挂了就切别家"比"降到关键词"强得多。但对本项目，这个直觉是错的，理由是四条具体的代价：

  1. 它不是一个 URL 的事。_effective_llm_config（agent_router.py:762-773）目前是单份 base_url / api_key / model / models 的扁平结构。要 failover 就得变成一个列表，配置页要改，_mask_key 的打码回显要改，白名单校验要改成"哪个供应商支持哪些模型"的二维关系。
  2. 评估矩阵再乘一次。10.4 刚说过每加一个模型验证义务翻倍。多一个供应商就是多一批模型。
  3. 它救不了最常见的故障。真实故障分布里，"供应商整体宕机"是少数派；多数是超时、限流、单条请求 500。这些 agent_router.py:499 那个 30 秒超时已经在接了，切供应商并不比重试更有效。
  4. 它引入一个新的失败模式：静默的能力漂移。主模型挂了自动切备用模型，用户拿到的答案质量变了、工具选择倾向变了，但界面上什么都没说。这比降级到规则更不诚实——规则降级至少行为是可预测的、可解释的、能在 UI 上说清楚的；"你现在用的是备用模型"这句话对业务用户毫无信息量。

推荐顺序 ① 前端亮出 fallback 标签（今天就能做）→ ② 加同供应商内的一次重试 + 指数退避（改动仅在 _llm_request 内）→ ③ 规则路径把最坑的关键词顺序修掉（"供应商"分支下沉到"未来/预计"判断之后）→ ④ 都做完了、且真的出现过供应商级宕机，再谈多供应商。

10.6　超时与预算：五层预算的设计

先把现状的完整链路摆出来，因为这里藏着一个真实的错位：

前端 axios timeout: 30000 ── frontend/src/api/index.ts:8 ↓ nginx proxy_read_timeout 300 ── nginx/conf.d/default.conf:59 ↓ FastAPI /chat 无端点级超时 ↓ _chat_with_llm for _ in range(4) ── agent_router.py:522 ← 轮次上限 ├─ _llm_request httpx timeout=30.0 ── agent_router.py:499 ← 每请求级 └─ tool_calls[:4] 每轮最多 4 个工具 ── agent_router.py:532 工具本身无超时 最坏情况：4 × (30s LLM + 4 个工具的执行时间) ≈ 120s + 工具耗时 浏览器在 30s 就放弃了 ── 后端还在跑，还在烧 token，还在占数据库连接
这不是"前端没有超时兜底"，是"前端超时比后端最坏情况短 4 倍"

frontend/src/api/index.ts:8 是有 30 秒超时的（同一文件 :28 还专门为 blob 下载把它关掉，说明这个值是被认真想过的）。问题是：只要 LLM 需要两轮，用户就必然看到"请求超时，请检查网络或重试"——而后端此时正常运行、马上就要返回正确答案，并且会把这条问答完整写进审计日志。于是运维看到的现象是：审计表里全是成功记录，用户群里全是"助手又崩了"。这是本章最值得单独拎出来的一个真实缺陷，它比 token 成本、比数据库压力都更早伤害信任。

正确的做法是五层预算，且必须满足一个不变式：从外到内严格递减，外层至少比内层最坏情况长 20%。

层作用本项目现状建议值为什么是这个值
① 客户端超时用户体验的上限30s（api/index.ts:8）75s（仅 /agent/chat 单独放宽）= 全局 deadline 60s × 1.25。必须比 ② 长，否则用户永远看不到成功的多轮回答
② 全局 deadline整个问答的硬上限，超了就降级没有60s业务用户对"问数"的忍耐极限。实现：进 _chat_with_llm 前记 deadline = time.monotonic() + 60，每轮开头检查，超了直接抛异常走 :957 的规则降级——降级路径 1 秒内必出结果，用户至少拿到东西
③ 单次 LLM 超时防单次挂死30s（agent_router.py:499）25s，且取 min(25, 剩余 deadline)固定 30s 的问题是：第 3 轮开始时若只剩 8 秒，仍然会等满 30 秒才失败——白白吃掉 22 秒
④ 单工具超时防慢查询拖垮全局没有5s本项目最重的工具 morning_report 是 4 次全表扫；单表几千行时应在 1 秒内。5 秒说明索引或数据量出问题了，此时应该失败而不是等
⑤ 轮次上限防重复调用死循环4（agent_router.py:522）3正常问答的轮次中位数是 2。第 4 轮几乎必然是 10.1 形态 ⑥（重复调用），继续跑只是多花钱多压库
⑥ token 预算防话痨与账单失控没有 max_tokens单次 max_tokens=2000；单次问答累计输入 ≤16k7 个工具 schema + 系统提示词 ≈ 1.5k；每个工具结果最多 20 行（agent_router.py:93 等处的 rows[:20]）≈ 1.5k；4 轮 × 4 工具 = 16 个结果就是 24k——已经超了很多模型的舒适区，这本身就是轮次该降到 3 的旁证

配套 审计表 agent_chat_logs（models.py:1108-1122）目前有 duration_ms 但没有 token 用量、没有轮次、没有工具入参。上面这套预算如果不落到审计里，就没法回答"我们的 P95 轮次是多少""哪个问法最烧钱"。补三列（rounds / prompt_tokens / completion_tokens）的成本极低——OpenAI 兼容响应体里 usage 字段本来就带回来了，现在的代码只是没读它。

10.7　数据库压力：本书前面欠的一笔账

现状：全表扫 + Python 侧过滤

7 个工具全部是同一个模式。以 tool_po_arrival_overdue（agent_router.py:66）为例：一条 select(models.PurchaseItem) 带三个 WHERE 条件，然后 r.scalars().all() 全部拉进内存，在 Python 里算超期天数、过滤、排序，最后 rows[:20] 返回（agent_router.py:93）。SQL 层没有 LIMIT，没有 ORDER BY，没有分页。tool_balance_due（:138）、tool_overdue_orders（:168）、_hr_due_rows（:199，条件只有 status != "离职"——真正意义上的全表）全都一样。

更要命的是 tool_morning_report（agent_router.py:219）：它不是一个查询，是四个——内部依次调 tool_po_arrival_overdue、tool_overdue_orders、tool_balance_due、_hr_due_rows，各取 Top5。模型看到的是"一个工具"，数据库看到的是"四次无分页扫描"。

叠上 ORM 的关联加载：models.py 里有 39 处 lazy="joined"。PurchaseItem 一行会带出 supplier 和 buyer（models.py:654-655），SalesLedger 一行会带出 project 和 sales_user（models.py:319-320）。这在页面场景下是好设计——避免 N+1，一次查询拿全。但在"全表扫"的前提下，它意味着返回的宽度也随行数线性增长：500 行采购明细不是 500 行数据，是 500 行 × (采购明细 + 供应商 + 用户) 三张表的宽 JOIN 结果集。

目前为什么还没炸

诚实地说：因为数据量小。几十人的制造业内部系统，采购明细、销售台账、部门任务都在几千行量级，PostgreSQL 全表扫几千行是毫秒级的事。这一节讲的所有压力在今天的本项目上都不构成问题。但两件事会让它变成问题：① 数据自然增长到几万行；② L2 的主动推送和 L3 的卡片提案让 Agent 的调用量从"用户偶尔问一句"变成"系统持续跑"。写这一节不是因为现在疼，是因为改这个的成本随时间单调上升。

改成"调 router 函数"之后，压力怎么变

第三章那条原则"工具不写 SQL，只调现有 router 函数并传真实 current"主要是为了安全（行级权限单一访问路径）。它对性能的影响是大概率变好，但不是必然——本仓库里正好有正反两个例子：

router 函数分页实现Agent 调它之后
purchase_mgmt_router.py:368 采购明细列表真 SQL 分页 stmt.limit(page_size).offset(...)，page_size 默认 100 上限 500（:340），且 _buyer_restricted（:349）把采购员收窄到自己的行明显变好。SQL 层就限了行数，权限过滤也下推到 WHERE，扫描范围比现在的工具小一个数量级
sales_router.py:275-276 销售台账列表Python 切片 :252-253 先 execute(q) 把全部匹配行取出，关键词过滤、排序、算合计都在 Python 里，最后 ledgers[start:start+page_size]不变好。DB 侧的扫描量和现在的 tool_balance_due 一样。注释里写得很清楚，这是有意为之——合计要针对全集、附件名只对当前页构建
reports_router.py:425 项目毛利榜全量多腿聚合 四条 GROUP BY 分别扫 WhTxn / PurchaseItem / AfterSales 等，无分页无筛选明显变重。这类报表端点本来就是"人一天点一次"的设计。如果 L2 让 Agent 每天定时调它，就等于把一个低频重查询变成了高频重查询

所以"复用 router 函数"这条原则要配一句限定：复用列表类端点是双赢，复用报表类端点必须先看它是不是全量聚合。给 Agent 用的 page_size 也不能照抄页面默认值——页面给人看 100 行合理，给模型看 100 行是纯浪费：模型最终只会在回答里列 5-10 行（工具现在的 rows[:20] 已经是这个逻辑），Agent 侧的 page_size 建议固定在 20-30，并且在工具描述里告诉模型"只返回最紧急的 N 条，完整清单请引导用户去页面"。

并行工具调用对连接数的放大

现状是串行的：agent_router.py:532 那个 for tc in tool_calls[:4] 里每个 await _run_tool(...) 顺序执行，共用请求作用域内的同一个 AsyncSession（get_db 注入，database.py:28）。所以今天一次问答最多占 1 个数据库连接。

迁到 AgentScope 之后，parallel_tool_calls 会把这一轮的多个工具用 asyncio.gather 并发起来。这时候串行的那个"共用一个 session"就不成立了——SQLAlchemy 的 AsyncSession 不是并发安全的，同一个 session 上并发 execute 会直接抛 InterfaceError。正确做法是每个并行工具开自己的 session，而这就直接把连接占用乘上去了。

算一下这笔账，用本仓库的真实配置：

连接池上限（每进程） database.py:10-13 create_async_engine(url, echo=False, pool_pre_ping=True) ↑ 没有 pool_size，没有 max_overflow → SQLAlchemy 默认 pool_size=5, max_overflow=10 = 每进程最多 15 个连接 进程数 backend/Dockerfile.prod:16 uvicorn --workers 4 = 15 × 4 = 60 个连接（上限） 数据库 docker-compose.prod.yml postgres:16-alpine，未覆盖 max_connections = PostgreSQL 默认 100，其中约 3 个保留给超级用户 并行后的占用 1 个 Agent 问答 × 每轮 4 个并行工具 = 峰值 4 连接（而不是现在的 1） 4 个人同时问 = 16 连接 再叠加 20 个人在正常用页面 = 20 连接 = 36/60，池子还够，但 单进程 15 的软上限会先到： 某个 worker 上 4 个 Agent 请求撞一起 = 16 > 15 → 第 16 个请求排队等 pool 排队等待没有超时上限 → 表现为"页面也一起卡了"
这里最危险的一点：Agent 和页面共用同一个连接池

get_db 是全局唯一的会话依赖，Agent 的工具和采购页的列表接口从同一个池子里取连接。也就是说，一个人问了一句话把 Agent 的并行工具铺开，代价由所有正在用页面的人一起承担。这在架构上是不可接受的——AI 助手是增值功能，业务页面是生产系统，增值功能不该有能力拖垮生产系统。

三条建议，按性价比排序

  1. 先把池子的数字显式写出来。现在 database.py 靠默认值，等于这个关键容量参数没人做过决定。显式写 pool_size=10, max_overflow=10, pool_timeout=5——pool_timeout 尤其重要：没有它，池满时请求会无限期等待，症状是"整站变慢但没有任何报错"；设成 5 秒，池满时会抛 TimeoutError，至少能在日志里看见。改这一行的成本接近 0，收益是把一个不可见故障变成可见故障。
  2. 给 Agent 单独一个引擎 + 单独的池预算。用同一个 DATABASE_URL 再建一个 agent_engine，pool_size=3, max_overflow=2（每进程 5，4 workers 共 20），Agent 的工具只从这个池取连接。这样 Agent 再怎么并行，最多吃掉 20 个连接，业务页面的池子完全不受影响。这是"增值功能不得拖垮生产系统"这条原则最直接的工程表达，也是本节唯一一条我认为在 L2 之前必须做的。
  3. 并行度上限 + 慢查询日志。并行度上限用 asyncio.Semaphore(3) 包住工具执行即可，比连接池上限更早生效、错误信息更明确。慢查询日志用 SQLAlchemy 的 before_cursor_execute/after_cursor_execute 事件记 >500ms 的语句——本项目工具全是全表扫，这个日志上线第一天就会告诉你哪张表先撑不住。

10.8　成本的第二种形态：放大效应

把一次真实交互摊开算，用本项目的实际数字。用户问一句"今天有什么要盯的，顺便看下 TH-2501 的进度"：

走页面走 Agent（当前串行实现）放大
HTTP 请求2 次（晨报视图 + 项目详情）1 次 POST /api/agent/chat0.5×
LLM 调用02 次（一轮调工具 + 一轮总结）—
工具执行—2 个（morning_report + project_status）—
SQL 查询页面端点带分页与筛选，约 4-6 条morning_report 内部 4 次全表扫 + project_status 的项目/任务/采购/尾款查询，约 8-10 条且大多无 LIMIT≈2×，扫描行数 ≈10×
连接占用时长每次几十毫秒整个问答期间持有（session 请求作用域），含等 LLM 的 30 秒数百倍
token0输入 ≈ 提示词 1.5k + 工具结果 2k + 历史；输出 ≈ 0.8k—
最贵的一格不是 token，是"连接占用时长"

这一格容易被完全忽略：get_db 的 session 是请求作用域的，它在 POST /chat 进来时就取了连接，在返回时才还。中间那 30 秒 Agent 在等 DeepSeek 回话——数据库连接就这么空占着。一个页面请求占用连接几十毫秒，一个 Agent 请求占用连接可能是 30-60 秒，相差三个数量级。当 10.7 说"4 个人同时问就是 16 个连接"时，那 16 个连接不是瞬时峰值，是持续半分钟的稳态占用。

这也顺带给出了一个比"分池"更彻底的解法方向：让工具执行结束就释放 session，别让它跨越 LLM 等待窗口。代价是要脱离 FastAPI 的 Depends(get_db) 惯用法，在工具内部用 async with SessionLocal() 自管生命周期。这也正是第三章"工具只调 router 函数"那条原则要付出的第一个真实工程代价——router 函数签名要的是一个 session，你得决定这个 session 从哪来、活多久。

而最坏情况的放大是这样的：4 轮 × 4 工具 = 16 次工具执行；若其中有 3 次 morning_report，就是 12 次额外全表扫；总计单次问答可以打出 30+ 条无分页 SQL。这个最坏情况今天可以由一句话触发，没有任何东西拦着——这就是 10.6 建议把轮次上限从 4 降到 3、加全局 deadline、加单工具超时的最实际理由：那些参数不只是省钱，它们是数据库的保险丝。

换个项目会怎么变
  • 私有化部署的客户：10.4 的多模型问题会消失（通常只有一个自部署模型），但 10.1 的失败形态会更严重——中小参数量的开源模型在 function calling 上的幻觉参数率经常不是 0。此时该做的不是换模型，是把工具改成零参数版本：与其让模型抽 days，不如提供 po_arriving_3d / po_arriving_7d 两个工具。工具数量换参数可靠性，这是私有化场景的标准交易。
  • 数据量大一到两个量级的客户（十万行以上）：10.7 从"迟早的问题"变成"第一天的问题"。工具必须从一开始就带 SQL 层 LIMIT，lazy="joined" 的宽 JOIN 要改成显式的 load_only + 只取需要的列。不要等到工具写完再优化——全表扫工具一旦上线，用户的问法就固化在上面了。
  • 已经有成熟 BI/报表层的客户：可以把 Agent 的工具直接指向物化视图或报表表，SQL 压力问题基本消失，代价是数据有延迟（通常 T+1 或小时级）。这个取舍必须写进需求文档并让业务签字——"助手说的数和页面上的数差一点"是最伤信任的一类问题，第七章那条"事实源必须一致"在这里会被直接违反。
  • 高并发的客户（几百人以上同时在线）：10.7 里"给 Agent 单独分池"从建议变成硬要求，而且要更进一步——Agent 的请求应该走独立的进程/服务，与业务 API 物理隔离。本项目共用 uvicorn 是几十人规模下的合理简化，规模上去后这个简化会变成事故源。
  • 不变的部分：10.2 那份基准的方法在任何项目上都成立——20-30 条真实问题、标注期望工具与参数、只断言意图不执行工具、幻觉率和越界率零容忍。变的只是题面。这是本章唯一一件可以照搬的东西。
本章可以立刻做的五件事（按性价比排序）
  1. 前端 /agent/chat 单独放宽超时到 75 秒，并在 fallback: true 时显示降级标签。纯前端，半小时，解决"审计表全成功、用户群全报错"这个最伤信任的问题。
  2. 显式写死连接池参数（database.py 加 pool_size / max_overflow / pool_timeout=5）。一行，把不可见故障变成可见故障。
  3. 加 max_tokens 和全局 deadline，轮次上限 4 → 3（agent_router.py:492 / :522）。三处小改动，同时压住成本和数据库压力。
  4. 审计表补 rounds / prompt_tokens / completion_tokens 三列。响应体里本来就有 usage，只是没读。没有这三列，上面所有预算都无法验证是否生效。
  5. 把 10.2 那 24 条基准写成一个 tests/ 脚本。这是 10.4 那套"默认/可选"分层的前提——没有基准，分层只是一句口号。
