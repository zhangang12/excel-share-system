第九章　合规：把公司数据送给第三方模型这件事

前八章讨论的是「做得对不对」。这一章讨论的是「允不允许做」。企业客户的法务和内审不会问你 function calling 怎么实现，他们只问一句：我们的客户名单和合同金额，现在是不是正在发给一家我们没签过合同的公司？本章先把这个问题的真实答案摆出来（是的，正在发），再给出把它变成「可解释、可审批、可撤回」的完整路径。

本章一句话

第五章防的是「我们公司的人看到了不该看的」，第九章防的是「数据离开了我们公司」。同一批字段，两道闸，闸门位置不同、失效后果不同、可逆性完全不同——内部越权可以改权限、删记录、追责；数据出境一旦 POST 成功就永远收不回来。把这两件事混成一件事讨论，是企业 Agent 项目最常见的合规事故根因。

9.1　先把事实摆清楚：一次问答，哪些字节离开了公司

本项目的 LLM 调用只有一处：backend/app/routers/agent_router.py:487-507 的 _llm_request。它把 cfg["base_url"] 拼上 /chat/completions，用 httpx 直接 POST 出去。base_url 的默认值是 https://api.deepseek.com/v1（backend/app/config.py:60）。payload 里只有 model / messages / temperature / tools，没有任何脱敏、字段过滤或分级判断。

9.2　base_url：一个放在网页表单上的「数据接收方」开关

把 9.1 的图再看一眼：整张图里唯一决定「数据发给谁」的，是 cfg["base_url"] 这一个字符串。改它 = 换数据接收方。而它现在的形态是：

  • 存在数据库里，不在代码里。app_settings 表（models.py:1067-1075）的一行 kv，读取逻辑 _effective_llm_config（agent_router.py:762-773）是每次请求实时读库——改完不用重启、不用发版，下一秒全公司生效。
  • 写入口是一个普通的输入框。frontend/src/views/AgentView.vue:354，一个 el-input，占位符写着 https://api.deepseek.com/v1；保存按钮在 :374，saveConfig（:87-99）里没有任何二次确认，成功就弹一句「配置已保存，全局生效」。
  • 后端校验只有一行。agent_router.py:849：if "base_url" in writes and not cfg["base_url"].lower().startswith("http")。也就是说 http://1.2.3.4:8000/v1 完全合法。没有域名白名单。
  • 权限确实收紧过，但只收紧了「谁」。_require_admin_only（agent_router.py:788-792）比 deps.require_admin 更严，manager 也 403——这是个好设计。但它管的是身份，不是流程：没有审批、没有双人复核、没有告警。
  • 审计几乎等于没有。agent_router.py:875 只记 「LLM 配置已由 %s 更新（字段：%s）」——只有字段名，没有新旧值。而且这条 log.info 写的是容器 stdout；docker-compose.prod.yml 的 backend 服务只挂了 uploads_data 一个卷，日志没有持久化卷，ops/upgrade.sh:50 的 up -d --build 一重建容器，旧日志随容器一起消失。表里也帮不上忙：AppSetting 只有 updated_at（models.py:1074-1075），没有 updated_by、没有历史版本。

对比一下同一个仓库里另一条出境路径：企业微信的地址 _WECOM_BASE 是 notify.py:25 的一个模块级常量。要把公司数据改发到别的地方，得改代码、过 review、走 ops/release.sh 发版。同样是「数据发给谁」，一个要发版，一个是网页上一个输入框加一次点击。这个不对称本身就是本章最该修的东西。

改造建议（按性价比排序，前两条是必做）
  1. 记录变更前后值。新增 app_setting_audit 表：key / old_value / new_value / changed_by / changed_at / client_ip。api_key 这一项只存 _mask_key 打码值（复用 agent_router.py:776-780），base_url 存明文——它不是秘密，它是证据。这是唯一能回答「上周三那次问答，数据发给了谁」的东西。
  2. base_url 变更独立告警。改动一旦落库，立刻走 notify.push_message 推给 manager 角色 + 记一条不可删的审计行。理由很直白：正常运营中这个值一年改不了一次，任何一次变更都值得惊动人。而 api_key 轮换是常规运维，可以不告警——把这两个字段区别对待，是让告警不被无视的前提。
  3. 域名白名单。在 settings 里加 agent_llm_allowed_hosts（.env 配置、不可从页面改），:849 的校验从「以 http 开头」升级为「host 必须命中白名单」。它防的不是恶意 admin——防的是输错、被钓鱼、被社工，以及「测试时临时指到一个自建代理然后忘了改回来」这种最真实的事故形态。
  4. 变更走审批。本仓库已经有现成的可逆开关范式（settings.export_approval_enabled、sales_order_approval，config.py:51,56）和请款/开票的审批链。base_url 变更完全可以套同一套流程：admin 提交 → manager 确认 → 生效。代价是多一次点击，收益是法务终于有东西可看。

迁移提示：换个客户，「高危配置项」的名字会变（可能是 webhook 地址、SFTP 目标、导出邮箱域），但判据不变——凡是「决定数据发给谁」的配置项，都不该和「决定功能怎么跑」的配置项放在同一个表单、用同一套权限、写同一份日志。进场后第一件事就是把这类配置项从设置页里挑出来单列。

9.3.1 四级分类落到本项目的域

级别判据（泄露后果）本项目对应的域 / 字段能否进 messages
L0 公开本来就对外公司名、产品品类、状态枚举中文名（agent_router.py:45-46）、部门名可以

L2 这一格是本项目真正的争议点，而且没有标准答案——它是业务决定，不是技术决定。可选的三档：全部放行（现状，最好用）／只放行给已签零留存条款的境内供应商（推荐）／按域切开（尾款和客户名走本地模型，采购到货走公有云）。FDE 的职责不是替客户选，是把这张表摆到会议桌上，让能签字的人在上面画一条线。

9.3.2 为什么这和第五章是两件事——讲透

第五章 5.2 已经列过一张几乎一模一样的字段清单。同样的字段、同样的「不许出现」，为什么要写两遍？因为它们防的是不同的对手，控制点也在不同的位置。

维度第五章（权限红线）第九章（出境红线）
防谁本公司员工（销售 A 看到销售 B 的单）第三方推理服务及其所在司法辖区
边界在哪用户与用户之间的行 / 字段可见性公司法人边界，可能还是国境
控制点返回给用户之前——出口序列化时 pop 掉放进 messages 之前——比出口早了整整两轮 HTTP
失效后果内部越权，可查、可追责、可补救数据出境，不可召回；对方日志里有没有、留多久，你不知道
能不能靠权限系统兜住能——菜单 + 行级规则就是为它设计的不能——见下面那个决定性反例
验收方式换身份问同一句，断言结果集不重叠（第七章 L-权限）抓请求体，断言字节流里不出现 L3 字段（本章新增的一层）
决定性反例：管理层问工资

管理层拥有全部菜单权限，menus.py:151-152 对 admin/manager 直接返回全量菜单，deps.py:125 的 user_can_view_project 对管理层无条件放行。所以当总经理问「这个月工资总共发了多少、谁最高」时——第五章的所有门控全部放行，而且放行是对的，他在人事页面上本来就能看到这些数字。

但第九章必须拦。因为「他有权看」和「DeepSeek 可以看」是两个完全不同的命题。这是唯一一类第五章拦不住、而第九章必须拦的场景，也正是这两章不能合并的原因。推论很硬：出境白名单不能实现成权限检查的一个分支，它必须是一层与身份无关的、无条件生效的序列化过滤——无论调用者是谁，工具返回值里的 L3 字段一律不进 messages。

落地形态：写一个 egress_filter(payload) -> payload，白名单制（只允许具名字段通过，不是黑名单），在 _run_tool 返回之后、messages.append 之前无条件调用一次。它不接收 current 参数——签名里没有用户对象这件事本身就是设计声明：这一层不看你是谁。

诚实说明：小参数本地模型很可能撑不住本项目的 function calling

本项目对模型的要求不是「文笔好」，是在 7 个工具里选对那一个、把参数抽对、最多 4 轮内收敛（agent_router.py:522 的 for _ in range(4)，:496 的 tool_choice="auto"）。第七章 7.1 已经记录了一个真实的漂移：同一句「下周有什么到货」，可能调 po_arriving(days=7)，也可能调 po_arrival_overdue——两者语义正好相反。这是 DeepSeek 级别模型的表现。

换成本地 14B 级模型，失败会集中在三处：多工具选择（工具越多越糊）、参数抽取（days=7、code="2026-008" 这类要精确到字符的值）、以及拿到 {"error": "..."} 之后要老实转述而不是编一个答案。而本项目的失败形态不是「答得差一点」，是数字错了——用户数了 13 条，助手说 12 条，从此他不再问助手。这个信任一旦丢掉，省下的合规风险换不回来。

所以真正可行的降配方案不是「把 function calling 硬塞给小模型」，而是把架构改成另一种形状：用规则 / 小分类器把问题路由到工具（本项目已经有这条路——_rule_chat 降级路径，agent_router.py:962，现在它是 LLM 挂掉时的兜底），然后让小模型只负责把结构化 JSON 讲成人话（纯 NLG，不做工具决策）。这样模型能力不足只会影响措辞，不会影响数字。代价是能问的问题变窄——但窄而准，好过宽而不可信。

迁移提示：这个「把 _rule_chat 从降级路径升格为主路径」的方案之所以在本项目成立，是因为它已经写好了。换到一个没有规则兜底路径的客户现场，选 C 就意味着要额外写一套意图路由——把这个工作量算进报价，不要口头答应「本地模型也行」。

9.6　合同与制度：技术做完之后还剩的一半

9.6.1 与供应商签什么（逐条，可直接给法务）

  • 不用于训练：明确覆盖「模型训练、微调、评测、人工标注、服务改进」全部用途——只写「不用于训练」会被「用于服务改进」绕过。
  • 留存期：写具体天数或「零留存」，并写明风控 / 反滥用留存是否例外、例外的留存期和访问人范围。
  • 删除权：客户书面要求后 N 个工作日内删除并出具删除证明；写清楚备份中的副本是否同步删除、多久（这一条最常被含糊过去）。
  • 数据处理地：限定境内 / 指定区域，跨区容灾需事先书面同意。
  • 转委托限制：子处理者需提供名单、变更提前 30 天通知、客户有异议权。
  • 安全事件通知：具体小时数（如 72 小时），不接受「及时」「尽快」。
  • 审计权：至少能拿到最新审计报告；理想是有年度问卷回复义务。
  • 合同终止后：数据处置方式与期限，以及 API 访问密钥的失效时点。

9.7　agent_chat_logs：它既是审计资产，也是一份泄密面

这张表（models.py:1108-1122）每次问答写一行：user_id / username / question / answer（各截断 5000 字，agent_router.py:892,915-916）/ tools_used / via / model / duration_ms / created_at。第七章要靠它做评估集和回归，第五章 5.2.1 已经把它整表拉黑防止 Agent 自己去读它。本章补上第三个视角，也是最容易被忽略的一个：

它是全系统七类行级隔离规则的汇聚点，而且它长期留存、还有 30 份副本
  • 明文存了两份。question 是用户打的字，answer 是模型输出的 Markdown 表格——里面有客户名、尾款金额、供应商、人名，原样落库，没有任何脱敏。
  • 它是横向聚合。销售 A 问过的尾款、采购 B 问过的供应商，答案全在这一张表里。任何能读它的人，一次性拿到全公司所有人「看到过什么」。
  • 没有保留期，没有清理任务。全仓库找不到任何针对这张表的定时删除；overdue_scheduler 只跑那 6 个扫描器。它会一直长下去。
  • 备份把它复制了 30 份。ops/backup.sh:45,51 每天 pg_dump 全库，:20 的 KEEP_DAYS 默认 30、:75 按 mtime 轮转。所以「删掉某一行」在 30 天内是不成立的——这一点必须写进任何对内对外的「删除权」承诺里，否则那句承诺就是假的。
  • 前端遮挡不是访问控制。见 9.6.2 那一行：v-if="isAdmin" 只是不渲染那张卡片，端点本身对 manager 是开的。
建议（保住审计价值，砍掉泄密面）
  1. 分层保留期。明细（question / answer）留 90 天；超期只做字段级清空而不是删行——保留 user_id / username / tools_used / via / model / duration_ms / created_at。这样第七章要的用量统计、工具分布、降级率、耗时分位全都还在，泄密面归零。删行会让统计出现断层，比留着更糟。
  2. 入库前过同一个脱敏函数。9.3.2 那个 egress_filter 写好之后，_log_chat（agent_router.py:909-926）也调它一次。一个函数、两处调用——这样「哪些字段算敏感」永远只有一个定义，不会出现出境防住了、日志里还是明文的分裂状态。
  3. 访问收紧 + 访问留痕。:975 从 require_admin_or_manager 改为 _require_admin_only；谁在什么时候查了谁的记录，本身要记一条。审计日志的访问日志听起来像套娃，但正是内审最先要的东西。
  4. 补三个字段，一次性把三章的缺口都补上。prompt_tokens / completion_tokens（第六章：_llm_request 在 :502 拿到了完整响应体，usage 字段就在里面，:524 只取 choices[0].message 把它丢了）、base_url_snapshot（本章：让每一行都能回答「这条问答发给了谁」）、tool_args（第五章：现在只记工具名不记入参，出事时查不出他到底问的哪个项目）。

9.8　可迁移方法论

9.8.1 进任何客户现场，关于「数据能不能出去」必问的 8 个问题

  1. 法律上能不能出境？先定行业和数据类型再谈技术——个人信息、重要数据、以及金融 / 医疗 / 车联网 / 军工的行业专门规定，路径完全不同。这个问题的答案不是工程师能给的，你的任务是把它问出来并要到书面结论。
  2. 谁有权在这件事上签字？IT 总监签不了。通常是法务负责人、信息安全负责人，或者董事会。找错人的代价是整个项目在验收前一周被叫停。
  3. 现在已经出去的有哪些？先摸基线。本项目的答案很有意思：企业微信推送（notify.py:25）早就把「项目编号 + 项目名 + 尾款金额」发给腾讯了（overdue.py:121-122）。你多半不是第一个把数据发出去的人——找到既有先例，谈判难度立刻降一个量级。
  4. 客户已经批准过哪些云服务？有没有过会的供应商白名单。蹭一个已批准的供应商，比新申请一个快三个月。
  5. 有没有数据分级制度？分到字段还是只分到系统？只分到系统的（「ERP 属于机密系统」）最麻烦——意味着整套 ERP 一刀切成机密，你得推动他们细化到字段，或者接受最严档。
  6. 内审多久查一次，查什么？这个答案直接决定日志留多久、留什么字段。问不到就按「随时可能查、要能回答任意一次问答的完整链路」来设计。
  7. 出了事，谁通知谁，多久之内？把它写进合同和内部制度。这个问题问出来，通常还能顺带发现客户内部的安全事件流程根本没覆盖 AI 场景。
  8. 如果不能出境，愿不愿意为此付 GPU 的钱？这是把技术问题转成预算问题的关键一问，也是最该早问的一问。很多客户嘴上说「绝对不能出去」，听到数字之后会改口成「境内公有云 + 零留存条款可以接受」。不问这一句，你会白做三个月私有化方案。

9.8.2 「客户说不能出境」之后，方案怎么变

客户说：「数据不能出去」 │ ├─ Q1 先追问一句：不能出「公司」，还是不能出「境」？ │ ├─ 不能出境（多数情况的真实含义） │ │ → 方案 A′：境内公有云 API + 零留存条款 + 域名白名单 + 出境字段过滤 │ │ 代价 ≈ 现状，能力不降，两周内可交付 │ └─ 不能出公司 ────────────────┐ │ │ ├─ Q2 预算能不能过会（年 ≥ 数十万）？ │ ├─ 能 → 方案 B：专有云 / 私有化闭源模型，能力最接近公有云 │ └─ 不能 ─────────────────────┐ │ │ ├─ Q3 能不能只让「一部分」数据出去？ │ ├─ 能 → 方案 A+C 混合：L0/L1 域走公有云（采购到货、任务逾期、日期统计） │ │ L2/L3 域走本地（客户名、尾款、人事）——按工具分流，不按用户分流 │ └─ 不能 ────────────────────┐ │ │ └─ Q4 最后一档：规则路由 + 本地小模型只做措辞 （本项目已有 _rule_chat 现成路径，agent_router.py:962） 能问的问题变窄，但数字永远来自代码而不是模型 ── 再不行就诚实地说：这个场景现在不适合上 LLM，先把规则版做厚 ──
三条不随项目变的判据
  • 先摸基线，再谈方案。进场先数清楚「现在有几条出境路径」——企微、邮件、短信网关、云盘、BI SaaS。你要做的那条通常不是第一条，找到先例就找到了谈判的锚点。
  • 出境控制必须与身份无关。只要它实现成权限检查的一个分支，就一定会在某个「他本来就有权看」的场景里失效（9.3.2 那个反例）。白名单制、无条件生效、签名里不接收用户对象。
  • 「发给谁」这件事必须可回溯到每一次问答。不是「我们用的是 X 供应商」，而是「2026-07-14 14:03 那条问答，发给了 https://api.deepseek.com/v1」。做不到这一点，前面所有合同条款在事后核查时都是空的——你无法证明那天的流量没被指到别处去。

本章与前八章的关系：第三章给了「不写 SQL、只调 router 函数」的访问路径，第五章给了「谁能看什么」的红线，本章给的是第三道闸——数据在离开公司之前的最后一次过滤。三道闸在代码里的位置依次是：取数时（权限继承）、返回给用户前（字段脱敏）、放进 messages 前（出境过滤）。它们不能合并成一道，因为它们各自失效时，另外两道都拦不住。
