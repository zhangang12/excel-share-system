第十一章　L2 主动推送：与既有扫描器合流，以及业务口径会变这件事

本章是全书证据最扎实的一章——因为本项目早在 AI 助手之前就有一整套主动推送系统在生产跑着，六个扫描器、四种去重语义、两条推送通道，每一条都是从真实事故和真实抱怨里长出来的。L2 不是"给 Agent 加个定时任务"，是"把 Agent 塞进一套已经在运转、且已经被调教过的提醒体系里，且不把它搞砸"。本章后半段处理一个更麻烦的问题：这套体系依赖的业务口径会自己漂移，而 AI 侧对此毫无感知。

本章的核心结论（先说结果）

你的 Agent 不是客户收到的第一条提醒，是第 N 条。本项目的用户每天已经在收「逾期任务」「尾款到期」「尾款催办」「合同到期」「待办逾期」「未到货」六类推送，走站内消息 + 企业微信双通道。Agent 若再独立推一遍，用户收到的不是"更智能了"，是"这破系统怎么天天弹"。
L2 的正确形态只有一个：Agent 做汇总视角（一张报），扫描器做单件提醒（一条事），两者共用同一套去重事实，且晨报不得为已经被单独推过的条目再触发一次通知。
而这一切成立的前提是口径稳定——但口径不稳定。#332 改了 balance 列的写入语义，五个读它的地方语义各不相同，AI 助手是其中之一，而它没有任何机制知道这件事发生了。

11.1　先把已有的推送系统摊开：六个扫描器，四种去重语义

所有代码在 backend/app/overdue.py（430 行），由 overdue_scheduler(interval_hours=12)（overdue.py:391-430）驱动，在应用启动时挂成 asyncio 任务（main.py:95）。推送统一走 notify.push_message（notify.py:29-84）：先写 messages 表（站内），再尽力而为地发企业微信（notify.py:79-84，失败只记日志，绝不阻塞）。

11.1.2 三个反直觉设计，以及它们各自封住的抱怨

反直觉之一：尾款到期提醒终身只推一次（overdue.py:80-135）

幂等键 (balance_due, ledger.id) 里没有日期（:103-110），只要历史上推过就永久跳过。docstring 里写着来源：「用户 2026-06-17 确认」——这是业务方明确点头的口径，不是开发者偷懒。
理由很实在：尾款到期前 14 天进入提醒窗，如果按天推，一笔尾款从提醒到收回可能要推 30 条，销售会直接把企微应用免打扰。提醒的目的是"让你知道有这件事"，不是"让你天天记得"。
但这条口径留了一个盲区：推完一次之后，这笔尾款拖到天荒地老都不会再有任何声音。所以才有了第 3 个扫描器——它的 docstring 第一句就写着「补上 scan_balance_due『终身只提醒一次』之后的盲区」（overdue.py:139）。两个扫描器扫的是同一张表的同一个条件，只因去重语义不同就必须拆成两个函数，这件事本身就是本章要讲的东西。

反直觉之二：逾期尾款7 天一催、逐级升级（overdue.py:138-194）

week = (over_days - 1) // 7 + 1（:178）算出逾期第几周，然后：week ≥ 2 才抄送销售主管（:184-186），week ≥ 3 才抄送管理层（:187-189）。
这是把"催办强度"和"逾期严重度"绑定，而不是让所有人从第一天就开始收。对管理层来说，收到这条消息本身就携带信息量："这笔已经拖了三周了"。如果第一天就抄送管理层，这条信息就退化成噪音，管理层会像所有人一样学会无视它。
配套的去重是"距最近一次催办不足 7 天则跳过"（:167-177），注意它查的是该台账最近一条 balance_overdue 消息，而不是"该用户最近一条"——所以升级抄送出去的那几条也共用同一个键，下一轮整体推迟 7 天。这是个很容易写错的地方：如果按用户去重，主管会在第 2 周和第 3 周各收一次而销售被顺延，节奏就乱了。

反直觉之三：未到货提醒业务时间 <15:00 直接跳过（overdue.py:319-323） 

now = datetime.now(_CN_TZ)
if now.hour < 15:
    log.info("[scan_po_arrival_overdue] 业务时间 %02d 时 <15 时，跳过当日未到货提醒(#292)", now.hour)
    return {"scanned": 0, "notified": 0}
来源是反馈 #292：货车中午才发车，早上扫出来的"今天该到还没到"绝大部分在下午自然就到了。早报全是误报，采购员看两天就不看了。
这五行代码是本书里我最喜欢的证据。它说明了一件普通工程师很难自己想到的事：提醒的正确时机不由数据决定，由物流决定。没有任何一张表里写着"货车中午发车"，这条知识只存在于采购员的脑子里，而它直接决定了一个后台任务的判据。这就是 11.6 节要展开的"口径长在人的脑子里"。

11.1.3 一个必须先修的调度缺陷

现存问题：interval_hours=12 与 <15:00 跳过 组合起来，可能让第 6 个扫描器永远不推

overdue_scheduler（overdue.py:391-430）是"跑一轮 → sleep(12h) → 再跑一轮"，起点是进程启动时刻，不是墙上时钟的固定点。main.py:95 在 lifespan 里 create_task(overdue_scheduler())，而进程启动时刻 = ops/release.sh 发版重建容器的时刻。
于是：若某次发版落在凌晨 2 点，此后每一轮扫描都发生在 02:00 和 14:00——两个时刻的 now.hour 都 < 15，scan_po_arrival_overdue 每一轮都在 :322 处 return，一条未到货提醒都发不出去，且日志里只有一行 info，没有任何告警。若发版落在早上 9 点，扫描在 09:00 和 21:00，则每天 21:00 推一次——晚上九点推"今天该到的货没到"，业务价值接近零。
只有发版时刻恰好落在 03:00-11:00 之间，这个扫描器才会在 15:00-23:00 的合理时段工作。换句话说，一个被业务方专门提需求（#292）加上的时间窗，它到底生不生效，取决于上一次部署是几点钟。
这不是本章顺手挑的刺——它是 11.3 节"晨报为什么必须按墙上时钟触发、而不能挂在 interval_hours 上"的直接依据。做 L2 定时推送之前，先把调度器从"固定间隔"改成"对齐固定时刻"。

调度器的另外两件事做得是对的，L2 应当原样复用而不是另起炉灶：

  • flock 单实例（overdue.py:371-388）。生产是 uvicorn --workers 4，四个进程各跑一遍启动流程；如果四个都跑扫描，它们会同时通过"messages 表当日去重"的检查（典型 check-then-act 竞态），同一条提醒被推四份。fcntl.flock 抢文件锁，抢不到的 worker 直接不跑 scheduler，HTTP 服务不受影响。任何新增的定时推送必须挂进这同一个被锁保护的循环里，自己再起一个 asyncio 任务就等于把这道锁绕过去了。
  • 每个扫描器独立会话、独立 try（overdue.py:399-429）。一个扫描器抛异常不影响其余五个。晨报作为第七项加进去时，这个结构要照抄——晨报聚合的查询面比任何单个扫描器都宽，它挂掉的概率也最高。

还有一组手动触发端点（main.py:183-215，POST /api/internal/overdue-scan 等，管理层权限）。它们的真实用途是排障和补推：业务方说"我没收到"，你先手动跑一次看返回的 {scanned, notified}——scanned>0 且 notified=0 说明被去重挡了，scanned=0 说明判据没命中。晨报上线时应当同步加一个 POST /api/internal/morning-report-scan，理由完全相同。

11.2　Agent 进来以后，三种错误接法

接法做法为什么错
替代关掉六个扫描器，全部改由 Agent 生成推送把三年积累的口径（终身一次／逐级升级／15:00 特判／只推下单人）一次性清零，换成一个不确定性的模型。第一周就会有人问"为什么我合同到期没人告诉我"
并行扫描器照跑，Agent 再独立推一路自己算的同一件事推两遍，且两遍的口径必然不一致（11.5 节会证明为什么必然）。用户信任的是先到的那条，之后两条都不信
套壳让 LLM 把扫描器的文案"润色"一遍再发纯增加成本与失败面。overdue.py 的文案是模板拼的、稳定、可 diff；换成模型生成之后，同一件事每天措辞不同，用户反而更难扫读，而且多一次可能超时的外部调用
汇总扫描器=单件提醒（一条事），Agent 晨报=汇总视角（一张报）；晨报不重复触发已被单独推过的条目的通知这是唯一一种"新增信息量 > 新增打扰量"的接法。见 11.3

为什么"汇总"确实增加了信息量而不只是重排？因为六个扫描器每一个都只看自己那张表，没有任何一条推送能回答"我今天整体要盯什么"。采购员早上想知道的是"该到的三件、拖最久的那件、外加我那两个项目的尾款要到期了"——这需要跨四个域聚合，而这正是 tool_morning_report 已经在做的事（agent_router.py:219-238）。

11.3.2 设计：五条规则

规则 1：晨报是视图，不是新事实源

晨报的每一节都必须调用与扫描器同一份口径，而不是自己再写一遍 where 条件。这一点今天已经部分做到了、但做法是错的——_hr_due_rows 的 docstring 明写「口径同 overdue.scan_hr_reminders」（agent_router.py:200），tool_balance_due 的 docstring 明写「口径同 overdue.scan_balance_due」（agent_router.py:139）。"同"是靠注释保证的，不是靠代码。30 天/7 天窗口在 overdue.py:206-207 和 agent_router.py:206-207 各写了一遍；14 天窗口在 overdue.py:80（默认参数 advance_days=14）和 agent_router.py:141（硬编码 timedelta(days=14)）各写了一遍。
做 L2 之前先把这些判据抽成共享的谓词函数（放 app/calibers.py 之类），扫描器和 Agent 工具都从那里取。否则你就是在用一个新功能把口径漂移的概率翻倍。

规则 2：出现 ≠ 通知——晨报必须尊重各扫描器的去重窗口

这是本节最关键的一条。一条尾款今天已经被 scan_balance_overdue 单独催过了，晨报里可以再出现（它是当天全景的一部分，少了它这张报就不完整），但不应该让用户的手机再响一次。
实现上不需要新表：push_message 已经支持 exclude_user_ids（notify.py:38），且幂等事实全在 messages 表里。晨报生成后，先反查该用户今天已收到的 biz_type ∈ {order_overdue, balance_due, balance_overdue, hr_contract, hr_regular, mgmt_todo_remind, po_arrival_overdue} 的消息集合，然后：

情况晨报里是否触发通知
该用户今天一条单件提醒都没收到正常渲染推（站内 + 企微）
今天收到过单件提醒，但晨报里还有它没覆盖的条目正常渲染全部，已推过的条目标灰/带"已提醒"标记推，但文案只强调新增的部分
晨报内容被今天已推的单件提醒完全覆盖正常渲染（用户主动打开能看到）只写站内、不发企微
晨报四个小节 count 全为 0不生成完全不推（见规则 5）

注意第三行"只写站内不发企微"这个中间档：push_message 现在是站内和企微捆绑的（notify.py:75-84），要支持这一档需要给它加一个 silent: bool = False 参数，在 :79 的企微分支前判一下。这是本章唯一要求改动既有推送服务的地方，改动量约 3 行，但它是整个"信任预算"能不能守住的开关。

规则 3：分层——三层视角，一套域门控

不要给所有人发同一张报。复用 user_menu_keys 的既有语义即可自然分出三层：

层判定看到什么依据
管理层role_codes ∩ {admin, manager}（menus.py:151-152 直接返回全量菜单）四个域全量 + 总数；不给明细，明细点进页面看管理层要的是"哪块在恶化"，不是 20 行表格
主管有该域菜单 + 角色是 *_lead本域全量，部门逾期按 order_depts 收窄到有菜单的部门agent_router.py:437-439 已实现该收窄
个人普通账号本域中与自己有关的行：采购按 buyer_id、尾款按 sales_uid、任务按 worker_id今天做不到——见下方警告

"个人层"是这套设计里唯一需要新代码的部分，而且它卡在第五章那个 P0 上：tool_morning_report 内部调用的 tool_po_arrival_overdue / tool_balance_due / tool_overdue_orders 三个工具的签名里都没有用户对象，只有 tool_project_status 接收 current（agent_router.py:241）。今天的晨报是"域级"的：只要你有 purchase_mgmt 菜单，你就看到全公司的未到货 Top5，包括别人负责的。而 scan_po_arrival_overdue 在 2026-07-26 已经收窄到只推下单人本人（overdue.py:359-363）。
也就是说：定时晨报如果今天就上，它会以推送的形式，把扫描器刚刚收窄掉的东西重新广播出去。行级越权从"用户主动问才泄露"升级成"每天早上自动送到所有人手机上"。L2 的准入条件：行级过滤修复（第五章）必须先于定时晨报上线，没有例外。

规则 4：时间——按业务节律选，按墙上时钟触发

"晨报当然是早上 8 点"是个未经检验的直觉。本项目的证据指向别处：

  • 采购域的有效时间是 15:00 之后（#292，overdue.py:319-323）。8:00 的晨报里那一节的准确率约等于早报误报率——业务方为此专门提过反馈。
  • 尾款/人事/待办没有时间敏感性，早上推最好（当天还有时间处理）。
  • 部门逾期任务要在派工之前送到主管手里，本项目的班前会在早上。

所以正确答案不是一张报一个时间，是两班：
08:30 早班报＝尾款到期 + 人事到期 + 部门逾期 + 管理层待办（不含采购未到货，或只含"已超期 ≥2 天"的硬逾期——那部分与货车发车无关）；
15:30 午后报＝采购未到货（紧跟 <15:00 跳过 的窗口之后），只推采购域。
触发方式必须是墙上时钟对齐：计算"距下一个 08:30/15:30 还有多少秒"然后 sleep，而不是 sleep(12h)。理由见 11.1.3——固定间隔的相位由部署时刻决定，而部署时刻是随机的。落地上最省事的做法是把 overdue_scheduler 的循环周期改小（如 interval_hours=1 或直接 30 分钟），在循环体内按"当前业务小时 + 当日是否已推"决定各任务是否执行——这同时顺手修好了 scan_po_arrival_overdue 那个静默失效，因为一小时一轮必然会有若干轮落在 15:00 之后。

规则 5：空报不推

四个小节 count 全为 0 时不生成、不推送。这条看着理所当然，但很多晨报系统会推一句"今天没有异常，一切正常 ✅"——那是在用用户的注意力换你自己的存在感。用户对"系统还活着"的确认需求远低于你以为的；真想确认，去看后台的 log.info 行数。

11.4　信任预算：每一条无价值推送都在花钱

把用户对通知的注意力当成一个会被消耗、且回补极慢的预算。花光之后的表现不是投诉，是沉默——企微里把这个应用设为免打扰，站内消息角标常年三位数，然后某天真正紧急的那条尾款催办也没人看见。这是主动推送唯一的、也是不可逆的失败模式。

本项目已经因此收窄过一次口径，证据在代码注释里：

# 🆕 2026-07-26 口径收窄：只推采购下单人本人提醒及时跟进，不再推主管/管理层（反馈信息太多）。
# 无归属采购员的明细不再推任何人（原兜底推主管/管理层，一并去掉）。

—— overdue.py:359-361。注意括号里那四个字：反馈信息太多。这就是预算超支的账单形式：不是"提醒错了"，是"提醒对了但太多"，于是整类提醒被砍掉一半收件人。

read-all 这个陷阱值得单独说：它让唯一现成可用的指标失效。修法很轻——给 Message 加一列 read_via（item / bulk），read-all 写 bulk，逐条已读写 item，忽略率只统计 read_via != 'bulk' 的样本。一列字段换回一个能看的指标。
在没有这一列之前，你对"用户到底看不看"这件事的所有判断都只是感觉——而在推送这个领域，开发者的感觉系统性地偏乐观，因为开发者收到的是自己写的提醒。

11.4.2 「宁可少推」的四条硬规则

  1. 默认静默，显式放行。新增一类推送时，默认只写站内消息；只有当业务方明确说"这个必须弹到手机"，才开企微通道。反过来的顺序（默认全推，收到抱怨再关）已经在本项目发生过一次，代价是 overdue.py:359-361 那次收窄。
  2. 升级，不重复。同一件事第二次说话必须带新信息——要么升级收件人（scan_balance_overdue 的三级模式），要么变更严重度。同样的话再说一遍，除了消耗预算什么也不产生。
  3. 推送对象越窄越好，宁可漏抄送不要广播。scan_po_arrival_overdue 从"下单人+主管+管理层"收窄到"只有下单人"之后，这类提醒的实际处理率是上升的——因为收件人从"三个人互相以为对方会处理"变成了"一个明确责任人"。
  4. 给一个体面的关闭方式。没有退订入口时，用户的退订方式是企微免打扰——那是一刀切关掉你所有推送，包括真正紧急的。给出"关晨报、留催办"的粒度，等于把用户的一次性核选项换成可协商的。
一句话记法

推送的价值 = 信息量 − 打扰量，而打扰量是复利的。第一条没价值的推送成本很低，第二十条的成本是"这个应用以后说什么我都不看了"。所以判断标准不是"这条有没有用"，是"这条的用处，配不配得上它带走的那点信任"。

11.5　业务口径会漂移，而 AI 侧感知不到

11.5.1 活证据 #332：一列两义，五个读者

2026-08-01，业务方提了一个看起来非常小的需求：销售台账里填了"尾款到款时间"（一条批注），尾款金额应该自动归零。实现在 sales_router.py:611-624：

if data.field == "balance":
    if note_val:
        if led.balance:
            led.balance_contract = led.balance
        led.balance = 0
    elif led.balance_contract is not None:
        led.balance = led.balance_contract
        led.balance_contract = None

代码上方的注释（sales_router.py:611-616）把问题讲得很清楚：balance 是双语义共用列——催办/账龄/现金流/AI 只认 balance > 0 判"未收"；而台账合计与销售报表把它当"合同尾款条款额"统计。清零之后，前一组行为正确（立即停催，这正是诉求），后一组数据会随回款变小。当面说明过，用户仍选直接清零；为把"不可逆"兜住，加了 balance_contract 存清零前的值（models.py:314），删批注即原样恢复。

后果的形态是这样的：某天销售问助手"我还有哪些尾款没收"，助手漏掉了一笔——因为财务同事上周在那行插了到款时间（钱其实还在路上，只是排了付款计划）。助手没错，扫描器没错，写入侧也没错，错的是没人告诉助手口径变了。而这类错误在第七章的评估集里表现为"某条一直绿的用例突然变红"——如果你有那条用例的话。
更普遍地说：Agent 是所有业务口径的下游消费者，但它在任何一次口径评审里都没有座位。这是 FDE 交付之后系统性失效的头号原因，超过模型能力、超过 prompt 质量、超过工具设计。

11.5.4 怎么让口径变更自动通知到 Agent 维护者

先说清楚现实约束：本仓库没有测试 CI——.github/workflows 下只有 desktop-build.yml（桌面端打包），测试是"backend/.venv/bin/python tests/xxx.py 独立脚本 + 临时 SQLite"的人工约定。所以任何"挂个 CI job 卡住"的方案在这里落不了地。可落地的是下面这套，按投入从小到大：

层做法成本能挡住什么
① 口径标记在每个权威口径函数上方加一行结构化注释：
# @caliber: balance_unpaid readers: overdue.scan_balance_due, agent.tool_balance_due, reports.receivables
标记本身就是文档，且可被 grep		一次性写 8-10 处改动者在改这一行时眼睛能看到下游是谁。这是最便宜、也是收益最高的一层
② grep 守卫脚本ops/check_calibers.sh：对 git diff --name-only 命中的文件，grep 出改动块附近的 @caliber 标记，打印"你动了 X 口径，下游有 Y、Z，请重跑评估用例 Ennn"。挂 pre-push hook（不阻断，只打印）半天忘记看注释的情况。不阻断很关键——阻断式检查在没有 CI 的仓库里会被 --no-verify 绕过，然后彻底失效
③ 写进检查清单AGENTS.md 现有铁律「AI 助手的所有数据工具永远只读 SELECT」（AGENTS.md:56）旁边，补一条「改动带 @caliber 标记的函数，必须同步检查 agent_router.py 的对应工具，并在交接文档记录」十分钟这是给下一个人（包括 AI 编码助手）看的。本仓库的开发约定就是靠 AGENTS.md + 交接文档.md 传递的，走这条路才符合既有习惯
④ 口径快照测试一个脚本，对固定的小数据集跑一遍所有权威口径函数，把结果哈希存进 tests/caliber_snapshot.json。口径变了 → 哈希变了 → 必须显式更新快照文件，这个文件的 diff 就出现在 review 里1-2 天无声的行为变化。这是唯一能捕捉"代码没动但依赖的数据语义变了"的手段（比如 balance 清零逻辑改在别的文件里）
为什么不是"加个 CI 就行"

因为口径漂移大多数不以代码变更的形式发生。export_approval_enabled 翻一下、管理层在 OA 页面加一种单据类型、某个部门重组、录入习惯变化导致孤儿采购涨了三倍——这些全都是零行代码 diff。CI 对它们完全失明。
真正兜住这类漂移的是③ 的人的约定 + ④ 的快照，再加上第七章那条：评估集要定期重跑，不只是在改代码时跑。建议节奏是"每次发版 + 每月一次全量"，全量那次的目的就是抓这种无 diff 漂移。

11.6　FDE 特别注意：口径不写在文档里，长在代码和人的脑子里

本项目有 交接文档.md、AGENTS.md、docs/handbook/ 一整套文档，算是文档相当齐全的中小企业系统了。即便如此，本章引用的这些口径——货车中午发车所以 15:00 前不推、尾款提醒终身一次是 2026-06-17 用户确认的、催办第 2 周才抄主管、balance 是双语义列——没有一条能在需求文档里找到。它们全部只存在于两个地方：代码注释和某个人的记忆。这是常态，不是本项目的疏忽。

11.6.1 三条挖掘路径

路径一：读代码，专门找"不该存在的东西"

正常业务逻辑不需要挖，它写在那儿。要挖的是异常物，每一个异常物背后都有一条没写进文档的口径：

  • 魔法常量与特判：if now.hour < 15（overdue.py:321）、advance_days=14、window=30/7。凡是硬编码的数字，背后必有一次讨论。
  • 带工单号的注释：本仓库大量 #292 #332 #303 #78 这样的标记。这是最高效的入口——顺着编号去翻反馈原文，你能读到用户的原话，那才是口径的一手来源。
  • 同一件事写了两遍的地方：scan_balance_due 与 scan_balance_overdue 扫同一张表同一条件却拆成两个函数；_hr_due_rows 的窗口与 scan_hr_reminders 各写一遍。重复不是懒，是两个语义被迫共用一份数据。
  • 可逆兜底：balance_contract（models.py:314）、ship_receivable 的批注联动（sales_router.py:608-610）。凡是"为了能撤回而多存一列"的地方，都是曾经有人被不可逆操作坑过。
  • 被收窄过的范围：overdue.py:359-361 的 "2026-07-26 口径收窄"。收窄记录 = 上一轮做过头的证据。
路径二：找到那个"什么都知道的人"

每家公司都有一个。他通常不是项目对接人，也不是 IT 负责人——他是那个所有人在群里 at 的人：车间的老班长、做了八年的销售内勤、财务里管台账的那位。识别方法有三个：① 问三个不同部门"这个数字不对的时候你问谁"，答案会收敛到同一个名字；② 看系统里谁的操作审计最多、谁提的反馈最多；③ 开会时看谁一开口别人就停下来听。
问他的方式很重要，不要问"你们的规则是什么"（他会背一遍制度，那是理想态）。要问具体的、带反例的问题：

  • "上次这个提醒推错，是什么情况？"——直接指向特判的由来。
  • "这个字段有没有那种看着是 A 其实是 B 的时候？"——直接指向双语义列。balance 就是这么被问出来的。
  • "如果我按这个规则算，会不会有人跳出来说不对？谁？"——找出口径的利益相关方，报表口径的争议永远来自"这个数影响谁的考核"。
  • "这条规则从什么时候开始的？之前是怎么样？"——口径的历史比口径本身更有信息量，它告诉你下次会往哪儿变。

另外一条实践经验：他说的和他做的不一致时，以他做的为准。去看他的实际操作记录，而不是他的描述。

路径三：用真实数据反向验证——差值就是口径

这是最可靠的一条，因为它不依赖任何人的记忆。做法：同一个问题用两种方式各算一遍，然后死磕差值。

  1. 让业务方给一个他信任的数字（他自己维护的 Excel、他每周汇报的那个数）。
  2. 你用系统数据按你理解的口径算一遍。
  3. 两个数几乎不会相等。差值不是 bug，差值是你还不知道的口径。
  4. 逐条对差异行，每对上一行就问一句"这行为什么你算/不算"，把答案写下来。

本项目最典型的样本就是 reports_router.py:407-409 那段警告注释——毛利口径明写「不含人工/运费，是材料边际贡献口径」，而业务方嘴里的"毛利"大概率含人工。这种差异如果不在上线前对出来，就会在上线后以"你这个数是错的"的形式对出来，而那时你已经赔掉了一轮信任。
对完之后要做一件事：把每条口径连同它的来源写成台账——口径名 / 权威位置（文件:行号） / 下游读者 / 来源（谁在哪天确认的） / 上次验证日期。这份台账就是 11.5.3 那张对照表的原料，也是你交接时唯一真正有价值的文档。

11.7　知识型问答的兜底：不做 RAG，但要优雅

架构四不做里有一条是"不做 RAG"（第三章）。这个决定是对的：本项目没有值得检索的语料库——制度文件散在微信群和几个 Word 里，总量不到几十页，且更新频繁。为几十页会变的文档上一套向量库、切分、召回、重排，运维成本远超收益，而且召回不准的知识问答比不回答更危险——它会自信地编一个流程出来。

但用户一定会问。"报销流程怎么走""这个字段什么意思""为什么我看不到这个页面"是任何企业 Agent 上线第一周的高频问题。

11.7.1 一个关键发现：本项目的"流程"不是文档，是数据

"报销流程怎么走"的答案在数据库里，不在文档里

oa_approval_steps 表（models.py:927-941）存的就是某部门 + 某单据类型 → 第几步由哪个角色审批，管理层在页面上维护（oa_router.py:198-246），读取端点 GET /api/oa/chains?department_id=&doc_type=（oa_router.py:180-190）。单据类型字典在 oa_doc_types（models.py:914-924），种子里就有 expense「费用报销」和 travel_expense「差旅费用报销」（data_migration.py:1851-1860）。
所以"报销流程怎么走"是一个结构化查询，不是一个文本检索问题。它甚至比 RAG 好得多：答案永远是最新的（管理层改了配置，回答立刻跟着变）、永远是这个人所在部门的（department_id 就是他的部门）、且可验证。
这就是"不做 RAG"这个决定背后真正的道理：不是因为 RAG 难，是因为在 ERP 里绝大多数"知识问题"其实是伪装成知识问题的数据问题。它们的权威答案已经以配置、字典、状态机的形式存在系统里了。做 RAG 等于放着结构化事实不用，去检索一份描述这些事实的、可能已经过期的文档。

11.7.2 三类分诊

类型例子正确处理为什么
A. 伪装成知识的数据问题"报销要几级审批""我这个申请卡在谁那""采购申请归哪个部门审"做成确定性工具：读 oa_approval_steps / oa_requests，按调用者部门与权限返回权威答案在库里，且永远最新。这类问题值得投入
B. 真知识但极小且稳定"这个字段什么意思""尾款和发货前付有什么区别""毛利是怎么算的"静态 FAQ 工具：一个 Python dict 或 JSON 文件，几十条，人工维护，命中即原文返回并标注最后更新日期条目少、变化慢、答案短。见下方四个准入条件
C. 真知识且在系统之外"年假怎么算""出差住宿标准多少""劳动合同到期不续签怎么补偿"优雅拒答 + 指路，并记录这个问题答案不在你的系统里。编造的代价是真实的——员工会拿 AI 的回答去跟 HR 争

11.7.3 优雅拒答长什么样

拒答有好坏之分。坏的拒答是"抱歉，我无法回答这个问题"——用户得到零信息，且会认为这系统很笨。好的拒答有三个成分：承认边界 + 给出去处 + 收集需求。

这个我查不到——报销标准属于制度文件，不在项目管理系统的数据里。
你可以在 OA 审批 → 费用报销 里看到你们部门的审批流程（这个我能查），
但具体的标准金额要问人事或看公司制度文件。
（已记录这个问题，如果问的人多，我们会考虑把它做进来）

第三句不是客套。agent_chat_logs（models.py:1108-1122）已经在记 question / answer / tools_used / via；tools_used 为空 + 回答含拒答语义的记录，就是天然的"答不了的问题"池。第七章把它列为可观测清单第 19 条：这是需求池，不是垃圾桶。每月扫一遍这个池子，重复出现 5 次以上的问题就是下一个工具或下一条 FAQ 的候选。

11.7.4 什么时候值得做静态 FAQ（四个条件，缺一不做）

  1. 同一个问题在"答不了的池子"里出现过 ≥5 次，且来自 ≥2 个人。一个人问五次是他的个人习惯，不是需求。
  2. 答案能在 3 句话内说完，且不需要看具体数据。需要看数据的（"我的年假还剩几天"）不是 FAQ，是工具——去接 HR 模块，别写死。
  3. 答案有明确的责任人愿意签字。FAQ 条目必须有 owner，因为它一旦写进系统就变成"公司口径"。没人愿意签字的条目说明它本身有争议，那更不该由 AI 来说。
  4. 条目总数预期 < 50。超过 50 条就该开始考虑它是不是应该长在 OA 文档中心里，由 OA 负责维护，Agent 只负责指路。
什么条件下仍然不该上向量库

就算 FAQ 涨到几百条，也先试关键词/别名映射 + 精确命中再考虑向量检索。原因：企业内部的术语是封闭且高度特化的（"尾款""发货前付""封板组""冷作图纸"），这些词的语义模型不一定见过，向量召回未必比一张同义词表准；而 FAQ 答错一条的代价，是用户拿着错答案去执行。
真正需要上向量库的门槛是：语料上千页、有专人维护、且问题确实是自然语言模糊匹配的（比如产品手册、法规库）。制造业 ERP 的内部制度库几乎从不满足这三条。

11.8　可迁移方法论：进场先盘点客户已有的通知系统

进场第一周就要做的「通知资产盘点」

目标很直接：确保你的 Agent 不是客户收到的第 N+1 个吵人的东西。七个问题，一天之内可以问完：

  1. 今天系统会主动给人发什么？（列全清单：站内、邮件、短信、企微/钉钉/飞书、微信群机器人、甚至打印出来贴在墙上的表）
  2. 每一条的判据、频率、收件人是什么？——照 11.1.1 那张表的列填。填不满就是你还没摸清。
  3. 哪些是"当初开了后来被吐槽然后关掉/收窄"的？——这是最值钱的一问，直接给出客户的信任预算已经花在哪儿了。找收窄记录的最快方式是 git log 里搜"太多""不用推""关掉"。
  4. 用户实际是怎么处理这些通知的？——去看一个人的手机。他有没有把这个应用设成免打扰？未读数是多少？这一眼胜过一小时访谈。
  5. 有没有"反直觉"的时间/对象规则？——比如本项目的 15:00。问法："有没有哪个提醒是故意不在某个时间发的？"
  6. 去重是怎么做的？有没有幂等键？——没有幂等键的系统一定重复推过，那笔信任债你会继承。
  7. 谁有权关掉一类推送？——如果答案是"只有开发能改代码"，那么退订入口就是你要补的第一件事。
换个项目会怎么变
场景差异本章哪些结论仍成立哪些要重做
客户没有任何既有推送系统信任预算、宁可少推四条规则、空报不推、按业务节律选时间——全部成立，而且更重要（你的第一条推送会定义用户对整个系统的期待）没有现成口径可复用，你得自己从零建。先建幂等键和去重语义，再谈推什么；顺序反了必然重复推送
客户用的是钉钉/飞书/邮件而非企微双通道（站内+外部）、失败降级不阻塞主流程、silent 档位外部通道的已读回执能力不同：邮件几乎不可测、飞书卡片可带交互回调。度量方案要跟着换，L3 的卡片确认也可能直接落在 IM 侧
客户已有成熟 BI/报表推送"汇总视角 vs 单件提醒"的分工晨报可能已经存在了。那就别做晨报，改做"异常解释"——BI 推数字，Agent 解释"为什么这周应收涨了 40%"
行业节律不同（零售看日、医院看班次、SaaS 看周）"提醒时机由业务而非数据决定"15:00 这个具体数字毫无迁移价值，但"去找那个数字"这个动作必须做。问法固定：你们这行，什么时候的数据才算数？
客户是大型企业、有正式变更管理口径台账、@caliber 标记、评估用例对照表①-④ 那套轻量方案要升级成正式流程：把 Agent 维护者加进变更评审的通知列表。这在大企业反而更容易——那儿有 CAB，你只需要争取一个座位
知识库确实很大且有专人维护三类分诊、优雅拒答模板、"答不了的问题"池B 类可能真的需要检索。但仍然先做完 A 类（伪装成知识的数据问题）——那部分的投入产出比永远高于 RAG

最后一句：主动推送是 Agent 唯一一个"用户无法选择不听"的能力

问数是用户来找你，答错了他下次不问；推送是你去找用户，推错了他关掉整个通道，连带把真正重要的那条也关掉。这是 L1 到 L2 的真正门槛——不是技术门槛，是权限门槛：你从"被查询者"变成了"占用别人注意力的人"。
而这份权限的正当性完全建立在口径正确之上。#332 讲的就是这件事：口径会在你不知情的时候改变，改的人是对的，改的过程是审慎的，只是没人想到要通知 AI 这一侧。所以本章的两个主题其实是一个：你能不能持续地推对，取决于你有没有一条能感知口径变化的信道。没有那条信道，主动推送就是一门在慢慢透支信任的生意——它今天推对了，只是因为口径还没变。
