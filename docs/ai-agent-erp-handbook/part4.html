第四章　编排层：AgentScope 怎么接，以及它帮不了你什么

这一章要回答三个问题：既然现有的 Agent 循环只有三十行手写代码而且跑在生产上，为什么还要引入框架？引入之后哪些事真被省掉、哪些事一件都省不掉？如果三个月后 AgentScope 又改一次架构，我要付多大代价。

4.1　先算清楚：编排层到底帮你省了什么

backend/app/routers/agent_router.py:522 起的这段就是本项目全部的 Agent 循环：

for _ in range(4):                       # agent_router.py:522 工具轮次上限
    data = await _llm_request(messages, model, cfg, schemas)
    msg = data["choices"][0]["message"]
    tool_calls = msg.get("tool_calls") or []
    if not tool_calls:
        return (msg.get("content") or "").strip(), tool_names
    messages.append(msg)                 # :531 含 tool_calls 的 assistant 消息原样回灌
    for tc in tool_calls[:4]:            # :532 每轮最多 4 个工具，串行 await
        result = await _run_tool(name, args, db, user)     # :539
        messages.append({"role": "tool", "tool_call_id": tc.get("id"),
                         "content": json.dumps(result, ensure_ascii=False, default=str)})
raise RuntimeError("LLM 工具调用轮次超限")   # :546

三十行不到，跑了半年没出过循环层面的事故。第一个诚实的结论是：ReAct 循环不是难点，它是这个系统里最简单的一块。难的是另外三件事，而这三件框架一件都不管：

  • 权限继承。_run_tool（agent_router.py:427）只做到域级门控，页面侧做的是行级过滤，两者差一个数量级（案例见 3.1）——没有框架会替你补这一级。
  • 卡片契约。「哪些卡片类型合法」「端点由类型在可信前端代码里决定」这套白名单，是业务约束不是编排约束。
  • 出口守卫。系统有独立的导出审批闸门（export_router.py，开关 settings.export_approval_enabled，判定在 deps.py:75 ensure_can_export）。AI 一次吐 200 行等于绕过它——Top-20 是红线不是偷懒。而框架默认会把工具返回值原样塞进上下文。
选型标准要换一个方向

最难的三件事框架都不管，所以问「它功能多不多」是问错了。要问的是「它会不会挡路」——会不会让我没法把 current 注进去、没法在出口拦一刀、没法在并发下保证状态不串。一个功能少但完全不挡路的框架，远好过一个功能全但把请求上下文藏在全局单例里的框架。

那还引它干嘛？因为下面这些活「烦但不难」，正适合外包：多轮消息装配与 tool_call_id 配对、并行调用的 gather 与异常归并、流式分片与中断、结构化输出的重试。messages.append(msg)（:531）这种手工回灌改一次协议就得全量回归；而并行、流式现在压根没有——工具是 for tc in tool_calls[:4] 串行等的，前端是三点动画（frontend/src/views/AgentView.vue:247 的 .dot）等到底。

4.2　AgentScope 的契合点，逐条对应本项目需求

本项目的硬需求AgentScope 的对应机制现状证据
asyncio 原生（硬门槛，不满足直接出局） Agent / Toolkit / Model 全链路 async，工具本身就是 async def database.py:28 get_db 是 async generator，全栈 async SQLAlchemy；七个工具都是 async def。同步框架意味着把 ORM 塞进线程池——4 worker 的 uvicorn 上会直接改变连接池行为
注入模型看不见的请求级上下文 Toolkit.register_tool_function(fn, preset_kwargs={...})：preset 参数不进 JSON Schema，模型既看不见也无法填写 TOOL_SCHEMAS（agent_router.py:361）是手写的，参数表就是模型能看到的全部；current 一旦作为普通参数出现，模型就能篡改身份
审计要记到工具粒度 pre_reply / post_reply / pre_acting / post_acting 四类钩子 + register_instance_hook()（实例级，不污染类） _log_chat（agent_router.py:909）只在端点层记一条；agent_chat_logs（models.py:1108）有问/答/工具名/模型/耗时，缺 token、成本、工具入参、轮次
并行工具 ReActAgent 支持 parallel_tool_calls，内部 asyncio.gather agent_router.py:532 串行 await；晨报（:219 tool_morning_report）四个域顺序查，四段独立 SELECT 白等三段
流式 reply_stream() 事件流 前端非流式，AgentView.vue:247 三点动画。L1 一轮就完还能忍；L3 单轮明显更长，流式从「体验」变「刚需」

公道话：五条里真正只有 AgentScope 给得利落的是 preset_kwargs，其余四条不少框架都有。决定性理由是「asyncio 原生 + 上下文能藏住 + 组件可拆开单用」这个组合，不是功能清单更长。

4.3　五个必须堵死的问题

(a) preset_kwargs 是注册时绑定，不是请求时

本章最贵的一条。preset_kwargs 在 register_tool_function 调用的那一刻就被闭包捕获，而 current 每个请求都不同、db 每个请求都是新会话。所以 Toolkit / Agent / Model 三者必须每请求新建。下面是最容易写出来的灾难代码——它看起来还挺「有性能意识」：

# ❌ 灾难写法：进程内懒加载单例（"每次 new 太浪费"）
_AGENT = None

async def run(message: str, current: models.User, db: AsyncSession):
    global _AGENT
    if _AGENT is None:                          # 只有第一个请求会走进来
        tk = Toolkit()
        ctx = ToolCtx(user=current, db=db)      # ← 王芹的身份 + 王芹那次请求的 session
        tk.register_tool_function(po_arrival_overdue, preset_kwargs={"ctx": ctx})
        _AGENT = ReActAgent(name="pms", model=_model, toolkit=tk)
    return await _AGENT(Msg("user", message, "user"))   # 之后所有人都以王芹的身份查数

后果分三层，一层比一层坏：

  1. 身份被烤进去。第一个访问的人是谁，全公司就以谁的身份查数。第一个是采购员王芹（buyer+finance+logistics），别人问「未到货」拿到的是王芹的单；第一个是 admin，所有人都拿到全公司视图——而该菜单对所有登录用户无条件开放（menus.py:154：set(configured) | {"agent"}）。
  2. 与现存越权叠加，性质变了。现在的线上问题是「域门控通过后无行级过滤」，最坏是有采购菜单的人看到同一份全量数据——错，但至少是确定的错。单例把它升级成「以别人的身份行动」：agent_chat_logs.user_id（models.py:1114）记的是提问人杨倩，数据却是王芹的可见范围，审计与事实脱钩。
  3. db 会更早、更脏地炸。database.py:28 是 async with SessionLocal() as session: yield session，请求结束即关。单例持有它，第二个请求 await 时要么直接 Session is closed（好情况，炸得响），要么在连接池复用下拿到脏连接、把别人未提交的事务一起提交（_log_chat 有 await db.commit()，agent_router.py:920）——坏情况，静默。
落成可执行的硬约束

app/agent/ 目录下不允许出现模块级 ReActAgent(...) / Toolkit(...) / *ChatModel(...) 赋值。写进 AGENTS.md，并在 CI 里用一行 grep 拦住——比在 code review 里靠记性可靠得多：

可以缓存的只有无状态的东西：工具的元数据（名字/描述/JSON Schema 字典）、system prompt 模板。凡是持有 ctx、db、api_key 的对象，一律请求级。

(b) 守卫放在工具包装器最内层，钩子只用于审计

一个很自然的想法：既然有 post_acting 钩子，就把 Top-20 截断、字段剔除挂在钩子上，一处生效、所有工具受益。不要这么做。三个理由：

  • 包装器是强制的，钩子是可选的。工具想被模型调用就必须经过包装器；钩子是框架给的礼物，礼物可以不给。
  • 钩子的触发时机是框架版本的一部分。今天 post_acting 每个 tool call 后触发，明天改成每轮一次、或并行下只触发聚合结果——红线静默漏一半，而测试很可能照样绿（它测「结果里没有 bank_account」，不测「钩子被调了 N 次」）。
  • 并行下钩子的顺序语义不保证。多个工具的 post_acting 谁先谁后、异常时还触不触发，都是实现细节。红线不能建在实现细节上。
模型（不可信） │ 它只看得见 {"min_overdue_days": 0} ▼ Toolkit ──preset_kwargs──▶ ctx（不进 JSON Schema，模型看不见也改不了） │ ▼ ┌────────────────────────────────────────────────┐ │ 我的包装器 @tool　　← 红线在这一层，绕不过 │ │ 1. ctx.budget.check() deadline / token │ │ 2. ctx.require_menu / require_roles 重放门禁│ │ 3. await router 函数（传真实 current） │ │ 4. slim(...) 字段白名单 │ │ 5. ctx.guard.filter(...) 第 2 步「重放门禁」值得单独说，它是「单一访问路径」原则在本仓库里最容易踩空的地方。语义层要复用的 reports_router，权限全部写在 FastAPI 依赖里：

_PNL_ROLES = ("finance", "finance_lead")                  # reports_router.py:414

@router.get("/fund-panel")
async def fund_panel(
    _: models.User = Depends(require_roles(*_PNL_ROLES)),  # reports_router.py:733
    db: AsyncSession = Depends(get_db),
):
    """资金面板：逾期应收账龄 / 预付敞口 / 应付账期利用 / 呆滞库存 / 未来13周现金排程。"""

注意那个下划线参数名——函数体内根本没用到用户对象。工具若直接 await fund_panel(db=db)，require_roles 一次都不会执行：它是 FastAPI 在路由分发时求值的，不是函数调用时求值的。对比 purchase_mgmt_router.list_items（:332）：后者把 current 收进函数体、在体内调 _buyer_restricted(current)（:349），传真实 current 进去行级过滤就自动继承。

复用 router 函数前先分类

把每个待复用函数分两类：门禁在函数体内（purchase_mgmt_router.py:349、sales_router.py:239、leads_router.py:87、orders_router.py:317）——传 current 即可；门禁在 Depends 里（reports_router.py:426/531/733）——包装器必须显式重放。分类结果写进注释，别靠记性。别的项目形式会变（Django 的 decorator vs. queryset filter、Spring 的 @PreAuthorize vs. 方法内判断），但规律不变：凡是靠框架在调用外层求值的权限，直接调函数就一定绕过。

第 5 步还有一条纪律：截断必须是出口的最后一步，不能出现在中间。现状有现成反例——tool_po_overdue_by_supplier（agent_router.py:121）在已截断成 Top-20 的明细上做聚合（:123-131），却把 item_total 填成全量 d["count"]（:135）：「20 家供应商，共 137 条」里 20 家是从 20 条聚出来的，137 是全量的，两个数字来自不同总体。让 guard.filter(rows, total=len(rows)) 同时返回「截断后的行」与「未截断的计数」，并规定聚合只能在 filter 之前，这类 bug 就没有土壤。

(c) 只取 agentscope 库：不用 runtime，不用 AgentApp 当服务器

不用 agentscope-runtime。它的沙箱是为「执行不可信代码」设计的——模型写 Python、丢进隔离环境跑。本项目工具形状完全相反：进程内、带身份的库读，需要的恰恰是「和 web 请求共享同一个 AsyncSession、同一个 current」。隔到另一个进程，要么把 db session 序列化过去（做不到），要么在沙箱里重新连库（current 和行级过滤又得重做）。隔离维度错位，成本全在，收益为零。

不用 AgentApp 当服务器。它现在直接继承 FastAPI，引入它等于进程里多一个 FastAPI 实例。而本项目挂在现有 app 上的东西有一整层：

  • 桌面客户端统计中间件（main.py:127 desktop_client_stats），读 X-PMS-Client / X-PMS-Device 头做 60 秒节流 upsert；
  • 外网登录两步闸门（gate.py，在 auth_router.py:81-93 生效）：浏览器 + 外网 IP + 非 admin 需要 6 位码，而桌面客户端凭 x-pms-client 头免闸；
  • 统一异常处理器（main.py:117 register_exception_handlers）；
  • 鉴权与菜单体系（deps.py:11 get_current_user → menus.py:142 user_menu_keys）。

第二个 FastAPI 实例 = 第二套中间件栈、第二套异常约定、第二个要挂鉴权的地方。Agent 应该是现有 app 上的一个 router，位置和 agent_router 现在（main.py:175）完全一致，只是内部实现从手写循环换成门面调用。这条在别的项目几乎总成立：只要目标系统已有 HTTP 层和鉴权，就永远只取「循环 + 工具 + 模型」三件，服务器那件留在原地。

(d) 版本节奏风险：用自建门面把它围起来

AgentScope 迭代很快——v1.1.0（2026-02）本身就是一次重大架构重构，2.0 又是另一套。对单人维护、几十人真实在用的 ERP，「跟着上游重构走」不是可选项：每次大版本都意味着几十个工具签名要动、回归要重跑、生产要重新灰度。缓解手段两条，必须一起用：

  1. 锁死版本（agentscope==x.y.z，不是 >=）。backend/requirements.txt 现在除 xlrd==2.0.1 外全是 >=；Agent 依赖走另一条规矩，因为它是唯一一个「上游改一次就可能让全公司问数行为漂移」的依赖。
  2. 自建门面 app/agent/loop.py。import agentscope 只允许出现在 loop.py 和 adapters.py 两个文件；所有工具只依赖自己定义的 ToolCtx，不 import 任何 agentscope 类型。将来换框架或上游改签名，改的是那两个文件里约二百行胶水，几十个工具一行不动。

代价要说清楚：门面是纯成本，约二百行，没有业务价值还得自己维护。愿不愿意付取决于工具数量——少于五个时门面不划算，直接写死更省；本项目工具会长到几十个（现在 7 个，仓库/物流/OA/售后/管理层待办零覆盖），门面就是必需品。这笔账每个项目都要重算。

(e) 模型配置实时读库 → 模型对象也必须请求级构造

本项目的 LLM 配置不是启动时读一次的环境变量，而是 每请求实时读库：_effective_llm_config（agent_router.py:762）从 app_settings 取 agent_llm.base_url / api_key / model / models，settings（config.py:60-64）兜底，admin 页面保存后全局立即生效。再加上白名单校验（_model_whitelist，:749）和用户可在请求里指定模型（ChatIn.model，:887），于是模型对象和 Toolkit 同理，必须请求级构造——模块级 _model = OpenAIChatModel(api_key=...) 会把 admin 改配置前的旧 key 一直用到进程重启。

换框架时最容易丢的一条红线：api_key 不许进日志

app_settings 存的是 AI 助手自己的 API Key 明文。现状为此做了两道防护：_mask_key（agent_router.py:776）保证任何接口只回 **** + 后四位；_llm_request（:503-507）捕获 httpx 异常后用 raise RuntimeError(...) from None 掐断异常链——httpx 异常携带 request 对象，request 头里就有 Authorization: Bearer sk-...。换成框架自带的 model client 后，它的默认异常包装和 debug 日志大概率会把整个 request 打出来。这是接入时必须第一个重新验证的点，并且要写成测试：故意配错 base_url，断言日志与响应体里都搜不到 key 的任何片段。

4.4　接入骨架：app/agent/loop.py

# app/agent/loop.py —— 全仓库唯一允许 import agentscope 的文件（另一个是 adapters.py）
import asyncio, time
from agentscope.agent import ReActAgent
from agentscope.tool import Toolkit
from agentscope.model import OpenAIChatModel
from agentscope.message import Msg

from .. import menus
from .context import ToolCtx, Budget, Deadline, BudgetExceeded
from .registry import REGISTRY          # 工具唯一真源，见 4.5
from .guard import OutputGuard
from .result import AgentResult

AGENT_DEADLINE_SEC = 45.0               # 🆕 全局硬上限（不是每次 LLM 请求的 30s）
TOKEN_BUDGET = 60_000                   # 🆕 单次会话 token 天花板

async def run(*, message: str, history: list[dict], current, db,
              model_name: str, cfg: dict) -> AgentResult:
    # ── ① 请求级上下文：身份来自 get_current_user，不来自模型
    ctx = ToolCtx(
        user=current, db=db,
        menu_keys=set(menus.user_menu_keys(current)),      # menus.py:142，算一次
        guard=OutputGuard(max_rows=20),
        budget=Budget(tokens=TOKEN_BUDGET, seconds=AGENT_DEADLINE_SEC),
    )
    # ── ② 每请求新建 Toolkit（绝不放模块级，见 4.3(a)）
    toolkit = Toolkit()
    for spec in REGISTRY.values():
        if not spec.visible_to(ctx):        # ③ 菜单门控在"注册处"：无权工具连 schema 都不下发
            continue
        toolkit.register_tool_function(
            spec.wrapped,                   # ④ 包装器里才是红线，见 4.3(b)
            preset_kwargs={"ctx": ctx},     # ⑤ ctx 不进 JSON Schema，模型看不见也改不了
        )
    # ── ⑥ 模型对象同样请求级：cfg 是刚从 app_settings 读出来的
    model = OpenAIChatModel(
        model_name=model_name,
        api_key=cfg["api_key"],
        client_args={"base_url": cfg["base_url"]},
        generate_kwargs={"temperature": 0.2},
    )
    agent = ReActAgent(
        name="pms-assistant",
        sys_prompt=build_prompt(current),   # 用户名/角色仍在首句，见第六章 6.5 缓存代价
        model=model, toolkit=toolkit,
        max_iters=4,                        # 与现状 agent_router.py:522 同口径
        parallel_tool_calls=True,
    )
    # ── ⑦ 钩子只做审计，不做权限（见 4.3(b)）
    agent.register_instance_hook("post_acting", "audit", make_audit_hook(ctx))
    agent.register_instance_hook("post_reply", "usage", make_usage_hook(ctx))
    try:
        async with asyncio.timeout(AGENT_DEADLINE_SEC):     # Python 3.12，后端已是
            msg = await agent(Msg("user", message, "user"))
    except (Deadline, BudgetExceeded, TimeoutError, Exception) as e:
        # 降级到规则路径（agent_router._rule_chat 同款），永远有回答，不返回 500
        return await rule_fallback(message, ctx, reason=_reason(e))
    return AgentResult(text=str(msg.content), cards=ctx.cards,
                       tools=ctx.tools_used, trace=ctx.trace, usage=ctx.budget.spent)

上面的 OpenAIChatModel(...) / register_instance_hook(...) 具体 kwargs 以锁定版本的签名为准——这正是 4.3(d) 说的「会随版本变」的那二百行，写在门面里就是为了让它变的时候只在这里变。

三处现状缺失在骨架里被补上了。全局 deadline：现状 30s 是 httpx.AsyncClient(timeout=30.0)（agent_router.py:499），每请求级别，四轮没有总闸，最坏 120 秒以上，而前端没有取消按钮。token 预算：现状历史截断只按条数 20 × 单条 2000 字符（agent_router.py:945），工具返回值不计入，最坏单轮 30–50k token 无保护。轮次与调用次数记账：agent_chat_logs 里根本没有这两个字段。

# app/agent/context.py
class Budget:
    def __init__(self, tokens: int, seconds: float):
        self.deadline = time.monotonic() + seconds
        self.tokens_left, self.spent, self.calls = tokens, 0, 0

    def check(self) -> None:
        """每个工具入口第一句就调；超限抛异常 → loop 捕获 → 规则降级，不是 500。"""
        if time.monotonic() > self.deadline:
            raise Deadline("Agent 总时长超限")
        if self.tokens_left <= 0:
            raise BudgetExceeded("token 预算耗尽")
        self.calls += 1
        if self.calls > 12:                 # 4 轮 × 每轮 3 个工具，与 max_iters 对齐
            raise BudgetExceeded("工具调用次数超限")

    def spend(self, usage: dict) -> None:   # post_reply 钩子回填
        n = usage.get("total_tokens") or 0
        self.tokens_left -= n
        self.spent += n

再看工具的标准写法。关键是它不 import 任何 agentscope 类型——换框架时这个文件一个字都不用改：

AgentResult 同时承载文本与卡片

@dataclass
class AgentResult:
    text: str                      # Markdown 正文（前端 markdown-it html:false 渲染）
    cards: list[Card]              # 🆕 L3 审批卡片；类型必须在白名单内
    tools: list[str]               # 实际调用的工具名 → sources 标签
    trace: list[dict]              # 工具名/入参/行数/耗时 → 落审计
    usage: dict                    # token / 成本 → 落审计
    fallback: bool = False
    fallback_reason: str = ""

两条关键约束。其一，卡片不进 text。若让模型把卡片写成正文里的 JSON 代码块再由前端解析，等于把「能力可枚举」交还给模型——它可以编造不存在的卡片类型，也可以编造端点。所以 cards 是工具在包装器里 append 到 ctx.cards 的结构化对象，模型只能决定「调不调那个工具」。其二，端点不出现在 Card 里。Card 只带 type（白名单枚举）+ payload（业务主键与展示字段），打哪个 URL、用什么方法由前端按 type 在可信代码里查表决定，请求带的是人自己的 token。这样 AGENTS.md 里「所有数据工具永远只读 SELECT」那条铁律不用动，也不需要 agent-bot 服务账号、不需要新写路径。

4.6　可迁移方法论：评估任何 Agent 框架的五个提问

五问按「先淘汰、后细究」排序，前两问答不上来就可以换候选。每问都给了半小时内做得完的验证动作——不要读文档得结论，要跑最小样例得结论：文档描述意图，代码执行事实。

① 异步模型对不对得上？

验：写个 async def 工具，里面 await 你自己的 ORM，打印 threading.current_thread().name，看是不是主事件循环线程。

为什么第一问：唯一无法用胶水弥补的。同步框架遇上 async ORM，要么每个工具套 run_in_executor（连接池行为立刻变、事务边界跟着乱），要么 asyncio.run() 嵌套直接报 event loop already running。

换项目怎么变：目标系统若是 Django 同步 ORM 或 Flask，结论正好反过来。没有普适答案，只有「和宿主一致」。

② 能不能注入不暴露给模型的请求级上下文？

验：注册一个带 ctx 的工具，把框架实际下发的 tools JSON 打出来，确认 ctx 既不在 properties 也不在 required；再让模型故意输出含 ctx 的参数，确认被忽略而非被采纳。

为什么关键：做不到就只剩两个坏选择——current 进模型可见参数（可篡改身份，出局），或 contextvars 全局态（并发极易串，签名还骗人）。

换项目怎么变：形式各异（LangChain 的 InjectedToolArg、OpenAI Agents SDK 的 RunContextWrapper、AgentScope 的 preset_kwargs），问题本身一样：模型不能是身份的来源。

③ 工具结果出口能不能强制拦截？

验：不改框架源码，让所有工具返回值必经同一个函数；写个「坏工具」故意返回 500 行含 bank_account 的数据，断言到达模型的内容里既没有第 21 行也没有那个字段。

为什么关键：Top-20 不是体验优化，是绕过导出审批闸门的防线；字段白名单不是洁癖，suppliers.bank_account 是付款诈骗素材。拦截点必须在你自己的代码里，钩子只是审计。

换项目怎么变：阈值和字段会变，「出口必须有一个你控制的收口」不变。框架若只允许在钩子里改结果，就降级使用：手动包装每个工具，别用自动注册。

④ 状态是否请求级隔离？

验：用两个权限最不一样的真实账号并发跑 20 轮（本项目就是王芹 vs 杨倩），断言每轮返回的行都只属于提问者的可见范围。这个测试要进 CI——它是唯一能抓住「有人手滑加了模块级单例」的手段。

为什么关键：见 4.3(a)。单人开发时这类 bug 100% 不会暴露：本地只有你一个人，第一个请求就是你自己，身份烤进去也正好是对的。

换项目怎么变：行级规则不同（本项目七类：buyer_id / sales_uid / owner_uid / 派单 / ProjectMember / worker_id / OA 四路可见），但测试形状完全可迁移。

⑤ 能不能只用它的一部分（可拆卸性）？

验：只 import Agent + Toolkit + Model，不碰 server / session / storage / tracing，看能否跑通。它若要求你从它的 App 启动、用它的 session 存历史——那它想当框架，而你只需要一个库。

为什么关键：企业系统已有鉴权、审计表、中间件、部署方式（本项目是 Electron 桌面端 + nginx + 4 worker uvicorn）。任何要求你按它的方式组织进程的组件都会和这些打架，见 4.3(c)。

换项目怎么变：基本不变。这是 FDE 场景里最稳定的一条：客户现场永远「已经有一套在跑」，你是嵌进去不是重建。可拆卸性 > 功能完备性。

最后：框架不是答案，边界才是

本章可压成一句话：AgentScope 帮你把「烦但不难」的循环、并行、流式做掉；权限继承、出口守卫、卡片契约、审计口径这四件「不烦但很难」的事一件都不帮——而恰恰是这四件决定了它能不能上生产。所以工作量分配大致是：调通框架半天，写门面和守卫两周。如果比例反过来了，八成是守卫没写够。
