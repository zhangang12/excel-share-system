第八章　FDE 能力地图：这个项目证明了什么，还缺什么

前七章讲的是「怎么把这个 Agent 做出来」。这一章换个视角：做完之后，你手上多了什么，还差什么。读者是准备转 FDE 的开发者本人，所以这章不写鸡汤，只写三件事——岗位到底要什么、这个仓库能证明哪几条、剩下的窟窿怎么补。每条结论都能在本仓库找到出处；证明不了的地方，我直说证明不了。

8.1　FDE 到底是什么岗位

Forward Deployed Engineer 的核心定义只有一句：在客户现场，用工程手段把业务问题解决掉，并对结果负责。这句话里每个词都在划边界。

岗位交付物成功判据与 FDE 的关键差别
后端工程师代码、接口、服务需求实现、性能达标、测试通过需求是别人给的；FDE 要自己从客户嘴里挖出需求，并且经常发现客户说的不是真需求
解决方案架构师（SA）架构图、选型建议、PoC方案被采纳SA 常在方案交付后退出；FDE 要把方案跑到生产、跑到用户天天在用
售前Demo、标书、答疑签单售前对「能不能卖出去」负责；FDE 对「卖出去之后能不能用」负责，这两件事经常打架
咨询顾问报告、流程建议报告被认可顾问动嘴不动手；FDE 的建议必须自己实现，因此不能提自己写不出来的方案
FDE在客户环境里跑着的系统业务指标改善 + 用户真的在用—

由此推出岗位真实要求的能力维度。这不是招聘 JD 的排比句——每一条后面都挂一个本仓库的锚点，挂不上的就不写。原稿里有「演示与说服」这一条，翻遍仓库找不到任何可举证的东西（没有对外演示稿、没有客户评审记录），所以它被并进第 4 条的括注、并在 8.3 里作为缺口老实承认。宁可七条有据，不要八条悬空：

  1. 业务理解——听得懂「请款」「对账」「职责分离」在这家公司具体指什么，而不是套教科书定义。锚点：「一人审批、另一人付款」这条口头内控规则（需求十六，交接文档.md:126）落成代码两处——purchase_mgmt_router.py:2563 审批时写 finance_approver_id，:2711 付款端点比 finance_approver_id == current.id 拦人，且按 user.id 比、admin/manager 也不留后门。
  2. 快速读陌生代码——进场第一周要在一个没人给你讲的仓库里定位「权限判定写在哪」。锚点：docs/analysis-sales-router.md（732 行）、analysis-orders-router.md（553 行）、analysis-leads-router.md（373 行）三份逐文件业务逻辑分析，以及 docs/agent-tool-gap-analysis.md——后者的做法正是本手册第二章的原型：先把 7 个工具的实际 SELECT 摊开，再对照可用数据源找差距。
  3. 数据与权限建模——把组织结构、岗位、数据可见性翻译成表结构和查询条件。锚点：第二章 2.5 那张 7 类行级规则表（A–G），逐条落在 deps.py:52,95,125、purchase_mgmt_router.py:46、sales_router.py:53、oa_router.py:354-367。
  4. 与非技术干系人沟通（含演示与说服）——把技术取舍讲成业务后果，让财务主管能做决定。锚点：反馈闭环整条链在代码里闭合——带截图提交（user_feedback_router.py:49）→ 回复（:155）→ 站内 + 企微双通道推给提出人（:163，走 notify.py:29）→ 未读拉取（:190）。这是「沟通」有据的部分；「5 分钟演示打动陌生客户」这一面本项目无法举证，见 8.3 缺口 5。
  5. 取舍与说不——识别哪些需求会毁掉系统，并且顶住。锚点：AGENTS.md:54「对『让计算列可编辑』这类设计上就危险的诉求，先反问是否合理、是否有更简单的满足方式，再写代码」；以及 #331——出纳要求「同一个账号审批+付款」，判定为内控规则冲突退回业务侧，一行代码没动（交接文档.md:256-263）。
  6. 交付纪律——上线、回滚、版本、备份、审计，不靠人品靠脚本。锚点：ops/ 下 19 个脚本，release.sh 是「备份 → 拉码 → 重建 → 健康检查 → 失败自动回滚」的完整链，ops/setup-cron.sh:29 每 5 分钟跑 health-check.sh、失败自动重启后端。
  7. 现场排障——只有一张截图和一句「打不开」，也要定位到根因。锚点：ops/diagnose.sh 一键收集诊断包（让不懂技术的用户也能把现场交出来）+ 8.4 故事三的桌面端黑屏定位。
最容易被低估的两项

第 5 项（说不）和第 7 项（排障）在简历上最难写，在现场最值钱。客户提的需求里有相当比例是「把计算列改成可编辑」这类会摧毁数据一致性的诉求——能把「先质疑需求再实现」写成仓库级硬约定（AGENTS.md:54），说明踩过。

8.2　这个项目已经证明了什么

先给规模底数，后面所有论断都建立在这上面：backend/app/ 26365 行 Python、31 个 router、models.py 55 个 ORM 模型；frontend/src/ 25248 行、47 个 .vue、21 个业务视图；backend/tests/ 71 个测试文件 10531 行；另有 Electron 桌面壳、Docker 生产部署与 19 个运维脚本（ops/）。这不是玩具。

① 真实用户与真实反馈闭环（对应维度 1、4）

反馈不是收集箱，是闭环，链路在代码里完整闭合：带截图提交（user_feedback_router.py:49）→ 修复 → 回复（:155）→ 同时双通道推送给提出人（:163「站内消息 + 企微双通道，绑了企微即微信可达」，走 notify.py:29）→ 未读回复拉取（:190）与已读回执（:205）。

更值钱的是反馈单号已排到 #333，且 AGENTS.md 沉淀了一整段「怎么读反馈」的方法论——「图文一起读，先给附件归位」「红框强制入境，文图冲突图赢」「不用改加倍举证」，每条挂着具体教训编号（#265、#283、#271）。用户打字随手、画圈深思——这句不是从书上抄的。

② 复杂权限建模（对应维度 3）

这是本项目最硬的资产，也是最像真实企业客户的部分。五层叠加（逐层细节见第二章 2.5）：

层权威位置说明
角色seed.py:14-4225 个角色；models.py:83 只有一处角色包含关系（finance_lead ⊇ finance），多角色取并集
菜单（一级）menus.py:142按账号配置 User.menus，角色菜单矩阵已废除；admin/manager 全量 bypass
行级7 处，各不相同采购 purchase_mgmt_router.py:46+:349（buyer_id）/ 销售 sales_router.py:53+:239（sales_uid）/ 线索 leads_router.py:87（owner_uid）/ 项目目录 deps.py:95（派单）/ 项目详情 deps.py:125（ProjectMember）/ 任务 worker_id / OA 四路可见
字段级field_perm_router.py:43、:132按角色 ID 配置字段读写，多角色取并集；只有 can_edit 在服务端强制，can_view 靠前端遮蔽
记录级（内控）purchase_mgmt_router.py:2561、:2712「当前用户相对于这条记录的历史角色」——职责分离，与角色无关、按 user.id 比，admin/manager 不留后门

真正证明「建模能力」的不是层数，而是那些反直觉的判定。purchase_mgmt_router.py:46 的注释是全仓最好的教材：

def _buyer_restricted(current: models.User) -> bool:
    """下单采购员(buyer 家族)只看自己下的单——判定依据只是"是不是采购下单角色"，
    与是否**兼任** finance / logistics / sales 无关（兼任财务不解除采购的行级隔离；
    这是反复出问题的坑：王芹=buyer/finance/logistics 曾因带 finance 而被判为看全部）。"""

「兼任更高权限的角色不解除本岗位的行级隔离」——这条在任何权限教科书里都找不到，只能从「王芹一个人干三个岗」这种真实组织结构里长出来。同类证据：deps.py:95 的 codes <= _DIR_RESTRICTED_CODES（全部角色都在受限集合里才受限，兼任一个更宽的就放开）。可迁移的方法论：权限测绘时别问「有哪些角色」，要问「谁兼任了什么、兼任时按哪个算」——兼任是所有权限模型的破绽所在。

③ 内控与合规意识（对应维度 1、5）

三条证据，一条比一条硬：

  • 职责分离不留后门：purchase_mgmt_router.py:2561「不能审批自己提交的请款单」、:2712「请款审批与付款需由不同人操作」。关键在 :2559 的注释——「同属职责分离，一并对管理层生效（不留后门）」。多数系统会给 admin 开豁免口子，这里没有：把「需求.docx 第十六项」当内控条款而不是功能点实现。
  • 导出审批闸门：export_router.py:37/:73/:100，用户发起导出申请 → 管理层 approve/reject，同一用户同时只能有一条 pending。这条闸门直接决定了「AI 一次只吐 Top-20」是红线而非偷懒——绕过闸门批量拉数据是合规事故。
  • 驳回闭环的设计判断：purchase_mgmt_router.py:2634 出纳付款环节驳回（「不走这里硬付下去，钱就打错账户了」），:2655 重提后必须重走审批，理由写在注释里：「收款账户变更属实质变更，审批人必须知情复核」。用户最初只说「发现账号不对怎么办」，落地成三个端点（pay-reject / withdraw / resubmit）+ 状态机 + 双通道通知（_do_reject 在 :2572）——「从模糊需求到可执行方案」的完整样本。

④ 生产运维（对应维度 6）

ops/upgrade.sh:2 一行讲清流程：「备份 → 拉代码 → 重建 → 健康检查 → 失败自动回滚」。细节里有真东西：:64-65 backend 60 秒不起来就回滚、:76-77 健康检查不过就回滚、退出码分三档（0 成功 / 1 失败但已回滚 / 2 回滚也失败），release.sh:106-109 对第三档打印「请立即人工登录处理」。health-check.sh 检容器 / postgres / /api/health / 磁盘，每个探测都套 timeout——原因写在注释里：「诊断脚本是出故障时跑的，被查的服务本身卡住时，无超时的 curl 会让脚本一起无限期卡死（就是之前在服务器上卡住的原因）」。踩过才会写这行。

桌面端有独立版本治理：desktop/main.js:141 启动拉 version.json，低于 min_version 进强制更新页（只给「立即更新」一条路），其余走 electron-updater 静默下载；服务端按 X-PMS-Client 头聚合在线版本分布与设备明细（desktop_router.py，该模块自带只读红线「仅 SELECT」）。这就是灰度所需的最小观测面：我知道谁还在跑旧版。

⑤ 诚实的技术判断（对应维度 5）

两个反向证据，比任何「我很严谨」的自述都有力。

其一，主动上报自己的越权 bug。agent_router.py 的 7 个工具里，只有 tool_project_status（:241）在签名里接 current；:66 tool_po_arrival_overdue、:138 tool_balance_due、:168 tool_overdue_orders 等 6 个函数签名里根本没有用户对象，因此不可能做行级过滤。而页面侧的过滤是齐的（purchase_mgmt_router.py:349、sales_router.py:239）。后果是：普通销售员问一句「尾款」，拿到的是全公司客户名 + 尾款金额 + 归属销售。这个洞是在写本手册的测绘过程中自查出来的，不是别人报的。

其二，把代价讲清楚再执行用户的决定。sales_router.py:611 那段注释是范本：

# 🆕 #332 尾款到账批注(=插入到款时间) → 尾款金额自动清零（用户 2026-08-01 明确选定此口径）。
#   注意 balance 是双语义共用列：催办/账龄/13周现金流/AI 只认 balance>0 判"未收"（清零后
#   立即停催，这正是诉求），但台账合计与销售报表「收款计划汇总·尾款」把它当合同条款额统计，
#   清零后那两处会随回款变小——已当面说明，用户仍选直接清零。
#   为把"不可逆"这一条兜住：清零前把合同尾款额存进 balance_contract，删批注即原样恢复

三段式：指出隐藏代价 → 记录用户的决定与日期 → 用工程手段把最危险的一条（不可逆）兜住。FDE 的「说不」不是拒绝，是这个。

⑥ 跨端交付（对应维度 6、7）

Web（Vue3 + Element Plus）+ Electron 桌面壳 + 企业微信推送三条投递路径，且三者互相知道对方存在：外网登录闸门 gate.py 对桌面客户端（带 X-PMS-Client 头）免闸、验证码经 push_message 发给 manager 池；消息推送在站内落库后尽力而为地外发企微（notify.py:79-83，企微失败只记 warning 不影响站内）。降级路径是想过的。

8.3　还缺什么，怎么补

这一节是全章最重要的部分。诚实清单，每条给可执行动作。

缺口 1：评估体系（最硬的短板）

现状要说准确：Agent 相关有 3 个测试（tests/test_agent_perms.py 160 行、test_agent_chat.py 323 行、test_agent_chat_logs.py 162 行）。test_agent_perms.py 的 docstring 覆盖得相当细（warehouse 用户问采购被拒、finance 用户 project_status 含 ledger、配置接口仅管理层），但它明确走规则降级路径、不依赖 LLM Key（os.environ["AGENT_LLM_API_KEY"] = ""）。

也就是说：权限有测试，回答质量没有评估。没有一条测试能回答「问『本月尾款』时模型选对工具了吗」。这是 AI 项目最硬的短板——模型换个版本、prompt 改一句，你不知道有没有变差。

补强动作（可在两周内做完）：

  1. 建 backend/tests/agent_eval/cases.jsonl，每条 {question, as_user, expect_tools, expect_denied, expect_facts}。种子直接来自反馈台账——真实用户问过的话就是最好的评估集，不用自己编。
  2. 三层判据，从便宜到贵：(a) 工具选择准确率（断言 tools_used 集合，无需调模型即可对比）；(b) 越权红线（每条 case 换 5 个身份跑，任何一次返回了不该看的行 = 硬失败，这层永远不许降级）；(c) 数字正确性（对少数口径 case，用 reports_router 直算的值做 golden，容忍文字不同但数字必须相等）。
  3. 把 agent_chat_logs 补齐（现状 models.py:1108-1122 只有 question/answer/tools_used/via/model/duration_ms，缺 token 用量、成本、工具入参、轮次），补上之后线上日志本身就是持续 eval 的语料池。
  4. 接进 ops/：发版前跑一次 eval，(b) 层不过就不许发。

缺口 2：多客户 / 多租户经验

现状是单租户内部系统：menus.py:142 的 DEFAULT_ACCOUNT_MENUS、seed.py 的 25 个角色、reports_router 里的资金口径，全都是这一家工厂的形状。_buyer_restricted 里甚至写着「王芹」的名字。

补强动作（不必真做第二家，但必须想清楚并写下来）：写一份《第二家工厂适配评估》，逐项回答：哪些是行业通用的（请款→审批→付款三段式、项目编号做跨域枢纽）、哪些是这家特有的（25 个角色的具体切分、「业务时间<15:00 跳过」这种特判）、哪些必须变成配置（角色定义、行级规则、逾期天数阈值）。关键判断题：行级可见性规则现在是 7 段硬编码 Python，要不要抽成声明式规则表？答案很可能是「不要」——把 deps.py:95 那种「全部角色 ∈ 受限集才受限」的语义塞进配置表，配置的复杂度会超过代码。能把这个『不做』的理由讲清楚，比真做一个多租户 demo 更能证明判断力。

缺口 3：团队协作与交接

现状基本是单人 + AI。好消息是交接资产真的存在：AGENTS.md（87 行硬约定）、交接文档.md（1080 行，含文档地图、分支约定、生产踩坑、排障流程）、权限矩阵.md、OPERATIONS.md、ops/README.md。坏消息也真实：交接文档.md 头部写着「最后更新:2026-07-08」，而它自己定的规则是「每次代码/流程变更，推送前必须同步更新本文档……与变更同一个 commit 提交」——今天是 08-01，中间至少经历了 #329–#333 五批需求和桌面端崩溃恢复。规则写了没执行，这本身就是单人项目最典型的病。

补强动作：(a) 把「更新交接文档」变成机器执行的门（pre-push hook 检查 交接文档.md 的 mtime 或顶部日期），而不是靠自觉；(b) 找一个真人做一次盲测交接——给他仓库和文档，不做口头讲解，看他能否独立完成一次发版和一次排障，把他卡住的每一处补进文档。这一步产出的东西在面试里可以直接讲。

缺口 4：英文沟通与文档

全仓注释、文档、commit 是中文。FDE 常在跨国团队，架构决策要用英文写给不在场的人看。补强动作：把本手册第三、四、五章（原则与架构部分）翻成一份 3-4 页的英文 Design Doc，重点练三类表达——权限模型描述、取舍论证（"we chose X over Y because…"）、事故复盘。不要求全仓英文化，要求能用英文把一个架构决策讲服人。

缺口 5：演示能力

补强动作：一个 5 分钟脚本，掐表练到不看稿。建议结构：

时段做什么要让对方记住的一句话
0:00-0:40用销售员账号登录，问「本月尾款还有多少没收」「这是普通员工问的，看它返回什么」
0:40-1:30换财务账号问同一句，结果范围明显变大「同一个问题，答案跟着人的权限变——因为工具调的是页面同一个函数」
1:30-2:30问「XX 项目现在什么情况」，展示跨域串联（任务+采购+回款）「以前要开三个页面对着看」
2:30-3:40触发一张审批卡片，当场点确认，回到业务页面看到状态已变「模型只决定把哪件事推到你面前，按钮打的是你自己的 token」
3:40-4:30故意用自己提交的请款单去批，展示职责分离拦截「AI 不给内控开后门」
4:30-5:00打开审计日志，指出每一问每一答都有记录「出了事查得到」

要点：全程用真实业务数据和真实岗位账号，不用 demo 数据；第 5 段（被拦截）比前四段加起来更有说服力，别省。

缺口 6：定量的业务价值

现状最缺的一块：说不出「省了多少时间 / 少犯了多少错」。agent_chat_logs 只有耗时，没有业务口径的效果指标。

补强动作（上线前就埋，上线后才有对照）：

  • 基线先测：上线前找 3 个岗位各计时 5 次「查一次晨报要开几个页面、花多久」，这是唯一能拿到基线的时机，错过就永远补不上。
  • 过程指标：周活人数 / 人均问数、工具调用分布（哪几个域真被用）、规则降级占比、被权限拦截的比例。
  • 结果指标：卡片确认后的动作转化率（推了 10 张催款卡，几张被真的处理）、逾期项在推送前后的平均停留天数（数据现成——6 个 scan_* 扫描器在 overdue.py:35/:80/:138/:197/:238/:311 已经在按天算逾期）。「催办响应时间从 N 天降到 M 天」是能写进简历的那种句子，而它只需要一条 SQL。

8.4　作品集怎么讲这个项目

先给整体框架，一段话说完，别铺陈技术栈：

STAR 主叙述（面试开场 90 秒版）

S：一家几十人的制造企业，销售/设计/电工/生产/采购/仓库/物流/财务/售后/人事十几个环节，原先靠 Excel 传来传去，同一个项目的状态在四五个人手里各有一份。

T：我一个人负责把全流程搬进一套内部系统，并且要让 25 个岗位各看各的、互不越界；后来又要在上面接 AI 助手做跨域问数。

A：分三步——(1) 先把权限模型做成四层（角色 / 按账号的菜单 / 7 类行级规则 / 字段级），且把「兼任岗位怎么算」这类反直觉判定写进代码注释固化下来；(2) 把上线、健康检查、失败自动回滚做成脚本，桌面端做强制最低版本；(3) 做 AI 助手时定了三条不可让步的原则——工具不写 SQL 只调页面同款函数、事实源永远在服务端、能力白名单可枚举。

R：系统真实在用，反馈单号排到 #333，形成了「提反馈→修→回复→企微推送」的闭环；过程中我自查出线上 AI 助手的行级越权缺陷并主动上报和修复。

故事一：行级越权的发现与修复（讲安全意识与诚实）

怎么讲：为了写内部技术手册，我对 AI 助手做了一次逐函数测绘，发现 7 个数据工具里只有 1 个（agent_router.py:241）的签名接受当前用户对象，其余 6 个（:66、:96、:121、:138、:168、:219）连用户是谁都不知道——不是过滤写错了，是结构上根本没有过滤的可能。同一份数据在页面侧过滤是齐的（purchase_mgmt_router.py:349、sales_router.py:239）。而 AI 助手菜单对所有登录用户无条件开放（menus.py:142）。所以普通销售员问一句「尾款」就能拿到全公司客户名、尾款金额和归属销售。我当天上报，并把它定成整个 Agent 重构的第一条原则：工具不写 SQL，只调 router 里页面用的那个函数、并传真实的 current，让权限自动继承而不是重新实现一遍。

面试官会追问怎么答
为什么当初会写成这样？不甩锅：第一版是「先让它能答」的原型，工具直接写了查询语句，最快路径就是不传 current。问题不在写快了，在于没意识到「新加一条数据出口」等价于「新加一个权限边界」。
你怎么保证不再发生？三层：(1) 结构上——工具层禁止裸 SQL，红线守卫放在工具包装器最内层而非只挂钩子，current 为空直接断言失败；(2) 测试上——每条 eval case 换 5 个身份跑，返回不该看的行即硬失败；(3) 约定上——AGENTS.md:56 已把只读红线写死。
为什么不用 Text-to-SQL？正好用这个洞回答：权限模型套不进生成式 SQL。这套系统的行级规则是 7 段语义各异的 Python（比如「兼任 finance 不解除采购隔离」），没法表达成一句 WHERE 让模型去拼。
影响面多大？有没有真的泄露？如实说：审计表 agent_chat_logs 记了每一问每一答，可以回溯谁问过什么——先给出可查证的口径，再给结论，不要凭印象说「应该没人问过」。

故事二：职责分离拦住出纳付款（讲企业内控理解与「不擅自改规则」）

怎么讲：出纳杨倩在付款时被系统拦住，报错「职责分离：请款审批与付款需由不同人操作」（purchase_mgmt_router.py:2712）。用户第一反应是「这是 bug，我付不了款」。我的判断是这不是 bug，是需求文档第十六项要求的内控——审批人不能给自己审过的单付款，并且这条对管理层同样生效、不留后门（:2559 注释明确写了这一点）。我没有改规则，而是去查为什么她同时是审批人：因为岗位配置让她既能审又能付。解决办法是调整岗位而不是拆掉校验。

同一时期还有个反例：销售主管杨坛被 _is_sales() 拦住（反馈 #333），那次是 bug——判定漏了「主管也是 sales 家族但应享全量视图」，就改代码（sales_router.py:53 的 _all_view）。两件事看起来一样，处理相反，区别在于被拦的那条规则是不是有意为之。

面试官会追问怎么答
客户坚持要改，你怎么办？先讲后果（审批付款同人 = 审计上的重大缺陷），再给替代方案（换个人审 / 加一个审批岗），最后如果客户仍坚持——这类涉及内控的变更要有书面决定和留痕，不能口头改完就上线。参照 sales_router.py:611 那次的做法：注释里写清代价、决定人、日期。
你怎么区分「拦对了」和「拦错了」？看规则有没有可追溯的意图：能指到需求条款、注释里写了理由的，默认是对的，去改流程；找不到出处、行为与页面其他地方不一致的，默认是 bug，去改代码。
admin 为什么也不给豁免？因为豁免口子一旦存在，「临时用 admin 账号付一下」就会变成常态，内控等于没有。这是有意的设计成本。

故事三：桌面端黑屏的定位（讲现场排障）

怎么讲：用户报「客户端放着放着就黑屏，点什么都没反应，只能去任务管理器杀进程」，证据只有一张截图。关键观察：屏幕不是纯黑，是深蓝——而 desktop/main.js:209 里主窗口的 backgroundColor 正是 #0f1d30（当初为了「切窗不闪白」和登录页底色对齐设的）。这就把范围锁死了：窗口还在、底色还在画，说明主进程活着；但没有任何页面内容，说明渲染进程死了。原有代码只监听了 did-fail-load，那管的是「页面没加载成功」，管不了「加载成功之后进程被回收」。修复是接住两类死亡事件并自动恢复：:251 render-process-gone（Electron 22+ 取代已废弃的 crashed）直接 reload，:256 unresponsive 先记一笔、卡满 15s 再重载；:234 的 recover() 里还做了两件防御——5 秒去抖防止崩溃风暴里反复重载，以及 webContents 彻底不可用时重建窗口。token 存 localStorage，重载后不用重新登录，用户无感。

面试官会追问怎么答
只有一张截图，你怎么开始的？从「屏幕上那个颜色是谁画的」倒推。UI 上任何一个像素都有代码来源，深蓝不是随机的。这比问用户「当时你在干什么」更快，因为用户通常记不清。
怎么确认修好了？诚实说这类偶发问题的验证难点：不能等复现。做法是加 logCrash 落盘 + 服务端能看到版本分布（desktop_router.py 的 /api/admin/desktop-clients），发版后看崩溃日志有没有出现并被自动恢复，而不是看用户还报不报。
为什么是自动 reload 而不是修根因？根因是系统回收/OOM，在客户机器上不可控。这是有意识的取舍：先把用户体验的止血做掉（自恢复），同时把观测加上（崩溃日志），根因靠日志攒够样本再谈。顺带也加了 backgroundThrottling: false（:218），解决切后台后定时器被降频、回来看到一屏死数据的相邻问题。

8.5　通用 FDE 落地清单（可带走）

把全书方法论压成一张纸。这张清单不依赖本项目，换个客户照样用。

进场两周做什么

  1. 第 1-3 天：跟人不跟文档。找 3-5 个不同岗位的真实使用者，看他们实际怎么干活（开几个页面、Excel 传给谁、什么时候会出错）。文档写的是应然，人做的是实然，差异处就是需求。
  2. 第 4-7 天：权限测绘。问三个问题——谁能看到什么？谁兼任了什么？兼任时按哪个算？谁是例外（老板、admin、临时工）？把答案落成表，让客户签字。这一步不做，后面每个功能都要返工。
  3. 第 8-10 天：找口径。同一个词（「毛利」「应收」「逾期」）在财务和销售嘴里往往不是一个算法。把每个关键指标的口径写成一行公式，找到那个最终拍板的人确认。
  4. 第 11-14 天：跑通一条最窄的端到端。哪怕只覆盖一个岗位的一个动作，也要真上生产、真有人用。「能跑」比「设计完整」在现场值钱十倍。

测绘要产出什么（四份，缺一不可）

  • 权限矩阵：角色 × 功能 × 数据范围，标出所有「仅本人」和所有兼任例外
  • 口径表：每个业务指标一行公式 + 拍板人 + 日期
  • 数据地图：哪些实体是跨域枢纽、哪些关联是软关联（本项目里 projects.code ↔ purchase_items.project_code 是字符串软关联无外键，会静默漏数——这类地雷必须在图上标红）
  • 写操作清单：系统里所有会改钱、改状态、改权限的动作，各自的审批链是什么

架构要守住哪三条

这三条是本书的核心，也是可迁移性最强的部分
  1. 单一访问路径——新增的任何数据出口（AI 工具、报表、导出、开放 API）都不许自己写查询，只能调既有业务函数并传真实身份。权限继承而非重新实现。违反这条，你就有了 N 份需要同步维护的权限逻辑，而它们必然会漂移。
  2. 事实源在服务端——模型/前端/缓存只能决定「把哪件事推到你面前」，不能成为「你正在处理的是什么」的来源。卡片上显示的金额，必须在点确认那一刻由服务端现查。
  3. 能力可枚举——能做的事是一张白名单，端点由类型在可信代码里决定，绝不出现在模型输出里。做不到枚举的能力，就是做不到审计。

上线前查什么（七项，逐项打勾）

这七项是任何系统上线都该查的，与 Agent 无关，所以能背下来；Agent 特有的两份清单在 5.7（8 条安全，管"能不能上"）和 7.8（16 条运营，管"上了怎么活"），那两份要照着念不要背。

  1. 换 5 个不同岗位的账号各跑一遍关键路径，看到不该看的立即停
  2. 回滚脚本真跑过一次（不是「写了」，是「在生产上执行过并成功」）
  3. 备份能恢复（同样：真恢复过一次到一个空库）
  4. 健康检查的每个探测都有超时——出故障时跑的脚本不许自己卡死
  5. 审计日志覆盖所有写操作和所有数据出口，且记录了「谁、什么时候、改了什么」
  6. 降级路径存在且被测过（第三方挂了会怎样？本项目的规则降级路径有独立测试）
  7. 客户端版本可观测、可强制升级（否则你永远在支持 5 个版本）

交付什么

不是代码，是让别人能接手的一整套：跑着的系统 + 运维脚本（含回滚）+ 权限矩阵 + 口径表 + 交接文档（含踩坑与排障流程）+ 反馈通道。验收标准很实际：把它交给一个没参与过的人，他能独立完成一次发版和一次排障。

8.6　诚实的风险提示：这个项目作为作品集的四个短板

面试官会看出来的，与其被问出来，不如自己先说。原则是承认事实 + 说明你为此做了什么 + 指出它换来了什么，不辩解也不自贬。

短板不要这样说建议的正面处理
单人项目，没有协作证据「我一个人也能做完整个系统」（听起来像不会合作）「单人做完全栈让我对每一层的取舍都有第一手判断，代价是没有代码评审兜底。我的补偿手段是把约定写成机器可执行的规则——AGENTS.md 87 行硬约定、72 个测试文件、发版脚本强制健康检查与自动回滚。我知道这替代不了同行评审，所以下一步我想找人做一次盲测交接。」
内部系统，不是对外产品回避规模问题「用户只有几十人，但岗位复杂度不打折：25 个角色、7 类互不相同的行级规则、有人同时兼三个岗。对 FDE 来说，客户现场遇到的正是这种组织复杂度高于并发复杂度的场景。我没有高并发经验，这我不装。」
无同行评审，质量无外部背书「代码质量很高」拿可验证的东西替代自我评价：主动自查并上报了自己的行级越权缺陷；关键判定处的注释都写了「为什么」和「哪次踩坑」；邀请对方现场翻 purchase_mgmt_router.py:46 那段注释——让代码替你说话。
业务价值未量化编一个「效率提升 40%」「我目前只能给出使用侧的事实：系统真实在用，反馈闭环到 #333。我没有『节省了多少小时』的数据，因为上线前没测基线——这是我复盘出来的一个真实失误。我现在的做法是：AI 助手上线前先测 3 个岗位的操作基线，并在审计表里补上 token/成本/工具入参，让效果可度量。」
最后一句方法论

上面四条的处理方式其实是同一个动作：把短板转述成一个你已经识别、并且正在用工程手段解决的问题。FDE 这个岗位每天面对的都是「条件不理想但必须交付」，所以对方真正在评估的不是你有没有短板，而是你知不知道自己的短板在哪，以及知道之后会做什么。这个项目最好的证据不是它做对了多少，而是它留下了一条清晰的记录：发现问题 → 讲清代价 → 做出取舍 → 把不可逆的那部分兜住。
